The planner and its steps (DECODED 2026-10-27)

Every NPC's behaviour runs through a PLANNER object at [character+0x2CE8] that executes STEPS. A step type is a GameDB category under AI/Planner/Steps/ (its records hold the tuning: FleeAmbush.TraitsRequired, FleeAmbush.SearchDistance, ...) with a C++ class that implements it. AI/Planner has 69 categories: Context, Steps (the base), Trees and 66 step types:

Animate, AssembleAtNode, Attack, AttackPreview, Attract, BaitAttract, BeckonWithTalk, CaptureBattleNode, CheerExitCombatSpaceSource, CircleAlly, CircleTarget, CombatRecoil, CombatState, CombatTaunt, CombatWeaponChange, Cower, DespawnOffscreen, ElevateTransientAlarm, ExitCombatSpace, Fall, FindAlertnessSource, FindPreceivedOpponent, Flee, FleeAmbush, FollowLeader, FollowRoute, FollowWaitForBand, GiveUpOnPlayer, GoTo, GoToAndMount, GoToCircleAlly, GoToPreferredAttackPosition, GoToRallyPoint, Idle, Investigate, Investigating, LeadPlayer, LeaveObstacle, MenaceTask, Mounted, MoveTowardSpawner, NodeAnimate, Patrol, PerformSyncAction, PresentationIdle, Priority, ReactToAlertnessChange, ReactToAreaAlarmLevelChange, ReactToDeadBodyInvestigation, ReactToGlimpsed, ReactToKnownDeadBody, ReactToMoraleModifier, Retreat, RetreatIdle, RetreatToDistance, ReturnToBandLeader, ReturnToBattleNode, ReturnToConfinementNode, ReturnToPursuitConstraint, TauntOpponentNonAttackable, TraitCatalystReaction, UseAttackNode, UseFixedArcherNode, UseWorkNode, WargChaseTarget, WargCircleTarget.

The step interface (MEASURED on Flee / FleeAmbush, 2026-10-27)

Six step classes in the planner module fill the same slots (vf0, vf1, vf5, vf8, vf9, vf10, +vf16). Read from Flee (vt_0x1DC5010) and FleeAmbush (vt_0x1FBCCC8):

slot Flee / FleeAmbush role
vf0 0x72A3AC / - scalar deleting destructor: dtor 0x72A3E0, then 0x8C4370(this, 0x5F0) when bit 0 of the flag is set. A Flee step is 0x5F0 bytes; 0x8C4370 (5-byte thunk, 4,839 callers) is the sized operator delete
vf1 0x780680 / 0x780690 writes 2 bytes to out: {class constant (Flee 1, FleeAmbush 0), this+0x19}; the vf1s of all step classes sit together at 0x780680-0x780710
vf3 - PREPARE(ctx): called on each candidate right before vf5 at plan selection (0x191030)
vf4 - RELEASE: after a rejected vf5, and after vf10 when a step leaves the stack
vf5 0x4473A4 / 0x444964 EVALUATE(ctx, &out) -> status at plan SELECTION (0x191030): 0 = take this step, non-zero = reject (CORRECTED 2026-10-28, twice: first "begin", then "called from the tree build" - that call, 0x45B614 <- 0x45B290, is the ServiceSet loop on SERVICE objects, not steps). Returns 2 when the precondition fails (NPC::IsFleeing(this+8) false; FleeAmbush also needs the player's bodyguard, TraitsRequired and SearchDistance from its record)
vf7 - called on the finished step during unwind; a non-null result is copied into the parent's context (LEAD: result payload)
vf8 0x4E7DD0 / 0x7F7DE0 return true (both); the vf8s sit together at 0x7F7CC0-0x7F7E90
vf9 0x3EC558 / 0x1B01438 UPDATE(forced, ctx = tree+0x48, &out) -> status, from 0x191ADC every tick: 0 = keep running, 1 or 2 = finished; returns 2 (abort) when [planner+0x810] no longer equals the target the step stored (Flee this+0x5E0, FleeAmbush this+0x430)
vf10 0x359844 / 0x1B012D0 END(reason): reason 1 when the step finished with status 1, else 2. Cancels the step's move request (0x44344C on this+0x20 / this+0x48), stops fleeing (0x359988), clears [planner+0x697], sets [planner+0x500] = 1.0f
vf11 - EVENT(msg): 0x3F5B38 sends one message to every active step (from character vf19)
vf12 / vf13 - CHILD FINISHED, on the parent: vf13 when the child returned 1, vf12 when it returned 2; a non-zero return ends the parent too (behaviour-tree propagation, 0x3763A8)
vf14 - called on every active step by 0x3F566C (from 0x4428B0, which also reads AI/Count/Configuration.RunSimulation)
vf15 - STILL VALID(ctx) -> bool: 0x3F5AD0 (from character vf53) unwinds the stack from the first step answering false
vf16 - / 0x1B00D28 debug description: appends "Approaching" or ""
vf17 - debug filter match (0x1B04B68, only while the byte at 0x2A361F1 is set; filters at 0x2A361F8 / 0x2A36200)

Status meaning (LEAD): 1 = succeeded, 2 = failed / aborted - Flee returns 2 both for a failed precondition and for a lost target. Would settle it: ai_plan_watch around a step that completes normally (a GoTo arriving).

Step object: +0x08 the NPC (CCharacter), +0x10 the step's definition RECORD (its AI/Planner/Steps/<Type> record; the field accessors take it), +0x19 a byte that vf1 reports. Planner object [character+0x2CE8]: +0x810 the current target / plan the steps validate against, +0x7D0 read by Flee's update, +0x697 byte and +0x500 float reset on END, +0x910 = despawn requested (memory: war-spawner-pile-backlog).

Why it matters for mods: a step's behaviour is tuned by its record (writable through the write gate, field_flow says when a change is picked up), and its preconditions are code in vf5 / vf9. Status 2 from either ends the step, so "make orcs never flee" is a precondition question (NPC::IsFleeing, the record's gates), not a matter of patching the step.

Planner construction and the step factory (MEASURED 2026-10-28, offline)

  • The planner object: the AI character class (vt_0x1FB3640) constructs it in 0x49B858 (lea rcx, [this+0x2CE8]; call 0x49CB20): 0x49CB20 = malloc(0xFF8) + constructor 0x45F354, stored at [character+0x2CE8] - a 0xFF8-byte object with no vtable (seven 0x58-byte sub-objects at +0x118..+0x328 built by 0x45FC68, more members after). The character's destructor 0x49CEC0 tears down +0x2CE8, +0x2CE0, +0x2CD8 in reverse order. 779 functions read the pointer (64-bit loads of [x+0x2CE8], byte scan + disassembly check), including the NPC script natives (NPC::Search, NPC::CircleMidPoint) and character methods vf19 / vf54 / vf75 / vf111.
  • The step tree is built once, at character setup, from the NPC's AI/CharacterTypes.PlanTree record (accessor 0x7279C0) and stored at [character+0x2D38] (next section): vt_0x1FB3640::vf12 (0x3FA718) -> 0x45AFDC -> 0x6FC774 -> 0x6FC7B8 -> ... -> the step FACTORY 0x45CEE8 (2,800 bytes). The factory reads the step record's category ([record+0x18]) and compares it with a table of cached category pointers at 0x2A359D8 + n x 0x18, jumping to the type's creator: Flee 0x6E71D8 -> ctor 0x6E7288, FleeAmbush 0x6EB52C -> 0x6EB5DC, Cower 0x1ADD54C -> 0x1B02E84 (all three only called from the factory). So a step's GameDB record TYPE selects its C++ class. The factory recurses (0x45CEE8 -> 0x45C724 -> 0x45CEB0 -> 0x45CEE8): composite steps build their child steps.
  • Slot calls located: vf10 (+0x50, END) is called by 0x3EB9C4, reached from character vf17 (0x4A1764), the character destructor 0x49CEC0 and the tick's reset request (below). CORRECTED 2026-10-28: "vf5 is called by 0x45B614 from the tree build" - 0x45B290 is called with [character+0x2D00] and each AI/CharacterTypes.ServiceSet record (the loop at 0x45B1B8), so that +0x28 call is on a SERVICE; steps get vf5 at plan selection (next section).
  • All 64 factory branches mapped (live category table + the creator's constructor chain; script step_factory_map.py, 2026-10-28): 64 / 64 resolve a category and a class vtable; the 16 classes named by class_category above agree 16 / 16. Shared bases seen in the constructor chains: vt_0x1FBD1D8 (every step), vt_0x1DAA7E8 / vt_0x1DB5500 / vt_0x1DB1050 (move-request steps: Flee, FleeAmbush, DespawnOffscreen). The live reader ai_plan names steps from their record's category, so it needs no table.

The plan tree: where the running steps live, and its tick (MEASURED 2026-10-28, live + offline)

The planner at +0x2CE8 holds NO step (a two-level pointer scan of its 0xFF8 bytes over 40 NPCs found only stray hits; +0x7F8 is an intrusive list of observer hooks from many objects). The steps live in the plan tree at [character+0x2D38], a unique_ptr: 0x45AFDC builds it with 0x6FC774 from the PlanTree record and move-assigns it (0x75F2DC; the old tree is freed by 0x3EB630). Live check, desert, 74 / 74 spawned NPCs (all vt_0x1FB3640) have one; trees: BasicEnemy 62, Warg 6, BasicEnemy_Archer 5, Troll 1.

tree offset holds
+0x00 the AI/Planner/Trees record
+0x08 the NPC
+0x10 the root step: AttackPreview ForcedAttack in 74 / 74
+0x18 / +0x20 ACTIVE STACK, 0x18-byte entries {u8 ticks, u32 status @+4, u64 @+8, step* @+0x10}, root first, the running leaf last. Example: Priority:IsFleeing (ticks 0) -> Flee:Flee (ticks 1)
+0x30 / +0x38 every step of the tree, 0x10-byte pairs {step*, u8 forced_ok @+8, u8 presentation_ok @+9}, in the order selection tries them. BasicEnemy: 53 steps, 53 / 53 resolve to a typed record
+0x48 the context passed to step slots
+0x50 / +0x51 / +0x52 replan request / presentation latch / reset request

A step's +0x10 record names its type through its category (AI/Planner/Steps/<Type>), so the vtable-to-type table is not needed to read a plan.

The tick 0x1919C8(tree, forced): - callers: vt_0x1FB3640::vf119 (0x2F79A4, per frame, forced = 0, skipped while 0x11548E0(npc)) and 0x2FD850 (forced = 1), reached from 0xF41E30's batch right after Quest_AI_REPLAN_Requesting_replan... (a quest-requested replan ticks at once). The label "RigidBody::vf2" that 0x2F79A4 carried was a vtable-split artifact (kb/binary-code.md, phantom starts). - +0x52 set -> 0x3EB9C4 ends every active step (vf10) and clears it. - the planner's presentation state (0x190FF0 = planner+0xB20 || +0xB18 || +0xB1C) is latched in +0x51; on its rising edge 0x4E7E04 ("presentation started") unwinds the plan, so a scene pre-empts whatever the NPC was doing. - +0x50 set and character vf113(1) true, or an empty stack -> 0x3F65F4 -> SELECT 0x191030: walk +0x30 in order, skip the running step and every pair not allowed now (0x191374: a forced tick needs byte +8, a presentation needs byte +9), call vf3 then vf5; the first step whose vf5 returns 0 is pushed - list order is priority order. - UPDATE 0x191ADC: each stack entry with ticks != 0 and status 0 gets vf9; a non-zero result either parks in the entry (when a deeper entry follows) or finishes the top step via 0x376E28. - UNWIND 0x376E28 / 0x3763A8: the finished step gets vf10(reason) and vf4 and is popped; its parent gets vf13 / vf12 with the child's status and ends too when that returns non-zero.

Other tree methods: 0x3F5B38 (vf11 event broadcast, from character vf19), 0x3F5AD0 (vf15 validity, from character vf53), 0x3F566C (vf14, from 0x4428B0).

Read it live: call("ai_plan") (every NPC: tree, stack, leaf; 74 NPCs in ~0.1 s; first run read leaves Attack 10, FollowLeader 9, Flee 8, CircleTarget 7, MenaceTask 7, FollowRoute 7, CombatRecoil 7, Idle 6, Mounted 5, ...), call("ai_plan", steps=True) (+ the priority list), call("ai_plan_watch", seconds=30) (leaf transitions; BUILT, the one run so far saw a frozen world clock - game unfocused - so transitions are NOT yet measured). Code anchors guarded by tests/test_ai_plan.py (13 / 13).

Why it matters for mods: "what is this orc doing and why" is a pure read. A behaviour change has three levers, in increasing risk: the step's RECORD (tuning, read by vf5 / vf9), the pair bytes +8 / +9 (whether a step may be chosen in a forced replan / during a presentation), and the ORDER of +0x30 (priority). None of them has been written yet; the pair bytes and the order are per-NPC heap state, re-built with the tree (vt_0x1FB3640::vf12), so a write would last until the NPC's tree is rebuilt.

Combat behaviour measured live (2026-10-28) and the global AI constants

Live combat capture (MEASURED, desert, 73.5 s of world clock, 1,215 samples, read-only; combat_capture.py in the session scratchpad): up to 17 NPCs engaged against the player, one fight circle (the player's) the whole time. In 122 timeline samples, NPCs whose leaf step was Attack: 0 in 65, 1 in 32, 2 in 25, never 3+. Typical snapshot: 10-12 in CircleTarget, 1-2 in Attack. Leaf transitions: CircleTarget -> Attack 30, Attack -> CircleTarget 25, GoToPreferredAttackPosition -> CircleTarget 25, CircleTarget -> CombatRecoil 19, CircleTarget -> GoToPreferredAttackPosition 17, CombatRecoil -> CircleTarget 16. So the planner's CircleTarget / Attack alternation IS the fight circle handing out attack turns (kb/combat-systems.md "Fight circle"). The suspend byte npc+0x2C21 never fired and no stack entry parked a status in the whole capture (both stay open leads).

AI/Constants (one record, Constants): PersonalBubbleDistance 50, ThreatUnseenTime 10 s, OnScreenCheckDelay 0.1 s, RetreatThreshold 3, RetreatCount -1, BrandedDefendPlayerMinimumRange 500, FindUnreachablePositionDelay pools, BattleNodeMaxSelectionsPerFrame 255 / Child 32, MaximumAllyGruntsInCombatSpace 10 / MaximumOpponentGruntsInCombatSpace 10* (registered min=0;max=10), DefaultCharacterModel Orc_Infantry, NPCKnockBackAttack NPC_Knock_Back. The grunt caps are read through 0x6DD4B0(ally): a live override [[GameManager]+0x6C60]+0x588 (ally) / +0x58C (opponent) wins when >= 0, else the record (the System::ClearRetreatCount label on the record getter is a shared-body name). The same field exists on Quest/Quests (min=-1;max=10): LEAD - the quest system ([GM+0x6C60], vt 0x1FCD308) copies the active quest's value into the override; both read -1 in free roam (MEASURED).

AI/Simulation/* (15 categories) = the cheap crowd AI of army battles: 12 Configurations (OrcDefender, Spiders, FellBeast, ...) each pick animation pools (Idle / Movement / OffMesh / Activity / Attack / Recoil), CanTargetNonSimulated, riders, and an attack budget AttackThrottling {AttackCapacity, AttackWeight}: Grunt 4 / 1 (four grunts on one target), Named 4 / 4 (one), Warg 8 / 4, Troll 20 / 20, FellBeast 40 / 4. A second attacker limit, separate from the fight circle.

AI/LeadPlayer (16 records): escort / guide NPCs (e.g. DLC3_Architect): ReachRadius, LeadRange / SlotRadius pools, WaitWidth / WaitExtension, beckon delays + audio prompt, repath delays, MovementData -> AI/BandTypes/BandMovementData.
