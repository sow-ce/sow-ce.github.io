Mercenary Camp — DOM's hiring in the main campaign (IN-GAME CONFIRMED 2026-10-03)

Army menu -> empty or dead captain slot -> Browse Mercenaries -> Hire, for Talion. User-confirmed in order: the screen opens; a free hire put Drúgred into Lithlad's dead captain slot as a follower; he survived save + reload; DOM's own Oasis camp stage shows after a fast travel (AIRE watcher, then the DLL lane: "Tested working"). Zero hooks; every cell checked against its measured value and journalled.

A hire is a cross-army TRANSFER, not a recruit. Mercenary OnAction 0xDBC910 takes the selected FM from Faction_desert_mercs_DLC4, prices it (GetHireCost 0xFA3AF0), pays (PayCurrency 0x189353C), then 0xCFBFD0 -> FactionSystem::TransferMember(FS, fm, dest{faction,row,col}) 0xF6AC90: refused unless both factions share a Pool; unlink 0x1C25500; FM+0x178 (and +0x180 if empty) rewritten; the destination's EventSetup.TransferIntoFaction fires (every base army already ships Transform_HireMercToEmpty). Emulated: island captain -> Faction_snowMtn passes the pool check, so moving captains between any two MainGame armies is stock code.

All 38 armies exist in every game mode. Contexts at FS+0x98 (38 x 0x290; entry+0 = Faction/Definition, ctx = entry+8, vt 0x1FDDF78), pools at FS+0x68 (9 x 0xC0, object = entry+8, vt 0x1FD8310, member vector +0x18/+0x20); FM+0x174 = the FM's index in its pool vector (500/500). A full row = built but unseated (all three Seregost captain rows were full; the warchief rows had one free column each). Army Menu Camera — BOTH VIEWS CRACKED (IN-GAME PROVEN 2026-08-12)

The Army menu's 3D view and the captain [X] zoom-in are two different camera branches, and the whole limit in both is one field: CameraOffsetRange, a type-7 float pair (yaw, pitch) in DEGREES on a _StructuresUIOrbitPointParams orbit key. No hooks, no NOPs, no freecam to enable — the freecam is already on and clamped.

BRANCH 1 — the fort orbit. Faction/HierarchyMenu/Setup.ArmyCameraState names CS_Army_Cursor, but that record does NOT drive the view. It carries UseWorldMapCameraPredicate -> HierarchyFreeCursor, whose IncludedTopMenuLayers is [HierarchyLayer, ContractAssignment, Mercenary]; with the Army menu on top that predicate is live-active, so the camera is handed to the WorldMap layer:

Interface/Menu/MenuLayer/WorldMap.HierarchyCameraState
  -> Interface/Camera/CameraStates :: HierarchyFreeCam
       .Keys[0..1] -> _StructuresUIOrbitPointParams   (zoom-in / zoom-out)
            .CameraOffsetRange   (24,12) near / (16,10) far   <- THE CLAMP

BRANCH 2 — the captain zoom-in. CS_Char_Detail has UseWorldMapCameraPredicate = NULL (gates() verdict permissive), so it never reaches HierarchyFreeCam — which is exactly why widening branch 1 leaves the detail view clamped. Its UICameraSettings is an array of 153 UICameraStates selected by predicate per orc row and slot (Orc_Row2_L, Orc_SlotOverlord_Row4_3, Orc_Dead, Talion, RingWraithOverlord_C, ...), each -> Interface/Camera/CameraStates -> .Keys[] -> orbit points.

There is no single record to patch — but 153 states collapse to 8 pools:

pool (yaw, pitch) keys covers
0x3D77C37C (0,0) 76 fixed row/slot views — SENTINEL, NEVER WRITE
0x3E0B3590 (90,20) 16 _base_Orc_* / _base_Olog_* — the standard captain
0x3E0B3520 (90,25) 2 dead
0x3E0B3540 (80,15) 2 decapitated
0x3E0B3970 (60,20) 3 restricted
0x3E0B3660 (60,15) 2 decapitated restricted
0x3E0B34E0 (45,15) 5 orc captured
0x3E0B3838 (40,15) 5 olog captured

(90, 20) is a numeric match to the observed quarter-turn. Widening the 7 non-sentinel pools to (180, 85) unlocked the detail view in-game.

THE DETAIL VIEW HAS NO ZOOM AXIS. All 111 of its camera states carry exactly ONE orbit key (radius 250-550), so OrbitRadius there is a FIXED camera distance, not a near/far range — there is nothing to "widen". The Army orbit zooms because HierarchyFreeCam has two keys (1025 near / 5250 far) and the camera interpolates between them; a key COUNT of 2 is what creates a zoom axis at all. Scaling the 111 single-key radii moves the fixed distance (x1.8 -> 450..990 applied live, 111/111 written, 0 failed).

OrbitRadius is a plain Float in the primary's OWN instance — not pooled, so each key is private and a write affects only the states referencing that primary. Contrast CameraOffsetRange, which is a shared pool pair. Same record, two different sharing models; check which before estimating blast radius.

MOVING THE CAMERA WITHOUT THE DEPTH OF FIELD MAKES THE SUBJECT BLURRY (user-visible, 2026-08-12). Each orbit key carries a DepthOfField link to Client/DepthOfFieldSettings (FarInFocusDistance, FarBlurredDistance, NearInFocusDistance, NearBlurredDistance, FarBlurIntensity), authored for the SHIPPED radius. Orc_Details is sharp 120..325 and fully blurred past 375; the x1.8 pull-back put the camera at 450..990, i.e. well outside the band, so the captain rendered as blurred background.

Fix by pushing the FAR planes out, sized per record from the radii that actually reference it — never a blanket multiplier: the 8 DOF records span Orc_Details (max radius 576) to OverlordSlotting (2500 already, 75 keys, needs nothing). Applied FarInFocus = maxRadius * 1.35, FarBlurred = FarInFocus * 1.25, clamped to never fall below shipped.

Do NOT "fix" it with FarBlurIntensity = 0 — that also kills the background blur, which is part of the look. Only the focus DISTANCE should move.

0x3D77C37C IS THE GADB-WIDE UNSET SENTINEL — 72,774 REFERENCES (control in the same scan: 62). It is the (0,0) "no value" pair. Writing it moves 72,774 consumers across every subsystem at once. Detect it by VALUE, not address: a pair reading exactly (0,0). That is simultaneously the sentinel guard and the "this view has no rotation axis" check, and unlike a hardcoded address it cannot go stale.

THE 76 KEYS PINNED TO IT WERE FREED BY ENUM-SWAP — IN-GAME PROVEN 2026-08-12, 76/76, 0 failures, no crash. Their values can never be written, so the only route is repointing the CELL at a different pool entry. That is the ENUM-SWAP class, which the chaos-ladder says kills hot-thread domains — and the mitigation that makes it safe is do it COLD: the hazard is a thread dereferencing the cell as it changes, not the store, which is an aligned atomic 4-byte write. Performed in free roam with the Army menu CLOSED, all 76 swapped cleanly and the slot views then rotated correctly.

Rules that made it safe, all of which should carry to any future enum-swap: - swap COLD — subsystem not running (!isArmyOpen, never a UI button handler: the mod overlay can be open while the game menu is not); - guard on the expected old pool per cell, so a cell that moved is refused rather than blindly overwritten; - validate the destination is a real float pair before pointing at it; - point at an entry you already own and proved (here 0x3E0B3590 at (180,85)) rather than allocating or guessing a free one; - journal the cells — revert restores the POINTERS, not the values.

Consequence: those 76 now share a pool with the 16 _base_* detail cameras and move together. Independent ranges would need a second entry. 75 of the 76 are SlotOverlord context, 1 is Upgrades.

Write class matters. Camera is a hot-thread domain: POOL/FLOAT mutation is the TOLERATED class, ENUM-SWAP (repointing the type-7 cell) is the class that crashes. Both mods write the pair BEHIND the pointer and never the pointer. Pool entries are shared — measured 1-22 refs for the camera entries, so a write can move a sibling view; back up the pair and restore it exactly.

C++ side: framework/sowframework/sdk/sow_army_camera.hpp (Controller for the orbit, DetailController for the zoom-in), driven from the Camera panel in ui/tabs/sow_tab_movement_new.cpp. AIRE side: set_pool_primary / set_field_primary.

What did NOT work — do not re-attempt

  • DebugCamera.FreeCamControls "1"/"0" — did nothing because it takes a MODE NAME. CORRECTED 2026-10-24 (code): the handler is 0x17CFF54; it compares argv[0] with "Cinematic" / "ClipMode" / "Marketing" and stores 0 / 1 / 2 at the debug camera manager [base+0x2A86860]+0x118; anything else is ignored. 0x17D0074 (described here before) is DebugCamera.Track, which looks an OBJECT up by name (ObjectServer vf13) to follow. The manager (vt 0x22F4A90, a state machine: slot 1 = SetState 0x159DE4; resolver.db calls the static "MacroStateMachine") is built at client start (0x17CD2EC) and read by the screen camera copy 0x4E0CFC; what switches the view to it: not found yet.
  • The 18 hardcoded "camera limit" RVAs the old mod wrote EVERY FRAME: rva_audit (max_hits 6000, none truncated) returns 0 of 18 LIVE — 12 UNREFERENCED, 5 DEAD_LITERAL, 1 DEAD_SHARED. Their values are pi/4 (0.785398) and sqrt2/2 (0.707107) — generic pooled math constants found by value-searching for "45 degrees in radians", the same methodology that produced the debunked Havok constants. 0x202EC94 is read by 18 unrelated functions, so writing it corrupted every consumer. Removed 2026-08-12.
  • CS_Army_Cursor -> Fort -> HierarchyOverview_ExcludeScratch — the non-freecam branch. Its CameraOffsetRange is (0,0); writing 360 into it changed nothing in-game.
  • k_vWorldSpaceEyePos as "the camera" — per-DRAW, so consecutive samples jump between render passes. Circle-fitting a 2,388-sample path gave radius 530-800 with median residual 67-225 and a 17:1 path-to-displacement ratio.
  • The model viewer (FactionMemberModelCam, OrcViewerCameraData, Min/MaxExtents) — a real subsystem, but not consumed by the captain detail view. Writing its pitch and its Extents Vec3s did nothing in-game.
  • WorldMapCameraMode is not a free/locked switch: 153 of 155 camera states use 4, with single outliers at 5 (Store) and 6 (Mercenary).
  • CameraManager (0x26FFB40) reads NULL — see the fake-manager audit.

Method note: every attempt that started from a plausible field NAME failed. The two that worked started from gates() (which record is SELECTED at runtime) and from deduplicating the reachable set so picking correctly stopped mattering.
