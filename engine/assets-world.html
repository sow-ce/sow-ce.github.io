Asset Content Layer (EXPOSED 2026-07-21 via aire.formats.assets)

The old "asset contents are undecodable blobs" ruling is STALE. The frozen substrate carries full per-tag EMBB section parsers (mesh_parser: positions/triangles/bone-weights/OBJ export + replace_mesh_from_obj; skel_parser: bone names/transforms; anim/tex/cdef/prfb/objr parsers). AssetInternals is the AIRE surface over them: 400,238-path index across all 71 archives (the substrate resolver only knows a subset — the index covers everything), priority-aware extraction, container probe, deep section decode, OBJ export to aire/data/world/asset_exports/. PROVEN offline 2026-07-21: sauron_fairform.embb = 6 MMSH / 7 SKEL (SKEL#6 = 100-bone body rig) / 73 ANIX / 68 TEXR; MMSH#2 exported to OBJ (1,623 verts, 996 tris).

SECTION COUNTS AND SIZES FROM BEFORE 2026-08-06 WERE SCAN-DERIVED — RE-READ THEM. EMBBParser located sections by SEARCHING for tags and sized each as "distance to the next hit". Measured over 637 shipped containers / 5,668 real sections: 3.2% exact, 2,392 mis-sized (dominant delta +4 — it swallowed the next section's size prefix), 154 phantom, 3,092 missed, and 338 containers where the scan saw nothing at all. Repaired: the parser now walks the [u32 size][payload] chain, agrees with aire/formats/embb.py 637/637, and round-trips byte-identically 300/300. SECTION_TAGS listed 10 tags; there are 24 — PRFB/BKHD/OBJR/UISH/UIWD/SCRI/WDSC/ HKAI/VEGG/TERR/MESH/VIDO/SLVT/CPUT/SUBB were all invisible. This retires the "placement layers expose 0 media sections, format TBD" ruling: they were never media bundles and nothing was looking for their tags. sabotagecages_00.embb now probes as 26 sections across 13 tags (SCRI/WDSC/PRFB/LTMI/VEGG/LTFX/TERR/HKAI/ TEXR/OBJR/SRHR/UISH/UIWD). probe() now returns chain_valid, and warns explicitly when sizes are scan-derived instead of presenting guesses as measurements.

Remaining real limit: some MMSH segment-table variants fail mesh_parser's heuristic (MMSH#0/#1 in sauron_fairform). That is a MESH-parser limitation, not a container one — A/B'd across every MMSH in 637 containers under old vs exact bounds, net change 0 (58 parsed before, 58 after; no verdict flipped either way).

MeshParser located its OWN mesh, and had the same blind spots (FIXED 2026-08-06). It ran raw.find(b"MMSH") over the whole container, ending at the first SKEL/LTMI hit — so it never saw MMSH #1+ (find returns the first), and its end was wrong in 73 of 78 containers (dominant delta +4, the next section's size prefix; worst +43,939, a whole neighbouring section). asset-mesh-to-obj --index was accepted and silently ignored. Bounds now come from the chain, stamped in bounds_source (exact / embb_chain / scan); an out-of-range index is refused rather than served mesh #0. The write path was the live defect: replace_mesh_from_obj spliced at the scanned end and never rewrote the u32 size prefix, and asset_replace_mesh repacked that into an archive — the load-hang class of §"WHAT ACTUALLY BREAKS A RESIZE". Reproduced on a shipped bundle: emitted 253,578 B whose chain ends at 253,262 (+316 slack), prefix still declaring 248,878, section count 3 -> 4. It re-emits through EMBBParser now (prefixes repaired, bndl_stale reported on size change). Regression: 58/58 route agreement, 78/78 out-of-range refused, 29/29 round trips walk with neighbours byte-identical, 25/25 resizes walk, 15/15 broken chains refuse to rebuild. The chance-tag truncation this also removes is a latent hazard, not an active defect — 1,292 MMSH payloads swept, 0 contain a stray SKEL/LTMI. asset-skeleton / asset-materials were measured and are CLEAN (SKEL 121/121, LTMI 568/568): parse_all finds every magic and sizes each section from its own header, so only MMSH depended on an end marker.

Record -> ASSET link (COMPUTED 2026-08-03) — aire/formats/asset_link.py

The engine graph joined binary/GADB/live but never the record->asset edge; the 400,248-path archive index and the GADB sat as two disconnected worlds. call("asset_link_build") computes the whole set offline in ~7s: 26,999 edges over 14,632 distinct paths and 19,322 records.

All 25 GADB-bearing archives are MERGED in archcfg order, not read one at a time. Reading only hotchunk was incomplete: over the 31,966 String values where hotchunk and Patch_04_LC disagree, hotchunk uniquely resolves 1,809 and the patch uniquely resolves 1,651 — the loser is almost always UNSET (empty, or a string offset below 13, which reads a suffix of the block's root type name GameDatabase and surfaced as the literal 'ameDatabase'). Highest-priority non-unset value wins; each edge records its gadb_source. Purely additive: 0 edges changed, 0 removed, 1,996 added (e.g. Character/Models::DarkTalion.BehaviorResource -> behaviors\player\player_elf.bvr).

Values are read at the offset each String/String2 field actually REFERENCES, never by splitting the string block on NUL — the block is shared-SUFFIX, and the split route produced paths with foreign leading bytes (\x10@fx\characters\...). Path shape is constrained from the index itself, not guessed: 0 of 400,248 archive paths contain whitespace and all 37 extensions match [a-z0-9_]{1,10} (max 7).

Only ~9% of referenced paths are archive entries, and that is not decoder error. The GADB names SOURCE assets (characters\...\x.skel) while archives ship BUILT containers (bundles\...\y.bndl/.embb), with the source asset INSIDE the container — proven by parsing a bundle manifest, whose internal path table lists exactly the .tex/.mat/.skel/.anix paths that dangle against the entry index. Per extension: .bndl 29.5% exact (bundles ARE entries), .fxp 2.5%, .mat 0.9%, .skel 0.1%, .tex 0.0% (never an entry).

Every edge therefore carries a resolve verdict rather than being silently dropped:

The container hop — aire/formats/bundle_index.py (CLOSED 2026-08-03)

A .bndl is the manifest for its paired .embb and lists the SOURCE paths it holds, so it is the map from "asset the GADB asked for" to "container that ships it". 224,871 .bndl-named entries -> 219,031 content-verified manifests (97.4%), 1.87M membership edges, ~150s.

A NAME DOES NOT ADDRESS A BLOB — key membership by (ARCHIVE, ENTRY INDEX). Several entries legitimately share one name_offset: Patch_06_LC has 32 groups of 4-5 distinct blobs on a single name string (different offsets, different sizes — variant copies, not chunks and not duplicates), and Patch_01 has 400 such entries. A name is a LABEL; only the entry index is an address. Two earlier attempts failed because they went through names:

  • keying by bundle path alone — the same path ships in several archives (ingame_navmarkers.bndl exists at two paths), so a global first-wins archive field pointed at a copy that did not list the asset;
  • keying by (archive, path) — still ambiguous inside an archive, for the reason above.

Validated end-to-end through an independent code path (re-open the archive, fetch the blob by entry index, re-parse, confirm membership): 60/60 over ALL in_bundle edges, up from 25/30 when lookups went through names. bundle_name_uncertain (from the archive's calibrated name-rule confidence, plus name uniqueness — globally 64,646 of 479,031 entries (13.5%) have a non-unique name) now qualifies only the human-readable LABEL, never the membership fact.

Entry NAMES themselves are in good shape: 99.7% carry a legitimate extension, and the odd 0.2% (subb, cres, wldmsh, strdb) are real extensions, not truncations.

LTAR v4 name resolution — CALIBRATED PER ARCHIVE (FIXED 2026-08-03)

The old _resolve_name_offset took the string CONTAINING name_offset plus a "if it lands on a NUL, step forward" special case. That made entries[i].path name the data at entries[i-1] — silently, since a neighbouring path still looks valid. Direction was settled by CONTENT, not shape: a BNDL manifest names its own assets, and name[i] matched the content of data[i-1] 40/40 while data[i+1] matched 0/40; no archive ever preferred +1.

No single rule is right everywhere — LTAR v4 has packer VARIANTS. Over 3,161 content-verified entries in 65 archives, next wins 51 archives but every *_lighting archive prefers containing decisively (volcano_lighting 27/30 vs next 0/30). The _file variants (skip names-table strings with no extension, since folder paths are interleaved) dominate their plain counterparts everywhere and never lose. So the rule is calibrated per archive against content and cached in aire/data/engine/ltar_name_rules.json:

rules chosen: next_file 33, next 22, containing_file 9, containing 1
confidence:   40 of 65 archives >=0.95, 52 >=0.80

Measured by the magic oracle (a .bndl-named entry must contain BNDL, scored where neighbours differ so alternating runs cannot fake agreement): 63.8% -> 95.2%. The asset path index recovered 400,248 -> 401,054 paths as collisions cleared. The residual ~5% is real and is why the bundle index verifies every manifest by content instead of trusting names.

Anything derived from archive ENTRY NAMES before 2026-08-03 may be wrong — extraction by path returned a neighbouring asset. Re-derive rather than trusting a cache.

A NAME IS NOT AN ADDRESS — content-verified blob addressing (2026-08-03)

aire/formats/entry_index.py; call("entry_index_build") / call("asset_blob", path=...).

The calibrated LTAR rule fixed the global naming error (63.8% -> 95.2%) but every path-based extraction in AIRE still resolved a blob by NAME, and the residual is not spread evenly — it is concentrated exactly where the world data lives. Measured over all 479,031 entries in all 72 archives by reading each blob's true magic: 9,181 entries (1.9%) carry a name whose extension contradicts their content, and per archive that is ui_assets 63.9%, corecharacter 35.1%, minasithil 35.0%, island 14.8%, volcano 14.0%.

Consequence, measured: of 60 sampled worlds\*\sectionsandlayers\*.embb paths, 49 extracted to a blob that was not an EMBB at all — usually a neighbouring layer's small BNDL manifest, which then decodes to nothing and reads as "this layer is empty". Dumping minasithil.arch06 shows the shape, and the shift ALTERNATES (the names table interleaves folder strings the *_file rules skip), so no constant offset repairs it:

645   366783  EMBB   named "...\sabotagecages_00.bndl"   <- IS sabotagecages_00
646     1020  BNDL   named "...\sabotagecages_00.embb"
647   104694  EMBB   named "...\sabotagecages_01.bndl"   <- IS sabotagecages_01

The oracle: an EMBB names ITSELF. Its path table lists its own parts (...\powerstruggles\sabotagecages_00.terrain/.objres/.hkai/.scripts), so a layer's identity is decidable from content with no naming rule involved. Peeking is cheap — an LTAR v4 entry is chunked, so one 64 KB chunk carries the header and the whole path table (0.26 ms/entry; the full 479K sweep is ~190 s, cached per archive).

_extract now resolves through this and reports HOW: named (magic agrees), content (the container identifies itself as that layer), stem_neighbour (the sibling blob of the right magic — the .bndl/.embb pair the error swaps), or named_unverified. Layer paths went 11/60 -> 60/60; the .bndl control 37/40 -> 38/40. Region disambiguates a stem (beasthunt_01 exists in island AND volcano) — without that hint, resolution refuses rather than picking a region.

RE-ATTRIBUTION: the documented sabotagecages_00 numbers belong to sabotagecages_01. The "104,694 B, 104 instance records" measured in 2026-07 came from the name-addressed blob. The real minasithil/sabotagecages_00 is 366,783 B with 286 instance records; 104,694 B / 104 records is sabotagecages_01. Any per-layer figure recorded before 2026-08-03 may be filed under the wrong layer — re-measure through asset_blob, and note the LAYER COUNT itself moved from 690 name-derived paths to 1,303 content-identified layers. Environmental Object System (DISCOVERED 2026-07-21 — world-building surface)

Cages/pits/nests/traps are a THREE-TIER system; nothing is hardcoded:

  1. GameDB behavior tier — DynamicObjectGroup/* (11 categories): - Setup (449): the interactive object definitions — EnvOps_Cage_Caragor, EnvOps_Cage_Drake (+_Empty/_StartHidden variants), EnvOps_Cage_Graug/Prisoner, EnvOps_Bait_{Caragor,Ghul, Graug,Spider,Fellbeast} (+_Hidden), GhulMound, barrels, fire traps. Fields: States -> StateTransition FSM records (439), Tags -> Tag/*, brush-damage validation bools. - PlacementID (14): fort-architecture slot types (CageGateOnly, TowerKit, WallFace...) — fort object placement is SLOT-based, same pattern as army garrison slots. - Creature side wiring: AI/SpawnAmbient/SpawnScenarioSetup (OpsCaragorCage, AmbGhulWave, AmbRapidGhuls...) + RemoteScript (SM_FortCaragorCages{Obj,Reset,Spawn}).
  2. World placement tier — worlds\retail\<region>\sectionsandlayers\<scenario>_NN.embb/.bndl (per-scenario layers: guardcaragors, raidcaragors, trialcaragors, sabotagecages...). Instance positions live here; Anvil can repack these archives (format decode still TBD).
  3. Art tier — prefabs\common\props\cages\* (graug cage art), fx\prototype\morgaiflynest (morgai fly nest FX), interface\bundles\shootwargcages.* (UI).

Mod route (untested): redirect what existing placements CONTAIN (swap Setup record links, promote _StartHidden/_Empty variants, retarget SpawnScenario creature links) — same proven pattern as gang/mount redirects.

THE DOG STATE MACHINE IS A TAG SYSTEM — the GADB does NOT hold the behaviour (MEASURED 2026-08-04, user-confirmed negative in-game). A live probe swapped EnvOps_Cage_Caragor.States[0] from EnvOps_BeingDestroyed_Interact to EnvOps_BeingDestroyed_SpawnGhuls (gated, journaled, readback-verified, reverted). No visible change, and the reason is structural, not a bad address:

  • a DynamicObjectGroup/StateTransition is a GUARDED RULE, not an action: IncludedBrushDestroyedAttackCategory is the attack that TRIGGERS it and StateToEnter is the tag entered. Swapping the whole rule therefore swaps the TRIGGER too — the player's interact emits PC_EnvOps_Damage_Interact, which after the swap matched no rule, so nothing fired;
  • all 77 DynamicObjectGroup/StateType records have field_count == 0 — every one is a bare enum tag carrying no FX, no spawn, no content.

So no GADB record swap can make a cage spawn ghuls: the GADB decides only WHICH TAG is entered by WHICH ATTACK. The content bound to a tag lives in the layer's scenario Lua / prefab (DynamicObjectGroup.Create(...) + Script_SetState(DBDOGStateType.X)), which is on disk.

What IS live-moddable here is the GUARD — retarget IncludedBrushDestroyedAttackCategory to change which attack opens/destroys an object. Everything else in this subsystem needs the layer (Anvil) or the native DOGMgr.SetDOGsToStateList call.

World placement layers CRACKED (2026-07-28) — aire/formats/world_layers.py

call("world_layer", path=...) / call("world_layers_index", region=...), OFFLINE.

The old ruling ("placement-layer .embb files parse but expose 0 media sections, format TBD") was misleading: they are normal EMBB v5 containers. The generic probe scans for the 11 MEDIA tags (MMSH/SKEL/TEXR/...) and a world layer legitimately contains none — so "0 sections" meant "wrong scanner", not "unparseable".

A layer (e.g. worlds\retail\minasithil\sectionsandlayers\sabotagecages_00.embb, 104,694 B) holds:

  • an asset list naming its parts by extension: .terrain, .uis, .uiwd, .objres, .scripts, .wldclnt, .hkai (Havok AI navmesh), .veggrid, .inst, plus any PREFAB it instantiates (prefabs\gameplay\quests\powerstruggle\guard_caragors.inst);

  • DOG state strings (DOGS_Alive, DOGS_Fire, DOGS_Destroyed), Setup record names (EnvOps_FirePit), quest objectives, and world-space coordinate blocks.

Objects are CREATED BY SCRIPT. The embedded Lua calls DynamicObjectGroup.Create, TriggerSpatialDims.Create, TeleportPoint.Create, CombatExplosion.Create, SpecialFXSeq.Create, LookAtTrigger.Create, Group.Create, QuestRelay.Create, and drives state with cageDOG1.Script_SetState(DBDOGStateType.QuestObjective). So "place anything anywhere" is a SCRIPTING problem, not (only) a binary-placement-table problem — which is a very different and more tractable attack surface.

Layer -> GameDB linkage is proven. Proven on 4 layers: sabotagecages_00 = 1,193 lines / 52 KB / 8 entry points; raidcaragors_00 = 2,037 lines / 85 KB; trialcaragors_00 = 1,287 lines; guardcaragors_01 = 844 lines. Entry points are _<name>_<8 hex> (_guard_caragors_QR_StartQuestScript_ec143e55).

PER-OBJECT TRANSFORMS CRACKED (2026-07-28) — call("world_instances", path=...)

The old ruling ("not unit quaternions — a full-file scan found zero") was an ALIGNMENT ARTIFACT, not a fact about the format. Instance records are packed at UNALIGNED byte offsets (a record's position field routinely starts at an address that is not a multiple of 4), so a 4-byte-aligned scan structurally could not see them. Read at every byte offset and the quaternions are there, unit-normalised. Never conclude "encoding X is absent" from an aligned scan of a packed format.

Instance record — 0x32 (50) bytes, unaligned:

Offset Type Field
+0x00 u16 link — 0xFFFF = root, else parent instance index
+0x02 u32 name/string index (sequential 0,1,2… for a table's LEADING records only)
+0x06 f32[3] position (world space)
+0x12 f32[4] rotation quaternion (x,y,z,w), unit
+0x22 u32 zero
+0x26 u32 per-instance id
+0x2A u32[2] monotone byte offsets into the name table

Tables are located by the leading sequential-index signature (no wrong stride can fake a monotone 0,1,2,3 run), then extended by parse validity — requiring index==k throughout truncates a table early, because the index column is a name index, not a global counter.

Evidence (four independent checks): leading sequential run; 0 non-unit quaternions across 43,257 decoded instances (120 layers); instance positions match the same layer's PFDG positions (83.7% within 120 units); a run terminates exactly at the next container block (sabotagecages_00: 104 records ending precisely at the PRFB at 0x9331, 50 of them genuinely rotated). 74% of instances carry a real (non-identity) rotation.

PFDG = prefab placement group (in world_layer's prefab_placements): +0x00 'PFDG' | +0x04 u32 ver(1) | +0x08 u32 count | +0x0C u32 aux | +0x10 count × {f32[3] world pos, f32[3] AABB half-extents}.
