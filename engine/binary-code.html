PE Section Layout — the binary is PROTECTOR-PACKED (CRACKED 2026-08-03)

The textbook assumption "code lives in .text, below ~32 MB" is FALSE for this binary and it was baked into AireMemory.is_code as the magic bound 0 < rva < 0x2000000.

Real section table (IMAGE_SCN_MEM_EXECUTE from the header, not inferred):

Section RVA range Exec Note
.arch 0x0001000 - 0x1D87C00 YES the original ~30 MB of code
.sdata 0x1D88000 - 0x1D91400 YES (also carries the static manager cluster)
.xtext 0x1D92000 - 0x25AC000 no the DB Explorer schema metadata string pool
.pdata 0x2AA5000 - 0x2C85000 no 159,018 function entries
.bss a 0x2C89000 - 0x729714D YES 70 MB of executable, CNT_CODE (0xE0000020)
.rsrc / .sbss / .text1 / .bind 0x7298000+ YES small executable tails
.text 0x7299000 - 0x7299014 no 20 bytes, NOT executable — a decoy

is_code therefore declared every function in a 70 MB executable region "not code", which silently under-detects vtables: the >=4 of 6 slots are code test fails for any class whose methods live there. Measured — 880 RTTI-confirmed vtables scored ZERO code slots under the old bound and 1-24 under section-derived executability. is_code now derives its ranges from the section table (cached, offline, with the old bound only as a last-resort fallback).

Consequence for earlier results: any heuristic gated on is_code was a FLOOR, not a measurement — including the world-object owner walk's 84-88%. Re-running vtable_method_sweep after the fix: dead vtables 880 -> 0, slots 12,527 -> 32,934, unique engine methods 5,480 -> 15,540 (2.8x).

.pdata IS NOT THE FUNCTION UNIVERSE — the leaf-function law (MEASURED 2026-08-03). x64 Windows requires a .pdata RUNTIME_FUNCTION only for a function that needs UNWIND data. A leaf — allocates no stack frame, touches no non-volatile registers, and calls nothing — is legally allowed to omit its record. So "absent from .pdata" means "never needs unwinding", NOT "not a function".

Measured: 61,244 call targets have no .pdata entry, and the classification is unambiguous: - 0 of them appear as a call SOURCE — every one is a leaf, exactly as the ABI predicts; - 0 land inside another function's [begin,end) range — so these are not stray mid-function targets, and the call graph is not manufacturing them; - 0 are int3 padding — essentially no false positives; - 75.3% start with a textbook prologue, 22.9% with other real leaf code, 1.7% are e9 tail-jmp stubs, 0.2% are ff 25 import thunks. - 171 are called 50+ times. StringHash (0x423E70, in-degree 2,060) is one of them.

Treating .pdata as the universe therefore silently excluded 61,244 real, heavily-called functions. The true universe is .pdata UNION every call target = 224,819 — which is what the engine graph had been using all along; only the labeller had not. label_enrich now covers all of it, and the summary reports pdata_starts and leaf_functions_outside_pdata separately so the two denominators can never be confused again.

FUNCTION IDENTITY — fragments, leaves, tails, and the obfuscated half of .bss a (MEASURED 2026-10-05; aire/analysis/unwind.py, xref_index.py, xref_decode.py). The 224,819 above was still wrong in kind:

  • 26,293 of 163,575 .pdata entries (16.1%) are FRAGMENTS: UNW_FLAG_CHAININFO, their unwind record ending with the parent's RUNTIME_FUNCTION (8,140 flush after the parent's end, 11,001 within 64 KB, 7,152 far = cold blocks; 12,232 functions own fragments; all unwind v1, 0 unparsed). Counted as functions, each had 0 callers (entered by fallthrough/jmp), 26,742 call edges were credited to them instead of their function, and their strings were missing from it. UnwindMap folds them; function_info / callers_of answer for the function.
  • The function list is 243,845: 137,282 .pdata functions + 106,563 leaves, 36,907 of them absent from the old list (24,057 .arch callbacks only ever lea'd, 8,794 data-pointer targets, 3,275 data-referenced .bss a methods). Only 11 old entries dropped, all outside code sections. Start profile of the new ones: 99.1% (control .pdata starts 97.0%).
  • Jump targets never create functions (IDA's model: a jump destination is a tail). .bss a holds the protector's OBFUSCATED code too: 5,219 .pdata bodies of stack juggling (popfq; jmp, mov [rsp],rbp; lea rbp,[rip+..]; xchg [rsp],rbp) chained by jumps across 70 MB. Trusting jumps made 29,170 junk "functions" passing the start profile 21%. Only data references (vtable slots, pointer tables) create functions there.
  • Start profile = 16-aligned, or CC/90 before it, or flush after a known body. A bare ret (C3) before an unaligned start is NOT enough: real functions after a ret are flush after a known body 17,962/17,964, junk 14%.
  • Decode by recursive descent, never linearly past a terminator. The protector put junk after the ret of the methods it moved into .bss a (branch targets beyond it): a linear leaf decode dropped 54 real vtable methods. Parents enter fragments MID-body (0xF7427E at 0xF742A6), so inbound jump targets are extra roots and gap fill repeats until coverage stops growing.
  • Jump tables sit INLINE in .arch after their function (MSVC lea rB,[__ImageBase]; mov eJ,[rB+rI*4+T]; add rJ,rB; jmp rJ, the bound found through register copies like movsxd rax, edx). A linear decoder turned their bytes into ~2.8M fake instructions. 175/181 resolved.
  • Tails: 4,822 call-free blocks outside every .pdata body that a function jumps to and back from (no unwind needed), 1,977 in .arch, 2,845 in .bss a; owned by the jumping function.
  • Undecodable bytes inside .pdata bodies: 6.94 MB in .bss a (protector), 29 KB in .arch.
  • Startup pointer tables (live snapshot, aire/pipeline/live_image.py): 33,354 .idata slots are zero on disk and hold code pointers live (21,343 targets). Measured across launches (PID 37456 -> 32240, 2026-10-05): Jaccard 0.9997 over 33,347 slots (8 pairs only in the previous, 1 only now). The differing values are runtime state, not tables: 0x27250F0 (a return-address variable) and a 7-slot record at 0x29E0D60..0x29E0E30 that held odd, mid-function RETURN ADDRESSES in one session (beside "Invalid heap type!" code) and nothing in the other - a captured call stack, now classed dynamic_slots.   • Control Flow Guard is off (load config size 148, 0 GuardCF functions): no compiler-made list of address-taken functions exists to shortcut any of this.
