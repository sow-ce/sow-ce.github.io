Game builds: Steam, GOG and Microsoft Store

The three PC releases of game version 1.21 side by side: their executables, install layouts and archive sets, how code, data and object layouts correspond between them, the platform layer each one runs on and where each keeps its saves, with the addresses of key engine objects in all three.

Shadow of War 1.21 ships on PC as three builds: the Steam release, the GOG release (the game with its Expansion Pass) and the Microsoft Store package played through the Xbox app. They run the same engine on the same data formats and the same object layouts. They differ in where every function and global sits in the executable, in packaging, and in the platform layer that supplies accounts and save storage. Every address elsewhere in this reference belongs to the Steam build; this chapter describes the other two and how an address carries over.

The executables

Steam

The Steam image has no relocation table (file characteristics 0x23, IMAGE_FILE_RELOCS_STRIPPED; DLL characteristics 0x8120, no DYNAMIC_BASE), so it always loads at 0x140000000 and an address is the same in every run. It carries an Authenticode certificate table (0xCE0 bytes) and a PE checksum. Its 17 section names do not describe their contents (see The executable). It exports 286 names: the Wwise sound engine's API, Scaleform's system and matrix functions, two memory pool ids and an assert hook.

GOG

The GOG image is a later build of the same engine source (see How the builds correspond):

  • Relocatable. File characteristics 0x22 (relocations kept), DLL characteristics 0x8160 (DYNAMIC_BASE, HIGH_ENTROPY_VA, NX_COMPAT, TERMINAL_SERVER_AWARE) and a relocation table of 0x72EDC bytes: Windows picks the base at every start, and an address is the module base plus the GOG build's own RVA.
  • Identified by size and time stamp. The file is unsigned and its PE checksum is 0; its size (44,474,880 bytes), time stamp (0x631BB422) and image size (0x2E3D000) identify it.
  • Runtime libraries. It imports the Visual C++ 2015-2022 runtime (MSVCP140, VCRUNTIME140, the universal C runtime, mfc140u) and delay-loads d3d11.dll and amd_ags_x64.dll.
  • Steamworks without Steam. It still imports four Steamworks functions, SteamInternal_ContextInit, SteamInternal_CreateInterface, SteamAPI_GetHSteamPipe and SteamAPI_GetHSteamUser, so steam_api64.dll ships beside it. It does not import SteamAPI_Init, which the Steam build calls first in its initialization (0x11798AC).
  • Exports. Steam's 286 names plus GetModuleVersion.

Its section table is an ordinary one, and its names say what each section holds:

The engine's codename appears again here: the package is WB-Kraken and its entry point Kraken (the executables' build paths name the project proj\Kraken).

  • Relocatable, like GOG's: DLL characteristics 0x9160 (DYNAMIC_BASE, HIGH_ENTROPY_VA, NX_COMPAT, APPCONTAINER, TERMINAL_SERVER_AWARE), 225,362 64-bit relocations.
  • Runtime libraries. The Visual C++ app runtime (msvcp140_app, vcruntime140_app, vccorlib140_app, concrt140_app) and Windows API sets instead of the desktop DLLs; it delay-loads nvapi64.dll. Its middleware is the Windows Store builds of the same libraries: amd_ags_uwp_x64.dll, bink2winrt_x64.uni10.dll (Bink 2) and oo2core_5_winuwp64.dll (Oodle). It ships neither NVIDIA Ansel nor Steamworks.
  • Exports. 304 names, not Steam's set: 19 Scaleform functions shared with Steam, Wwise's plug-in list g_pAKPluginList, and 284 functions of Microsoft's C++ REST SDK (web::http, web::json, web::websockets, utility::conversions), the HTTP and JSON layer the Xbox Live services library is built on. The Wwise API is linked but not exported.
  • Unwind entries: 180,664.
  • Reading the package. The game's data files in the package (the archives, default.archcfg, SKU.cfg) open for the game's own process only: another process can list them and read their sizes, and is refused when it opens one. The package manifests read normally.

The install root

All three hold the archives, the Game\ folder and the executable's folder. GOG adds its own files: goggame-1324471032.info describes the game (product 1324471032) and goggame-1911721374.info the Expansion Pass (product 1911721374, root product 1324471032); the game's play task runs x64\ShadowOfWar.exe with x64 as its working folder. The Store package adds the package files (AppxManifest.xml, AppxBlockMap.xml, AppxSignature.p7x, resources.pri, Localization\, SplashScreen.png) and xboxservices.config.

The Game\ folder holds the same five entries in every build: SKU.cfg, projectconsole.cfg, cinematics, interface and sound. SKU.cfg and projectconsole.cfg are byte-identical on Steam and GOG.

Archives

  • GOG ships 71 archives: Steam's 76 without the five high-resolution texture archives (uhdmip, uhdmip_DLC1 - uhdmip_DLC4, 17.3 GB together). The other 71 have the same sizes as Steam's, and those compared byte for byte (Patch_DLC3, 3,437,374,050 bytes, and the config list) are identical.
  • The Store ships 66: Steam's without those five, Blade, Lithlad, Patch_04, Patch_04_LC and Presentations_ptbr (the package declares no Brazilian Portuguese). Of the 66, 37 have Steam's sizes. The other 29 (Patch_03 and Patch_05 - Patch_13, Patch_DLC1 - Patch_DLC5, each with its _LC twin except Patch_12_LC) carry the updates in another split: Steam's Patch_09 is 5,545,787,101 bytes and the Store's 546,573,005; Steam's Patch_12 is an empty archive and the Store's holds 311,972,138 bytes, while the Store's Patch_08 is the empty one.
  • The config list is written for both layouts: each high-resolution archive is listed twice, as ..\uhdmip.Arch06 and as uhdmip.Arch06, under the list's own comment "'../' needed for steam, flat needed for UWP". Steam and GOG keep it beside the executable in x64\, the Store in UWP64\. How the list is read and searched is in Archives and file formats.
  • Texture tiers. Without the uhdmip archives, GOG and the Store lack the 8,752 .texuhd files (the highest texture tier) those archives hold, of 10,297 in the Steam build; a texture whose .texuhd shipped there is drawn at most from its .tex0 (see Archives and file formats).

How the builds correspond

Code

GOG is the same code at other addresses. Of 839 functions compared instruction by instruction with addresses and branch targets masked, 833 have the same instructions as their Steam counterparts; the other six were confirmed by reading them or by the order in which they register with the engine. An alignment of the two images by function bytes, propagated through call sites and vtables, pairs about 160,000 functions and 76,000 data addresses. The compiler's inlining differs in places: the quest-slot check 0x596FF0 is folded into its only caller, and the identity-scale look rebuild 0x1BC3AA8 has no standalone copy, only its callees.

The Store build is a separate compile of the same source for the Universal Windows Platform, linked ten minutes after Steam's. Stack frames differ (the dead-body cull's locals at [rsp+0x20] and [rbp+0x67] on Steam sit at [rsp+0x30] and [rsp+0x38] on the Store), so many bodies do not match byte for byte. The same alignment pairs about 84,000 functions and 26,000 data addresses; the rest is matched by structure: strings, call-graph position, constants and the field offsets a function uses.

Registration tables pair exactly. Tables the engine fills at start-up keep their order and ids. The 110 attack-predicate registrations have the same kinds and flags in the same order on Steam and GOG, and the 40 animation codec evaluators of the three codec registration tables pair one to one on GOG and the Store, by the FourCC each registration carries as an immediate (see Animation).

Object layouts

Object layouts agree wherever they were compared. Read in running games with the Steam build's field offsets, the captain records (FactionMember) and characters read correctly on 542 of 542 captains in 9 of 9 pools and 17 of 17 spawned characters on GOG, and on 543 of 543 captains and 65 of 65 spawned characters on the Store.

State that does not depend on where the player stands agrees too:

  • Static world objects. Objects placed by the region's data have the same count per class in the same place. On the same save in the same region, all eight AI-node classes have equal counts on GOG and the Store, among them 153 ranged-attack nodes, 1,292 route nodes, 5,443 menace places, 753 flee nodes and 114 gather nodes.
  • GameDB category databases are allocated at start-up in a fixed order, so the distance between two of their heap pointers is the same in every build: 0xE18 between the databases in [base+0x2701708] and [base+0x2701D10] on Steam, GOG and the Store.

Some pools allocated at start-up are larger on the Store: the inventory item's second base class (vt_0x1FDABD0 on Steam) has 10,223 objects on Steam and GOG and 14,809 on the Store, with the constructors confirming the class.

Globals

Globals keep their order within a run of one object file's data, so neighbors keep their distances: the client shell's slot is 0x10 below the GameManager's and the main scene's 0x08 above it in all three builds. Across the image the shift changes from run to run, and no single offset converts addresses. One block of flags is laid out differently: the engine switch bytes 0x2A34D67, 0x2A34D6B, 0x2A34D6C, 0x2A34D72 and 0x2A34D8E are packed into one block on Steam and on the Store (one shift, +0x66AA9B, confirmed by code for three of the five) but are five separate 8-byte-aligned globals on GOG, each with its own shift.

Each function pair rests on matching code: the GOG functions' bytes with addresses masked, the Store functions' instructions, strings, call-graph position or registration order. Slots and vtables pair through the paired functions that address them, and the slots were read in running copies of each build: the captain layout reads above go through the GameManager slot, and on GOG the main scene's slot holds an object whose vtable pairs with Steam's MainScene vtable.

Methods that pair addresses

When bytes do not settle a pair, these readers do, each independent of the others:

  • A data cell by the code that addresses it. Steam's RIP-relative instructions for a cell, with displacements and branch targets masked, occur once in the other image; the cell that instruction addresses is the twin. On GOG this confirmed 286 of 327 data pairs with no conflict.
  • A vtable by its slots, when its methods are already paired, and by live object counts for classes whose objects come from region data (above). Slot shapes alone cannot tell apart subclasses that share a base class's slots.
  • A class through its descriptor: the class-name string, the create function that references it, the constructor it calls, and the vtable that constructor stores at [this].
  • A factory by its allocation size, and a function by the one caller both images share.
  • An import thunk is never a function's twin. Where Steam calls an initializer, the Store build calls memset at the same position (the initializer itself, Steam's 0x596E84, exists in the Store build instruction for instruction at 0x34644D0), so a pairing by call position alone names the memset import thunk.

The platform layer

Steam

SteamAPI_Init is the first call of the game's initialization 0x11798AC, and the storage interface comes from the SteamClient017 interface's slot 17 (0x1179068). The save reader 0x119A2C8 reads through Steam's remote storage when the platform object's cloud check (its slot 221) passes: it asks ISteamRemoteStorage::GetFileSize (slot 15, through 0x11A6FB8), allocates that many bytes and calls FileRead for exactly that count (slot 1, through 0x11A6FEC); only a read that returns a different count falls back to the local file. It then decrypts as many bytes as the file's own header names, whatever the read returned. Saves are written with FileWrite (slot 0, through 0x52C348).

GOG

The GOG build has no store account: it names its save after the computer (the executable imports GetComputerNameW) and keys it with the account value 0, where the Steam build uses the Steam account number.

Microsoft Store

Addresses and offsets in this section are the Store build's own.

  • The app container. The game process runs with an app-container token at low integrity, inside a job object. It can read its own package and the package's per-user data folders, among them %LOCALAPPDATA%\Packages\WarnerBros.Interactive.WB-Kraken_ktmk1xygcecda\LocalState. Other folders of the Windows profile, such as Downloads, deny it access. It may start child processes.
  • Xbox Live. The Store build signs the player in through the Xbox Live services library. The local profile is reached from the client shell's user list (+0xEB8, current index +0xED0) and has the Store vtable 0x2C411C0. It holds the sign-in wrapper at +0x168, whose [+0x30] is the services library's user; that user's implementation, at [+0x10], holds the Xbox user id (+0x18), the gamertag (+0x38) and the web account id (+0x98) as wide strings.
  • The storage request. After the sign-in completes, the profile asks for save storage through 0xF60720 (also reached from its vtable slot 2). Before the request proper, at 0xF60B15, it calls StoreConfiguration.IsStoreWebAccountId with the web account id and never uses the result. When that call throws (inside the game it fails with E_POINTER, and every measured start ended this way), the catch handlers at 0xF60E9C and 0xF60EC9 mark the request finished before the code that copies the Xbox user id (0xF60B27) and the storage request itself (0xF60B6D) have run, and nothing asks again. The profile then has no storage provider: the game neither loads a save nor keeps one in that run.

The profile's request state, Store offsets:

Offset Meaning

Storage handed to the profile after the request has failed is not taken as a save to load: the game is by then set up for a run without one, and its next save writes an empty profile into that storage.

Saves on each build

The three builds write the same format: a SOM3 container around a SAVE version 2 file holding the profile sections and the three slots (see Saves, the store and the network layer). What differs is where the file lives, which account value enters its key, and the storage the game reads through.

Beside the main file, Steam and GOG keep five numbered copies, <name>_1_ShadowOfWar.sav to <name>_5_ShadowOfWar.sav: _1 matches the main file and each higher number holds an older save. Steam's and GOG's saves share the local folder, and neither build reads the other's.

The build number. Each build writes its build number at +0x14 of the decrypted file: 0x22AA (8874) on Steam and the Store, 0x98D (2445) on GOG. The GOG executable has 0x98D at the same three mov r8d sites and one cmp where Steam's has 0x22AA. The profile loader 0x17C6500 reads the value into a local and never compares it, so a save written by one build loads in another once it is encrypted with that build's account value (and, for the Store, its key constants). A profile that fails to load is not kept: any load status but 1 sends the loader to the new-profile reset 0x17C4D6C, which starts the introduction, and the game then saves that empty profile over the old file.

Open questions

  • Whether every path resolves to the same bytes on the Store as on Steam, given its different patch split. Where compared, it does: one animation file's 523 patched sites hold the same bytes in both.
  • Whether the GOG build calls the four Steamworks functions it imports, and what it does when they answer nothing.
  • Which code reads or writes the GOG image's 8-byte .SHARED section.
  • Whether StoreConfiguration.IsStoreWebAccountId throws on every Windows installation or only on some; a start where it succeeds would show whether the Store build then keeps its saves.
  • Why the Store build's start-up pools are larger (14,809 inventory item objects against 10,223): a different pool configuration compiled in, or a different allocation path.
