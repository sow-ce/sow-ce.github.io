Inventory, Affixes & Gear Stats (DECODED 2026-10-03, live + static + save)

Full reference: aire/documents/INVENTORY_SYSTEM_DECODE.md; read-only actions in aire/pipeline/inventory.py. A weapon has no stats of its own - Inventory/WeaponData holds sheath/FX/predicate only. Every number is an AFFIX.

  • Value law (10/10 live): affix value = FloatIndex.IndexedValues[ItemLevel - 1] of the affix's VariableMin table (Int_LevelValue is the ITEM's level). Sword "Melee Attack" = affix 1Sword_Base_Prop_<rarity|5Lgnd_Set> -> Float_DmgMod_M_FLAT (L80: Common 160, Epic 166, Legendary 169). The player's Float_DmgBase_M_BASE is 0: the sword's roll is the whole flat input to DmgForm_Plyr_Melee.
  • Chain: vc = [[base+0x2797808]+0x2348] (VisualComponent, vt 0x1FD63F0); inventory embedded at vc+0x3D8 (373/373 VCs); 25 slot vectors at vc+0x4D0 + i*0x18 (0 Melee, 1 MeleeAux, 2 Ranged, 3 RangedAux, 6 Utility, 7 Tribe, 9 MeleeOffHand = Combat/Predicates/InventorySlot; 11 cloak, 12 armor, 22 ring by contents).
  • Item instance (vt 0x1FDABF8): +0x20 u32 id, +0x24 u32 level, +0x38 Items record, +0x40 EWD, +0x60 socket objects, +0x78 affix instances {+0 Affix/Definition, +8 f32 value, +0xC f32 ModifyOtherAffix bonus}, +0xA8 u8 new, +0xA9 u8 equipped (+ node +0x08 linked), +0xB0 nemesis origin, +0xB8 upgrade challenge (vt 0x1DC0F70; +0x78 u32 progress / u32 target = the card's "5 / 10"; the card's LOCKED line is the gear's NemesisAffix, not in the affix vector), +0xC8 GUID. Slot index 0 is NOT the equipped item. Ability list = owned-byte vector (+0x88 cap, +0x8C owned): the item dtor (0x1C7DB4 -> 0x114D828) frees ability OBJECTS always, the BUFFER only when owned - an external tool may grow the list in its own memory (owned 0) but must reuse engine-allocated objects.
  • Equip = deltas: 0x40136C(rcx=item, dl=apply, r8=owner combat obj) -> per affix 0xFE68F0 -> 0x1A105D8(store, var, +/-(value+bonus)). Unequip subtracts the CURRENT float, so never write affix+8 on an equipped item without remove/apply around it - the engine's own upgrade (sub_FBAAC0 @ 0xFBB2EC: strip, level = min([owner+0x568]+1, 80), recompute) is the template.
  • Player stats: [[[player+0x26A8]+0x318]+0x60] + recordIndex*0x50 = {var record, +8 f32 value}; 622 entries = Combat/Stat/Variable/Float; lookup 0x1E53B8.
  • Save keeps identity, not numbers: id, level, item/EWD/affix hashes, GUID, nemesis origin; float 157.0/169.0 occur 0 times in the decrypted save. Level, affix list and item record persist; an affix+8 edit does not.
  • Gems: GemData.SocketAffixes = one affix per socket type (Red sword = Float_DmgMod_M_PCT 0.10-0.30, Green lifesteal 0.04-0.20, White Mirian 0.05-0.15, Blade crit dmg 0.20-1.00). Sockets are per SLOT (6 live objects, vt 0x1FDAED0): [vc+0x3D8+0x80] = {entries, 8}, entry {GemSocketType, socket}; socket {+0x18 gem, +0x20 type, +0x28 affix vector}. Ctor 0x1BFB8AC(mem, type, gem), SocketGem 0x1BFBCB8, apply 0x1BFBC50(sock, 0/1, owner, GemItemLevel) loops the vector. Item +0x60 sockets are a dormant per-item path (0 ship). Owned counts: vc+0x740/+0x748* records {+0 item, +0x20 u32 count} (engine count 0x509074, consume 0x4F163C(vc, item, n), give 0x1BCE0C0(vc, item)). vc+0x3D8+0xF0 is an append-only CHANGE LOG (+0x24 count after, +0x28 amount) - not the counts.
  • Stacked gems (RUN 2026-10-03): gem_stack_add builds extra slot sockets with the engine's ctor + apply and pays real gems: 2x Red Wondrous on the sword = Float_DmgMod_M_PCT +0.60, owned 20 -> 18 (Gems screen x18 IN-GAME CONFIRMED; damage IN-GAME CONFIRMED 2026-10-03, user: "two shot caragors now"). Live only (no container holds them); gem_stack_reapply after a load, gem_stack_clear returns the gems. C++ port (2026-10-03, cl /Zs clean, NOT YET RUN IN GAME): Talion > Gear tab (ui/tabs/sow_gear_gems.hpp) over sdk/sow_gem_stack.hpp; native ops gemstack / gemunstack in sdk/sow_main_native.cpp (identity-checked, SEH, refund on any failure after paying). Journal config\gem_stack.txt (campaign = glaive item GUID, proof = count after paying); liveness by a CANARY in Float_DmgPCT_DmgTroopsVsPoisoned (0 GADB refs), never by addresses - the stat table can be re-initialised in place. dev=1 unlocks free sockets.

Skill rows and the Skills screen (IN-GAME CONFIRMED 2026-10-13)

A skill row = Inventory/ActiveItemGroup record (89 live): Entries[] -> _StructuresInventoryActiveItemGroupEntry {RequiredItem = the variant's UNLOCK item (held = bought), ActiveItem[] = the *_SKILL / *_DUMMY item whose possession makes it active}. An unlock item finds its row through Inventory/Items.ActiveItemGroup (P919 0x234F317E). These four fields have exactly TWO readers in the binary (field bindings + callers, 2026-10-13): - Skills-screen active test 0x1BCD6DC(inv, unlock): unlock held -> unlock.ActiveItemGroup -> first entry with RequiredItem == unlock -> its ActiveItem[0] held (the loop re-reads element 0 only). inv = [UIManager+0xB0] = the player's VisualComponent (live). Node state 0x18A1770: 3 active (drawn white) / 2 owned / 1 available / 0 locked; the FX pickers 0x19453D0 (SkillChild vt 0x1F8DE98 slot 21) and 0x19480D4 ask the same test. - Click swap 0x1BC8C94(vc, unlock) (wrapper 0x1BC8C6C(vc, Skills record)): unlock held -> entries with another RequiredItem have their ActiveItems removed (count 0x509074, consume 0x4F163C, event GM+0x6D18 type 8), entries with this RequiredItem have theirs given when not held (0x1C01E0, event 7). Other callers of the wrapper: ItemLoadouts apply 0x1BCC1C4 (from inventory re-init 0x4F0938), 0x17D9E4C, 0x1B56FA4. - Held test 0x24DF7C(vc, item): bit recordIndex(item) (0x1898E8) of the held BITSET [vc+0x490] {u32* begin, end} (0x24EB74); without one, a walk of the stacks vc+0x740/+0x748 (0x36A17C). 102 callers: faking a bit fakes possession for combat, quests and the swap alike.

Showing a choice without changing it (sdk/sow_skill_variants.hpp, All Skill Variants Active): while the top menu layer [UIManager+0xF0] is Interface/Menu/MenuLayer/Upgrades::UpgradesLayer (= MenuManager.UpgradesLayer, hash 0x8B0D31A2; MenuManager = [[UIManager+0x50]+0x518]), each bought-but-unselected unlock's ActiveItemGroup cell names a PRIVATE row: an arena copy of its row whose every Entries cell names an arena copy of its entry whose every ActiveItem cell names the unlock itself (shipped descriptor runs kept, only instances copied). The test answers active; the swap finds no other entry and gives nothing (unlock held) = a click is a no-op, so the saved selection cannot move. Restored the frame the screen leaves the top (the swap's other callers never run with it open), before the save clean-up's swap, and on a GameDB rebuild (guarded: the cell must still name our arena row). Emulated first against the live game (emulate_live with the private rows mapped into emulator memory only): 4/4 rows test 0 -> 1, swap with no inventory call. In game: 127 bought, 37 drawn selected before, 90/90 after. The earlier relink of the Owned FX looks to the Active ones changed nothing: the FX are not the white tint, the node state is. Any "show X as owned/selected" UI request: find the state function, list the readers of every field it reads, and redirect the field whose other readers can be kept away from the change.

Which move a button press runs (MEASURED 2026-10-13, code + live tree). Node runner 0x30FD80 (called by the combat tick 0x162560): the current node's Links first, then the ROOT list Combat/Tree.Nodes of the tree at comp+0xEF0 (Player_Character_DarkTalion live) IN ORDER - each root resolved to its KBMNode (0x310C00), validated (0x310C5C: node type, cancel condition, transition type; 0x310F10: the input), then PickAttack 0x275730; the FIRST root that yields an attack wins. Priority ([attack cache entry+0xC]) only ranks attacks INSIDE one node. State nodes (0x2C2288, Tree.StateNodes) are first-match too. So a skill variant whose moves sit in their own root node earlier in the tree hides every later node on the same input once both are allowed. Weapon Record System (PROVEN, Broom Mod)

Record Tags:

  • 0x0A4B = Inventory/Items (weapon item records)
  • 0x0A1B = Inventory/EquippedWeaponData (EWD records)
  • 0x0A08 = Model/SimpleModelPieces
  • 0x0A0C = Inventory/ArmorData (AD overlays)
  • 0x0A07 = Model/SimpleModelHeads

Weapon Slots (via Inventory pointer at FM+0x050, CONFIRMED 2026-04-24: 72.5% INV fill, 100% weapon when INV present):

  • INV+0x38 = Primary melee weapon item (tag 0x0A4B) — 58/58 confirmed
  • INV+0x40 = Primary melee weapon EWD (tag 0x0A1B) — 58/58 confirmed

FM Internal Weapon Records (deep offsets, per-orc variable):

  • FM+0x0CA8/0x0CB0 = Primary melee (Item + EWD) — ALIASES INV+0x38/0x40
  • FM+0x10A0/0x10A8 = Ranged/throwing weapon (Item + EWD)
  • These deep offsets are in the trait object area and may shift between orcs

Pool Walking Technique: Records in the same category are packed in 0x28-stride pools. Use any valid record as anchor → walk backward to pool start → walk forward checking names. live_record_map.json addresses are session-specific (ASLR). Always validate tag before use.

Broom Weapon Records:

  • Broom (Inventory/Items, tag 0x0A4B) — item definition
  • Orc_Misc_Broom (Inventory/EquippedWeaponData, tag 0x0A1B) — equipped data
  • Wep_Orc_Misc_Broom (Model) — 3D mesh
  • IB_Broom (Inventory/ItemBuilder) — build template
  • Animations: Prisoner_Broom_Entry/Loop/Exit, AI_Prisoner_Broom_Loop/Entry/Fidget

Gear Effect System — AoE on every sword hit (IN-GAME PROVEN 2026-08-15)

Legendary gear effects ("Enemies explode", "Resurrect on melee kill") are pure RecordLink wiring. The affix is a wrapper carrying no behaviour:

Inventory/Affix/Definition  (2,961)
  .Buff        -> Combat/Buffs (1,126)                    a HELD effect
  .Proc        -> Combat/Buffs/Procs/Definitions (223)    an ON-EVENT effect
  .Chance      -> Combat/Buffs/ChanceTypes (78)           bare tag, fc=0 = the KEY
  .ChanceValue -> Combat/Stat/Variable/FloatIndex         "1" = 100%

Combat/Buffs/Procs/Definitions   slot 3 ResourceGain  slot 4 TargetBuff
                                 slot 5 chanceKey     slot 6 Buff  slot 8 Predicate
  Predicate  -> Quest/AutoObjectives      the engine reuses its QUEST event vocabulary
  TargetBuff -> Combat/Buffs
                 .OneTimeAOE / .LoopingAOE / .OneTimeAOE_Player / .DeathAOE
                   -> Combat/AOE -> .Tick -> Combat/AOE/Tick
                        Radius / Angle / MaxAIToHit / Attack / AOEFX

affix.Proc IS LIVE-EDITABLE. affix.Buff IS NOT. Proved by one experiment with both wired at once: freeze (via Proc) fired, resurrect (via Buff -> Buff.Procs -> ProcDef) did not. A held Buff is aggregated onto the player at EQUIP time. Slot 5 empty = the proc fires unconditionally; a populated chance key needs an affix registering it.

Working recipe — _Base_Prop_ affixes are always-on (_SetProp_ wants set pieces) and ship Buff/Proc/Chance/ChanceValue NULL but DECLARED: 1Sword_Base_Prop_5Lgnd_Ringwraith.Proc = ProcDef_TargetExplode_HeadshotKill (Predicate = PlayerHit_Sword, TargetBuff = AoEFreeze | PC_CurseAoE_OnHoGKill | Buff_5LgndMachine_ExplodeOnDeath). Predicates: PlayerHit_Sword/PlayerHit_Melee (unconditioned hit), PlayerKill_AnyKill (2 non-null cells, ZERO attack categories — an AoE kill counts). PlayerKill_AllMeleeKills carries FIVE attack categories and only matches a MELEE-attributed kill, which a big AoE steals.

TICKDELAY > TIMER = THE AoE CAN NEVER TICK. Silent, no error. Killed three effects before it was found: PLBoG_OnFire_FlameAoE (2.0/1), AOE_MoraleBombSmall (2.0/1), RingwraithGear_ResurrectGrunt (3.0/1). Working shapes are 0.0/1 and 0.5/1. MaxAIToHit on the tick caps victims (-1 = uncapped; the resurrect ships 1, which is why it looked "hit or miss"). Radius envelope over all 752 tick records: min 0, median 550, max 1,000,000; 20,000 is the shipped "whole arena" value. Combat/AOE.Alignment decides who is damaged — *_DamageAll includes your own followers.

Live GADB instance writes are reverted by a LOADING SCREEN (the engine re-deserialises on load). Control: a written cell polled uncached for 45 s in free roam showed zero drift, so nothing restores them continuously. Make apply scripts idempotent and re-apply after travel. Not every load (CORRECTED 2026-10-03): the Mercenary Camp's 15 cells survived two region-change fast travels with 0 re-arms - which loads re-deserialise is not yet measured, so keep re-arming on detection, not by schedule.

The post-data route is INERT for gear-driven AoE — do not re-attempt. _StructuresCombatAttackPostData.AOEOnHit + AOEOnHitChance is what the Machine set's 57 vanilla glaive entries use, but writing the same pair into all 463 Talion sword attacks (926 cells, 100% verified written) produced nothing.
