Combat: attacks, targeting, predicates and resources

How combat is decided and executed: combat objects; the compiled attack cache and its 105 predicate evaluators; targeting and the three copies of a lock range; the player's input tree and aerial moves; ranged shots; cooldowns, Might and ammunition; health and damage (the apply path, the pushed health bar, the evaluator's floor, the hit dispatcher and its friendly-fire gate, damage formulas and their cache); weapon elements, procs and slow motion; weapon-buff effects; capture points; the fight circle that decides who attacks; combat actions and states; area attacks; the player's execution companions; struggles and hit categories.

Every combatant carries a combat object, and every attack is a record whose compiled predicates decide when it may run. This chapter follows an attack from those records through targeting, input and damage, then covers resources, weapon elements and slow motion, capture points, the fight circle, combat states and actions, area attacks, the player's execution companions, struggles and hit categories.

Combat objects

CCharacter+0x2410 (mirror +0x2EF0) is the character's Character/Alignments record (one of 52, among them Player, PlayerFollower, BuddyFollower, Orc_FactionA, Troll_Cave and Warg_Brown), and +0x23B8 is its follower byte. Dead characters leave the spawn manager's array, so its count is a count of the living. Destructible props (for example Env_Destroy_FirePit) are combat objects too and can be targeted.

The player's combat component is [player+0x2FA0] (comp+0x08 = the player). It holds FreeAim at +0x668, the targeter container at +0x5C0, the companion manager at +0xC68, the active attack record at +0xF00 and a list of hostile types at +0xEF0.

Attacks and their compiled cache

Combat/Attack has 16,976 records. An attack names its AnimationData (clip, playback rate as an enum pair read at attack start, sync, overrides), AttackData (target selector, area attack, teleport, translation scaling, item slot to draw, ranged overrides) and AttackPostData.

The targeting cache [GM+0x6CD8] is compiled at world start:

Offset Content
+0x08 / +0x10 the Combat/Attack entries (16,976 x 0x58 bytes, in database order)
+0x8058 the Combat/Target entries (0x1B8 each, built by 0x1B69838)
+0x8088 the compiled Combat/Pool entries (0x48 per pool record index)

An attack entry holds +0x00 the Combat/Attack record, +0x18 the damage formula and +0x40 .. +0x48 the compiled predicate pairs {evaluator, record} (0x10 each). The damage formula is a plain pointer to a Combat/Stat/Formula/Damage record (DmgForm_All_Instakill in 1,681 entries, DmgForm_ZERO in 1,563, DmgForm_AI_Melee in 809); it is null in the 8,879 attacks that ship no formula. A change to a predicate record's value is seen at the next test; linking an attack to a different predicate record takes effect only when the compiled pair changes too.

A compiled pool entry ([[GM+0x6CD8]+0x8088] + recordIndex * 0x48, data at +0x08) holds at +0x00 an attack-type restriction and its vector (0x3FC280), and at +0x20 a combat-state restriction and its vector (0x3FC254, tested against the current state [[0x2F5288(component)]+0x2F0]+0x58). They are compiled at load from the pool's original attacks.

Targeting

A lock range exists in three copies, and only the third gates acquisition:

  1. the GameDB value Combat/Target.WeightData.DistanceRange (a pair in the shared float pool);
  2. the compiled Combat/Target entry in the targeting cache (compiler 0x1C0B634), which holds +0x0C the maximum range, +0x14 the maximum range without input, +0x168 the maximum angle, +0x20 / +0x24 the screen width and height, and compiled boolean pairs {present, value} from +0x194. +0x190 holds MaxDistance_PlayerAlly x 100 (the field is authored in meters), and the byte +0x1B5 enables it; +0x195 is RequireLOS, +0x1A0 the outside-screen test (off for every player selector) and +0x1B0 / +0x1B1 RequireStraightPath;
  3. the player's live targeters: the container at comp+0x5C0 keeps a pool at +0x18 / +0x20 of 0x80-byte targeters (vt_0x1DB1040; +0x28 the current target, +0x30 the Combat/Target record, +0x38 the range; 114 in the player's pool) and lists at +0x48 / +0x50 (0x20-byte {key, begin, end, capacity}, 192 lists keyed by candidate character type). Every list is sorted by range, longest first, and acquisition (0x18D06C) returns at the first targeter whose range is below the candidate's distance. Keeping a target (0x18CDD4) checks +0x38 too. Membership in a list is the type filter.

The candidate filter 0x18626C has 38 logged rejection reasons ([COMBAT|TARGET]). A follower is rejected (0x366B88) when the ally byte is set and its distance exceeds the ally maximum. The scorer is 0x30B2D4. RequireStraightPath rejects any target without a straight walkable path (sword selectors set it, the bow does not), which excludes enemies below a rooftop. The compiled ally byte is set exactly when the authored maximum is above zero, so the data cannot express "reject allies at any distance".

The player's input tree

Combat/Node = {Type, Predicate -> a primary {Input, Chord}, Pools[] -> Combat/Pool.Attacks[], Links[], RequiredTransitionType, KBMNode}. 0x310C00(node, isGamepad) returns the node's keyboard and mouse variant (KBMNode, field 16; node slot array at 0x2650EE0), and its six callers resolve every node of a list through it. The player's tree (Combat/Tree::Player_Character) has 146 roots (192 PC_* nodes in all).

  • Input records. The ActionID cell is the action id itself (Light 0xA247C387, Heavy ...388, Stun ...389, Dash ...38A; keyboard-only actions 0xE8C05C0x). InputType is 0 for press, 1 release, 2 held and 3 held for the previous node. GameChanger_WraithDash_HeldPrev (Light + mode 3) is a shipped hold-to-chain.
  • Holds. MinHeldDuration (0x6FEF14) passes on a released button only when the release time equals the current time, which never happens in practice. Every shipped hold therefore uses InputType 2 plus MinHeldDuration (for example Tackle_Attempt, Riding_KillMount). An input entry is {u32 press, u32 release, u16 action} (0x19B488).
  • The input-driven node runner 0x30FD80 is reached only from the player tick (0x162560 <- 0x43B8F4); AI combat has no virtual controller. It picks an attack with PickAttack 0x275730, which runs PoolCheck 0x3FBA8C on each of the node's pools. The pool's predicate (_StructuresCombatPoolPredicate) can require an item, typically a skill item, tested by 0x276E1C(inventory, list); a pool that fails is rejected before any attack predicate runs, and a null item skips the test. The pool rejection log 0x19C83AC is an empty ret in the shipped build.
  • AI attacks carry no target selector (AttackData.Target is null): an AI's target comes from its perception and threat picker.

Synchronized attacks. Combat/Sync.InitialAlignment decides who moves: 0 moves the attacker to the victim (EnableAlignment), and 1 with TeleportDuringInterpolation moves the victim to the attacker. Any synchronized kill therefore closes the distance itself. AttackData.Teleport -> Combat/AttackTeleport (11 records) teleports at attack start without a sync. AttackData.AOE -> Combat/AOE spawns an area attack (1,840 attacks set it). AttackData.AOEOnStart fires it at the start; otherwise only a clip event (such as PL_WraithAOE) fires it. The Shadow Strike kills already sever the head (SeverActionTarget Head, SeverTargetOnKill). A swapped animation changes what plays; the attack record keeps what it applies (its categories and actions).

Aerial combat is ordinary data. The fell beast's death-from-above moves are combat nodes and pools like any other (AI_FellBeast_DFA_Shallow_*, _Steep_* and _Troll_*, each with Into, Attack and Out). The player's gliding is a set of input predicates (for example Combat/Predicates/Input::DLC4_Gliding_Start, _Exit, _DFA and _Ranged) and behavior-state lists (PC_Gliding, DLC4_Gliding, DLC4_GlidingRanged, Aerial_Ranged, AerialRanged_Active), and aerial archery's animations are the player graph's PL_AerialRanged_* nodes. The aerial bow mode PC_Ranged_Sniper_Aerial is chosen only while the player's behavior states include falling, jumping, wall-jumping or gliding (see Characters, the player and the camera, for the ground predicate every ground shot carries).

Ranged attacks

The attack's target comes from 0x76A890(component, attack) in two lanes. When the attack's selector equals FreeAim's +0x88 (the draw mode's TargetOverride), the target is FreeAim's ray-cast targeter [fa+0xB0], which is what the reticle is on; otherwise it is the selector's live targeter in comp+0x5C0, the lock. A targeted projectile never ray-casts: the shot (0x4CDE54 -> 0x2E8994 -> 0xFC15A0) and the projectile update (0x116E64 -> 0x11734B) find the target alive (0x1A4F2F0) and apply the hit at its node (0x4EBED0), so walls do not stop a locked arrow.

The reticle color is FreeAim's state byte fa+0x4CA, set by 0x1A0EE8 from the target in FreeAim's weak handle (fa+0x30): 0 hidden, 1 nothing, 2 neutral, 3 hostile, 4 ally and 5 a world point. 0x114C588 passes it to the HUD crosshair. Each frame 0x379578 ray-casts. A character hit goes to 0xFA640 -> 0xFA788(fa, player, combat object, hit), and anything else to 0xFA788(fa, player, 0, 0), which clears FreeAim's targeter through its vf1 (0x18D298). The draw-snap aim assist (0x19F9E0 -> 0x19E73C, CP_RangedAutoTarget) does not steer the shot and expires after about 0.4 s.

Resources

Cooldowns are one latched end time. CheckCooldown 0x493320 returns [obj+0x10] - now, floored at 0. StartCooldown 0x1A78B34 evaluates MinTime and MaxTime through the stat-value evaluator 0x30F42C when the cooldown starts. It takes MinTime plus a random fraction of the difference (0x1B3C6C; MinTime alone when MaxTime is not larger), multiplies by 1000.0 (the float at 0x202E644) and stores now + milliseconds, so a duration change applies at the next use. The time source 0xF23310 reads one of four of the engine's clocks chosen by Combat/Cooldown.TimerType (obj+0x14; 0 the unscaled clock 0x2702550, 1 the world 0x2702598, 2 the real-time clock 0x2702590, 3 the player 0x2702548; see Engine core). Every combat character owns a cooldown table at [combat+0x5A0]: +0x00 slots (stride 0x20: +0x00 key, +0x08 record, +0x18 the u32 end time, +0x1C the clock id), +0x08 count (356 = the whole Combat/Cooldown category), +0x10 the category. The start path 0xF13920 indexes it by record index. Of the 356 cooldown records, 342 use a raw value, 8 a formula (the summon wheel's mounts and followers, through MountCoolDown and FollowerCoolDown) and 6 a variable.

Might is a charge meter at combat+0x338 (vt_0x1DAA9C0: owner +0x20, value +0x2D0, maximum +0x3A8 = 200, two chunks of +0x348 = 100). Wrath is the same class at combat+0x340. A hit's gain is not a Combat/ResourceGain record: IncrementHitCounter 0x2DC668 -> AddCharge 0xFFA8C takes the amount from a table compiled into the meter at +0x28 / +0x30. The player's table has 62 entries of 0x18 bytes, {Combat/Category, item list, stat value option}; the first category match wins, and the last entry is the default. Combat/ResourceGain is the other path (ApplyResourceChange 0x59CD94, used by executions and abilities). FillToMax 0x19D37B0(combat object) -> SetValue 0x44FCD0 fills the meter. Its only caller is the buff system (Combat/Buffs.FillChargeMeterOnRemoveBuff, 0x451EF0), and the path allocates from the engine heap, so it belongs on the main thread.

Ammunition is the object at combat+0x2F8 (player only). It holds the owner at +0x20, six slots of 0x90 at +0x28 for ammunition types 2-7 (slot 0 = arrows; AddResource 0x19D24F8) and, at +0x38C, the reference count of the Combat/Buffs.UnlimitedAmmo buff. A slot holds the maximum at +0x54, the stat variables Int_AmmoCount, Int_AmmoCount1..6 and HasFullAmmo at +0x60 / +0x68 / +0x70, the stored count at +0x88 and the HUD slot at +0x8C. The setter 0xEE9D40(slot, count, owner) clamps to the maximum, returns when the count equals the stored one, stores it, and updates the stat variables (0xEE9FC0), the quiver visual (0xEE9F20) and the HUD. The refills are 0xEE5BE0 (all) and 0xEE5CD0 (one type), both gated on GameModes.CanRefillAmmo, and 0xEE5CB0 (ungated). The ammunition tick 0x45144C refills every frame when the byte [base+0x2A34D6C] is set or the unlimited-ammo buff is active. That byte is the engine's own infinite-ammunition switch, written nowhere in the shipped code. Arrows are spent by Combat/ResourceGain records with a negative additive value (SniperShot_Spend, NormalShot_Spend, ShadowStrike_ToNav_Spend -1, ShadowStep_Spend -2, AllAmmo_Spend -50).

Health and damage

The damage info passed with a hit holds +0x20 the attacker's combat object (0 when there is none), +0x28 the damage and +0x30 the attack or source. ApplyDamageInternal 0x2E4BE8(combat, info) reads [[info+0x20]+0x40] (the attacker's player slot) before Faction::TriggerAmbush (0x2E4E3A) and compares it with the target's mount (0x2E4C41).

ApplyDamageInternal (163 instructions, read whole) works as follows. A dead target returns at once. A mounted target can pass the damage to the mount's combat object. ActionsOnAttackHit_Target 0xF10D50 runs, and 0x2E4E80 copies the info into the last-damage record. Then:

  • A damage of at most 1e-4 in size ([0x202E860]) takes the zero branch: the owner's vf83 and 0x2E54BC, and nothing else (no state interrupt, no HUD push, no player branch).
  • For the player only, 0x778E88([GM+0x6D18], health + damage, damage, source) records it in a 10-slot ring of recent damage at +0x938.
  • Health = min(health - damage, maximum). At 0 or below the kill 0x4A022C runs, health is set to 0 and +0x4A0 to 1, all in this one call on the main thread, with no can-die gate, so no later frame can undo it. Otherwise 0x2E54BC runs.
  • The ratio is stored and the listener called; then 0x1E51B0(combat, health, source, attacker) runs, then the AI (0x441228) or player (0xF364A0) reaction.
  • A second kill test follows for a living character whose byte char+0x23BD is set (0x11548B0).

The health bar is pushed; nothing polls health. 0x1E51B0 updates the stat variables through 0x1E52D4 (the records at [[GM+0x6CD8]+0x8360] health and +0x8368 the ratio) and the health-triggered states 0x1E5F14 (Combat/States/Auto.HealthRemainRange, Definitions.InterruptOnHit), then calls 0x1E6018(char, health). On the player (char+0x2700), that function keeps the last health and a running delta at [GM+0x6D18]+0xBE4 / +0xBEC and calls 0x188F098(health, maximum). That call takes hud = [[UIManager]+0x30]+0x48 and runs 0x4AACDC(hud, hud+0x318, health, maximum), and the LowHealth byte hud+0x1370 follows ratio <= 0.25 ([0x202E9BC]). The element's target value is at +0x1F4 and its maximum at +0x200, and the change animates after Interface/ElementSetup.HUDResourceAnimationDelay (150 ms). The call checks [UIManager+0x30] but not the object under it. NPCs get a health nav marker instead. A write of the health value alone therefore leaves the bar where it was: read live once, health 722 of 722 stood beside a ratio of 0.5523 and a bar at 398.8 of 722.

The engine's setters. AddHealth 0x37FEE0(combat, delta) refuses a dead target, clamps health + delta to [0, maximum], stores the ratio, calls the listener and pushes (0x1E51B0(combat, health, 0, 0)). Its callers include CCharacter::Heal 0x19B6584, the Health cheat 0x65ADCC (delta = maximum), SetResource 0x19D9C7C and AddResource 0x19D24F8. The maximum refresh 0x37EFCC(combat) stores a new maximum when the stat is dirty or differs from [[combat+0x5F8]+0x50], clamps health down to it and pushes, so a raw write of the maximum is undone wherever it runs. Regeneration 0x44D1CC runs at most every 100 ms, not while dead or while the current state's AllowHealthRegen is false, and reads the stored ratio.

The damage evaluator 0x3643E8 (794 instructions) applies a floor, TargetMinHealth, which is the highest of:

  • the formula's TargetMinHealthFinal plus 0x6C74D8 (an auto state's ClampHealth);
  • Player.MinHealth, the float at 0x2A418D8, for the player only;
  • PlayerFollower.MinHealth (0x2A418DC) for followers, otherwise 0x2A418E0 for other NPCs;
  • the defense record's _StructuresCombatStatValue.MinHealth;
  • the character's own floor char+0x2500 (set by CCharacter::SetMinHealthPct 0x19B7294 as pct x maximum).

The three globals sit in writable data, have one reader each and no writer, and read 0.0. The floor then works in health points: a floor above the current health makes the damage 0, and a hit that would cross it is cut to health - floor (0x364F49). With dl = 1 the evaluator returns the target's whole health as damage (0x3644BD); 0x2E3B6C, 0x6A4194 and 0x115401C pass 0. 0x6A4194 with r8b = 1 is a lethal-hit prediction (health - damage <= 0), which the floor also answers. After the floor the evaluator applies the bonus-damage (critical) scalar FormulaBonusDamageScalarOverride, the victim's current defense record ([ctx+0x58], _StructuresCombatStatValue.DamageAmount -> _StructuresCombatModifier multiply / add) and two global multipliers. PlayerCanTakeDamageFromAllies governs the player as the victim of his allies.

The same path reads developer bytes that no shipped code writes: [0x2674820] = 1 (0 makes the player take 0), [0x2A34D67] (the player's hits forced to 1,000,000, and also any attacker-less hit on a victim whose +0x2700 is 0) and [0x2A34D68] (non-player attackers do 0, and the hit continues).

The hit dispatcher 0x2EE394 (16 call sites in 15 functions, 638 instructions) handles a hit before any damage:

  • The invulnerability test ([[GM+0x6CA8]+0x30], 0x115441C: the target or its rider is the player) sits at the top and leaves with 0, so the whole hit is discarded: no attack data, CanTakeDamage, evaluator, hit state (0x2EFD44, 0x2E3AAC), hit counter (0x2DC668), ApplyBuffListOnHit, hit effect (0xEAEDD0), damage over time or threat.
  • The friendly-fire gate sits at 0x2EE58B: when 0x2EF0E4(attacker side, target char+0x23E0) returns false, the hit is dropped whole. It is false only when 0x18BC88 returns 1. The attacker side is the attack's _StructuresCombatAttackData.AlignmentOverride (...Branded when 0x1156B94 says the attacker is branded) when set, otherwise a copy of the attacker's own side.
  • After the evaluator, 0x2EE6F3 overwrites the damage with 1,000,000 ([0x202E470]) when its eighth argument is set or [0x2A34D67] is on with a player attacker. Of the 16 sites, 7 pass a literal 0, 8 a cleared register and 1 forwards; the one that can pass 1 is the melee hit test 0x2C658C (ApplyDamageRange, "Hit - Distance ... Angle"), with r10b = 1 when the attacker's +0x691 is set and its +0xA8 is the target (0x2C6A53). 0x19D9C24 (one caller, 0x2C3D68) sets +0x691 only while +0xA8 and the current attack match its arguments, and StopAttack 0x2EA790 clears it. It is a transient per-attack state of synchronized kills.
  • The hit effect 0xEAEDD0 -> 0x1CDE00 keeps the damage in the hit event (+0x38; +0x00 position, +0x0C normal) and tests only its sign: a damage above 0 fires [[GM+0x6CD8]+0x8320 / +0x8328], one below 0 fires +0x8330 / +0x8338, and 0 fires nothing.

Sides at the gate. A character's effective side is the 0x58-byte stack at char+0x23E0 (see AI, "Sides"). It holds its Character/Alignments record at +0x30 (0 = none, and the gate lets the hit through) and from +0x38 seven u32 slot ids, which are record indices in Character/Alignments. An id of N or more is skipped, not a terminator (0x18BCAD; Talion reads 0xFFFFFFFF six times, then 7). 0x18BC88(table, row, column) returns the first non-zero cell of the relation matrix over the two sides' id pairs (the row's ids outer), 2 when all are 0, and 0 when either side has no record. The values are 1 friendly, 2 neutral, 3 hostile. The matrix ships 1,802 zero cells, 278 friendly, 201 neutral and 423 hostile, and it is not symmetric. In a live game, 48 of 48 followers read Talion as 2 while Talion reads them as 1, and 7 of 7 enemies are 3 both ways. Followers' hits therefore never land on Talion, while Talion's land on followers. The sides that call Talion a friend are, as followers, PlayerFollower, PlayerFollower_Beast, BuddyFollower, BuddyFollower_Beast, WraithInfight, Branded and WraithInfight_Beast (Talion reads them as 2), and also Aligned_AllFriendly, GP_PlayerBuddyAI and Despawn_BuddyDismiss (1). The table object has 33 code readers, 15 of them through 0x18BC88.

The attacker-less hit 0xEADE70(victim, ...) has no side test. It runs CanTakeDamage (0xEAE22F), the evaluator, the force at 0xEAE431 (victim +0x2700 = 0), the apply 0x42B290 and the kill 0x4A022C. It has six callers: the damage-over-time tick 0x2E7BA4 (whose source [dot+0x48] is null or the victim), the area tick 0x2E6BFC, the melee routine 0x2C642C (when the attacker's combat object is not resolved by 0x1A6CCE0), the projectile handler 0xFC15A0, 0xF43270 and 0x1BF8B30. CCharacter::Die calls ApplyDamageInternal directly with 100,000, past every floor.

Damage formulas. Combat/Stat/Formula/Damage (353 records; 101 are the player's) is a node list. Each node (_StructuresCombatFormulaDamageNode) has an optional VariablePredicate / DamagePredicate, an Operation (Combat/Stat/Formula/FloatOperation) and ReturnImmediateIfPassPredicates, and is evaluated per hit by 0x3643E8 with both sides' stat sheets (VariableSource 0 the formula's own side, 1 the other, 0x2783D4). An operation (0x362C34) sums its ADD entries minus its SUB entries into A. It sums its MUL entries (they add up, 1.0 when there are none), divided by the summed DIV entries unless those are about 0, into M. OperationType 0 gives (value + A) x M, and 1 gives value x M + A. The largest shipped float constant is 9999 (MultiplyBy9999). Nested formulas are cached per character, without an attacker. An entry with FormulaSource 1 calls 0x363DB0(the other side's sheet, formula, 0), which returns [entry+0x14] from sheet+0x48 (0x40-byte entries by record index, count sheet+0x50) and recomputes through 0x362688 only when the entry's dirty bytes (+0x08, +0x09) are set. A missing entry gives 0.0. A record edit therefore reads back but changes nothing until its entry is recomputed. Of the player's 101 formulas, 2 clamp their output, 88 reach five shared defender sub-formulas (Equip_BonusDef_Beasts / Undead / Uruks_DefScalar, Gem_GreenRing_DefScalar, Prestige_MountDefScalar), the most shared per-hit victim predicates reach 32 (IsTarget_Monster, IsCursedTarget, IsEnraged_Target, IsPoisoned_Target), and the most shared operations are Oper_DmgAll_ZERO (68) and Oper_DmgAll_InstaKill (24). Characters carry a bool stat IsPlayerFollower.

Weapon elements, procs and slow motion

A captain's weapon element lives on the attack; the item only unlocks it. The trait Curse_Weapon gives the items CursedWeapon, Item_HasAnElementalWeaponFromTrait and Item_HasACurseTrait. The hit is the category ApplyStatusEffect_Curse_WeaponKindRequired (PredicateHasItem CursedWeapon, ApplyBuffListOnHit Curse_NoBonusKind_Weapon), which the attacks themselves list. Of the 16,976 attacks, 1,234 carry the curse category, 1,328 fire, 1,370 poison and 1,225 all three. The freeze categories sit only on the player's attacks (PC_ApplyStatusEffect_Freeze_WeaponKindRequired 509, _Dagger 170).

An orc weapon's glow is a lookup on the weapon, keyed by a tag on the buff. Buff apply walks ClientFXAttachItemSlot twice: EquipmentFXType -> 0x4F4834(vc, slot, type) (0x453658) and EquipmentFXSequence -> 0x1BCE998(vc, slot, sequence) (0x4536C9). Inventory/EquippedWeaponData holds EquipmentFX / EquipmentFXActive lists of {FXType, FXSequence} pairs (914 pairs, all on orc weapons: 0 of 1,397 player weapon records has one, so on the player's weapons a tag draws nothing). Four tags exist: Poison 304, Cursed 301, Flaming 155, Bleeding 154. Bleeding is a cut element: Combat/Buffs::SavageWeapon has no holder, and Weapon_Bloody is named only by 150 pairs. The player's blade looks come from the charged-weapon table (Combat/FX/ChargeWeaponFX: PC_WeaponBuff_Fire / _Freeze / _Poison / _Curse, PC_FireSword01, CurseSword, BL_ChargedSword) and the buffs' FX contexts.

Frozen is an animation rate. PC_Freeze_FreezingWeapon is StateFlags Quick_Stunned for 7-10 s with Combat/States/AnimRateController::Frozen taking the rate to 0.0 over 0.5-0.9 s. Nothing freezes the player.

Procs run on a captain's own buff. There are 225 Combat/Buffs/Procs/Definitions (151 with player predicates). Buff_Trait_Lifesteal.Procs -> ProcDef_AI_Lifesteal (MustBeDispatchSource 1) heals the captain on a hit. Proc predicates are Quest/AutoObjectives of type 15 (AI_HitPlayer = SourceAttackHit + target type Player_Character + SourceAttackCanIncrementHitCounter). A proc's predicate can test the victim's stats (StatPredicateTarget -> Combat/Stat/Formula/VariablePredicate), and procs carry TargetAppliedState. The 27 shipped *_Clear buffs share a Group with the buff they clear. A group is a replace rule: 0x36A35C refreshes the same buff and first removes another of its group.

A buff's flags reach its holder (apply 0x452ED8, remove 0x451EF0) by three routes: NativePredicates strings go through 0x375044([char+0x28]+0x120, name, true); BoolStatVar goes through 0x1E4874([combat+0x318], variable, true), with the entry found by 0x1E4948 in the stat table's +0x90 {entries, u32 count, category} (0x18 bytes each, {record, u8 value at +0x08}, indexed by record index; "Bad record index" when the category differs); ClientFXSequence applies on any holder, and ClientFXSequencePlayer on the player only. A buff with LimitRawMoveMag of 0 or more stores it through the NPC planner [char+0x2CE8], which on the player is a self-pointing container head, so on the player the store lands inside his own object, with no fault.

Slow motion. Every slow-motion wrapper tail-jumps to the request 0x5D08B8([base+0x2A86888], slot, record or 0, flag), and the lowest slot runs. The slots are 4 0x5BB5E0, 5 0x19CFF60, 6 scripts (System::SlowMoStart 0x626C98), 7 0x19CFD60, 8 0x19CFDE0, 9 0x19CFEE0, 10 the player's weapon modes 0x7A35D8, 11 presentation elements 0x5D09E0, 12 0x4359DC, 13 the buff clear 0x19CFCEC, 14 an attack's AISlowMo 0x7BEB48, 15 0x6EEFC4 and 16 0x19CFE60, so a weapon mode outranks a presentation. A scale is (1, N), meaning N times slower, stored as a shared float-pool pair. A buff's SlowMo field only stops a slow motion (its accessor 0x451E14 has one caller, the remove path, which clears slot 13). A buff starts one through ForcedWeaponMode (holder [char+0x560], 0x19D9B94) -> the mode's SlowMo -> a SlowMo record in slot 10 (PC_Buff_GameChanger, DLC4_SlowMo_OnBrutalStealth; 7 buffs set the field), and the slow motion ends with the buff (read on 3 of 3 such buffs, in the same 50 ms sample). Of the 332 slow-motion records, 9 leave the world alone and slow only the player: DLC4_GC_1_SM 2x for 10 s, PlayerDeath_SM 4x, Predeath_Savior_Ranged_Paused_SM 5x, Kill_Sync_Obituary_Far_SM 10x, Predeath_LoseMinigame_SM 11x, Predeath_Savior_Entrance_SM 30x, Predeath_Savior_Ranged_SM and _Release_SM 50x. Under DLC4_GC_1_SM the clocks read world 1.000 player 0.500: the player's own motion follows his clock (see Characters, the player and the camera, for why his movement record's speed multiplier does not).

The player's element buffs are Flame_Weapon, Frost_Weapon, Poison_Weapon and Curse_Weapon, in the melee slot. Flame_Weapon lasts 10 s and is a chance bonus {C_PC_ApplyFire, +1.0}; Frost_Weapon is the same on C_PC_ApplyFreeze, with no FX type or context; and Curse_Weapon adds the material state _Curse.

Weapon-buff effects

The engine's [COMBAT|WEAPONBUFFFX] system draws a buff's effect on an equipped weapon, driven by buff apply and remove through ClientFXAttachItemSlot -> Combat/Predicates/InventorySlot.Slot.

  • The store [vc+0x4A8] is a 0xA0-byte block made on first use (0x4F4964), holding EquipmentFXType[10] and then ClientFXSequence[10] by equip slot (0 sword, 1 dagger, 2 bow). Every accessor asserts slot < 10. The type setter 0x4F4834(vc, slot, type) stores it (0x115F614) and re-dresses (0x4F49C0); the type clear 0x1BC9CB0 clears only while the slot still holds that type. The sequence setter 0x1BCE998 stores it in the block and at holder+0x1A8 and redraws nothing; 0x1BC9C40 clears it. The getters (0x4F48E4, 0x4F4904) have one caller, the holder build 0x40014C. A slot's holder is [vc+0x38 + slot*0x28]: each equip entry is a 0x28-byte reference at vc+0x18 + slot*0x28 (vt_0x1DB7630; +0x20 the target, the holder, 0 for an empty slot).
  • The re-dress 0x4F49C0(holder, type) caches the type at holder+0x1B0 and returns at once when it is unchanged or the parts vector holder+0x148 is empty. Otherwise each part [[holder+0x148][i]]+0x20 gets holder+0x1A8 when set, otherwise the weapon look's own pair for the type. 0x3FE1FC(look, type, part) takes the first EquipmentFXActive pair whose FXType matches and its FXSequence[part] only while part < count, otherwise 0 (0x3FE04C does the same on EquipmentFX). A one-hand orc look's pairs therefore hold one sequence (part 0), a shipped two-weapon look holds each twice (Orc_1HB_MeatBoneClubX2: Weapon_Fire, Weapon_Fire), and a Defender's shield (part 1) never takes his spear's effect. A set sequence overrides the look's pairs, and a type change is what makes it show. The generic orc sequences in the base list are Bleeding -> Weapon_Bloody, Cursed -> Weapon_Cursed and Poison -> Weapon_Poison; in the active list they are Cursed -> Weapon_Cursed_Active, Flaming -> Weapon_Fire (Flaming lives in the active list only) and Poison -> Weapon_Poison_Active.
  • The parts own their players. 0x3FE0F0(fx, sequence) stores fx+0x1C8 and, when the part has renderables (fx+0x120), makes a player at fx+0x188 if there is none, binds it to fx+0x58 and starts the sequence (EnterFXUseTarget). Sequence 0 stops it (0x771BDC). 0x3FE2A0 does the same for fx+0x1D0 and the player fx+0x190; then 0x3FE488 runs each active player only while [fx+0x1E5] is set and [fx+0x1E4] is not (0x7B24B4).
  • The active window belongs to the animations. [fx+0x1E5] is written for every part of all 10 holders at once by 0x1BCEAE8(vc, bool) -> 0x1BDF444(holder, bool), whose one caller is the model-string dispatcher 0x4CDE54 ([COMBAT|MODELSTRING]): the clip event ENABLEWEAPONFX (hash 0x630F8E71) sets it and DISABLEWEAPONFX (0x715E0EB6) clears it.
  • Re-equip order. The holder build 0x40014C re-dresses the new holder before it copies the sequence to +0x1A8, so a re-worn item shows nothing until the next type change.
  • Of the 11 buffs with weapon effects, only FX_GondorWeapon_* set a sequence, and they name no slot. Of 1,727 Client/ClientFXSequence records, 74 are named for weapons, swords or blades. PC_WeaponBuff_Fire and StormbringerWeaponFX are played by nothing (0 holders, against 172 for Weapon_Fire), and their files ship in no container.

Capture points

A fort or outpost capture point fills as follows, according to the code and the shipped records.

  • The tick runs 0x6546E8 -> 0xF324F0 -> 0x362304(manager, node, dt) once per node. The manager holds 256 character slots (0x28 bytes: +0x00 character, +0x10 node, +0x18 rate, +0x1C side, +0x1D present, +0x1F advancing), a node list at +0x2838 .. +0x2840, the player's node at +0x2850 and his rate at +0x2858. When +0x285E is set, the tick is skipped. Rates are summed per side into two pairs, presence and advance. The player counts for presence inside the shape at [node+0x240] and for advance inside the one at [node+0x270], into which CaptureRadius is copied (0x4A62C4).
  • The node (BattleNodeCapture, vt_0x1FB9E90) holds +0x580 the AI/BattleNodeCapture record, +0x590 the full amount, +0x594 the current amount, +0x598 a cap (used when 0 or more), +0x5AC the holder (0 defense, 1 offense, 2 neutral), +0x5AD the status and +0x5BC the active flag.   • CaptureRatio is not a speed. 0x361B6C reads it every tick (default 1.5, [0x202E8F4]), and 0x362068 uses it only to decide who holds the point. From holder 0, presence[1] > ratio x presence[0] flips it to 1; holder 1 stays while presence[0] <= ratio x presence[1]; and from 2 the larger side takes it.

The fight circle

The fight circle decides which NPCs attack a target, how many at once and when.

Data. The fight circle's data spans 27 categories under Combat/FightCircle/* and _StructuresCombatCircle*:

  • Circle (15, one per target kind, among them Player, Player_Eltariel, AI_Talion, Troll, Warg, FellBeast, Balrog, Cage and Barrel) holds ArcAngle, BucketRays (8 for the player), PreDeathAttackerLock (6 s for the player) and DefaultPlaybook[].
  • PlayBook (41) -> PlaySets[] -> Plays[]. A Play has a SelectionWeight (a weighted pick; 0 = never), difficulty weights, a predicate, delays on hit / miss / counter / abort, global cooldowns and Stages[] -> StageNodes (a small state machine with next-stage links) -> Stage.
  • Stage (201) holds NumAttackersMin / NumAttackersMax (1-16), AttackType, MultiAttackerDelay and Role (distance, camera, off-screen and last-attacker weights, stat predicates). The (min, max) pairs are (1,1) 160, (1,5) 6, (1,3) 5, (8,8) 5, (5,5) 5, (2,2) 3, (1,4) 3, (4,4) 3, (16,16) 3, (1,16) 2, (1,6) 1 and (5,10) 1.
  • Other categories include Participant (59, per attacker kind, with fields such as RequireLOSToAttack, FarDistance and RunDistance), Setup (11), Rings (28 radius bands) and CirclePolicy (16).

Against the player (VS_Player_Default, 42 plays), melee is PC_BaseMelee (weight 0.1), whose stage PC_Melee_Single has one attacker. PC_DoubleMelee (two attackers) has weight 0.0, so two-orc melee plays never start. PC_BaseMeleeAndRanged and PC_BaseRange add PC_Ranged_Single (1-3 archers). The mass stages belong to the Nazgul (5 melee with a 1.2 s stagger, 5 or 4 ranged), the no-path case (PC_Ranged_Multi 2-6, PC_Melee_NoPath 5-10), goblins (6, 1-16) and the fellbeast (5). The pre-death play is PC_BasePredeath, with weight 100,000 and one attacker.

Runtime. The fight-circle manager is the AI world's +0x28 (MainScene+0x778); its +0x48 is an intrusive list of circles (the list node is the circle object, about 0x200 bytes). The tick runs the scene tick -> AI world tick 0x1F7304 -> 0x6DE538(manager) -> 0x377528 (walk the circles) -> 0x3775A4(circle, now) -> 0x377744 (only while the byte 0x267358C is set) -> 0x377830 -> 0x3778D4 / 0x4259A0 -> 0x425B60 -> 0x425C3C. That function reads the stage's NumAttackersMin and Max on every stage start, computes count = min + rand(max - min) (0x426840), clamps it to the role's candidates (0x11D89C) and assigns attackers one by one with the stage's delay. The statics are 0x2673584 = 500 ms and 0x2673588 = 100 ms (the play re-evaluation interval). A circle holds +0x38 the target's combat object, +0x1A0 the current attacker's, +0x1E4 / +0x1E8 world-clock timestamps (the 100 ms and 500 ms checks) and +0x1F4 the number of participants. An NPC joins when its target changes (0x37CA3C "Target just changed." -> 0x37CAA4 -> 0x2C1004 -> 0x2C0FCC -> 0x2C0144 -> 0x2C0280, the circle's playbook accessor 0x2C0C6C) and from planner steps. The planner's CircleTarget / CircleAlly steps are the NPCs waiting their turn (see AI).

The player's execution companions

Combat/PlayerCompanion/* defines the spectral companions that execute for the player. Setup::Player links the groups Execution_Lvl1/2/3 (Quantity 20, a combat prop with its own tree, 68 CB_* execution attacks, selector CB_Duel_Instakill), which trigger while the parent attack carries an included category, on input or at a hit-counter value. The groups are compiled when the player's model is set (build 0x1881264, called from 0x183C0B8, which sits under the player's model and skin setters). Changing the records later has no effect until then.

A compiled group (vt_0x1F7A188, stride 0x2B0) holds +0x18 the group record, +0x40 owner, +0xA0 / +0xA8 included categories, +0xB8 / +0xC0 excluded, +0xD0 companion type, +0xD8 prop, +0xF8 effect sequence, +0x104 auto-trigger hit count, +0x13D can evaluate input, +0x13E swallow input, +0x13F parent must have an active attack, +0x140 parent must reject input, +0x142 auto-pick on an enemy's counter window, +0x143 auto-trigger on the hit counter, and +0x120 / +0x128 required item / buff. The manager is [comp+0xC68], with its groups at +0x58 / +0x60.

  • At every player attack start, 0x2C3D68 -> 0x4E8B54 -> per group 0x4E9094 latches the group when the attack has an included category and no excluded one.
  • Input goes through 0x4E85D0: first a swallow pass over a separate vector (mgr+0x70, holding only Counter_FromGTD), then the player's own tree, then the normal pass 0x4E8B94 over the groups. A group must pass its gates: the swallow flag clear, can evaluate input, latched, the item-slot mask, the parent's input decision, the event id (small command ids such as 0x6B attack, 0x6C and 0x85), and its required buff and item. It then gets an instance (0x65A990: one per latch with a budget, otherwise up to Quantity), and EvalNodes 0x795E7C picks an attack (PickAttack) and a target (0x76A890 with the player's component), places the companion (0x18800FC) and starts it (0x1888918).
  • EvalNodes evaluates every attack with the player as the attacker, so attacker-side predicates (Focus, distance, direction) are measured from the player.
  • Two launches happen without input, both with mode 5 (no input match): 0x6D27D0 from the hit counter (every multiple of the group's auto count) and 0x76EE08(component, enemy combat object), raised when an enemy opens a counter window, with an explicit target.
  • The execution pools require the wraith-execution skill item (CSP_Chord_InstaK_Child1 -> PS_Execution_Child1_WraithExecution_SKILL): without it every pool is rejected before any attack predicate runs.

Struggles

A struggle is the player's input minigame inside a paired animation: the Last Chance ring before death, button mashes, holds, stick directions and aiming. Struggles run only for the player; the other participant only plays its half of the paired animation.

Who can struggle

The struggle state lives on the player's combat component ([player+0x2FA0], also the combat object's +0x50):

Offset Meaning
+0x08 the player
+0xC70 the struggle started by a paired animation
+0xC78 the struggle started by a combat state
+0xE30 the per-type count table (entries of 0x18 bytes); +0xE38 the entry count
+0xE68 the combat object
+0xF5F / +0xF60 can lose a struggle / can lose an aim struggle (CCharacter.DEMO_SetPlayerCanLoseStruggle 0x19B397C, ...Aim 0x19B3998)

The pool evaluator 0x1843E04 returns nothing unless the combat object has both +0x40 and +0x50. On the player's combat object +0x40 is the player; on 11 of 11 non-player characters sampled live both are 0. For a paired animation the engine takes the participant whose combat object has +0x40, or that participant's rider, so a mounted player struggles through the mount's paired animations.

Choosing a struggle

0x1843E04(pool, combat object, target, option out) reads the type's count, walks the pool's options in order and returns the first whose predicates pass (0x18464E4: count range or count formula, buff, the player's items, the target's items, stat predicates, the target's health range). From the passing option it takes the struggle at index min(count, n - 1) (0x18458F4), so an option's list is a difficulty ladder indexed by how many struggles of that type have already happened, and its last entry repeats.

Each count-table entry is {type record, u32 count, u32 expiry in ms, stat-variable link}. The live table holds one entry per type, in record order. Starting a struggle adds 1 (0x17B2858 -> 0xCB03A0), sets the expiry to now + ResetCooldown x 1000 on the engine's millisecond clock ([[0x2702598]+0x8]+0x18) and mirrors the count into the type's stat. Reading an expired count zeroes it (0xCAF140). Entering a state with a fail condition resets every type marked ResetCountOnDeath (0x6EF838). Success / Perfect / Fail apply ResetCountOnPerfect and ResetCountOnLose (0x74B130), and the combat action ResetStruggleCount 0xF16840 resets one type.

Starting

  • From a paired animation, a struggle starts through 0xFB268 -> 0x6EF978 -> 0x6EF9DC. From a combat state, it starts through the state change 0x2C14C8 -> 0x6EF838 -> 0x6EF908 -> 0x6F0000, which requires the state machine's +0x58 to equal the state being entered and the state's timer to be running (0x6F03CC takes the largest remaining time over the 0x20-byte timer entries at [state machine+0x00], skipping paused ones). +0x58 of the state machine is therefore the current state.
  • 0x6EF9DC orders source and target by TargetStruggle, shows the option's HUD prompt, allows Perfect only if the player owns the sync's required item, and then builds one object per input kind. The objects are QuickTime 0x18421C0 (0x170 bytes, vt_0x1F76D28), Aim 0x1842120 (0x180, vt_0x1F76C80), PressCount 0x1842198 (0x178, vt_0x1F76C28), Hold 0x1842148 (0x1B8, vt_0x1F76CF0), InputDirection 0x1842170 (0x150, vt_0x1F76D60) and Ring 0x18421E8 (0x198, vt_0x1F76CB8), all on the base constructor 0x1842490 with seven virtual slots (0 destructor, 1 update, 2 finish with a result, 4 done, 5 kind-specific start).
  • The common start 0x1845C94 stores the player, source and target handles (+0x08 / +0x30 / +0x58, pointers at +0x28 / +0x50 / +0x78), the struggle record (+0x80), the input window (+0xF0 / +0xF4), the result (+0xFC), the type's four presentation events (+0x100 to +0x118), Perfect allowed (+0x138) and can lose (+0x139). It then applies the command set, starts the camera presentation on the player's presentation component ([player+0x2FC0], 0x17A505C) and attaches the widget to the configured bone.

The input window is animation data. 0x184340C reads the events BSW and ESW (0x227C894 / 0x227C898) from both participants' paired clips (0x1847248) and keeps the earliest start and the latest end; without them the struggle ends at once. The struggle's clock (0x18431E4) is the playback time of the source's paired clip (0x1143C0), so slow motion and animation rate stretch the window with the scene.

Running and resolving

Every frame 0x162560 ticks both slots (0x6EFF54, 0x6EFF9C): update, then done, then the result 0x184531C. A Fail is reported as Success when the struggle's can-lose byte is 0 or the static byte 0x2671491 is 0 (it is 1 in the executable and live, and no code writes it).

  • After a paired animation, Fail plays StruggleLoseSync, Success StruggleWinSync and Perfect StrugglePerfectSync (falling back to the win sync). The matching audio key plays (Perfect falls back to Win), the next paired animation starts through 0x19D96B8, and then the script event CCharacter.OnCombatStruggleEnd (its P919 hash stored at 0x272911C by 0x42E6490) fires with won and perfect flags.
  • After a combat state, Success and Perfect clear the state (0x19D2834 with no state).
  • The common finish 0x1847188 plays the type's OnFail / OnSuccess / OnPerfect presentation event with the struggle's camera type.

Button mash (PressCount). The phase byte +0x16E steps through waiting, window open at BSW, counting, timed out and done. The required button (+0x168) is a weighted random pick over the struggle's input list (0x18451F4). Each right press increments +0x16D, and reaching +0x16C wins (0x1846B38). A wrong press fails when FailOnIncorrectInput is set, and passing ESW fails. Both counters are single bytes (the start stores NumPressesForWin with mov [obj+0x16C], al at 0x6B11216 and the input compares bytes at 0x1846B78), so the value is taken modulo 256: the "impossible" goblin mash with 999999 presses needs 63.

Last Chance ring (Ring). The start (0x6B12660) moves the effective end of the window earlier by Interface/Shared.LastChanceInputLagBuffer (ms, +0xF8), evaluates the three ring scales against the player's stats and converts them to alpha references: perfect +0x170 = 0.025 x (1 - 0.2 x P / 50) + 0.0075, win +0x174 = 0.85 + 0.2 x (1 - 0.5 x W / 100) and moving ring +0x178 = 0.05 + 0.45 x (1 - M / 1500). It also stores +0x184 = 1 - Lose / 100, +0x188 FailTimeStart, +0x18C failure allowed (AllowFailure and 0x2671491) and +0x138 CanGetPerfect. The update 0x1848304 opens the window at BSW and starts the struggle's slow-motion record. At the shortened end it enters the failing phase when failure is allowed, and it resolves Fail at ESW. When failure is not allowed, 0x1847B20 instead saves the source's animation rate ([combat object+0x260]+0xB0) and sets it to 0, so the paired animation, and with it the struggle clock, holds until the player presses; resolving (0x18473D8) restores it, ends the slow motion and plays the cursor effect.

  • Do the player's buffs time out on his own clock? A 5 s buff lasted 9.6 - 9.7 s under a slow motion that halved his clock.

  • What do the fight circle's +0x188 / +0x190 pointers hold?
  • How is the Last Chance press judged? The open parts are the ring's input listener (vt_0x1F76BE0 slot 1 -> 0x1846974) and where LastChanceRingForgivenessBuffer (read by 0x18434A8) enters the comparison.
  • What is the update logic of the Aim, Hold, InputDirection and QuickTime struggles?
