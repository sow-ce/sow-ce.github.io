Combat: attacks, targeting, predicates and resources

How combat is decided and executed: combat objects, the compiled attack cache and its 105 predicate evaluators, targeting and the three copies of a lock range, the player's input tree, ranged shots, cooldowns, Might and ammunition, the fight circle that decides who attacks, combat actions and states, area attacks and the player's execution companions.

Combat objects

Every combatant has a combat object (vt_0x1F995E0) at CCharacter+0x26A8 (mirrored at +0x2978):

Offset Meaning
+0x28 / +0x38 / +0x48 the owner character (AI characters have vt_0x1FB3640)
+0x50 the combat component (player only)
+0x58 the AI class record (for example AI_Easterling_Defender)
+0x60 the character type (Easterling_Defender)
+0x68 race / model
+0xA8 its own current target
+0x2F0 the combat state machine (below)
+0x2F8 the ammunition object (player only)
+0x318 the stat table
+0x338 / +0x340 the Might meter / the Wrath meter
+0x4A0 dead: CCharacter.IsDead (0x190F1C) tests this byte
+0x5A0 the cooldown table

CCharacter+0x2410 (mirror +0x2EF0) is the character's Character/Alignments record (52: Player, PlayerFollower, BuddyFollower, Orc_FactionA, Troll_Cave, Warg_Brown ...) and +0x23B8 its follower byte. Dead characters leave the spawn manager's array, so its count is a count of the living. Destructible props (for example Env_Destroy_FirePit) are combat objects too and can be targeted.

The player's combat component is [player+0x2FA0] (comp+0x08 = the player). It holds FreeAim at +0x668, the targeter container at +0x5C0, the companion manager at +0xC68, the active attack record at +0xF00 and a list of hostile types at +0xEF0.

Attacks and their compiled cache

Combat/Attack has 16,976 records. An attack names its AnimationData (clip, playback rate as an enum pair read at attack start, sync, overrides), AttackData (target selector, area attack, teleport, translation scaling, item slot to draw, ranged overrides) and AttackPostData.

The targeting cache [GM+0x6CD8] is compiled at world start:

Offset Content
+0x08 / +0x10 the Combat/Attack entries (16,976 x 0x58 bytes, in database order)
+0x8058 the Combat/Target entries (0x1B8 each, built by 0x1B69838)
+0x8088 the compiled Combat/Pool entries (0x48 per pool record index)

An attack entry: +0x00 the Combat/Attack record, +0x18 the damage formula (a plain pointer to a Combat/Stat/Formula/Damage record: DmgForm_All_Instakill 1,681 entries, DmgForm_ZERO 1,563, DmgForm_AI_Melee 809; null in 8,879 attacks that ship no formula), and +0x40 .. +0x48 the compiled predicate pairs {evaluator, record} (0x10 each). A change to a predicate record's value is seen at the next test; linking an attack to a different predicate record takes effect only when the compiled pair changes too.

A compiled pool entry ([[GM+0x6CD8]+0x8088] + recordIndex * 0x48, data at +0x08): +0x00 an attack-type restriction and its vector (0x3FC280), +0x20 a combat-state restriction and its vector (0x3FC254, tested against the current state [[0x2F5288(component)]+0x2F0]+0x58). They are compiled at load from the pool's original attacks.

Targeting

A lock range exists in three copies, and only the third gates acquisition:

  1. the GameDB value Combat/Target.WeightData.DistanceRange (a pair in the shared float pool);
  2. the compiled Combat/Target entry in the targeting cache (compiler 0x1C0B634): +0x0C maximum range, +0x14 maximum range without input, +0x168 maximum angle, +0x20 / +0x24 screen width and height, compiled boolean pairs {present, value} from +0x194; +0x190 holds MaxDistance_PlayerAlly x 100 (the field is authored in metres) and the byte +0x1B5 enables it; +0x195 RequireLOS; +0x1A0 the outside-screen test (off for every player selector); +0x1B0 / +0x1B1 RequireStraightPath;
  3. the player's live targeters: the container at comp+0x5C0 keeps a pool at +0x18 / +0x20 of 0x80-byte targeters (vt_0x1DB1040; +0x28 the current target, +0x30 the Combat/Target record, +0x38 the range; 114 in the player's pool) and lists at +0x48 / +0x50 (0x20-byte {key, begin, end, capacity}, 192 lists keyed by candidate character type). Every list is sorted by range, longest first, and acquisition (0x18D06C) returns at the first targeter whose range is below the candidate's distance; keeping a target (0x18CDD4) checks +0x38 too. Membership in a list is the type filter.

The candidate filter 0x18626C has 38 logged rejection reasons ([COMBAT|TARGET]); a follower is rejected (0x366B88) when the ally byte is set and its distance exceeds the ally maximum. The scorer is 0x30B2D4. RequireStraightPath rejects any target without a straight walkable path (sword selectors set it, the bow does not), which excludes enemies below a rooftop. The compiled ally byte is set exactly when the authored maximum is above zero, so the data cannot express "reject allies at any distance".

The player's input tree

Combat/Node = {Type, Predicate -> a primary {Input, Chord}, Pools[] -> Combat/Pool.Attacks[], Links[], RequiredTransitionType, KBMNode}. 0x310C00(node, isGamepad) returns the node's keyboard and mouse variant (KBMNode, field 16; node slot array at 0x2650EE0) and its six callers resolve every node of a list through it. The player's tree (Combat/Tree::Player_Character) has 146 roots (192 PC_* nodes in all).

  • Input records: the ActionID cell is the action id itself (Light 0xA247C387, Heavy ...388, Stun ...389, Dash ...38A; keyboard-only actions 0xE8C05C0x); InputType 0 press, 1 release, 2 held, 3 held for the previous node. GameChanger_WraithDash_HeldPrev (Light + mode 3) is a shipped hold-to-chain.
  • Holds: MinHeldDuration (0x6FEF14) passes on a released button only when the release time equals the current time, which never happens in practice; every shipped hold therefore uses InputType 2 plus MinHeldDuration (for example Tackle_Attempt, Riding_KillMount). An input entry is {u32 press, u32 release, u16 action} (0x19B488).
  • The input-driven node runner 0x30FD80 is reached only from the player tick (0x162560 <- 0x43B8F4); AI combat has no virtual controller. It picks an attack with PickAttack 0x275730, which runs PoolCheck 0x3FBA8C on each of the node's pools: the pool's predicate (_StructuresCombatPoolPredicate) can require an item - typically a skill item - tested by 0x276E1C(inventory, list), and a pool that fails is rejected before any attack predicate runs (a null item skips the test). The pool rejection log 0x19C83AC is an empty ret in the shipped build.
  • AI attacks carry no target selector (AttackData.Target is null): an AI's target comes from its perception and threat picker.

Synchronised attacks. Combat/Sync.InitialAlignment decides who moves: 0 moves the attacker to the victim (EnableAlignment), 1 with TeleportDuringInterpolation moves the victim to the attacker. Any synchronised kill therefore closes the distance itself. AttackData.Teleport -> Combat/AttackTeleport (11 records) teleports at attack start without a sync. AttackData.AOE -> Combat/AOE spawns an area attack (1,840 attacks set it); AttackData.AOEOnStart fires it at the start, otherwise only a clip event (such as PL_WraithAOE) fires it. The Shadow Strike kills already sever the head (SeverActionTarget Head, SeverTargetOnKill). A swapped animation changes what plays; the attack record keeps what it applies (its categories and actions).

Ranged attacks

The attack's target comes from 0x76A890(component, attack) in two lanes: when the attack's selector equals FreeAim's +0x88 (the draw mode's TargetOverride), FreeAim's ray-cast targeter [fa+0xB0] - what the reticle is on; otherwise the selector's live targeter in comp+0x5C0 - the lock. A targeted projectile never ray-casts: the shot (0x4CDE54 -> 0x2E8994 -> 0xFC15A0) and the projectile update (0x116E64 -> 0x11734B) find the target alive (0x1A4F2F0) and apply the hit at its node (0x4EBED0), so walls do not stop a locked arrow.

The reticle colour is FreeAim's state byte fa+0x4CA, set by 0x1A0EE8 from the target in FreeAim's weak handle (fa+0x30): 0 hidden, 1 nothing, 2 neutral, 3 hostile, 4 ally, 5 a world point; 0x114C588 passes it to the HUD crosshair. Each frame 0x379578 ray-casts: a character hit goes to 0xFA640 -> 0xFA788(fa, player, combat object, hit), anything else to 0xFA788(fa, player, 0, 0), which clears FreeAim's targeter through its vf1 (0x18D298). The draw-snap aim assist (0x19F9E0 -> 0x19E73C, CP_RangedAutoTarget) does not steer the shot and expires after about 0.4 s.

Resources

Cooldowns are one latched end time. CheckCooldown 0x493320 returns [obj+0x10] - now, floored at 0. StartCooldown 0x1A78B34 evaluates MinTime and MaxTime through the stat-value evaluator 0x30F42C when the cooldown starts, takes MinTime plus a random fraction of the difference (0x1B3C6C; MinTime alone when MaxTime is not larger), multiplies by 1000.0 (the float at 0x202E644) and stores now + milliseconds, so a duration change applies at the next use. The time source 0xF23310 reads one of four of the engine's clocks chosen by Combat/Cooldown.TimerType (obj+0x14; 0 the unscaled clock 0x2702550, 1 the world 0x2702598, 2 the real-time clock 0x2702590, 3 the player 0x2702548; see Engine core). Every combat character owns a cooldown table at [combat+0x5A0]: +0x00 slots (stride 0x20: +0x00 key, +0x08 record, +0x18 the u32 end time, +0x1C the clock id), +0x08 count (356 = the whole Combat/Cooldown category), +0x10 the category; the start path 0xF13920 indexes it by record index. Of the 356 cooldown records 342 use a raw value, 8 a formula (the summon wheel: mounts and followers, through MountCoolDown and FollowerCoolDown) and 6 a variable.

Might is a charge meter at combat+0x338 (vt_0x1DAA9C0: owner +0x20, value +0x2D0, maximum +0x3A8 = 200, two chunks of +0x348 = 100); Wrath is the same class at combat+0x340. A hit's gain is not a Combat/ResourceGain record: IncrementHitCounter 0x2DC668 -> AddCharge 0xFFA8C takes the amount from a table compiled into the meter at +0x28 / +0x30 (the player's: 62 entries of 0x18 bytes, {Combat/Category, item list, stat value option}, first category match wins, the last entry is the default). Combat/ResourceGain is the other path (ApplyResourceChange 0x59CD94, used by executions and abilities). FillToMax 0x19D37B0(combat object) -> SetValue 0x44FCD0 fills the meter; its only caller is the buff system (Combat/Buffs.FillChargeMeterOnRemoveBuff, 0x451EF0), and the path allocates from the engine heap, so it belongs on the main thread.

Ammunition is the object at combat+0x2F8 (player only): +0x20 owner, +0x28 six slots of 0x90 for ammunition types 2-7 (slot 0 = arrows; AddResource 0x19D24F8): slot +0x54 maximum, +0x60 / +0x68 / +0x70 the stat variables Int_AmmoCount, Int_AmmoCount1..6 and HasFullAmmo, +0x88 the stored count, +0x8C HUD slot; +0x38C the reference count of the Combat/Buffs.UnlimitedAmmo buff. The setter 0xEE9D40(slot, count, owner) clamps to the maximum, returns when the count equals the stored one, stores it, updates the stat variables (0xEE9FC0), the quiver visual (0xEE9F20) and the HUD. Refills: 0xEE5BE0 (all) and 0xEE5CD0 (one type), both gated on GameModes.CanRefillAmmo, and 0xEE5CB0 (ungated). The ammunition tick 0x45144C refills every frame when the byte [base+0x2A34D6C] is set or the unlimited-ammo buff is active: the engine's own infinite-ammunition switch, written nowhere in the shipped code. Arrows are spent by Combat/ResourceGain records with a negative additive value (SniperShot_Spend, NormalShot_Spend, ShadowStrike_ToNav_Spend -1, ShadowStep_Spend -2, AllAmmo_Spend -50).

The fight circle

The fight circle decides which NPCs attack a target, how many at once and when.

Data (27 categories under Combat/FightCircle/* and _StructuresCombatCircle*):

  • Circle (15, one per target kind: Player, Player_Eltariel, AI_Talion, Troll, Warg, FellBeast, Balrog, Cage, Barrel ...): ArcAngle, BucketRays (8 for the player), PreDeathAttackerLock (6 s for the player), DefaultPlaybook[].
  • PlayBook (41) -> PlaySets[] -> Plays[]. A Play has a SelectionWeight (a weighted pick; 0 = never), difficulty weights, a predicate, delays on hit / miss / counter / abort, global cooldowns and Stages[] -> StageNodes (a small state machine with next-stage links) -> Stage.
  • Stage (201): NumAttackersMin / NumAttackersMax (1-16), AttackType, MultiAttackerDelay, Role (distance, camera, off-screen and last-attacker weights, stat predicates). (min, max) pairs: (1,1) 160, (1,5) 6, (1,3) 5, (8,8) 5, (5,5) 5, (2,2) 3, (1,4) 3, (4,4) 3, (16,16) 3, (1,16) 2, (1,6) 1, (5,10) 1.
  • Participant (59, per attacker kind: RequireLOSToAttack, FarDistance, RunDistance ...), Setup (11), Rings (28 radius bands), CirclePolicy (16).

Against the player (VS_Player_Default, 42 plays): melee is PC_BaseMelee (weight 0.1) -> stage PC_Melee_Single with one attacker; PC_DoubleMelee (two attackers) has weight 0.0, so two-orc melee plays never start; PC_BaseMeleeAndRanged and PC_BaseRange add PC_Ranged_Single (1-3 archers). The mass stages belong to the Nazgul (5 melee with a 1.2 s stagger, 5 or 4 ranged), the no-path case (PC_Ranged_Multi 2-6, PC_Melee_NoPath 5-10), goblins (6, 1-16) and the fellbeast (5). Pre-death: PC_BasePredeath, weight 100,000, one attacker.

Runtime. The fight-circle manager is the AI world's +0x28 (MainScene+0x778); its +0x48 is an intrusive list of circles (the list node is the circle object, about 0x200 bytes). The tick: the scene tick -> AI world tick 0x1F7304 -> 0x6DE538(manager) -> 0x377528 (walk the circles) -> 0x3775A4(circle, now) -> 0x377744 (only while the byte 0x267358C is set) -> 0x377830 -> 0x3778D4 / 0x4259A0 -> 0x425B60 -> 0x425C3C, which reads the stage's NumAttackersMin and Max on every stage start, then count = min + rand(max - min) (0x426840), clamped to the role's candidates (0x11D89C), and assigns attackers one by one with the stage's delay. Statics: 0x2673584 = 500 ms, 0x2673588 = 100 ms (the play re-evaluation interval). A circle: +0x38 the target's combat object, +0x1A0 the current attacker's, +0x1E4 / +0x1E8 world-clock timestamps (the 100 ms and 500 ms checks), +0x1F4 the number of participants. An NPC joins when its target changes (0x37CA3C "Target just changed." -> 0x37CAA4 -> 0x2C1004 -> 0x2C0FCC -> 0x2C0144 -> 0x2C0280, the circle's playbook accessor 0x2C0C6C) and from planner steps; the planner's CircleTarget / CircleAlly steps are the NPCs waiting their turn (see AI).

Area attacks and ragdolls

Combat/AOE (627 records: Tick, Timer, TickDelay, MaxAOELength, StartNode (a bone), Alignment, UseTargetLocation, UseRayCast, RecalcStartEachTick, CanHitSource, HitOncePerSpecialAttack ...) and Combat/AOE/Tick (752 records, 56 fields: Radius, Angle, dynamic radius, MaxAIToHit (-1 = unlimited), HitAllAI, CanHitMainWorld, attack overrides ...), plus Combat/AOE/Picker (33), ProjectileTarget (5) and ProjectileSpray (2). Area ticks apply damage through tick attacks whose compiled predicates decide who may be hit.

Ragdolls (14 categories): Ragdoll has two bodies (Orc_Base, OlogHai_Base), each a brain and 19 joint constraints (38 Ragdoll/Constraints records); Ragdoll/Behaviors (18: strength and stiffness ranges and masks, sequences), Sequences (16), TargetPoses (32), ConstraintTargetPose (112), BehaviorControllers (13), float ranges, masks and audio tables: the Havok active-ragdoll tuning.

The player's execution companions

Combat/PlayerCompanion/* defines the spectral companions that execute for the player: Setup::Player -> groups Execution_Lvl1/2/3 (Quantity 20, a combat prop with its own tree, 68 CB_* execution attacks, selector CB_Duel_Instakill), triggered while the parent attack carries an included category, on input or at a hit-counter value. The groups are compiled when the player's model is set (build 0x1881264, called from 0x183C0B8, which sits under the player's model and skin setters); changing the records later has no effect until then.

A compiled group (vt_0x1F7A188, stride 0x2B0): +0x18 the group record, +0x40 owner, +0xA0 / +0xA8 included categories, +0xB8 / +0xC0 excluded, +0xD0 companion type, +0xD8 prop, +0xF8 effect sequence, +0x104 auto-trigger hit count, +0x13D can evaluate input, +0x13E swallow input, +0x13F parent must have an active attack, +0x140 parent must reject input, +0x142 auto-pick on an enemy's counter window, +0x143 auto-trigger on the hit counter, +0x120 / +0x128 required item / buff. The manager is [comp+0xC68], its groups at +0x58 / +0x60.

  • At every player attack start, 0x2C3D68 -> 0x4E8B54 -> per group 0x4E9094 latches the group when the attack has an included category and no excluded one.
  • Input goes through 0x4E85D0: first a swallow pass over a separate vector (mgr+0x70, holding only Counter_FromGTD), then the player's own tree, then the normal pass 0x4E8B94 over the groups. A group passes its gates (swallow flag clear, can evaluate input, latched, the item-slot mask, the parent's input decision, the event id - small command ids such as 0x6B attack, 0x6C, 0x85 - and its required buff and item), gets an instance (0x65A990: one per latch with a budget, otherwise up to Quantity), then EvalNodes 0x795E7C picks an attack (PickAttack) and a target (0x76A890 with the player's component), places the companion (0x18800FC) and starts it (0x1888918).
  • EvalNodes evaluates every attack with the player as the attacker, so attacker-side predicates (Focus, distance, direction) are measured from the player.
  • Two launches happen without input, both with mode 5 (no input match): 0x6D27D0 from the hit counter (every multiple of the group's auto count) and 0x76EE08(component, enemy combat object), raised when an enemy opens a counter window, with an explicit target.
  • The execution pools require the wraith-execution skill item (CSP_Chord_InstaK_Child1 -> PS_Execution_Child1_WraithExecution_SKILL): without it every pool is rejected before any attack predicate runs.

Struggles

A struggle is the player's input minigame inside a paired animation: the Last Chance ring before death, button mashes, holds, stick directions and aiming. Struggles run only for the player; the other participant just plays its half of the paired animation.

Data

Combat/Struggle/Types 8 a counter family: reset rules, reset cooldown, presentation events, an optional stat mirror
Combat/Struggle/Pools 49 a type and an ordered list of options
Combat/Struggle/Options 131 predicates and a list of struggles
Combat/Struggle/Struggle 132 one minigame: input kind, buttons, timings, ring sizes, widget, audio, camera

The types are FF_PC_RMT_Melee, BH3_Sequence, BIP_TribeAtk_Dark, BIP_TribeAtk_Warmo, Werewyrm_Struggle, PreDeath, PreDeath_Caragor and PC_PinnedState_ButtonMash. Only PreDeath mirrors its count into a stat (Combat/Stat/Variable/Float.LastChanceCount), and its reset cooldown of 1e10 seconds means the count never expires.

The Last Chance ring is drawn with three materials (lastchance_red.mat for the moving ring, lastchance_blue.mat for the win ring, lastchance_white.mat for the perfect ring) whose alpha reference parameters Interface/UIMaterialOverride/Struggle.SharedStruggle names.

Struggles start from Combat/Sync records (paired animations): 49 of 1,507 carry a StrugglePool, with StruggleWinSync (46), StrugglePerfectSync (30) and StruggleLoseSync (10) naming the paired animation that follows each outcome and PerfectStruggleRequiredItem (23, all PS_Struggle_Crit) gating Perfect on a skill. Combat/States/Definitions also has a StrugglePool field, empty on all 112 shipped states. The shipped syncs reference 17 of the 49 pools.

Who can struggle

The struggle state lives on the player's combat component ([player+0x2FA0], also the combat object's +0x50):

Offset Meaning
+0x08 the player
+0xC70 the struggle started by a paired animation
+0xC78 the struggle started by a combat state
+0xE30 the per-type count table (entries of 0x18 bytes); +0xE38 the entry count
+0xE68 the combat object
+0xF5F / +0xF60 can lose a struggle / can lose an aim struggle (CCharacter.DEMO_SetPlayerCanLoseStruggle 0x19B397C, ...Aim 0x19B3998)

The pool evaluator 0x1843E04 returns nothing unless the combat object has both +0x40 and +0x50. On the player's combat object +0x40 is the player; on 11 of 11 non-player characters sampled live both are 0. For a paired animation the engine takes the participant whose combat object has +0x40, or that participant's rider, so a mounted player struggles through the mount's paired animations.

Choosing a struggle

0x1843E04(pool, combat object, target, option out) reads the type's count, walks the pool's options in order and returns the first whose predicates pass (0x18464E4: count range or count formula, buff, the player's items, the target's items, stat predicates, the target's health range). From the passing option it takes the struggle at index min(count, n - 1) (0x18458F4), so an option's list is a difficulty ladder indexed by how many struggles of that type already happened, and its last entry repeats.

Each count-table entry is {type record, u32 count, u32 expiry in ms, stat-variable link}; the live table holds one entry per type, in record order. Starting a struggle adds 1 (0x17B2858 -> 0xCB03A0), sets the expiry to now + ResetCooldown x 1000 on the engine's millisecond clock ([[0x2702598]+0x8]+0x18) and mirrors the count into the type's stat. Reading an expired count zeroes it (0xCAF140). Entering a state with a fail condition resets every type marked ResetCountOnDeath (0x6EF838); Success / Perfect / Fail apply ResetCountOnPerfect and ResetCountOnLose (0x74B130); the combat action ResetStruggleCount 0xF16840 resets one type.

Starting

  • From a paired animation: 0xFB268 -> 0x6EF978 -> 0x6EF9DC. From a combat state: the state change 0x2C14C8 -> 0x6EF838 -> 0x6EF908 -> 0x6F0000, which requires the state machine's +0x58 to equal the state being entered and the state's timer to be running (0x6F03CC takes the largest remaining time over the 0x20-byte timer entries at [state machine+0x00], skipping paused ones). +0x58 of the state machine is therefore the current state.
  • 0x6EF9DC orders source and target by TargetStruggle, shows the option's HUD prompt, allows Perfect only if the player owns the sync's required item, then builds one object per input kind: QuickTime 0x18421C0 (0x170 bytes, vt_0x1F76D28), Aim 0x1842120 (0x180, vt_0x1F76C80), PressCount 0x1842198 (0x178, vt_0x1F76C28), Hold 0x1842148 (0x1B8, vt_0x1F76CF0), InputDirection 0x1842170 (0x150, vt_0x1F76D60) and Ring 0x18421E8 (0x198, vt_0x1F76CB8), all on the base constructor 0x1842490 with seven virtual slots (0 destructor, 1 update, 2 finish with a result, 4 done, 5 kind-specific start).
  • The common start 0x1845C94 stores the player, source and target handles (+0x08 / +0x30 / +0x58, pointers at +0x28 / +0x50 / +0x78), the struggle record (+0x80), the input window (+0xF0 / +0xF4), the result (+0xFC), the type's four presentation events (+0x100 to +0x118), Perfect allowed (+0x138) and can lose (+0x139). It then applies the command set, starts the camera presentation on the player's presentation component ([player+0x2FC0], 0x17A505C) and attaches the widget to the configured bone.

The input window is animation data. 0x184340C reads the events BSW and ESW (0x227C894 / 0x227C898) from both participants' paired clips (0x1847248) and keeps the earliest start and the latest end; without them the struggle ends at once. The struggle's clock (0x18431E4) is the playback time of the source's paired clip (0x1143C0), so slow motion and animation rate stretch the window with the scene.

Running and resolving

Every frame 0x162560 ticks both slots (0x6EFF54, 0x6EFF9C): update, then done, then the result 0x184531C. A Fail is reported as Success when the struggle's can-lose byte is 0 or the static byte 0x2671491 is 0 (it is 1 in the executable and live, and no code writes it).

  • After a paired animation: Fail plays StruggleLoseSync, Success StruggleWinSync, Perfect StrugglePerfectSync (falling back to the win sync); the matching audio key plays (Perfect falls back to Win); the next paired animation starts through 0x19D96B8; then the script event CCharacter.OnCombatStruggleEnd (its P919 hash stored at 0x272911C by 0x42E6490) fires with won and perfect flags.
  • After a combat state: Success and Perfect clear the state (0x19D2834 with no state).
  • The common finish 0x1847188 plays the type's OnFail / OnSuccess / OnPerfect presentation event with the struggle's camera type.

Button mash (PressCount). Phase byte +0x16E: waiting, window open at BSW, counting, timed out, done. The required button (+0x168) is a weighted random pick over the struggle's input list (0x18451F4). Each right press increments +0x16D; reaching +0x16C wins (0x1846B38); a wrong press fails when FailOnIncorrectInput is set; passing ESW fails. Both counters are single bytes (the start stores NumPressesForWin with mov [obj+0x16C], al at 0x6B11216 and the input compares bytes at 0x1846B78), so the value is taken modulo 256: the "impossible" goblin mash with 999999 presses needs 63.

Last Chance ring (Ring). The start (0x6B12660) moves the effective end of the window earlier by Interface/Shared.LastChanceInputLagBuffer (ms, +0xF8), evaluates the three ring scales against the player's stats and converts them to alpha references: perfect +0x170 = 0.025 x (1 - 0.2 x P / 50) + 0.0075, win +0x174 = 0.85 + 0.2 x (1 - 0.5 x W / 100), moving ring +0x178 = 0.05 + 0.45 x (1 - M / 1500); +0x184 = 1 - Lose / 100, +0x188 FailTimeStart, +0x18C failure allowed (AllowFailure and 0x2671491), +0x138 CanGetPerfect. The update 0x1848304 opens the window at BSW and starts the struggle's slow-motion record; at the shortened end it enters the failing phase when failure is allowed and resolves Fail at ESW. When failure is not allowed, 0x1847B20 instead saves the source's animation rate ([combat object+0x260]+0xB0) and sets it to 0, so the paired animation, and with it the struggle clock, holds until the player presses; resolving (0x18473D8) restores it, ends the slow motion and plays the cursor effect.

Hit categories

What a hit does to its target and its attacker is a Combat/Category record: 2,559 of them, with 412 Combat/Category/Lists that group them for the category predicates (see the predicate table above). By name, 1,009 are the player's (PC_*), 755 the AI's (AI_*), 98 and 87 belong to the two story-DLC heroes (PLBar_*, PLBoG_*), and the rest cover the Wraith, dominations, resurrections, environment ignitions and kill cameras. Open questions

  • What the fight circle's +0x188 / +0x190 pointers hold.
  • How the Last Chance press is judged: the ring's input listener (vt_0x1F76BE0 slot 1 -> 0x1846974) and where LastChanceRingForgivenessBuffer (read by 0x18434A8) enters the comparison.
  • The update logic of the Aim, Hold, InputDirection and QuickTime struggles.
  • Which records use the 32 pools no shipped paired animation references (the BH3 sequence, warg and troll domination, the pinned-state mash and several boss pre-deaths): a later database layer, quest scripts, or the combat-state path.
