ASLR Session Reference (VALIDATED 2026-04-24, 87 PASS / 0 FAIL)

  • ASLR base: 0x140000000 (confirmed SoW 1.21; fingerprint 98450f3d510b6c12)
  • Formula: absolute = pm.base_address + RVA
  • The IMAGE never moves (MEASURED 2026-09-26 from the PE header): FileCharacteristics 0x23 = RELOCS_STRIPPED, DllCharacteristics 0x8120 has no DYNAMIC_BASE, and the base-relocation directory is empty. The exe always loads at 0x140000000, so module/static addresses are identical every launch. What changes per session is the HEAP (FMs, records, managers' objects) - the "never cache absolute addresses" rule is about those. Consequence for tooling: a slot holding an image address at rest is a CONSTANT POINTER, not a pooled literal (rva_audit verdict CONST_POINTER; .reloc cannot be used to find them here).
  • ALL 21 manager RVAs confirmed valid; ALL 8 function RVAs confirmed (valid code prologues)
  • ~~ALL 7 Havok physics constants confirmed~~ DEBUNKED 2026-07-29: the validator only checked that a float equals -9.8/0.9/1000.0, which proves nothing. All 7 are compiler-pooled .rdata literals with ZERO writes, read by 2-55 unrelated functions. There is no static Havok tuning block — real gravity is hknpWorld+0x9C0. See aire/documents/HAVOK_SYSTEM_DECODE.md.
  • Pointer chain GM→FS→Pools→FM stable across 3 consecutive reads (0 drift)
  • GameDB category walk: 2,742 categories live (matches DB exactly)

SIX OF THESE 21 RVAs ARE NOT MANAGERS (audited 2026-08-07, rva_audit, max_hits=6000, none truncated). Five are UNREFERENCED — no code reads or writes them anywhere in the binary — and AIManager is a DEAD_LITERAL. All six read hard zero (or a constant) during CONFIRMED free roam. The whole 0x2A34xxx "GameSystems" cluster is fake except NemesisManager (0x2A34C68, LIVE, 16 reads / 1 write - CORRECTED 2026-10-15: it is the global PLAYER LIST vector, see the table row). Control in the same call: SpawnManager = LIVE, 49 reads / 1 write, readers Spawn_AI_SPAWNAMBIENTSET / SummonNPCs. This EXPLAINS the in-game-detection note below that the cluster "measured the SAME in menu and open free-roam" — nothing writes them, so they never change. The 2026-04 validator only checked that an RVA was in range and dereferenced plausibly, so "NULL at the menu" was read as correct menu behaviour when it meant "never used". CameraManager / StateManager / QuestManager ARE real (the engine writes them) but read 0x0 in free roam — real slots, unpopulated in that state. See [[fake-manager-rvas]].

vtRVA caveat (vtable name audit, 2026-07-02): the vtRVA= values in this table are legacy session annotations, NOT audited vtable starts — the audit rejected them (confirmed example: HkaiNavManager's live object uses vtable 0x1DC92C0, not the annotated 0x1DB3480; that RVA is a big, still-unidentified 142-slot vtable). Do NOT treat these annotations as vtable addresses. resolver.db vtables (RTTI-audited, 0 garbage names) is the ONLY vtable authority — resolve via call("vtable_methods", name=...).
