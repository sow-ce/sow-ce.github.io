FM Offset Quick Reference (VERIFIED 2026-04-10)

THE FACTIONMEMBER IS 0x528 BYTES (MEASURED 2026-10-08, after two crashes) - every offset below from +0x530 up is OUTSIDE it. Both heap construction sites allocate 0x528 and then construct it (0x19ED468: mov ecx,0x528 -> alloc 0x3DE238 -> ctor 0x1BB4C1C; 0xF99FF0 the same through malloc / the typed heap); the ctor's last store is +0x520. FM+0x530.. is the captain's APPEARANCE object only when the engine allocated it right after him (the "inline" case, FM+0x2D8 == FM+0x530: dlmalloc's next user pointer for a 0x528 request is exactly p+0x530); otherwise it is whatever the heap put there. So body +0x558, armor/AD slots, head instance +0x6A0, the colour array +0x6A8, weapons +0x730 = appearance [FM+0x2D8] + (off - 0x530), and the "FM Extended Offsets" past that (trait mirrors, picker region 0x1068+, nemesis history 0x1850+) are NEIGHBOURING objects (often the captain's own vectors' buffers, allocated next to him - which is why they looked like his). The old "5-12% garbage equipment on unloaded orcs" was this. Two crashes of 2026-10-08 were the randomizer's dramatic palette writing fm+0x6A8: the Ash palette into a trait list the Army view then read, the Bog palette into an inventory item at fm+0x618 (+0x90) that the save serializer (0x52D770 -> pool serializer 0x59460C) followed. Address the appearance through [FM+0x2D8], the traits through the vectors at FM+0x198/0x1E0. Framework: ArmyRNG::Engine::FmSlot(fm, off) (built, cl /Zs clean, NOT run) - inside 0x528 the FM, 0x530..0x8D0 the real appearance, anything else 0 (refused). "Inline" is the exception, not the rule (MEASURED 2026-10-26, Nurnen save, live, read-only): [FM+0x2D8] == FM+0x530 for 0 of 206 row captains, while [FM+0x2D8]+0x28 named the body matching the class for 206 of 206 (control). So every fixed FM+0x530.. read in the framework reads another object. Two writers this hit, fixed 2026-10-26 (cl /Zs clean, NOT run): UrukV2::SelectOrc's "personality / body auto-fix" judged the body by [FM+0x558] (read nothing on all 206, so every body counted "not Olog") and would have written a random ORC personality into FM+0x270 on 34 of 206 captains - all 32 Ologs - on mere SELECTION, which runs every frame the menu is open (disabled, #if 0); and Orc Capsules (sdk/sow_orc_capsule.hpp, Orcs > Library) read and WROTE the look slots at FM+off (now SlotAddr = the FmSlot rule). The old Uruk Editor pages that write FM+0x500 (it is the resurrection counter, not an advanced class), FM+0x6A8.., FM+0x730.. were read-only, then UNREACHABLE: the Uruk Editor page was retired 2026-10-26 (its captain-address sharing is the Army Grid's Developer strip: left-click copies the address, "Copy report" a PID-stamped captain report; the Army-menu cursor capture UrukV2::ProcessCaptures is unchanged). Census: scripts/uruk_autofix_census.py (read-only; walks the MainGame pool, _Row_ captains, mirrors the auto-fix test).

Trait Object Layout (heap, vtable RVA 0x1FDABF8, stride 0x118)

CORRECTED 2026-10-03 — these are INVENTORY ITEM INSTANCES, not a trait class. All 10,569 live 0x1FDABF8 objects carry the item-data sub-object (vt 0x1FDABD0) at +0x18 and 10,457 hold an Inventory/Items record at +0x38 (112 empty pool slots); the orc's "traits" are its items (body LOD, mask, weapons, level 1). Same class as the player's swords - full layout in "Inventory, Affixes & Gear Stats" below. The +0x08 "self-ref" is the item's equip-list node.

Trait objects are on the external heap, pointed to by FM+0x0A0 array. NOT embedded at FM+0x770. Each trait object's self-ref at +0x008 points back into FM at stride-aligned offsets.

+0x000  vtable    (0x1FDABF8 — same as VTable::GADB_RECORD in C++ framework)
+0x008  ptr       Self-ref back to FM trait slot (FM+0x818, 0x930, 0xA48, 0xB60...)
+0x010  ptr       Same self-ref
+0x018  ptr       Code pointer (vtable sibling 0x1FDABD0)
+0x038  record    Equipment record (Slaver_Helmet, Black_Shoulders, etc.)
+0x048  record    AD decoration record (AD_Slaver_Helmet, etc.)
+0x0A8  int       Small integer (typically 1)
+0x0C8  u64       Hash/state data — trait parameter seed
+0x0E0  record    Faction/event record (optional)
+0x100  int       Integer field
+0x110  int       Integer field (e.g., 283)
+0x118  record    Tag record (Tag_Spearman, Tag_Archer) or vtable ptr

Per-trait equipment is mirrored in FM body (self-ref deltas CONFIRMED 2026-04-24 via 298 traits, 100% vtable match):

  • Trait#0: FM+0x818 (self-ref +0x818), FM+0x848 (equip), FM+0x858 (AD)
  • Trait#1: FM+0x930 (self-ref +0x930), FM+0x960 / FM+0x970
  • Trait#2: FM+0xA48 (self-ref +0xA48), FM+0xA78 / FM+0xA88
  • Trait#3: FM+0xB60 (self-ref +0xB60), FM+0xB90 / FM+0xBA0
  • Trait#4: FM+0xC78 (self-ref +0xC78), FM+0xCA8 / FM+0xCB8
  • Trait#5: FM+0xD90 (self-ref +0xD90) — 19 orcs had 6th trait
  • Trait#6: FM+0xEA8 (self-ref +0xEA8) — 12 orcs had 7th trait

Self-ref stride: 0x118 bytes between trait slots (0x930-0x818=0x118, 0xA48-0x930=0x118, etc.)

Nemesis History Region (FM+0x1850-0x1E00+)

Embedded past-encounter orc profiles — full FM-like records with AI class, body, equipment, faction, role, tribe, rarity, hierarchy, strengths, weaknesses, tags, event refs. Orc Name Encoding (PROVEN 2026-04-15)

Game stores orc inline names (FM+0x498) in Latin-1 / Windows-1252 (single-byte encoding). Diacritics: û=0xFB, ê=0xEA, ô=0xF4, ú=0xFA. These are single bytes > 0x7F. ImGui expects UTF-8. Must convert: Latin-1 byte b where b >= 0x80 → two UTF-8 bytes (0xC0 | (b >> 6)) + (0x80 | (b & 0x3F)). Do NOT pass raw high bytes through — ImGui renders them as ?. Do NOT break on byte 0x80 — it's a valid Latin-1 char; detect unused name slots by checking if ALL bytes are 0x80 (0x80-fill sentinel pattern).

Nemesis Captain Scanning (PROVEN 2026-04-15, updated 2026-04-20)

FortSystem Pool[8] (MainGame) contains ALL faction members (500 entries: captains + 344 story/grunt/dead FMs). Scanning raw pools yields non-randomizable junk.

Correct method: Use garrison record at FM+0x268. Only REAL nemesis captains have a record with format RegionName_Row_RankType_Column (e.g., island_Row_Captain_3).

Filter chain: FM+0x268 != NULL → name contains _Row_ → rank type is Captain/Warchief/Overlord → not dead (FM+0x508 flags bit 2).

Campaign/story orcs (Zog, Bruz, Orthog, Ranger, etc.) have NULL at FM+0x268 → automatically excluded.

Region internal names: MinasIthil, MtnPass, island, volcano, snowMtn, desert. AIRE's RegionScanner/ArmyMap implement this filter chain with VirtualQuery hardening.

FS = [[base+0x26FFAA8]+0x6C68]

        seat value = the occupant's POOL INDEX (FM+0x174), -1 = empty
  • FM+0x174 is the pool index, not a faction id - the MainGame and DLC pools both hold Zog at index 0, so any "FM+0x174 != 0" validity test silently drops him (FactionMember::IsValid and ForEachOrc did until 2026-10-13; they now test [FM+0x178] = a GameDB record: 526/526 members pass, 0/53 non-FM pointers do). FM+0x269 is byte 1 of the FM+0x268 POINTER, not a rank; FM+0x4C0 mirrors the level FM+0x4B8 (155/155), it is not "menace".
  • Which army is a region's: Regions/Region::<name>.Faction (P919 0x19C4F00C). desert -> Faction_desert_Real (the campaign army); Faction_desert exists with every seat -1.
  • Seat 0x61E13C(ctx, fm, rowRecord, column, flag): flag 1 = a new member (creator 0x1C1D378), 0 = a move (sim outcome 0x40C304). Refuses when FM+0x4F8 != 0 and a move into a Warchief row whose side differs from the Overlord's (0x1E4C08 / 0x114E020); vacates first, re-levels (0x1C1BDA8 -> SetLevel 0x35188C), checks column < count, not locked (0x24EBB8) and seat == -1, then writes the pool index, FM+0x51B = column and FM+0x268 = row (0x61B614). Vacate 0x61B274(ctx, fm): -1 in every seat holding the index, FM+0x51B = 0xFF, FM+0x268 = 0, dirty bytes ctx+0x1EE / +0x1F0. Mark moving 0x61D354(fm, bool) (FM+0x51F).
  • The engine's own seat swap (0x40C767): mark both, vacate B, unlink B's node (FM+0x18), seat A into B's seat, seat B into A's old seat (both flag 0), unmark. TransferMember 0xF6AC90 refuses a move inside the same army. Framework: native verbs seat / swap (sdk/sow_main_native.cpp, rollback on refusal) driven by the Army Grid's drag and drop; read side sdk/sow_army_seats.hpp. IN-GAME CONFIRMED 2026-10-13 (user: moving captains in the Army Grid "changes their position in real time"), together with the rebuilt right-click menu ("much organized").
  • CCharacter byte +0x23B8 = player follower (9/9 PlayerFollower, 22/22 Orc_FactionA by alignment +0x2410); health [char+0x26A8]+0x42C current / +0x428 max. SpawnManager entry +0x28 is the AI/SpawnAmbient/Removal record, never an FM (0/22 pass IsValid).

Fill seats, personality & voice, Army-screen poses (BUILT 2026-10-26, cl /Zs clean, NOT run in game)

Army Grid toolbar > Fill seats; right-click > Identity > Personality & voice; Look > Army screen pose. - Fill = the engine's own army fill FillFaction 0x1C1E13C(ctx) (army init's): per row, per column whose seat holds -1 and whose lock bit is clear (row +0x24 u32, 0x24EBB8), one NEW member - from the row's InitBuilderRecords by InitBuilderChance (0x1C1E280 -> 0x1C1CFAC) or the generic build 0x1C1D100: AllocFM 0x1C23C10 -> pool 0x1BD2E20 (full pool = recycles its least important UNSEATED member), build 0x1BC0084, pool link 0x61B5E8, level 0x1C1BDA8([ctx+0xD8], row, 0) -> SetLevel, seat 0x61E13C(flag 1), intel / follower / mercenary flags from Faction/Definition, henchmen 0x7DEEE0. Latch byte ctx+0x21C (once per init, 0x185FE0); its ObliterateAllFactionMembers assert sits behind the unset switch 0x2A369F2. The builder path calls no SetLevel (SpecialGuys_BackRow MinLevel 11). - Dead captains keep their seats (MEASURED, live census of all 38 armies: the six campaign armies held 0 empty seats and 1-3 dead each), so the native verb fm fill <member> <flags> (RunFmFill) can vacate first (bit 0): dead (bit 2), not returning (bit 4), no preset, no body, outside the Overlord row (0x61B274); a vacated seat left empty is seated back. The Overlord row's seats are locked for the call.
