GameDB Schema Format (PROVEN 2026-04-13)

Field Descriptor: 16 bytes each, stored in a contiguous array per schema.

+0x00  u32   Field name hash (game-specific hash, P=919 polynomial)
+0x04  u32   k-th entry of the run's ASCENDING sorted-hash list — a parallel
             array, NOT this descriptor's own sorted hash (CORRECTED 2026-07-28:
             Combat/Attack descriptor[0] is AnimationData yet carries
             ActionsOnAttackStart_Source's hash). Run-boundary detection by
             monotone break is still valid — the list is what ascends.
+0x08  u8    Absolute field index (inherited schema offset, may skip GROUP markers)
             MECHANISM (2026-10-05): a GROUP_BEGIN/END marker IS a slot in the
             type's static schema object (PropRegister arg 7 = 0x80000080 /
             0x40000080) but owns no field index, so index = slot - markers
             before it (Combat/Node: KBMNode slot 16 = index 14). See "GADB
             Field Bindings"
+0x09  u8    Sort-order index
+0x0A  u8    TYPE CODE: 1=Boolean(4B), 2=Float(4B), 3=Integer(4B), 4=String(8B),
                        5=StringEnum(8B cell: P919 of an enum NAME), 6=Int64(8B),
                        7=Enum(4B: 32-bit POINTER to a shared (min,max) float-pool
                        pair), 8=Vector3(12B), 9=Vector4(16B), 10=RecordLink(8B),
                        11=RecordLink to a PRIMARY record(8B), 68=String(8B)
             **TYPE 5 IS A STRINGENUM, NOT A VECTOR2 (MEASURED 2026-10-19)** -
             see "Type 5 = StringEnum" below. The DB Explorer's "Vector2" is
             type 7 (e.g. `RequiredScaleRange`, a float-pool pair).
             **CODE 11 WAS MISSING FROM THIS TABLE UNTIL 2026-08-16** and it is
             not rare: 27,088 of the main GADB's 361,939 descriptors use it
             (7.5%), third behind RecordLink and Bool. 10 and 11 are BOTH
             RecordLinks and differ only in which side of a category they
             address — 10 a SECONDARY record, 11 a PRIMARY (inline struct
             array) entry. Measured: `AITypes.Entries` ->
             `_StructuresAISpawnAmbientTypeEntry/primary[30]` = 11,
             `Character/Alignments.Alignment` -> `_StructuresRelationship/
             primary[37]` = 11, while `SpawnScenarioSetup.ScenarioType` ->
             `SpawnScenario/Cage` = 10 and `_StructuresRelationship.Others` ->
             `Character/Alignments/...` = 10. Random 70-category sweep:
             **type 11 -> primary 38/40 (95.0%), type 10 -> secondary 69/71
             (97.2%)** (4 residuals unchased, suspected `resolve_recordlink`
             side-picking, not a type-rule failure). Anvil's `TYPE_NAMES`
             already mapped `11: 'RecordLink'`, so only this table was stale.
+0x0B  u8    Zero (padding)
+0x0C  u16   Flags
+0x0E  u16   Link/bucket index

Type 5 = StringEnum (MEASURED 2026-10-19, live + disk; aire/gamedb/string_enum.py). Every reader called it "Vec2" and dereferenced the cell as a blob pointer. It is an enum held BY NAME: - disk: the cell is the string-block offset of the enum NAME, read forward from the root type name like any String (632 -> GameUnpause, 24116 -> MenuAux6, 27496 -> Request, 33168 -> Wraith ...); - live: the loader stores P919(name) in the low dword of the 8-byte cell, high dword 0 - 336,338 of 336,338 live type-5 cells (no zeros, no pointers); 12/12 disk names hashed to their live cells. P919 folds case, so HIGH and High are ONE value. - The same reflection system already said so elsewhere: BlendDB type 5 is a string enum (1,516/1,516, behavior_db.py), ClientFX PropRegister type 5 is a string enum, and FXDB type 5 (scripts/fxp_editor.py). The framework's Market gold prompt writes P919("MenuAux7") = 0xB425069D into type-5 Input cells and the game honours it (IN-GAME CONFIRMED 2026-09-28). - Read as a pointer, a hash can land in live heap data - the GameDB heap lives below 4 GB (records at 0x7Bxxxxxx-0x7Cxxxxxx in recent sessions), inside the range a 32-bit hash covers. That is where the old decoders' "Vector2 slots that point at a RECORD (tag 0x0A08)" came from, the three false disk_delta vec deltas (_StructuresSplashMovie.Locale, _StructuresCombatPlayPredicate.PlayAction, _StructuresCameraAnimatedPropertyDef.Type), and the SAFE WORLD ROLL v5 crash class: it swapped 8 bytes between the addresses the hashes named (FULL 6,896 writes over 163 addresses; in a BESTIARY twin one of the 55 was a live heap pointer). - Index: call("string_enum_build") (17 s, cached aire/data/engine/string_enum_names.json): 963 names over 1,772,448 disk cells, 455 fields, 25 archives, 0 hash collisions (350 offsets unresolved); names 100% of live type-5 cells. call("string_enum", value=0x7C1ABA9B) -> GameUnpause; call("string_enum", name="MenuAux7") -> hash + whether any GADB uses it. - Write it by name, never as floats: write_field(..., value="MenuAux7") (refuses a name no shipped GADB uses unless {"name": ..., "allow_unknown": True}), WriteGate kind "string_enum"; WriteGate kind "vec2" is refused (no_vec2_type). The substrate tuner / editor refuse type-5 and Vec3/Vec4 writes. Anvil's display shows the name (3,036/3,036 sampled values in 228 categories). C++: GDBRuntime::T_StringEnum (was T_Vec2). - resolver.db gamedb_fields.type_name still reads "Vector2" for 321 type-5 rows (seeded before the fix; the seeder now writes "StringEnum"): type_code is the authority. - World layers' ObjectPropertyDBs carry no type 5 (5 layers, 3,218 descriptors: types 1/2/3/4/8 only); world_props reads one as a name if it ever appears.

Vec3/Vec4 blobs are SHARED (MEASURED 2026-10-19, live). The engine deduplicates vector values: 2,597 blobs, 145 serve more than one category; one (0,0,0) blob serves 78 fields in 53 categories (12 of them hot or blocked). A write BEHIND a vec pointer changes every field that shares the blob - SAFE WORLD ROLL v5 rewrote Interface, camera and weather vectors that way. Permute by trading blob POINTERS, never write a blob in place from a bulk tool. AIRE's write_field still writes behind the pointer on request and says shared_blob_note; the C++ Tuner vec editor and the chaos ladder's vec mode still write blobs in place (open item).

Shared instances (MEASURED 2026-10-19, live). 3,394 of 676,930 record instances are pointed at by more than one record. An "owner" is a record that DECLARES cells there: 3,363 have one owner (the rest are zero-field records), 23 have none, 8 have two - same-layout duplicates in _StructuresServer.NPCBundleListPicker. A per-record tool must de-duplicate by CELL ADDRESS (a write through one record is a write through every record sharing the instance) and write only cells the record itself declares.

Field COUNT is at record header byte 0 (byte 1 always 0x0A). Record layout: +0x00=field_count|0x0A, +0x08=schema_ptr, +0x10=instance_ptr, +0x18=category_ptr, +0x20=name_ptr Category header: name string pointer is at category+0x00, NOT +0x20 (live-verified 2026-07-06 — reading cat+0x20 returns "" for every record class tested; it silently broke identity category pinning and RecordMap's category index for pool-walked records until fixed).

Metadata pool structure (REd 2026-07-28, aire/analysis/schema_meta.py, call("schema_meta_export")): it is a deduplicated TEXT string pool in the .xtext section — not a pointer table (zero qword/dword references to any field-name string exist anywhere in the binary; that was checked first). Fields form contiguous runs terminated by the owning category path in DOT form (over 726 ground-truth categories: marker lands after the run 412x, inside 306x, before 8x).

  • Trustworthy: field NAMES. 12,222 distinct names across 2,709 categories, each accepted only when its P=919 hash matches a real field hash of the category filing it.
  • NOT trustworthy: per-field attribution of types/docs/constraints. Dedup destroys the field↔annotation adjacency. Cross-checked against live FK targets: attaching public <Type> forward = 3.3% agreement (66/2027); backward = 58% (147/255). Both fail, so all of it is emitted under unverified_attribution and never merged into the verified fields map.
  • The pool is also far sparser than it looks: the WHOLE binary holds only 325 type=, 161 min= and 5 max= annotations. It is not a source of per-field ranges — the live call("value_atlas_export") envelopes are.

GROUP_BEGIN/GROUP_END markers (DB Explorer metadata) are NOT in runtime descriptors — but the DB Explorer's schema metadata table is still embedded in retail ShadowOfWar.exe as plaintext (DISCOVERED 2026-07-28, file offsets ~0x1B5B000-0x2004000): a deduplicated string pool holding every field NAME, its declared TYPE as a dotted category path (public Combat.Bool <name>), doc comments, GROUP_BEGIN=/GROUP_END= markers and constraint annotations (min=0.0f;max=5.0f). 725 of 2,891 category paths appear verbatim. This is ground truth for naming — no hashing needed — and is the source that finally cracked the last orphans. Adjacency parsing is NOT sufficient (the pool is deduplicated and interleaved). SOLVED 2026-08-03 by going through CODE instead — see "Schema Builders" below: the engine builds each schema by calling a per-field registration stub, so annotations bind by CALL rather than by string proximity.

Hash algorithm: h=0; for c in name: h=(h*919+LOOKUP[c])%2^32 LOOKUP: A-Z=a-z=1..26, 0-9=27..36, _=38. Dictionary: 11,755 entries = 100% coverage. Field names CAN START WITH A DIGIT (3DRotation, 3DMapShapeHuntingColor) — this is why the last 4 orphans survived every attack: every harvesting regex in the pipeline anchored on [A-Za-z]. Never anchor an identifier scan to a leading letter. Native hash (LOCATED 2026-07-13, Unicorn-verified 12/12): ~~the hash is ALWAYS INLINED — no standalone hash(str) exists (2,090 candidates emulated)~~ CORRECTED 2026-10-05: a standalone one exists - StringHash 0x423E70 (12-instruction leaf), identified by the library lane's behaviour test. It starts from r8 as a SEED (no accumulator clear), so an emulation that leaves r8 non-zero sees a different hash - the likely reason the 2026-07 sweep missed it. Inlined copies exist too (PropRegister 0xC6DA00 hashes every field name). LOOKUP byte table at RVA 0x1DB50D0 (full ASCII-indexed, punctuation included). Canonical inlined copy: hashed-string registry wrapper at RVA 0xF4E0F0 (0x55 bytes) — hash accumulates in R10D, complete at loop-exit 0xF4E12E, then binary-searches a global registry. call("emulate_hash", name=...) runs this natively.

UNIFORM SLOT LAW (2026-07-22 — supersedes the 2026-07-11 two-class ruling; proven by on-disk GADB bit-fingerprint oracle, 900+ categories adjudicated, dense won ZERO):

  • EVERY schema is slot-addressed. Live instance offset = descriptor link (+0x0E) * 8 (uniform 8-byte cells); on-disk GADB value index = link. "Dense" (size accumulation) NEVER existed — it only looked right where links were sequential. All pre-2026-07-21 offset tables derived by accumulation have SHIFTED FIELD NAMES (values were real, names wrong): e.g. "BaseSpeedMultiplier +0x40 = 2.3" is actually AimingRadiusScale; the real BaseSpeedMultiplier is slot +0x80 (default 1.0); PhysicsCharacterGravity slot +0x60 = -2000.
  • Packed bools (434 categories, e.g. Inventory/Items): bool link is a BIT index — value = bit link%32 of the u32 cell link/32. Detect: any bool/non-bool link collision. Bool writes MUST be single-bit RMW (full-cell writes clobber sibling bools). Verified 40/40 records vs disk (Inventory/Items cell 0 = 14 bools, bits 0-13).
  • Vec3/Vec4 slots hold a POINTER to the value blob — the floats live BEHIND the pointer (disk stores blob byte-offsets). NEVER write 12/16 raw bytes at the slot: it stomps the pointer + neighboring slot (proven crash class). Edit via deref - and know the blob is SHARED (deduplicated: one (0,0,0) serves 78 fields in 53 categories), so a bulk tool trades blob POINTERS instead of writing blobs. (CORRECTED 2026-10-19: there is no Vec2 type - type 5 is a StringEnum, P919 of an enum name, and must never be dereferenced. See "Type 5 = StringEnum" above.)
  • Per-record variants: sparse categories can carry RECORD-SPECIFIC descriptor runs (same hashes, different links) — always address through the record's OWN schema_ptr (rec+0x08). Run length = monotone sorted_hash prefix (record-header byte 0 is the TAG low byte, NOT fc, above 255 slots). Duplicate links inside a run are LEGITIMATE (bool bit indices + patch-era aliases) — never truncate on them.
  • Oracle: live values must bit-match the on-disk GADB under the correct rule (unique-value cells, cross-record columns, RL-encoding→live-pointer prediction where (cat_idx*16)<<16|rec_idx decodes via the DISK category order — paths use '.' on disk, '/' live).

  • ARRAY LAW / descriptor +0x0C is a COUNT (CRACKED 2026-07-28 from the engine's own resolver at RVA ~0x278760). The accessor reads:

    movzx eax, word ptr [rcx+0Ch] ; element COUNT (NOT "flags") cmp r8d, eax ; index bounds check jae default movzx ecx, word ptr [rcx+0Eh] ; link = BASE slot mov rax, qword ptr [r10+10h] ; record -> instance add ecx, r8d ; link + index mov eax, dword ptr [rax+rcx8] ; value = inst + (link+index)8

So a field owns cells [link, link+count) and +0x0C is the element count, not flags. Globally validated: max(link+count) <= sum(count)+2 in all 2,562 categories, zero exceptions. Distribution: 16,146 scalars (count=1), 1,669 EMPTY arrays (count=0), 543 true arrays (count 2-7+). - count==0 owns NO cell. Its link still points where it would start, so reading it returns a NEIGHBOUR's value — this is the entire "duplicate link" mystery, and it was producing real garbage (Combat/Attack had 8 such fields reporting other fields' records). crack_schema marks them empty: True; decode_instance returns None. - count==1 is a SINGLE field, set or not: a scalar RecordLink has count 1 while NULL (Faction/Rewards/Definitions.TriggerAmbush / RewardOnSpawn on all 1,239 records). "Not empty" is not "set" - test the value. MEASURED 2026-10-09: the framework's chaos-reward filter used !Field::Empty() as "set", called every definition risky and built an empty pool in every session (fixed: NativeTraits::HoldsLink, built, NOT run). - count>1 decodes as a LIST (Combat/Attack Predicates count=8 -> the 8 predicate records at cells 8-15; Category count=3 -> cells 5-7). Sum of counts == the record's cell count exactly (23 for that record). - This raised the 13 quarantined categories from ~0.15 to 0.79 disk-oracle agreement, and the residual gap turned out to be an ORACLE limitation, not a decode error — see below. - CELL IDENTITY LAW (PROVEN 2026-07-28): live instance cell i IS on-disk value index i, 1:1. Verified by pointer-identity joins (decode each disk RecordLink to the exact live record-header address it must materialize to, then find which live cell holds it): 1,000+ unambiguous joins across quarantined AND control categories, i == j in 100%. Live and disk address the SAME slot space — no translation, no per-category rule needed to move between them. What remains category-specific is only which field NAME owns a cell. - QUARANTINE LIFTED 2026-07-28 — all 13 dense_aligned categories are now sparse. They are ARRAY-BEARING schemas (Combat/Attack, Combat/SummonData, Profile/BindingSets, Interface/AchievementSetup, ...). The dense_aligned verdicts were a disk-oracle artifact: the engine assigns slots at GADB LOAD (the link is not stored on disk) and array fields take contiguous blocks, so live cell order legitimately diverges from the disk's flat value array — the oracle structurally cannot adjudicate them, and dense_aligned "won" only by walking array cells. Evidence for lifting: 1. the engine's OWN resolver (~RVA 0x278760) proves inst + (link+index)*8 with count at +0x0C; 2. live structural probe over the 13: slot+array = 3,734 valid / 16 garbage (99.6%) vs dense_aligned = 1,967 valid / 249 garbage (88.8%) — the test does discriminate; 3. count-aware probe = 3,528 valid / 0 garbage, identical to a 40-category control group; 4. semantic coherence (Predicates count=8 -> 8 real predicate records). sow_engine_layoutmap.hpp regenerated: Unverified 13 -> 0 (2,124 Sparse + 445 SparsePacked + 322 Empty = 2,891 — every category classified). CAVEAT: this is ADDRESSING only. Write-safety is a separate matter — Profile/BindingSets is a hot-thread input domain on the never-bulk-mutate list, and that ban still applies. Note abs (+0x08) was a red herring: it ties dense_aligned exactly in every quarantined category because both are sequential, and loses outright on controls (Faction/Events/Setup under link*8 gives FortDefenseEvent→FortDefense, KilledOnQuestEvent→ActiveKilledOnQuest; under abs*8 it gives NULL/HalfEmpty garbage).

RecordLink On-Disk Encoding (CRACKED 2026-04-23)

Formula: RecordLink_u32 = (category_index * 16) << 16 | record_index

Equivalently: RL = (cat_idx << 20) | rec_idx

Decoding: cat_idx = (RL >> 16) / 16 and rec_idx = RL & 0xFFFF

CRITICAL NOTES:

  1. category_index is the 0-based sequential index in the GADB's category array (sorted by hdr[5])
  2. record_index is the 0-based index within the target category's record array
  3. For categories with SECONDARY records (sc > 0), rec_idx indexes into secondary records
  4. For _Structures* categories (inline struct arrays), rec_idx indexes into PRIMARY records (pc)
  5. 0xFFFFFFFF = null RecordLink (no reference)
  6. 0x00000000 = null (record index 0 in category 0, treated as null in context)

On-disk type 10 fields contain MIXED DATA — not all are true RecordLinks:

  • IEEE754 floats (e.g., 0x3F800000=1.0, 0xBF800000=-1.0) stored in type 10 slots
  • True RecordLinks have hi16 always a multiple of 16 (cat_idx * 16)
  • 65% of type 10 values are valid RecordLinks; 35% are float/int values

Validation (2742 categories, 1,954,704 non-null type 10 values):

  • 1,271,632 values match formula (hi16 % 16 == 0, valid cat_idx, valid rec_idx)
  • 683,072 mismatches are ALL float values (0.8, 0.4, -1.0, etc.)
  • ZERO genuine RecordLinks failed the formula

Examples (Cat[155] = AI/SpawnAmbient/AITypes):

  • 0x6E400457 → Cat[1764] Inventory/Items rec[1111] = "Torch" (0x6E40/16=1764)
  • 0x6E400B77 → Cat[1764] Inventory/Items rec[2935] = "Item_Quirk_Fearless"
  • 0x61D00109 → Cat[1565] _StructuresAISpawnAmbientTypeEntry primary[265]

To construct a RecordLink: ((cat_idx * 16) << 16) | rec_idx — Anvil provides make_recordlink().

LIVE link cells (MEASURED 2026-10-14, Minas Ithil, every link cell of 2 records + 2 primaries per category): a live descriptor carries type 10 for both sides (0 type-11 descriptors seen; the on-disk 11 is not kept), so the type code cannot say which side a link targets. The TARGET CATEGORY does: links into a _Structures* category hit its PRIMARIES 4,506/4,506, links into any other category hit named records 10,533/10,533, 0 fields hit both. Every _Structures* category also has exactly one named record, a placeholder DEFAULT_RECORD_NAME<Type> (777 of 799), never a target. A link value lands exactly on a header (0 inside one) or outside every array: the misses are one field, hash 0xEF874E83, whose RecordLink-typed cells hold numbers (75.0f, 1300) in several Combat categories. Live category header: +0x18 owning DB, +0x20 type-table entry, +0x28 u32 record count, +0x2C u32 the category's own table ordinal, +0x38 / +0x48 record / primary arrays; the table is 2,742 contiguous categories starting 3 slots after find_category_table_base.

GameDB Float-Range Pool (DISCOVERED 2026-04-14)

148 Enum fields (type_code 7) previously classified as "string_ptr" are actually 32-bit pointers into a global float-pair parameter pool. Each pool entry = 8 bytes: (min, max).

These are shared templates — many records point to the SAME pool entry. Modifying one pool entry changes behavior for ALL records referencing it. Global tuning levers.

Key moddable parameters:

  • AI/Perception.SimulatedRecognizeEnemyDistance: [1600, 2200] — detection range
  • AI/PursuitConstraint.Range: [500, 800] to [2500, 4500] — chase distances
  • AI/Alertness/TransitionPredicate.Duration: 0-10s — alert state timers
  • Combat/Hint/Distances.Distance: [0, 200] to [700, 2000] — combat distances
  • Combat/Predicates/Distance.Distance: [0, 40] to [200, 800] — trigger ranges

ASLR: Pool pointers change every session. Must walk live GameDB (AIRE) to find current addresses.

GameDB Record-Level Writes (CORRECTED 2026-07-22 — slot law)

Direct 4-byte writes to record instance fields. Each record has its own instance data (instance_ptr at record+0x10), so modifying one record does NOT affect others.

The slot law has an exception (MEASURED 2026-10-27): a record whose header byte +0x01 has bit 0x10 is a native struct, not cells. Every BlendDB (.bvr) record is one (318,372 / 318,372 live records = 0x1A; main GameDB 278,865 / 278,865 = 0x0A). Its field lives at instance + SlotOffset(type, field) (kb/gamedb-bindings.md "The engine's own field-read path"; aire/formats/blenddb_layout.py), and instance + link*8 is a DIFFERENT field. Check the flag before any record write.
