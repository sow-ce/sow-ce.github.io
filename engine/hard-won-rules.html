Hard-Won Rules

  • An engine object's own bytes never prove it is alive (MEASURED 2026-10-23, the colour keeper crash): a freed CMaterialOverrideHandle still showed its vtable and store field, and the allocator's free-block footer landed on its use count (0xB0), so vtable ok && refs > 0 passed on freed memory. A pointer captured earlier (render-thread read, a previous tick) is re-found in the engine's own container (stage holders, SpawnManager entities, the owning list) on the MAIN thread, in the same job that acts on it. Render-thread-owned data (store records) is written by a command queued on the main->render ring after that proof (sdk/sow_tint_life.hpp, aire/documents/TINT_KEEPER_UAF.md).

  • NEVER dereference a GameDB type-5 cell, and never write a Vec3/Vec4 blob in place from a bulk tool (MEASURED 2026-10-19, after the SAFE WORLD ROLL v5 crashes): type 5 is a StringEnum - the cell holds P919 of an enum NAME (high dword 0, 336,338/336,338) - and a hash read as a pointer can address live heap data; vec blobs are deduplicated (one (0,0,0) serves 78 fields in 53 categories), so writing behind one pointer rewrites every field that shares it. A "pointer above 16 MB" test proves nothing for type 5. See "Type 5 = StringEnum" under GameDB Schema Format.

  • Memory the framework allocates AND reads back through GDBRuntime must sit above 16 MB (MEASURED 2026-10-18): Memory::IsValidGamePtr rejects anything below 0x1000000, and VirtualAlloc(nullptr) hands out the LOWEST free range (0x880000 in one launch). A RecordExtend copy placed there was invisible to the code that planned it (no schema, no instance, not a primary), so the shoulder-pads lane removed and re-installed its extension in a loop (141 copies) and a Ledger revert skipped the cells inside it. RecordExtend::Arena now asks VirtualAlloc2 for 256 MB - 4 GB, then above 4 GB. See "Shoulder pads" under the captain look sections.
  • Runtime material slots: kind 0 SOLID, 1 TRANSLUCENT, 2 DEPTH PROXY (setter 0x17AF0C = material object vt 0x1FFE3E8 slot 47, main thread; one 48-slot table at +0x1E8: solid 0-15, translucent 16-31 at +0x368, proxy 32-47 at +0x4E8). MEASURED 2026-10-12 against the engine-built wraith copy after a wrong remembered mapping made the ghost mount invisible. Undo per slot from your own plan - SetMaterialSet restores solids only. See "Play As" > The ridden MOUNT as a ghost.
  • A drawn weapon is never rebuilt by 0x40000C / 0x3FD228 (they build only an EMPTY holder; MEASURED 2026-10-12): rebuild with the holder pair 0x3FD21C (hide) then 0x3FD204 (show), the engine's own refresh 0x45ABE4. See "Play As - the donor as a NATIVE WRAITH" > Ghost weapons.
  • Create every MinHook detour at BOOT; enable/disable later (measured 2026-10-07): a trampoline must sit within +-1 GB of its target and the game fills that range during play, so a late MH_CreateHook fails with MH_ERROR_MEMORY_ALLOC. Creating patches nothing and freezes nothing. See "First Person Camera".
  • An in-process heap scan NEVER runs on the render thread, NEVER reads PAGE_WRITECOMBINE/NOCACHE pages, and NEVER caps region size (user-confirmed freeze + fix 2026-09-29, World > Physics). The UI draws in the Present callback; the process holds ~7.6 GB of write-combined D3D11 memory (60-75 s per sweep); and the Havok heap is ONE 512.1 MB region (measured live) holding every Havok object, so a <= 256 MB cap made SoW::Havok::Resolve() fail forever and re-sweep back to back. Reach Havok through the engine's own handle instead: [base+0x2A86760]+0x20 = hknpWorld, +0x9D8 material lib, +0x9E0 motion lib, each +0x30 hkArray (live-verified against the census). See aire/documents/HAVOK_SYSTEM_DECODE.md §10. The configured-material count GROWS during play (13 -> 18 in one world, 2026-09-29): count it live per write from the maxContactImpulse marker (FLT_MAX configured, -1.0 free), and never revert a surface by writing a value - each slot has its own vanilla.
  • NEVER write repeatedly to a SCANNED world-object address list without re-verifying the vptr on EVERY pass (user-confirmed crash 2026-08-03): world objects near a moving player are streamed in and out, so an address that was a LightCube at scan time is freed and its allocation REUSED within seconds — sustained writes then land in whatever took its place (use-after-free). A single one-shot write to the same objects was harmless; duration and repetition are what kill. A coordinate that DRIFTS between reads is proof the slot is churning — stop, don't continue. Never restore by arithmetic (current - lift); journal the original through WriteLedger and restore with a still-ours check. "The engine restores it automatically" is not a revert plan — measured ~1s once and still un-restored 1.5s later the next time.
  • NEVER write FM/SMC/INV while game_state == "loading" — the deserializer family is rebuilding those exact structures; racing it CRASHED the game (2026-07-06: SMC writes read back 0 mid-run, then crash). AIRE's randomize action now refuses during loading (force=True to override) and its write-verify circuit breaker aborts the run after 6 readback failures.
  • FM_BODY_TYPE detection: use body mesh name at +0x558, NOT class record +0x278/+0x054
  • FM+0x054 is always 0 (unknown field) — never use as body type indicator
  • NEVER clone entities via memcpy + SpawnManager injection (instant crash)
  • NEVER modify shared GDB records (Smp wrappers, Facial chains) — crashes
  • NEVER use DebugManager chains — not populated in retail builds
  • Writing FM_BODY_TYPE on a loaded orc crashes — must update atomically or when unloaded
  • NEVER claim mods work until user confirms in-game
  • SetModelOverride operates on CCharacter (NOT FactionMember)
  • ALWAYS use 64-bit reads (rp/ReadPtr) for FM pointers — 32-bit reads truncate heap pointers and return garbage
  • Trait objects are on the EXTERNAL HEAP — follow FM+0x0A0 pointer array, do NOT scan FM+0x770 directly
  • FM+0x1140-0x1540 is an internal linked graph (NOT record pointers) — contains AI distance ranges and self-pointers
  • FortSystem+0x78 is NOT a region index (sow_offsets.hpp is WRONG) — use FortSys+0x1B0 record name for region detection
  • FM+0x3A0 is NOT a rank/display field — it's FactionMemberBuilder (spawn template). Use FM+0x268 for army grid position
  • FM+0x6F8 is NOT a faction reference (DEBUNKED 2026-04-24) — contains mixed combat/AD/trait data. 0% faction in 100-captain audit.
  • IN-GAME DETECTION (CORRECTED+VERIFIED 2026-06-29, both states sampled live): the ONLY reliable signal is SpawnManager (0x26FFBE8) is NULL at the main menu, LIVE in free-roam (SpawnManager valid + spawned-count at +0x190 in [0,100000)). Signals that DO NOT work: (a) 0x2A34BE0 == 0x800000068 — packed ENTITY HANDLE, identical in BOTH states; (b) the 0x2A34xxx cluster (Army/Fortress/Combat/Input/Quest) AND Camera/State/Quest — measured the SAME in menu and open free-roam; (c) GM subsystem count in GM+0x6800..0x7000 — only 179(menu) vs 246(game), a fragile gradient, REJECTED. GameManager itself is LIVE in both states so it proves nothing alone. AIRE's Cortex.game_state() implements the correct rule.
  • The framework's GameStateTracker never reports ArmyMenu (MEASURED 2026-10-03): across 5 sessions with Army menu use (hires included) every "Game state changed" line was Unknown/Transitioning/InGame - IsArmyMenuOpen() (base+0x2A2E0D0 -> +0x1B0 -> [0]) does not fire, so isArmyOpen in ApplyActiveCheats is always false. Do NOT just repair the detector: ApplyActiveCheatsGuarded runs only while the state is InGame, so a working detector would STOP every cheat tick (merc hire-save clear included) whenever the Army menu is open. A replacement signal must be wired in without that gate.
  • Equipment offsets (BODY, HEAD, HAIR, HELMET, etc.) show 5-12% "garbage" on UNLOADED orcs (FM+0xD8 == NULL). This is heap paging, NOT wrong offsets. Always check FM+0xD8 before trusting equipment fields.
  • AD overlays: SMC is the rendering authority, not FM. FM AD offsets are lazy/cached and often NULL while SMC has valid data. Always write BOTH FM and SMC AD offsets.
  • FM+0x570 (Quiver) is NOISY — 73% quiver/empty but also contains shields (Orc_Shld), weapons (Orc_1H), and markers. Filter by record name before trusting.
  • NEVER bulk-mutate hot-thread GameDB domains (chaos-ladder forensics 2026-07-22, 8 crash-verified): NativeLife, Camera, Interface/WorldUI (Scaleform redraw), AudioHook RTPCs (Wwise thread), Profile (input bindings), AI/Sensors, _Structures* inline arrays. They tolerate FLOAT/BOOL/POOL mutation (L2-proven) but die on INT/VEC/ENUM-SWAP/FK mid-frame. Gameplay-config domains (Combat/AI/Faction/Quest/Inventory/Difficulty) tolerate everything.
  • Vec slots are pointers — never write 12/16 raw bytes at a vec field's slot (stomps pointer + neighbor slot). Deref first. Packed bools need single-bit RMW.
  • The C++ Engine tab's chaos ladder self-learns: every crashed run's last-logged category (logs/framework/diagnostics/chaos_run.log) is auto-banned on next run. Atlas-clamped ints only mutate within live-observed envelopes (sow_engine_atlasranges.hpp).
  • SAFE WORLD ROLL v6 (2026-10-19, built, cl /Zs clean, NOT run in game) - the Dashboard button crashed the game; a read-only twin of its planner against the live game measured eight causes (type 5 dereferenced as a vec pointer, shared vec blobs written in place, index ints moved, min/max pairs split, text keys moved across argument signatures, identity / streaming / save tables in scope, rig-bound names moved, summon catalysts moved). Rules + a time-budgeted, field-granular shuffle: ui/tabs/sow_engine_saferoll.hpp (its header lists them with the twin's numbers). The text table is read on a worker thread (the first roll of a session waits for it), every run pauses saving (above), and the crash-ban learner trusts only " v6 " run headers.
