REFERENCE RESOLUTION — the last 4%, closed and fully accounted (2026-08-04). The first pass resolved 82,361 of 85,771 references and left 3,410 "unknown". None of that shortfall was a decoder gap; it was three separate mistakes, each with its own fix:

  1. The lookup table was incomplete. record_to_category_map.json carries 153,977 of the 270,537 names the shipped GADBs declare, and stores ONE category per name, so it can neither answer for the other 116,561 nor express an ambiguous name. A miss there is indistinguishable from "not a record" — 122 of the "unknown" names were real records all along. aire/gamedb/record_index.py (call("record_index_build"), ~17 s) merges every GADB-bearing archive in archcfg order instead. +1,639 references resolved. CONSUMERS MIGRATED 2026-08-04. The complete index was added BESIDE the legacy file rather than replacing its readers, so Cortex._load_offline_data and EngineGraphBuilder._record_categories still served the old answers. Both now resolve through RecordNameIndex (legacy file kept only as a fallback, and the fallback says so in the log). Measured on the migration: 116,561 names the legacy map cannot answer and 56,640 ambiguous names it collapses to a single category — but 0 entries whose stored category is not a declaring category, so the legacy map was INCOMPLETE, never wrong. CompatibilityManifest now fingerprints record_name_index.json too; keying the graph only on the legacy map would let it go stale silently.
  2. DB<Kind> is the GADB TYPE NAME with its separators dropped (Faction.Trait -> DBFactionTrait, Combat.Attack -> DBCombatAttack), matched under the same normalization family the declared types needed (last segment, concatenation, de-pluralisation). That makes the kind a SCOPE, not just a label: it pins 20,248 of 27,695 ambiguous references (73%) to exactly one category. Verified on 5,000 scoped edges — 0 whose category disagrees with its kind. call("db_kind", kind=...) exposes it.
  3. _DBREF matches any DB<ident>.<ident>, and a layer's binary sections manufacture plenty (DB0ICB0ICB.x, DBM.I_). 769 references were regex artefacts. A kind is credible if it NAMES A REAL TYPE, or >=2 members resolve and it reads as a class or has >=10 hits, or it resolves once and reads as a class — that last clause exists because WeatherDefinition is real and appears once while F3FNE is not. Rejected references are FLAGGED noise with a reason, never deleted.

What genuinely remains is the GAME's own dangling data: 1,002 refs / 27 names. 954 refs over 19 names are absent_from_its_own_category — the kind names a real, populated category and the record is simply not in it (PC_Bip_Sync_Intrgtn_Idle in Combat/Attack, ChatterExplosionIncrement in AudioHooks/Keys, dx_ne_ps_ExecPace in AudioHooks/DialogEvents, and — conclusively — WhatEverWeNameThisOne in Presentation/Relays). The other 48 refs / 8 names have a near name in the target category (AI_BIP_PC_PreDeath_Humiliator vs ..._R) and are kept as LEADS, never auto-resolved: Pass_FearCam_PIS_Test_IT vs Pass_HateCam_PIS_Test_IT is a different record. call("world_catalog_reresolve") redoes all of this in ~1 s without re-sweeping the layers.

Trap avoided: the first sweep capped stored objects at 400/layer and silently dropped 59% of them (227,107 of 558,908). The richest layer holds 7,365, so the caps now sit above the measured maximum and exist only as a runaway guard — the re-sweep stores 558,908 / 558,908, 0 truncated. A per-layer named object is keyed by (layer, NAME); repeats inside a layer are counted in instances_with_this_name rather than overwriting each other.

STAGE CACHES ARE KEYED ON INPUT FILES, NOT ON STAGE CODE. Editing a stage leaves its cache valid, so the new logic never runs and the build reports success while silently omitting the new edges (caught when name-inferred stubs failed to appear). CORRECTED 2026-10-05: for ONE stage, bump STAGE_REVISION[<stage>] instead (aire/pipeline/engine_graph.py). THE SCRIPT-API PLANE IS JOINED (2026-08-04) — script_api stage, aire/analysis/script_api.py, call("script_api_build"), ~13 s offline. The graph could follow a scenario layer's Lua (DynamicObjectGroup.Create(...), cageDOG1.Script_SetState(...)) exactly nowhere: the plane was keyed by stub because the class name was believed unrecoverable.

The class name is in the stub — POSITIONALLY. Every binding is a ~90-byte LEAF stub that stores two strings in two ADJACENT stack slots and the CLASS is always the one at the larger offset:

lea rax, [rip + member]  ; mov [r11-0x20], rax   <- MEMBER
lea rax, [rip + class]   ; mov [r11-0x28], rax   <- CLASS
lea r8d, [r9 + 2]        ; declared arg count
call <registrar>         ; shared arg-count/diagnostic helper
call <implementation>    ; the real accessor

Frame size varies (-0x28/-0x20, -0x38/-0x30, -0x48/-0x40, -0x58/-0x50, -0x78/-0x70); the relative ORDER never does. This is why a frequency heuristic fails and position does not: ranking by how many stubs share a string promotes Serialize (125 stubs), Cast (124) and Create (123) — members that nearly every class registers — into the class column. That is the exact artefact behind the old "member list mixes methods with class-like names" ruling.

15 registrars, discovered by SHAPE not by address (a hardcoded single registrar found 1,574 of 5,923 sites): 5,923 stub sites, 5,498 decoded (92.8%) -> 144 classes, 1,560 members, 1,290 implementation RVAs.

THE CODE↔DATA BRIDGE — the weakest join, and how it was strengthened (2026-08-03). The original bridge was displacement matching: function -ACCESSES_OFFSET-> native_offset -MAY_MAP_TO_GAMEDB_FIELD-> gamedb_field. That is a SHORTLIST, not an identification — measured median 3, mean 63, max 3,820 candidate fields for a single offset, and only 34 confirmed matches (OFFSET_MATCHES_FIELD) in the entire graph. A displacement like +0x40 matches hundreds of schemas; treating that as a link would be a false identity claim. The schema builders give the SAME link as an identity, because it is a fact about CALLS: BUILDS_SCHEMA (1,042 builder→category, carrying the F1 match as confidence) and REGISTERS_FIELD (11,808 stub→field). Identity-level code↔data links went 34 → 12,884; 59.6% of fields now have an identified registering function and 37.2% of categories an identified builder. Spot-validated against independently documented facts: Client/PlayerMovement ← builder 0x843EDC (f1=1.0), BaseSpeedMultiplier ← stub 0x163580C. A second, WEAKER grade closes part of the rest: 1,340 builders never had their category resolved, but 85.7% of GADB field names are declared by exactly one category, so those stubs can be attributed by name. Emitted at confidence 0.5 with inferred_by: unique_field_name and kept a separate grade on purpose — the two-sided F1 match exists precisely because a one-sided name score once let a 63-field builder claim a 3-field category. Adds 855 edges; fields with a registering function 59.6% → 62.0%. The remaining ~38% is not a decoder gap. It belongs to the 1,723 categories with no identified builder, and those builders are mostly not GADB schema builders at all — of their stubs, 2,472 name a field that is not in the GADB and 1,597 are ambiguous. Chasing them further would add noise, not coverage. CORRECTED 2026-10-05 — it WAS partly a decoder gap, and the bridge now has READERS. The stub-only decode never sees a slot registered INLINE in the builder (GlobalVarUnlock in AI/Templates: 1,682 slots engine-wide) nor a self-contained first-field stub, and it identified categories by field-SET F1, which cannot use order. Reading the schema OBJECTS instead (see "GADB Field Bindings") binds 2,567 categories to their object EXACTLY through the engine's own type table (0 ambiguous) and, the part this note never had, names the functions that READ each field: 14,265 field nodes have a BINDS_/ACCESSES_GAMEDB_FIELD edge, all live-verified by the engine's own cached descriptor index (14,558/14,558, control 0/14,310). Registration links (REGISTERS_FIELD) say who DECLARES a field; these say who USES it.

THREE dispatch mechanisms reach a function, not one. callers_of now reports all three and unions them into reachable: direct CALLS (static call graph), vtable_refs (virtual dispatch — see the .bss a law above), and tail_calls (entered by jmp). The third was found by this audit: every GameDB schema builder is tail-called, so 0x843EDC — a function that demonstrably builds Client/PlayerMovement's schema — scored callers=0, vtable_refs=0 and reported unreachable. The static call graph records call edges only. The tail-call scan runs ONLY when the other two lanes are empty, so the O(1) fast path is unaffected. Bogus RVAs (including addresses inside .bss a) still report reachable: False. Trap: classify_rel32_hit returns {disp_rva, kind} and no mnemonic unless the disassembler was initialised — filtering on mnemonic silently matched nothing and made the whole lane read as "no tail calls exist". Filter on kind.

ROOT CAUSE OF THE CHURN: hashing a WAL SQLite file's BYTES (FIXED 2026-08-03). The fingerprint hashed resolver.db's raw bytes. resolver.db is a WAL database, so a checkpoint rewrites pages and the file digest moves while every table is unchanged — measured: all 15 tables identical in row count and values, sha256 f93c2089… -> 8c2f42fd…. The graph is keyed by that digest, so it minted a fresh empty 2 GB database on nearly every run (four distinct fingerprints in one afternoon: 3644081…, 3b3c9b9…, a5f790d…, 4d97004…). The earlier mtime fix was correct but addressed the wrong volatility. CompatibilityManifest._fingerprint_file now digests any .db/.sqlite input by its LOGICAL CONTENT — rows of every table in name order, skipping the volatile sessions/crash_log/sqlite_sequence bookkeeping — and drops size from the digest for the same reason. Measured stable across 3 separate processes; 0.25 s for 101,666 rows. It still moves when knowledge genuinely moves, including value-only edits like vtable_slot_counts_refresh that row counts alone would miss.

NEVER PICK THE GRAPH BY FILE SIZE — pick it by FINGERPRINT (2026-08-04). Sibling graphs are within ~0.2% of each other in size, so "largest wins" silently selects a stale one: the verify pass after adding the script-API plane read the 3,667 MB PREVIOUS graph instead of the current 3,660 MB one and reported script_class = 0, i.e. a correct build looked like a failed stage. Resolve through Cortex._ensure_engine_graph() (fingerprint) — note label_enrich's _graph_semantics() still picks by size and should be treated with the same suspicion.

THE GRAPH IS KEYED BY A CONTENT FINGERPRINT AND FAILS SILENTLY WHEN IT MOVES. _ensure_engine_graph names the DB engine_graph_<sha256[:16]>.sqlite over the CONTENT of resolver.db + tuner_offline_schema.json + field_hash_dictionary.json + record_to_category_map.json + the exe + the archive inventory. Any content change correctly mints a NEW database — but nothing carried the old one forward, and every lookup returned ok: true with nodes: 0 and node: null, which is indistinguishable from "this function is not in the graph". RecordLink Spine — the cross-session primary key (BUILT 2026-08-02)

aire/pipeline/idmap.py. Live keys records by heap ADDRESS (dies with the process) or by NAME (ambiguous — see below); disk keys them by ORDINAL, RL = (cat_idx * 16) << 16 | rec_idx, which is unique and survives every restart. The Cell Identity Law proved the bijection in 2026-07; this materialises it, so a finding from session N re-points in session N+1 instead of being re-resolved by name with the ambiguity risk each time.

  • Alignment is MEASURED, never assumed: audit_alignment() reads real record names on both sides. Result 1.0000 — 2,742/2,742 categories matched, 278,865 records on each side, live-only = disk-only = 0.
  • Fast because it is CATEGORY-level: ~2,742 category headers read; record addresses are COMPUTED (rec_array + rec_idx * 0x28), never enumerated. This is what retires the "never use resolve_record, hand-walk the table" workaround — the walk IS the tool now.
  • Session cache guarded by (pid, base, module_size); a cache from a dead process is refused.
  • Live table slots holding stray pointers are rejected by a printable-alphabet check — without it the walk reports ~200 garbage "categories".

Primary Records — the other 60% of the GADB (CRACKED 2026-08-03)

The RecordLink spine originally addressed 278,865 secondary records = 40.1% of the database. The other 415,767 are PRIMARY records — the inline struct-array entries of 736 _Structures* categories. RecordLinks point at them, but nothing could resolve them.

category +0x40   u32 primary count        (400/400 categories == disk count)
category +0x48   primary record array     (stride 0x20, 250/250)
primary  +0x00   u32 field count
primary  +0x08   schema ptr
primary  +0x10   instance ptr             (slot law holds: instances packed fc*8 apart)

A primary header carries NO 0x0A tag byte. A secondary starts 06 0A 00 00, a primary 06 00 00 00. Every structural scan in the codebase keys on byte[1] == 0x0A, so primaries return ZERO hits and look like they do not exist. That single byte is why they were invisible.

Validated 736/736 categories against the disk primary count, 0 mismatches; decoded values are semantically coherent (_StructuresFactionDifficultyEntry primaries decode to the difficulty bands: [55,9999]->Enemy_VeryHard, [30,55]->Enemy_Hard, [10,30]->Enemy_Easy).

Spine coverage is now 278,865 + 415,767 = 694,632 records = 100% of the GADB — a number that independently equals the engine graph's gamedb_record_entry node count. addr_of resolves a primary-target RL to a live address, and disk_delta's rl_target_primary skip lane is gone.
