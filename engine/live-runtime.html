Live VFS — assets served live, no file change (PROVEN IN-GAME 2026-09-24)

The engine resolves EVERY asset path through one priority vector on its file system object (static base+0x2A54600, getter 0x3DDD34). Index 0 is consulted first:

fs+0x00 SRWLOCK (resolvers shared, Mount exclusive)
fs+0x68/0x70 MountEntry {u32 kind, Source*} 16 B   kind 0 CArchiveTree vt 0x22C21B8
fs+0x78 u32 capacity                                kind 1 DirectorySource vt 0x22C21C8 (+0x10 "dir\")
fs+0x80 hash->path table {u32 P919, char*}, fs+0xC0 its generation
fs+0xE0 archive-scan bound = last kind-0 index + 1

A DirectorySource answers with GetFileAttributesW(dir+path); a hit stops the archive search and the loader opens the loose file itself (0x529BF8 -> GetLooseFilePath 0x52A2F8). Retail already mounts ..\Game\ as the last entry — that is how Game\cinematics\*.vib ship. Mount(fs, Source** out, path, r9 unused, index) = 0xC28560 is what -arch and the runtime DLC mounter call; there is no remove slot, so unmount = erase our row under the exclusive lock, recompute +0xE0, keep the refs (never run an engine dtor from framework code).

Framework packets/sow_live_vfs.cpp + AIRE link ops 30-35 (they bypass the world-state gate). A staged mod IS a mountable folder, so a mod goes live in place:

call("live_vfs_mount", mod="dark-ranger")   # index 0, NEW paths registered, verified through
call("live_vfs_unmount", mod="dark-ranger") #   the engine's own GetLooseFilePath (24/24)
call("live_vfs_status") / call("live_vfs_fs")   # framework view + uncached outside read

Proven 2026-09-24: dark-ranger mounted live -> unequip, fast travel, re-equip Ranger armor -> the modded look on screen, with no archive and no archcfg line; nothing survives a restart. A mount changes the NEXT load only — re-stream the asset to see it. Read the vector with raw_live(): raw() is region-cached and reported a stale vector after four mounts.

Live Lua — our own scripts in the engine, no hook (PROVEN IN-GAME 2026-09-24)

The scripting VM is HavokScript (Havok's Lua 5.1 fork; libs table 0x21DAEB0, source compiler present, hstructure/hmake). Main VM: GameManager+0x6CE8 -> CScriptVM (vt 0x230EF00) +0x58 -> lua_State (+0x10 global: +0x560 compiler settings, +0x588 panic 0x1CFEEB4; +0x48/+0x50 api top/base; 16-byte slots {u32 tag, value}). The engine is pipelined (MainThread / RenderThread) and the link tick runs on the render thread, so the main VM is never called — it is read only.

sdk/sow_live_lua.cpp (AIRE link ops 36-38) builds a private VM with the engine's own CreateVM 0x1CFE890 + SetupVM 0x1CFEBCC, then replays RegisterAllScriptBindings 0x1C01778 piece by piece against it (its helper 0x1D87644 registers into the MAIN VM through the global agent GM+0x6CF0, so it is replicated, not called; every other piece reads no GameManager — 181/18/18/30-36 functions scanned). The master binder 0x1B9F69C gets a stand-in agent: slot 1 returns our state, slot 14 (RegisterEvent — lets the engine call INTO a VM) is a no-op.

call("live_lua_exec", code="System:ChangeForecast(DBWeatherForecast.None) "
     "System:ChangeWeatherPattern(DBWeatherPattern.MI_Night_PartlyCloudy_Rain_Light) return 'ok'")
call("live_lua_probe") / call("live_lua_reset") / call("live_lua_explore")

Proven: that call turned Minas Ithil to night rain on screen. DB<Kind>.Name resolves through WBDBRecordLookup (enum _hcat = live category, P919 hash, BinarySearch 0x278540). Rules, each measured by a fault (SEH-caught, VM retired, game unharmed): - Call engine methods ONLY in the shape shipped scenario Lua uses (aire/data/world/scripts, colon form System:X(DBKind.Name)). Natives do not validate arguments and engine asserts are null writes — System:GetRegion() (never called by shipped scripts) faulted. - NEVER tostring() or return a record: SScriptRecord::ToString faulted. Chunks return strings. - Anything that DISPATCHES to script listeners runs in the MAIN VM: System:ActivateRemoteScript is ScriptBus Notify 0x605990, which calls the GLOBAL agent (GM+0x6CF0) slot 6 per listener — from the render thread it faulted. Safe: calls that set engine state (weather) or queue work. - No instruction limit (no debug.sethook): a chunk that never returns freezes the render thread. - A VM costs 20 MB and cannot be freed; a faulted VM is retired (cap per process).

Main-thread Lua — a poller delivered as content (PROVEN IN-GAME 2026-09-24)

Anything that DISPATCHES into the game's scripts (remote scripts, quest relays, object events) must run on the main thread, and the no-hook rule stands. aire/pipeline/main_poller.py injects a poller into region layers' script parts and serves them through Live VFS:

  • A layer's script is a bare SCRI payload: "SCRI" | u32 1 | u8 1 | u32 len | Lua text. The chunk ends _G.loadedresource = section_<hash>; entries are script threads function(self, threadId, scriptId) that may LithThreadSleep(threadId, s).
  • Parts resolve BY PATH. Patch archives ship <layer>.scripts STANDALONE (DLC2/3/4) and they win over the copy inside the .embb — a rebuilt container changed nothing. Serve the part itself. The DLC5 .bndl sizes match those standalone parts, not the base container.
  • Compiled scripts are cached per VM (0x6A60EC skips the compile when reinstall[id] is set - CORRECTED 2026-09-26): mount at the MAIN MENU of a FRESH process, then load. Quitting to the menu does not reliably rebuild the VM.
  • *.SC objects are StartupCommand; wrapping their _<prefab>_SC_Script_<hash> entries gives engine-started threads. A pool (2 standbys per layer across night01, t1/t2postfallprops, ambientpostfall/prefall) with one owner and a shared tick keeps one poller alive.
  • The game PAUSES its simulation while its window lacks focus — every script thread (the poller included) waits; the render thread keeps running. A stale heartbeat usually means "tabbed out", not "dead"; live_main_exec queues and runs on return.
  • Proven: System:ActivateRemoteScript(DBRemoteScript.MI_HideKeep) then MI_ShowKeep (user saw the keep hide), MinasIthil_EnableCurseBarrier, ScenarioEventStartLarge (fired; no visible effect — context-gated). No SEH on the main thread: an engine fault there crashes the game.
call("live_main_mount")                        # at the main menu, before loading the save
call("live_main_status")                       # heartbeat: tick, owner, pool, owning layer
call("live_main_remote", script="MI_HideKeep") # a RemoteScript by name, shipped call shape
call("live_main_exec", code="return System:IsDayTime()")
call("live_main_cancel")                       # drop a queued command

The framework's own bridge — World Scripts v2, always on (PROVEN IN-GAME 2026-09-26, all regions)

sdk/sow_main_bridge.hpp + sdk/sow_poller_build.hpp + sdk/sow_main_native.cpp do the above natively for every user (no AIRE): the DLL builds region-wide hosts from the user's own archives (118 parts, Lithlad via a source wrapper that loadstrings the precompiled chunk), checks the build stamp at launch, arms at the main menu by default, and reports one region-aware verdict (GetCoverage()). Laws, each measured by a failure: - Compiled layer scripts are cached for the whole process in the main VM global reinstall (0x6A60EC: reinstall[id] nil -> compile the buffer, set -> reuse; not resources[id]). A region first loaded before the mount can never host that launch - arm before any save loads. - result.txt is written in text mode (CRLF). Compare the head with the \r stripped - with it left in, no result ever matched and every command stayed "in flight" until cancelled. - cmd.lua is never cleared and a new process has no memory of what ran -> a leftover command replays next launch (an object address from 02:42 ran at 19:09 and faulted in SetState). Reset it at launch and after every result; native chunks check the pid op before touching addresses. - Refresh the heartbeat from the frame tick, not from a panel: Alive() read a snapshot only the World Scripts panel updated, so every other caller saw a frozen status. - Region = FortSys+0x1B0 record name lower-cased (= build folder). Cancel an in-flight command on a region change; loads read the region as "" briefly, so compare against the last non-empty one.

World Scripts v3 — the native main-thread pump (IN-GAME CONFIRMED 2026-10-05, Lithlad)

Layer hosts die with their layers (save reload, fast travel inside a region, Army menu) and on 2026-10-05 never started at all in Lithlad on a fresh launch (chunk compiled, no StartupCommand entered). sdk/sow_main_pump.{hpp,cpp} runs the same poll() from the window procedure, which the engine's own loop calls on its main thread. No hook, no content, no layer dependence. User-confirmed: runs in Lithlad (log running on the game's main thread ... frame wait, merc camp's merc_fill through it), INSIDE THE ARMY MENU (an Army Grid captain edit fired there, which the hosts never could), and across a fast travel Lithlad -> Nurnen (waited out the load, resumed by itself); 1,032 runs, 0 refused contexts. Not yet observed: a save reload / same-region travel. - The frame: main loop 0xC25568 -> app object [base+0x26FEFD8] (vt 0x1FFE760) slot 33 (+0x108) then slot 29 (+0xE8) -> PeekMessageW(&m,NULL,0,0,PM_REMOVE) + DispatchMessageW at 0xC2589A -> Sleep limiter. The game window belongs to the main thread. - Ring 0x272E8D8 = main->render command buffer (0x381FCC posts {0x1EE088, ctx, fn} with an UNLOCKED bump alloc - never post from another thread; consumer = render thread, 0x1CEE78). The main thread's frame wait (slot 28 0x380FAC -> 0x38105C -> 0x1CF430) is backpressure for ring space, and it pumps messages through 0x6EE5D0 (dispatch 0x6EE670). Both pumps share re-entrancy byte 0x277DBB0; other pumps (0x10129AC..0x101CF03) are display-mode code. - Execute only in a known context: first game-image return address 0xC258A0 (loop), or 0x6EE676 with 0x6EE5F6, 0x101550E, 0x3810BC, 0x380FDA, 0x38085C, 0xC25621 beneath it. - Main VM from C++: LoadBuffer 0x55B920(L, [L+0x10]+0x560, ...) + Pcall 0x406344 on [[GM+0x6CE8]+0x58]; restore the API top (L+0x48/+0x50), never clear it - the engine owns it. - Script-only natives FAULT from the bridge (MEASURED 2026-10-15, one fault + code). The engine keeps a running-script stack: depth u32 [0x2702540], entries 0x277C1B0 + i*0x80 (max 16; depth 0 = static 0x2680000), entry +0x28 = the running script's NAME. 0x503EF8 returns top+0x28; NPC::SetAlignment 0x7D2ED4 asserts ("This function should only be called from script code", null write at 0x819113) when that name is empty. Only the engine pushes: the __eventmap dispatcher 0x406538 (push 0x4066B8 -> 0x5029D0 -> 0x502A00 -> 0x502A44, which always writes a name, "Invalid" at worst; pop 0x406744 -> 0x115F8E0), the resource loaders 0x4FD9C0 / 0x4FEFA8 and 0x4A6088 (via 0x4A61A0). LoadBuffer + Pcall pushes nothing, the null write is not a Lua error, and the pump stopped itself for the launch (a pit-fight test: "Nothing has happened"). Direct users of the name (callers_of 0x503EF8, complete): NPC::SetAlignment, CPlayerObj::SetAISpectatorInvisible, player vf32 SetHidden (log only, behind debug byte 0x2A34C0B), 0x1BA7C8C, 0x1BAE1F8 (SetRetreatingEnabled), 0x1D86F28. Run such calls INSIDE an engine-dispatched handler (a layer script's __eventmap entry, e.g. its ScriptTimer's TimerTick) and let the bridge only queue requests. Despawn (0x1A8BA4C) never reaches the stack (4 levels). - One command, many runners: de-dup is the main-VM global _G.__SOWCE2_LAST (v1: _G.__SOWCE_LAST); every runner is on the one main thread, so hosts, the pump and AIRE coexist. - A runner that never dies must cancel on loads: an in-flight command is cancelled 1 s after a new World06cTask unless its result exists (a command that STARTS a load writes its result after creating the task). Gate: spawned > 0, settled 1.5 s, no new load task in 3 s. - Steam's overlay inline-detours PeekMessageW/DispatchMessageW (jmp relay); unwinding is unaffected. - ~~AIRE xrefs_to does not see IAT call [rip+x] sites~~ FIXED 2026-10-05: the xref index decodes them and names the slot from the game's real IAT (.xtext 0x1D92000+, 1,164 slots; the import directory only lists the protector's 199+11-entry stub table).

World scripts on disk - the shipped Lua corpus and HavokScript bytecode (MEASURED 2026-10-27)

Every world layer's script is a SCRI payload ("SCRI" | u32 1 | u8 flag | u32 len | body; flag 1 = Lua SOURCE, 0 = HavokScript BYTECODE), shipped as a standalone <layer>.scripts entry (patches; it wins) and/or a SCRI section in the layer's EMBB container. Census (call("world_scripts")): 3,829 source payloads (2,562 distinct) in every region; 480 bytecode payloads (117 distinct), all in desert, 0 errors. The sources are the authored scripts (comments, hstructure layouts, hmake), cached by sha1 in aire/data/world/hks/sources/.

  • world_script_search(query=...): every script that says it, with the layers that ship it (Script_SetState: 1,370 of 2,562 scripts, 22,888 lines, 6 s).
  • world_script_source(label=...): the shipped text of one layer, patch copy first.
  • hks_disassemble(label=...) / hks_verify: lossless bytecode listing (117 / 117 byte-identical round trips) and the operand oracle (0 violations over 2,040,690 instructions; controls 9,935 and 141,077).
  • hks_decompile(label=..., name=...) (BUILT 2026-10-27, aire/formats/hks_decompile.py): bytecode -> Lua. 617 / 617 desert functions with a shipped same-named source match it (call multisets, string literals); 117 / 117 chunks structure completely; 210,926 / 210,926 calls conserved. world_scripts_decompile_all writes them so world_script_search covers desert too. Names (2026-10-28): 82.7% of the source's own local / parameter names reproduced from code evidence (local SO = ScriptObject.Create(scriptId, "SO")), control 0%.
  • VM and chunk format with engine RVAs (dispatch 0x1D88000, table 0x1D8B208, loader 0x1D1A234): aire/documents/HAVOKSCRIPT_BYTECODE.md.

Desert (bytecode-only) objects still get source: 60.2% of their distinct bound functions are defined by name in another region's source, and same name = same code (616 / 617 by constants, control 33 / 617); world_object_script returns it with provenance (HAVOKSCRIPT_BYTECODE.md s5). For mods: read and search the source here, change behaviour by running a modified copy through Live Lua above. A script is a game FILE: serve changes live, never write the install.

Where it lives. core = [base+0x2A86750] = the bundle owner + 0x30 (kb/live-bundles.md; owner built by 0x119E5D4, the stages by 0x1183E8C). Open stage core+0x20, load stage core+0xF8, parse stage core+0x1F0. Each thread's argument is its own stage (3 / 3 measured): ResourceOpenThread 0x11AECC8, ResourceLoaderThread 0x11AEE50, ResourceParserThread 0x11AEF58.

Stage layout. - Open / load stage (0xD8 / 0xF8 B): two 0x38-byte queues at +0x00 / +0x38, the KRAKEN thread object at +0x70, CRITICAL_SECTION +0xA0, work event +0xC8, stop event +0xD0; the load stage adds the path table at +0xD8. A queue = double-buffered vector of 16-byte {object, control block} handles (make_shared): in {+0x00 begin, +0x08 end, +0x10 u32 cap}, out {+0x18, +0x20, +0x28}, +0x30 u32 high-water, +0x34 u32 count. The consumer swaps in / out and reverses the run, so service is FIFO; the runner takes the FIRST non-empty queue, so queue 0 always drains first. - Parse stage: request vector +0x00 (pushed by 0x3DD248 under the lock +0x60), a second vector +0x18 (cap 0x80, lock +0x88, consumed by 0x3DC654 - LEAD: what it carries), thread object +0x30, work event +0xB0, stop event +0xB8. - Bytes [base+0x262B520 / 521 / 522] switch the open / load / parse THREAD on; 0 = that stage's work runs inline in the caller (live 1 / 1 / 1). [0x27C4EE8 / EE9 / EF0] turn on per-stage QueryPerformanceCounter timing (live 0).

SResourceLoadRequest (make_shared, no vptr; its destructor 0x3DD77C carries the name in "SResourceLoadRequest is destroying a finalized CResourceData"):

off field
+0x00 the opened file (vf0 closes it); null until the open stage ran
+0x08 u8 cancelled: every stage skips a cancelled request
+0x10 CResource (+0x28 the path) - a resource request
+0x18 stream detail (set by 0x3DD548 from the texture streamer's argument)
+0x20 u32 queue: 1 when the path names a .tex0 / .texuhd tier (0x3DD45C), else 0
+0x28 CResourceData (+0x18 u32 state; the destructor asserts on 3 = finalized; +0x10 -> +0x08 = the type that receives the parsed data)
+0x30 CResourceBundle - a bundle CONTENT request: the path is the bundle's .embb at +0x70
+0x38 / +0x40 the bundle load's out slot and u32 argument

The flow (each hop is a call in the code): submit 0x3DDDEC (open stage, or straight to the load stage when the open thread is off) -> open 0x3DD588: skip if cancelled; 0x3DD5C8 picks the path (+0x10 -> +0x28, else +0x30 -> +0x70); 0x3DD648 WAITS on the semaphore at core+0x7B8, then opens the file through the file system at 0x2A54600 (function-local static, 0x3DDD34) -> push to the load stage -> load 0x2D3444: a resource goes to 0x3DCFDC (reads the bytes into a new CResourceData at +0x28, 0x3DCF80) and on to the parse stage (0x3DD248); a bundle content request goes to 0x3DBE50 (bundle, file, +0x40, the path table, +0x38) -> parse 0x3DD2A8: releases the semaphore slot (0x3DD424), parses (0x3DD3C4 with the data and the path), hands the result to its type (0x3DD310). The global path table (load stage +0xD8 = core+0x1D0): a sorted vector of {u32 P919(path), u32 0, char* path}, 30,639 rows, 30,639 / 30,639 ascending, 503 / 503 sampled keys = P919 of the path; capacity 30,656.
