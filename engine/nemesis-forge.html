The Nemesis Forge: imported captains

Shadow of War's own importer for a player's Shadow of Mordor captains: the title-configuration switch, the check at world entry, the two captains the online reply stores, the 13-key payload, the two story jobs that use them, the import through the pool, the conversion tables and the builder, the creation mark and the introduction sim event, the look replayed from the seed with Mordor's own generator, Shadow of Mordor's captain document, War's member documents and their readers, and the console commands.

Shadow of War ships an importer, the Nemesis Forge, that rebuilds a player's Shadow of Mordor follower and nemesis as War captains (Mordor is "Firebird" and War "Kraken" in its names; compiled from ...\KRAKEN_CODE_STREAM\source\Game\Shared\NemesisForgeUtils.cpp, log tag [NEMESISFORGE]:, the logger compiled out of the shipping build). The captains came from the publisher's online service, never from Mordor's files, and enter the game through two story missions; the import itself is an ordinary member build fed by a 13-key payload and a set of conversion tables.

The chain

title configuration key nemesis_forge (bool) -> parser 0x18368B0 -> [GM+0x6D48]+0xD1
world entry 0x1E3E78 (its only caller) -> check 0x1B3ABFC on the online manager [GM+0x6D30]
  stop if a captain is already stored (+0x38, +0x80) or Invasion/Settings.HaltNemesisForgeCheckPredicate holds
  -> request 0x1B3AA94: stop unless the switch is on; stop while one is in flight (+0x28)
  -> reply 0x1B3D500: Follower[0].attributes -> parser 0x1B3A148 -> +0x30 ; Nemesis[0].attributes -> +0x78
quest job filler 0x1BD40C4 (a story mission's job setup)
  -> UseNemesisForgeAlly (Rat3_Ally1, "Damaged") takes +0x30 ; UseNemesisForgeNemesis (CapChief_HighPIS, "The Arena")
     takes +0x78 ; no valid payload -> the job fills the ordinary way
  -> 0xF636F0(FS, payload, job context) -> 0xFD51A0(the region army's context, payload, ...) -> 0x1BC05D0
     -> conversion 0x1C6369C -> builder 0x1BBF928 -> its Firebird look branch 0x1C04F20 -> FM+0x520 = 4
     -> creation sim event NemesisAlly_Levels (a PromoteEmpty event seats him) ; telemetry 0x1B2CC68 (event 42)

The switch and the check

The title configuration's boolean nemesis_forge is stored at [GM+0x6D48]+0xD1 by the configuration parser 0x18368B0 (at 0x1836A6F, through the bool reader 0x17C6F50; its neighbors are ssc_version +0xC8, garrison_size +0xCC, challenges_enabled +0xD0, conquests +0xD2, purchase_system +0xD4 and ps2_epoch +0xD8). The same parser reads two keys named for the import's telemetry event, Events_NemesisForgeImportEnabled and Events_NemesisForgeImportSampled.

The check 0x1B3ABFC has one caller, the world-entry routine 0x1E3E78 ([ENTER_WORLD_HANG_DETECTED]). It returns while either stored captain is valid, and once the halt predicate holds: Interface/Predicates/GameState::IsPastNemesisForgeUsage, a _StructuresUIGameDataPredicates {GameData/Variables::StoryState, GameData/Predicate::StoryState_300+}, true from StoryState 300, the end of the campaign. Otherwise it tail-jumps to the request 0x1B3AA94, which returns unless the switch is set and no request is in flight. The request carries the player's FirebirdProfileID (when one is known), the platform user id, the platform and the web environment, and registers 0x1B32CD0 as its completion handler. FirebirdProfileID ([0x2A364F0]) is a static string initialized empty (0xC2D10, default at 0x1DB10E0) that no code writes (its 3 references are the initializer, its exit cleanup 0x10820B0 and the request), so the request identifies the player by platform user id only. The game therefore asks on every world entry until it holds a captain or the campaign is over.

The online manager [GM+0x6D30] (see Saves, the store and the network layer) keeps the forge's state:

Offset Meaning
+0x28 u8, a request is in flight (set by 0x1B3AA94, cleared by 0x1B3D500)
+0x30 the follower payload (0x48 bytes; valid byte at +0x38)
+0x78 the nemesis payload (0x48 bytes; valid byte at +0x80)
+0x468 the Invasion/Settings record (HaltNemesisForgeCheckPredicate)

The reply and the payload

On success the handler 0x1B3D500 checks that element 1 of the result is a map (engine value type 6), reads its Follower and Nemesis lists, and passes the attributes map of each list's first object to the parser; on failure it only clears +0x28. The parser 0x1B3A148 fills a payload object (vt_0x1FCB338, 0x48 bytes) from exactly 13 keys and sets its valid byte last:

Payload Key Type Used by the conversion
+0x08 (valid) u8 = 1 tested by every consumer
+0x0C CombatTreeRecord name hash the class template and War's Combat/Tree
+0x10 FactionRecord name hash never; the parser stores the tree's value here (0x1B3A1AC reads the tree key's register)
+0x14 NameStringIdHash name hash the name, when War's string store has it
+0x18 PersonalityRecord name hash FirebirdFactionPersonality (no fallback)
+0x1C RoleRecord name hash FirebirdFactionRole, else War's own roles
+0x20 RowRecord name hash never
+0x24 ScarTypeRecord name hash FirebirdModelScarType
+0x28 ISCurrent int never
+0x2C MenaceLevel int the level
+0x30 RandomSeed u64 the look, and the builder specification's +0x170
+0x38 IsBranded bool the player's follower (specification +0x17D)
+0x39 IsWarchief bool never
+0x3C / +0x40 TraitList count, pointer to 32-bit hashes the traits

Every record value is the 32-bit name hash of a Shadow of Mordor record. No look, color or memory travels: the look is rebuilt from the seed.

The two jobs and the two missions

Quest/Jobs/Definition (849 records) has three bools the job filler 0x1BD40C4 tests before filling a job the ordinary way: UseNemesisForgeNemesis (0x1BD3494), UseNemesisForgeAlly (0x1BD344C) and UseOnlineArenaOpponent (0xF729F0 -> 0xFA2F60, the online arena). One job carries each forge flag:

Job Flag Takes Setup -> quest Ordinary builder Notes
Rat3_Ally1 Ally the follower Rat3_Captains -> Quest/Quests::Ratbag3, "Damaged" (an allied captain while the player retakes the fortress from Brûz) Rat3_BackupAlly1 (all 5 trees, Captain armor, MinLevel 12, enters through Builder_EnterHierarchy_Rat3) row rank Captain, a living player follower, no ologs; reward Ratbag3_ProtectAgainstForgeAlly, a marker the hierarchy-duel jobs NemesisAlly_Other* exclude
CapChief_HighPIS Nemesis the nemesis Gon2_Fighters -> Quest/Quests::Gondor2, "The Arena" (Minas Ithil's arena) CapChief_HighPIS (5 trees, Roles_who_are_unimportant, MinLevel 14, reward GP_Gondor2_Cap1) AlwaysUseBuilderRecord; the setup awards intel level 2

With a valid payload the filler makes the captain, fm = 0xF636F0([GM+0x6C68], payload, job context), keys the job to him ({FM+0x178, FM+0x174}) and sends the telemetry event 0x1B2CC68([GM+0x6D18], fm, is_follower). Without one, the job's builder record makes an ordinary captain, so both missions play the same either way, and the forge only ever showed in those two missions, before StoryState 300.

The missions' world scripts stage the result (2 classes, 7 of the 2,679 script bodies):

The script fires the faction event AddNemesisAlly (one level more and the sim-event tag NemesisAlly, which is never removed; the member is the ambusher).   • "The Arena" (worlds\retail\minasithil\sectionsandlayers\narrativequests\gondor2.scripts, class gondor2_Go02_SO_Script, method Captain4Spawn, prefab gondor2_gangspot.prefab06c): the nemesis is the fourth captain. The script uses GP_Gon2NemForgeCheck (a saved marker item with no data test of its own) and NemesisStory_NemesisForge_AuxBanner_IT (saved; its UI data NemesisStoryUI_NemesisForge, name UI_Nemesis_Forge = "Nemesis", gives his nemesis story a banner), plus the arena champion items.

The import

  • The pool. 0xF636F0(FS, payload, r8) takes the current region's army (FS+0x1B8 -> its context) and tail-jumps to 0xFD51A0(context, payload, r8). That allocates a member in the army's pool (0x1BD2E20; r8 is the job context, 0 from the console), sets FM+0x178 and, when empty, FM+0x180, and calls 0x1BC05D0; it removes the member again when his name hash is one of five keys reserved for Ratbag.
  • The conversion 0x1C6369C fills the builder's specification:
Input Conversion Specification
tree the template (0x1C76C68) and War's Combat/Tree (0x1C76C0C, 0x1C4EDC0), both found with the same hash class
seed copied +0x170
personality FirebirdFactionPersonality.KrakenPersonality (0x1C76F10; no row maps to nothing, 0x1C62B24)
role FirebirdFactionRole.KrakenRole (0x1C770BC); a hash with no row is searched again in War's Faction/Roles/Definitions by the same hash, so a Mordor title War also has comes through as War's +0x148
level max(MinXPLevel, MenaceLevel + 1) - 1 (0x114FFD0 is an unsigned maximum; every template's MinXPLevel is 14, so never below level 13, shown 14) +0x178
IsBranded copied +0x17D
name kept (0x1C62ABC) only when War's string store has the hash (its slot 8, a has-test); otherwise the builder gives him a War name
scar type FirebirdModelScarType.KrakenScarType (0x1C77158) +0x158
traits each through FirebirdFactionTrait.KrakenTraitPicker (0x1C774B8; a trait with no row skipped) -> 0x1C62AA4, then the template's TraitMarkers (Marker_OrcRarity_Legendary, 0x1C4EE48)
  • The builder 0x1BBF928 then runs as for any builder-made member, and for an import its Firebird look branch 0x1C04F20 (below).
  • The creation mark FM+0x520 (u8, saved by 0x594788 and loaded by 0x1BC0F2C) records how a member was made: 0x1BC00C8 writes 0, 0x1BC02AC 1, the builder build 0x1BBF928 2, the preset path 0x1BC06C0 3 and the forge's 0x1BC05D0 4, after the builder's 2, so an import reads 4.
  • The introduction. The template's CreationSimEventPicker NemesisAlly_Levels (job NemesisAlly, tag list NemesisAlly) runs the sim event NemesisAlly_Levels: participants NemesisAlly, PromoteEmpty_* events, the subject always wins, world-UI presentations, nav markers always shown. That event seats him in an empty seat; the payload's RowRecord is never read.

How the tables are searched. vt_0x1FBD460::vf3 stores the categories the import uses at 0x26FFEE8 .. 0x26FFF28 (templates [0x26FFEE8], roles [0x26FFF18] then War's own [0x2701D70], traits [0x26FFF20], personalities [0x26FFF28]). Every lookup is a binary search of the category's record array by hash (0x1C77018: BinarySearch([cat+0x38], hash, [cat+0x28])) that ignores the category's "unsorted" byte +0x30; all six Firebird tables ship sorted. Rows the engine's gamedb_patch merge appends to a category are therefore in the table the import searches, but are found only where their hash sorts. And because one hash picks both the template and the tree, a template can be replaced by name (the merge's override, 0x4BAB60 -> 0x17675FC) but not added for a single captain.

The look: Mordor's generator, replayed

The payload has no look; the builder's branch 0x1C04F20 (one caller, at 0x1BBFA6E) rebuilds one by replaying Shadow of Mordor's own generator over the Firebird tables, from RandomSeed:

  • Scale: t = float32(low32(xorshift64(seed))) * 2^-32 (0x1C5B76C -> 0x17956D4, shifts 13, 7, 17; the constant 2^-32 at 0x202ED88), Mordor's size rule.
  • The random stream: 0x1C76F8C(rng, min, max), the engine's 64-bit generator state = state * 0x0BB38435 + 0x3619636B, value (state >> 32) / 4294967295.0 scaled into [min, max], starting at the seed itself. The same constants sit at 136 places in Mordor's executable and 86 in War's.
  • Picks (0x1C767E0): the weights summed in float32, nothing when the total is under 1e-4, one draw in [0, total], the first entry whose running sum reaches it; at most 32 entries, in record order.
  • Order, as Mordor draws: body (0x1C76238: the template's Models entries whose RequiredScaleRange, a float-pool pair, holds t and that have a body piece, weighted by the piece's SelectionWeight), armor (a spent draw), head (0x1C763EC, the entry's heads), helmet (spent), hair (0x1C7632C, only with CanApplyHair: the head's hair pieces), legs (spent), one spent draw per NumAccessories, then nine colors.
  • Colors (0x1C7686C and its eight siblings -> 0x1C7664C): a weighted pick of a Firebird color entry (0x1C76B24) gives a War color setup (KrakenColorSetup) and a color id (ColorId, one of 15: Red, White, Fleshtone, Grey, Black, Blue, Brown, Yellow, Blue_Rare, Charcoal, White_Rare, Green, Brown_Rare, Green_Rare, Purple). War's entry of that setup with that FirebirdColorId (94 of War's 542 color entries carry one) is rolled (0x1158AC, HueDeltaRange) on a copy of the state, and then the Firebird entry's NumRandomCalls draws are spent on the real state to stay in step with Mordor's color roll. Each entry's AppearanceTag is applied (0x2EA128). The palette entry is chosen through 0x2EBB4C before each tint: skin 0, eye 1, clothing 7, tattoo 3, paint 4, hair 2, armor 1 to 5 and armor 2 to 6; the leg-leather roll goes to a local the branch drops, so 8 of Mordor's 9 colors land.
  • What lands: the template's base model (orc_anim_base) at appearance +0x20, the head record at +0x170, the combat tree, the body type at +0x00, and SetPieceSlot 0x4C62EC for slot 0 (the body's KrakenModelPiece), slot 1 (the Head of the KrakenHead record), slot 2 (hair), with slot 7 cleared. Armor, helmet, legs and accessories are not carried: their draws only keep the stream aligned.

For a Berserker the body is Smp_Orc_Buff_Torso01 for t in [0, 0.5] and Smp_Orc_Stk_Torso01 for [0.5, 1.0]: the Berserker's and the Defender's Slim entries have no body row, so War draws such a captain Buff. Templates without CanApplyHair (Berserker, Defender) never get hair. The entries are full per body: 11 of 11 hold 10 heads, every entry of one body lists the same 10, and Archer and Spearman have one Slim entry; the limit is the 30 head rows (24 War heads).

The replay equals Mordor's own roll. Read live from 48 captains of a Mordor campaign army, 28 are "plain generated" (his head record is in the head list of an entry whose body is his body): his own seed draws his head for 23 of 28 and his body for 26 of 28. The control, seeds swapped between captains of the same class, draws the head for 17 of 253 (6.7%) and the body for 180 of 428 (42.1%, mostly the scale band). The other 20 wear heads that have no Firebird row (17 DLC1_, DLC2_ and GI_ heads, GraugRider twice, OrcBuff16): Monolith's tables carry the base game's generated heads only. Because the look depends on nothing but the seed and the template, the seed in the payload decides the face an import wears.

Shadow of Mordor's side

The two games never exchange data directly: no string in Mordor's executable names War (Kraken, ShadowOfWar, Shadow of War or War's request: 0 hits, where the same scan finds 13 NemesisForge strings), War never reads Mordor's files, and War's request carries no Mordor profile id (above). Shadow of Mordor reached the publisher's earlier online platform, Agora (Social/Agora, AgoraUserDataMgr, ProfileAttributeData), Shadow of War its successor, and the publisher's servers joined the two through the player's account. Mordor's document does not use the payload's 13 key names (it writes CombatTree, Role, XPLevel where the payload has CombatTreeRecord, RoleRecord, MenaceLevel): the reply was assembled by the service. The addresses in this section and the next are in Mordor's executable.

A Conquest mode. In Shadow of Mordor the Nemesis Forge is Conquest/Definition::NemesisForge, one of eight Conquest definitions (BG_Easy, _Medium, _Hard, _Random, SON_LordOfTheHunt, _Lithariel, _BrightLord and NemesisForge). It names the world WorldInfo::SeaOfNurnen, the game mode GameModes::NemesisForge, the army Orc_Faction_NemesisForge, the difficulty range Region_SeaOfNurnen, the tutorial NemesisForge_Intro and the active variable ConquestActive, with UseFactionSerialize true, no loot, no leaderboard, no award and an empty unlock predicate. Its completion counts (warchief and captain kills) and failure limits (time, deaths) are all -1: an endless sandbox with no goal (text Conquest_Mode_NemesisForge, failed header DLC_ChallengeMode_Failed). The game mode (one of 13, with the Conquest modes' 38 fields: default world SeaOfNurnen, inventory type DLC1, Type 4, UIAreaState 3, CanSave) turns off, against Conquest, CanGainXP, CanSpendCurrency, AllowRuneSlotPurchases and AllowRuneSlotUnlockPresentation, and turns on EnableNemesisNavMakers, CanScriptRegionFaction, FOWRevealFastTravelMsg and a flag of its own, NemesisForgeQuitConfirm. Talion does not progress there; the army is the point.

The army Orc_Faction_NemesisForge is serialized, tracks 32 members of the five orc classes, uses the event setup OrcFaction_NemesisForge (the standard Active* events) and has the rows NemesisForge_Row_warchiefs (5 seats), _2 (8), _3 (7) and _4 (5) at Sea of Nurnen locations. CanPopulateNemesisForge is true on exactly the two campaign armies, Orc_Faction_BG and Orc_Faction_SoN (of 12 armies; false on the downloadable and Conquest armies), and NemesisForgeFromThisFaction only on the forge army. Of Mordor's 503 quests, 65 list the forge army among their required factions, all of them Sea of Nurnen side missions (trials 5, duels 10, beast hunts 5, riots 5, executions 5, assassinations 5, recruitment 5, feasts 5, betrayals 8, outcast rescues 12). In this mode the Army screen has two states of its own, NemesisNonBranded and NemesisBranded (MemberState::NemesisForge requires the game mode): a living member whose Nemesis state is true, split by BrandedTarget false or true.

The main-menu entry MM_NemesisForge registers four handlers in the main menu's table (0x68C1E0, through 0x5E68B0), by kind:

  • 0, the enable gate 0x688F30;
  • 4, the start 0x689F80 (the mode found by the name "NemesisForge");
  • 2, the card 0x68C1B0 -> 0x68B940 (a save card: an empty-save field, a Nemesis field, DLC_NemesisForge_Available_Desc, the save status, an install-progress check);
  • 6, a dialog (0x68A400, id 0x7F) when the menu's +0xBFA is set.

The restart and continue prompts are 0x689390, and the pause page Pause_Skills_NemesisForge (0x6A8770) tests the mode by name. The gate reads the active user (p = [base+0x18F1228]+0x10, slot = u32 [p], 6 = none, user = [[[p+8] + slot x 8] + 8]), takes the object at [user+0x3A0] (getter 0x4E8790) and opens only when its bytes +0x1BB and +0x1BC are both non-zero. In a running Mordor at its main menu both read 0, so the entry is closed; the only instruction in the executable with displacement 0x1BB is the gate's own read (0x1BC has 116), so the code that set them must have written through a wider store, a copy or a table.

Debug tools. DebugSpawnAI (0x53AD00) holds a forge-nemesis key at +0x178 and a forge-follower key at +0x188 ({faction record, index}, tested by 0x868F90) and offers "Spawn NemesisForge - Nemesis / Follower"; the debug command DebugSpawnAI.NemesisForge.FetchNemesis is described as querying the forge nemesis from Agora. A single captain can be saved to and loaded from an .orc file through Profile/Commands::DebugFactionMemberSave, Load and List, enabled only in the debug command sets (menu layers FactionMemberSave, FactionMemberList, FactionMemberLoad, linked from no normal menu).

Shadow of Mordor's captain document

The captain document, the form a Mordor captain is written in, has 99 keys. Its writer 0x8558C0 writes 54 keys from the member:

  • FactionRecord (+0x58), FactionID (+0x54), NPCProfileGuid (+0x2F0, u64), RowNumber (the index of his row record +0x88 in his army's Rows, or 0xFF), ColumnNumber (+0x3A0, u8) and CanSave (always 1);
  • CombatTree (+0x60), Role (+0x2B8), RandomSeed (+0x48), Personality (+0x90), NameStringIDHash (+0x50), Name (its text), Location (+0x2C0), XPLevel (+0x340), TraitLevel (+0x344) and PlayerKills (+0x348);
  • twenty bits of the flag dword +0x3A4 (IsDead 2, KilledByPlayer 3, CanResurrect 4, PresentedToPlayer 5, SpawnConditionComplete 9 and its previous value 10, HasVow 12, IsSevered 17, IsSquealer 18, GangLeader 19, GangLeaderMatchClass 20, HasNemesisTrait 21, IsMockDead 23, RevengeTarget 26, WasEverPreset 27, OnlySpawnWithBoss 29; IsResurrected = bit 0);
  • one Trait key per trait (+0x70), the interaction scores (+0x384 / +0x388) and one FactionEvent key per history entry (+0x2A0, stride 0x10);
  • OverrideCharacterModel (+0x98), IntelDataLevel (+0x3AA), SpawnCondition, PreSetRecord, Purpose, PurposeStringIDHash, PurposeTimeOut, ResurrectionScarType (+0x2D0), AppliedScarType (+0x2D8), LastDeathType, the encounter indices, CanInterrogateAbout, ResurrectionCount (+0x394), LastDeathCharacterType, LastDeathAttack and LastDeathPlayerKiller.

Then come two scar keys (CFactionMemberScars_Scar / _Brand, from +0x290 / +0x298) and the look block's own 43 keys:

  • 20 records (SMC_BaseModel, BodyModel, BodyModelOriginal, BodyFlairModel, HeadSimpleModel, HeadModel, LegsModel, HelmetModel, FactionMemberHelmetModel, HairModel, ArmorSet, ArmorModel1 to 4, AccessoryModel1 and 2, HeadScarModel, BodyScarModel, ScarSetup);

  • 12 mesh-group bytes, written as four keys each;
  • up to 4 appearance tags and up to 8 flairs.

Its users are the faction save (0x8EE2B0, FACTIONDATA), a debug export of one captain to a <name>_<date>.orc file (0x91A800) and the presentation recorder (0x5FBA10, a text file). The number writers differ in sign: 0x5F9BA0 stores type 3, printed "%s = %lu", and 0x5F9BE0 type 4, printed "%s = %ld".

The document is read back by 0x855F70, which also takes the member's index, army, row, seat and GUID. Mordor's own apply over an existing member is the reader 0x863040 (675 instructions; used by its save load, the .orc load 0x91ACB0 and the presentation load 0x5FB6E0), which reads 44 of the 54 member keys and then the look (0x886830). A missing key resets its cell (every getter defaults to 0), and the trait and event lists are emptied before their keys are read, so an apply is a whole document. Exceptions: IntelDataLevel only ever rises, and CanResurrect, ResurrectionScarType and AppliedScarType are written by the writer and read by no code. The reader never touches the member's index, army, row, seat or GUID. The document is text: lines split on \n, every space, tab and carriage return removed, # starts a comment, [Name] opens a section, and keys and values keep 63 characters.

War's documents for a whole member

War keeps four doors through which a whole member can be written or read: the binary save (0x594788 / 0x1BC0F2C, see The Nemesis system), the online member document (exporter 0x1BC5044, importer 0x1BC21B4, 57 keys read), and a capitalized member document with a writer 0x1BC45A8 and a reader 0x1BC159C. The last one descends from Mordor's: of the reader's 61 key and node names, 29 are spelled exactly as in Mordor's 54, but War groups them into nodes where Mordor is flat.

Two document classes. The SAVE document (constructor 0x18786F0, 0x18 bytes; nodes 0x40, properties 0x60, values 0x70) is built by the writer's API (add child 0x1878CA0 and the setters); the LOAD document (constructor 0x1878608, 0x30 bytes: a parser-state stack, then the top nodes; nodes 0x20, properties 0x20, values 0x108 with a 0x100-byte text) is read by the getters (find child 0x18791F0 / 0x1879358). The only bridge between them is text:

  • Writing: a named node 0x187A580 writes "\n" NAME " = {\n", its properties one tab deeper, then "}\n"; a property 0x187A654 writes "%s = " and its value, or for several values "%s = [\n", one per line, then "]\n"; a value 0x187A824 writes a record as its name ([rec+0x20] when [rec+1] & 2, 0x18BDB0, else empty), integers as %llu, %lld, %lu or %ld, booleans as True / False, a string's first 0x7F characters, and a child node in braces. The text save is 0x187A3CC (0x187AAFC -> fwrite).
  • Reading: the text load 0x1879AC4(path, unused, callback, context) opens the file and the parser 0x1879B48(document, {begin, end}) splits lines on \n; 0x187A2F4 strips every space, tab and carriage return and # comments; a normalized line index reaching 0x400 is the engine's assert.

The reader is a whole-member re-initializer. 0x1BC159C(fm, node) reads these nodes:

  • Identity (CombatTree, Role, PreviousRole, BuilderInstance, Tribe, RandomSeed, Personality, NameStringIDHash, CharacterModel, PreSetRecord);
  • Flags (Location, LocationArea, XPLevel ... PlayerFleeCount, 24 flag bits through the bare bit setter 0x1156740, IntelDataLevel (raise only), RevengeType, Purpose, ResurrectionCount, the last-death keys and the scar types);
  • PIS, Relationships (BossID), EventHistory, SMCStorage, HierarchyMenuOverrides, Inventory and Traits.

A record is read by name from one category table per key (0x187985C: the name's hash, then a binary search of [table+0x38] over [table+0x28]; trees [0x2700960], roles [0x2701D70], personalities [0x2701A88], models [0x27018B8], presets [0x2701D08], tribes [0x2701D80]) and stored without a null test; inside a node a missing key writes null, and a missing node is skipped. Between nodes it always destroys his relationship objects, and it frees his appearance object and makes a new one before SMCStorage (0x2EB59C, 0x2EB490, 0x2EB56C at 0x1BC1D19 .. 0x1BC1D42, so [FM+0x2D8] changes). It also destroys and rebuilds his 25 items and re-dresses him (0x61BAD4), and empties his active traits and re-adds his pickers (0x7CD03C; the trait rebuild decides every slot again). A partial document therefore leaves him with an empty look.

Its last step, 0x1BC3554 (138 instructions), first acts under flag bit 1: it clears bits 1, 11 and 26 and unlinks his body (FM+0x28, the character at [FM+0x48]) without despawn events. It then destroys the quest handles at FM+0x3B8, sets FM+0x518 to 0xFFFF, clears bits 23 and 47 (and 6 and 46), and runs the trait rebuild with reason 0, the rarity and the importance; finally it zeroes FM+0x3A8, +0x388, +0x470 and +0x380, sets FM+0x51C to 1 and +0x51F to 0, and applies Faction/Global.ModelFixups. Its callers are the member factory 0xF99FF0, the presentation loader 0x182AFBC, 0x1C619FC and 0x1C69B58; every chain that feeds it a document from outside starts at a console command, the debug member load or the [FS+0x250] request. Monolith's own brackets are 0x61AE80 / 0x7C9DC4 around it (the sync-action debugger's load) and 0x1B5F4B0(FS) after it (the load-member event). The member copy 0x1BB936C is not an apply: it unlinks the body and copies the seat, the army and the whole flag word.

The look sub-reader 0x1C0546C(look, node) reads BaseModel, HeadSimpleModel, BodyModel, HeadModel, HairModel, AccessoryModel1 and 2, BodyFlairModel, BodyScarModel, HelmetModel, HeadAccessory1, ArmorShoulder, ArmorChest, ArmorArms, ArmorPants, ArmorLegs, LowLOD, HeadScarModel, the colors SkinTint, EyeColor, HairColor, TattooColor, PaintColor, Metal, Leather, Cloth, Bone, TrimColor and their Faction* twins. Of these, 11 model keys and 5 color keys are Mordor's names without SMC_; the armor is cut differently (Mordor's set, ArmorModel1 to 4 and legs, against War's five armor slots).

Dormant doors. The console command FactionMember.Load (0x1C5B9DC) parses the file, but its callback 0x1C5B4B0 only fetches the current target (0x16A550): the apply step is compiled out. FactionMember.Save (0x1C5BAC4) still writes FACTIONMEMBER_SINGLESAVE through 0x1BC45A8 to a text file. The data-driven loader Faction/Events/Setup.LoadMemberEvent -> 0x1B5D4BC -> 0x1C61AD8(FS, fm, name) runs only while [FS+0x250] is set, and that read 0 in a live campaign. Its path goes through the platform storage interface [0x26FEFD0] slots 7, 15 and 17, _wfopen_s, a whole-file read and a binary parse, then FACTIONMEMBER -> 0x1C619FC: the reader plus the row's DemoImportFactionEvents. The faction system's tick has an asynchronous form of the same request (0x1E2BC4 -> 0x1E34FC). The GameDB still holds Profile/Commands::DebugFactionMemberSave (left key, left on the pad) and DebugFactionMemberLoad (right).

Console commands and leftovers

  • NemesisForge.CreateFollower (0x1C775EC) and NemesisForge.CreateNemesis (0x1C77604) create the stored follower or nemesis at once through 0x1C77514. When the payload is valid, 0xF636F0(FS, payload, 0) makes the captain; then 0x1B5EE34(FS, fm) -> 0x1C28018 makes him his army's interrogation subject (the context's +0x160 = his key, cleared instead when he is dead), fires the army's EventSetup.SetInterrogationSubjectEvent and refreshes the old and the new subject. The quest path takes that step for neither captain, and neither path seats him: the quest path leaves the seat to the introduction sim event. The commands are registered by 0xCC460 and torn down by 0x10892D0.
  • NemesisForge.Override.ClearAll is a console entry referenced only from a command table (0x267DA68).
  • Telemetry 0x1B2CC68 ([GM+0x6D18]) sends event type 42 (NemesisForgeImport in the event-name table 0x716210) with is_follower, npc_role, npc_type, npc_advanced_class, npc_full_name and npc_guid, behind the telemetry switches.
  • Other names: a player-profile property User.OwnsShadowOfMordor (a data table at 0x266EDF8, no code use traced), Interface/Movies::FirebirdFrontEndLoop (frontendloop.vid), AI/Count::Firebird and Model/SimpleModelColorSetup::Firebird_Orc_Eye_Color_Grey.

Open questions

  • Why some Mordor captains wear a head their own seed did not draw (3 of the 28 plain captains): something in Mordor appears to re-pick heads after generation; reading Mordor's later head writers would settle it.
  • Whether War's 13 payload keys are a server-side rename of Mordor's document keys (CombatTree -> CombatTreeRecord, Role -> RoleRecord, AppliedScarType -> ScarTypeRecord, XPLevel -> MenaceLevel), and whether Mordor's Army-screen states NemesisNonBranded / NemesisBranded mark the nemesis and the follower that were handed over (non-branded as the nemesis, branded as the follower with IsBranded); what sets a member's Nemesis state is not read.
  • Which code fills Mordor's forge army from the two campaign armies: the readers of CanPopulateNemesisForge sit behind Mordor's cached schema tables (its static schema 0x1974A40 is referenced only by its builder 0xA87AB0 and a data registry slot), and what the mode stored on the online platform, and how, was not found in the client.
  • The exact success reply: element 0 of the result list and the value types used for the 13 keys (the parser's readers accept any integer tag through 0x7DFBF8).
  • What removes an imported member that no sim event has seated: of six captains imported through the console route and left unseated, five were gone minutes later and their members reused. Two candidates: the next import's interrogation-subject step, or the pool's recycling of its least important unseated member at the next allocation.
  • What creates members with creation marks 0 (0x1BC0084 -> 0x1BC00C8) and 1 (0x1C1CDAC -> 0x1BC02AC).
  • What NemesisForge.Override.ClearAll clears, whether User.OwnsShadowOfMordor gated anything, and what the two mission scripts do with GP_Gon2NemForgeCheck and the banner item (only the names the scripts hold were read, not their lines).
  • Whether anything besides the member holds the appearance object the member reader frees: a world body draws from its own copy (the bind copy 0x40EF82 -> 0x2EBA60).
