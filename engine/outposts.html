Outposts, strongholds and fortress upgrades

How the game's outposts work across every layer: the engine's own name for them (strongholds), the per-outpost switch and the warchief missions it gates, Lithlad's outposts as seats of an army, the fortress-upgrade table every army keeps and who picks it, the spawn-scenario tables that fill a stronghold, the world scripts that drive them, and the world map that draws them.

Every region has outposts: warchief strongholds whose missions, map zones and signal fires follow one saved switch each, and in Lithlad five outposts that are seats of an army with a commander and a reward. The engine's data and scripts mostly call them strongholds; the population inside one is shaped by spawn-scenario tables, and a fortress keeps a table of upgrades that its army's tribe and warchiefs choose.

The army, seats and faction events are in The Nemesis system; quests and the campaign store in Quests, story and scenes; spawning in AI; the map's interface in User interface.

Two names for one thing

The game's text says "outpost"; most of the spawn data and the world scripts say "stronghold". Across the shipped database, 2,335 record names in 131 categories contain either word. The spawn tables are almost all strongholds:

Category Records named for strongholds / outposts
AI/SpawnAmbient/SpawnScenario 13 (StrongholdBattle, StrongholdDynamic, StrongholdEventLarge ...)
AI/SpawnAmbient/SpawnScenarioCategory 28 (Stronghold, StrongholdDaytime, StrongholdDummyArcher, OutpostCaravan, OutpostRanging, OutpostSentry ...)
AI/SpawnAmbient/SpawnScenarioSetup 78 (CapCheckStronghold, CapStaticStronghold ...)
AI/SpawnAmbient/SpawnScenarioOverrideList 21 of 142 (Stronghold, StrongholdCenter, StrongholdSlaughter, OutpostCoreStrict, OutpostLargeStrict, PlayerControlledSH_DLC4 ...)
AI/SpawnAmbient/Predicates 15 (StrongholdCaptain, Stronghold_40M ... Stronghold_150M, with and without line of sight)
AI/SpawnAmbient/Removal 7 (StrongholdCaptain, Stronghold_Removal50M ... Stronghold_Removal150M)
AI/SpawnAmbient/NodeTags 13 (Stronghold_Core, Stronghold_Leader, Outpost_Guard, Outpost_Captain ...)
AI/SpawnAmbient/Locations / AlarmAreas 29 / 23, one or more per outpost (IS_Outpost_Harbor, D_Outpost_East ...)

The rest is the game around them: 1,000+ audio and dialogue names, 174 inventory items (rewards, intel, the outpost boosts), 120 quest variable predicates, 88 sim events with their participants, 73 quest lists, 31 map canvases, 27 interface game-state predicates, 18 remote scripts (EnableAllOutposts, DisableAllOutposts ...). In the executable, 103 functions carry an outpost or stronghold name in their own strings or field registrations: 8 schema builders, 33 field registrars, 45 field bindings and 11 string users. One script binding is exposed: Faction::GetOutpostCount_PlayerFollowerOrEmpty (implementation 0xF647F0).

The outpost switch and the warchief missions

Each region's warchiefs live at outposts: Lithlad DE_Outpost_Central / East / North / NorthWest / West, Núrnen I_Outpost_Harbor / Lighthouse / RiverRuins, Cirith Ungol MP_Outpost_Arena / LostHearth / Shelob, Seregost SM_Outpost_ArmyCamp / FrozenLake / Summit, Gorgoroth V_Outpost_BlackIron / Camp / Ledge, Minas Ithil MIOutpost_01..05. Each has one boolean in GameData/Variables, true by default. It is saved state.

  • Its only writer is the world script method DeactivateOutpost in the regions' spawn-condition layers, called from a warchief mission's end paths (the warchief killed, one of seven domination events, branded; never a death threat) and only when the active quest is on that outpost's own list. Nothing in the shipped scripts sets one back to true. Counted over the script copies the game loads (a later patch archive's copy replaces an earlier one, 1,403 of the 2,679 distinct script bodies): 193 bodies name a switch, with 748 SetValue(false) calls, every one inside DeactivateOutpost (34 bodies, 22 switches each), and 0 SetValue(true).
  • Its readers: the region's stronghold controller (below) subscribes to the variable's change event; the 889 GetValue reads are all in side-activity layers' CheckMapCanvas (caravans, guarded caragors, camps, feasts, war councils, labour, supplies, drills), which run only while the outpost is active.
  • The missions. At a world turn, a captain seated in the region's captain rows generates <R>_Outpost_OP<n> when its GlobalVarPredicate passes (0x5935DC; in Lithlad the switch AND NOT the outpost's DLC capture flag). Each event weighs 999 against 0, so one per outpost per army. The generating captain must pass the job SC_Subject_OutpostCommander himself (0x61EF8C -> 0x61FC88 -> 0x622170, job matcher 0xF9BB20): captain rank, enemy, alive, not a prisoner, spy or vow holder, not on another sim event (FM+0x4F0), not an Easterling, not tagged OP<n>_UnfinishedBusiness, no revenge within 3 turns, not a bodyguard, not in the world, not on a DLC outpost seat. The event binds to a placed quest whose predicates pass (0x597884 -> 0x19EFAB4), so a mission is offered only while its region is loaded. The quests are SpawnCondition quests (<R>_SC_OP<n>_KillArchers, _KillBerserkers, _SustainedAlarm, _RapidStealth ...); Quest/Types::SpawnCondition is replayable, so completion blocks nothing and the switch is the only lock. Variant gates such as DE_Outpost_01_Berserkers add a class unlock (BerserkersUnlocked) to the outpost's gate.
  • The zone on the map is Interface/MapCanvasSettings::<R>_ZoneMap_<X> (Núrnen 3, Cirith Ungol 3, Seregost 3, Gorgoroth 3, Minas Ithil 6, Lithlad 5). Its game-state predicate is the outpost's own switch, so a zone is drawn while the outpost is active and dropped once it is cleared.
  • Where an outpost is: the centre of its commander spawn points, AISpawnerAmbientQuestJob objects such as SC_Sp_<nn>.OutpostCmdr in the region's spawnconditions_op<n> layer (116 placed objects carry "Outpost" in their name, every one a quest-job spawner; the points of one outpost spread 22 to 91 m).
  • Setting a switch back to true through the engine's own variable setter (0x59A1D8 on [GM+0x6C58]) relights the signal fires at once (the controller's change handler) and the outpost's missions are offered again from a later world turn.
  • In Desolation of Mordor's mode (DLC_DLC4Active) the same DeactivateOutpost captures instead of clearing: a win sets DLC4_OPCaptured_<X> true and the outpost's D_OP_* areas player-owned, and leaves DE_Outpost_<X> true.

The stronghold controller

One world-script class, strongholdcontrol, runs both the fortresses and the warchief outposts of the five base regions (its own comment: "Set to a default value so that outposts don't do fort stuff!"); Lithlad uses strongholdcontroldlc. The copy each region loads is the same 926-line body.

  • Start. A fortress calls FortStatusInit(<Region>Fort) once (4 regions); each outpost's relay object (srO<X>Control, after a 1 s delay) calls OutpostStatusInit(<switch>), 17 in the base regions. In Lithlad each outpost runs FortStatusInit(DLC4_OPCaptured_<X>) and then OutpostStatusInit(DE_Outpost_<X>).
  • What the switch drives: only the outpost's AINodeElevateTransientAlarm nodes (its signal fires). The map canvas calls are commented out ("handled entirely in the DB"): the zone follows its own game-state predicate. An outpost also stays dark while StoryState is below minStoryState (a per-placement property, 100 by default), re-checked on every story-state change.
  • The alarm. Orcs that reach the signal fire raise the area's alarm. Above Low, the controller adds the HighAlarm spawn override list (training dummies, dummy archers and the arena categories off) and the red alarm canvases; at the second and third high waves it fires a fear burst: every tagged enemy flees, or 40 % of them when a captain is present. A warchief mission raises the alarm to High when its commander spawns and resets it to Low when the objective ends.
  • An owner change in a base region swaps only the map style (Strongholds versus the Friendly_* canvases) and the gate logic. No spawner, override list or garrison changes there; garrisons that follow the owner exist only in Lithlad. On a loss the script writes the cave style to the main canvas variable (localMC) where the cave canvas variable (localCaveMC) is meant, in every loaded copy.
  • All outposts at once. The remote scripts DisableAllOutposts and EnableAllOutposts are fired 160 times in 101 loaded script bodies: story missions, DLC missions, tribe fights and statues silence every outpost when they start and release them at cleanup. The controller's enable path respects each outpost's switch.
  • Calls into the engine from the outpost scripts: AISpawnManager:AddScenarioOverrideRecord / RemoveScenarioOverrideRecord; Faction:GetAreaPlayerOwned, SetAreaPlayerOwned, GetOutpostCount_PlayerFollowerOrEmpty, VacateLocationList, CreateFactionMemberBuilder, AddFactionSimEventPicker, AddFactionEventJobSourceAndOther, IsEventOnEventList; System:ActivateRemoteScript, SetAlarmLevel, ElevateAlarmLevel, GetObjectsWithTag, IsDayTime; and the game-data variables' GetValue, SetValue and change events.
  • Class unlocks. The mission-variant predicates <R>_Outpost_0<n>_<Unit> are the outpost's switch AND <Unit>Unlocked AND NOT the capture flag. The same <Unit>Unlocked booleans gate the AI templates themselves (BerserkersUnlocked has 98 users, AI/Templates::Orc_Berserker among them): they decide which orc classes any garrison can contain.

Spawn scenarios and override lists

What stands in a stronghold is ambient spawning: spawn scenarios (AI/SpawnAmbient/SpawnScenario) grouped into categories (SpawnScenarioCategory) and filled through setups (SpawnScenarioSetup). An override list (AI/SpawnAmbient/SpawnScenarioOverrideList: Priority, Overrides, CategoryOverrides) changes them inside a ScenarioOverrideVolume or for as long as a script holds it (AISpawnManager:AddScenarioOverrideRecord). It names no unit types; it switches and caps scenarios and categories:

Entry (_Structures...) Fields
SpawnScenarioCategoryOverride CategoryType (a category), ForceEnabledStatus (a Combat/Predicates/Bool: True, False, or none to leave it), MaxConcurrentAI, MaxConcurrentSetup, Priority, MinDistance, AutoCooldownChance (-1 = leave as is)
SpawnScenarioOverride ScenarioType (one scenario), disable, MaxConcurrent, MaxConcurrentAI, FrequencyDecay, Priority

Three lists, as read from a running game and the shipped data:

List Priority Effect
Stronghold 4 categories Wilderness and AmbStartGraug off, AmbSentries capped at 3 bodies, AmbColumn at 4, SHOnlyEvent and FortPlayerWelcomeBlocker on; the scenario AIBlockout disabled (MaxConcurrent 0)
HighAlarm 8 StrongholdDummy, StrongholdDummyArcher and Arena off; StrongholdDynamic and StrongholdDynamicArcher listed with every field left as is
PlayerControlledSH_DLC4 1 Orcs off, StrongholdEasterling on: who guards a held Lithlad outpost

The tables never name a unit. A setup (SpawnScenarioSetup: ScenarioType, ScenarioCategories, RequiredAITypes, Priority, global and instance cooldowns, MaxConcurrent, MaxConcurrentAI, MinDistance, StartDisabled, ForceAISpots, ForceNextScenario, IgnoreMaxConcurrent, AllowFailedSpawn) belongs to a scenario (SpawnScenario: ScenarioCategories, Priority, FrequencyDecay, MaxConcurrent, MaxConcurrentAI, StartDisabled), and a category carries only MaxConcurrentAI. The shipped data has 151 categories, 53 scenarios and 282 setups, 87 of them stronghold or outpost setups. RequiredAITypes points at {AITemplate, NumRequired} entries: all 114 of them in the shipped data have no template and require 0 (a running game agrees). What spawns is decided by the spawners placed in each outpost's layers and the AI types they hold; categories and override lists only decide which placed scenarios run and how many bodies they may field.

The code that applies them is one module of about 200 functions that reads every field of the override lists, both entry kinds and the setups. It is called from the ScenarioOverrideVolume class (vtable 0x1FB4BA0), a placed volume whose +0x120 holds its override list, and from the setup code.

How lists compete. 0x5ED360 resolves the overrides per running scenario: the spawn manager keeps its running scenarios in a table ([mgr], count [mgr+8], 0x60-byte entries with the scenario record at +8) and the active override lists in a vector at [mgr+0x10130] to [mgr+0x10138]. For each scenario it walks the lists and considers a list only when its Priority is strictly above the best one applied so far, so the highest priority wins and a tie goes to the earlier list. Inside the winning list, the direct Overrides entry for that scenario applies first, then the first CategoryOverrides entry whose category contains the scenario. A scenario no list mentions gets its own values back. The list priority is read in three places (0x5ED1B8, 0x5ED360, 0x5ED50C).

The stronghold vocabulary around them: distance predicates Stronghold_40M to Stronghold_150M (with and without line of sight), despawn rules Stronghold_Removal50M to Stronghold_Removal150M and StrongholdCaptain, node tags Stronghold_Core, Stronghold_Leader, Stronghold_Gather, Outpost_Guard, Outpost_Captain, Outpost_Defense.

Lithlad's outposts: seats of an army

Desolation of Mordor's five Lithlad outposts are records of Faction/Outposts (fields Row, Column, UIName, GlobalVarToSet, CreateSimEventOnDie, CreateSimEventOnVacate, PlayerOwnedItemGiverPicker): seats in an army's row table that a captain holds as the outpost's commander.

  • The capture flag. GlobalVarToSet (DLC4_OPCaptured_<X>) is written by the faction system through the boolean setter 0x59A1D8, which fires the variable's change event. Its binding 0x100F4C0 has 5 callers: 0xFE2E90 (a seat change: true when the new holder is a player follower, false otherwise; true on vacate, then CreateSimEventOnVacate), 0xFD4DE0 and 0xFDCAB0 (bulk false), 0xFE0A60 (recompute) and 0x1010750 (a setter wrapper).
  • The garrison follows the owner. Each outpost's gameplay layer has a controller (script object outpostcontroldlc) that runs OutpostStatusInit on the capture flag: with the player as owner it switches on a ScenarioOverrideVolume (vtable 0x1FB4BA0, +0x120 -> the override list PlayerControlledSH_DLC4) and shows the outpost's faction-member props; with Sauron as owner the volume is off and the props hidden.
  • The reward. PlayerOwnedItemGiverPicker names DLC4_OutpostItems: 16 givers (Faction/Outposts/ItemGiver::OutpostBoost_<X>), each with 3 entries selected by the commander's rarity (RequiredRarity), and each entry's Items hold a CombatType filter (the player, or a mercenary class) and the items to give (33 OutpostReward_* items whose passive stat modifications are the boost).
  • Who has outposts. Faction/Definition.Outposts lists the five on 2 of the 38 armies, Faction_desert_DLC4 and Faction_desert_mercs_DLC4. Quest/FactionOutpostPredicate::DLC4_AllOutpostsOwned asks for 5 seats held by a player follower, dead or empty (the count Faction::GetOutpostCount_PlayerFollowerOrEmpty returns); DLC4_NotAllOutpostsOwned for 0 to 4.
  • The spawn areas change hands too. Faction/AreaOwnershipTransform::DLC4_Outpost_<X>_To_Player sets the outpost's AI/SpawnAmbient/Areas player-owned (1) and _To_Sauron sets them back (2): D_OP_Umbral (West), D_OP_SorrowSea (North), D_OP_SouthWatch (North-West), D_OP_SootGulch (East), D_OP_Stillwind and D_OP_Stillwind_A (Central). The fortresses use the same mechanism (<Region>_FortAreas_to_Player / _to_Sauron, 10 records). DLC4_Outpost_N_To_Sauron holds no area entry, so the North outpost's area is never returned through its transform.
  • Two systems on one spot. The warchief outpost's gate in Lithlad is DE_Outpost_<X> == true AND DLC4_OPCaptured_<X> == false, and its mission generation uses the same gate: held by the player the spot runs the seat system, lost it runs the warchief system.
  • The intro. Presentation/Events::DLC4_Outpost_Intro_EVT (priority Quest_Urgent, blocks fast travel) has one sequence of nine elements: a camera cut that disables the player (DLC4_Outpost_Teleport_Hold_ELM, which teleports nothing), the outpost's fixed frames, a start camera and its voice, an identify hold, then the enter-zone camera and the return transition DLC4_Outpost_Return_TR. Its predicate assumes no target (Target_Empty_OPR). The frames are per outpost (DLC4_Outpost_<X>_WF1_Begin / _End / _RTP), chosen through the camera pools DLC4_Outpost_Begin_CP, _End_CP and _RTP_CP, whose predicates Outpost_<X>_CPR require the assault mission's camera type D4OA_<X>_CT: the intro frames the right outpost only when it is queued with that camera type. The one relay named for outposts, Presentation/Relays::PS_Outpost_Intro_00, has no event and no camera type.
  • No shipped record has an enemy captain attack a player-held outpost commander: a job's MustBeAssignedToOutpostPosition (0 ignore, 1 must hold a DLC outpost seat, 2 must not) is 2 on 245 of 849 jobs, including every duel and power-struggle job, and the job matcher rejects at 0xF9F5BF. An outpost is lost only when its commander dies or leaves the seat.

Fortress upgrades: one table per army

Every army keeps one fort-upgrade set at [armyCtx+0x40], where armyCtx is an army context (an entry of the faction system's context map at FS+0x98, plus 8):

Offset Type Meaning
+0x00 pointer a table of 16-byte rows {UpgradeType record, Definition record} indexed by the UpgradeType's record index (28 rows)
+0x08 u32 the row count
+0x10 pointer the category of the upgrade-type records (0x107A74 asserts "Bad record index" for a type from another category)
+0x18 / +0x20 pointers a vector of the Faction/FortUpgrade/Definitions the army has unlocked

The read path is 0x4F6644 (does an army hold every upgrade of a Faction/FortUpgrade/Group; the fortress's defence rating adds a warchief's group contribution only when it does) -> 0x4F66D8 (the army context for a faction) -> 0x10681C -> 0x107A74. In a loaded late campaign, 31 of 38 contexts held this table. An enemy fortress fills one Defense_* row per family: 6 of 6 rows on each of the two enemy-held fortresses, 0 on each of the four whose Overlord served the player.

Who chooses. Faction/FortUpgrade/PickerEntry records select a definition by the fort's tribe list (IncludedTribe -> Faction/Tribes/Lists) or by a warchief's trait marker list. The tribe lists group the tribes:

What a pick does. FortAssault/Modifiers keyed on the definition hold a Makeup (AISetup, Count, Weight, Priority, SpawnOnlyOnce, NeverRemove), and the FortAssault/AISetup names an AI type:

A graugapult is a tamed graug and an item list. The AI types Troll_Graugapult, _Poison and _Curse all build the template Troll_Tame; what makes the siege beast is GruntPlayerAllyItems / GruntPlayerEnemyItems (the list used depends on the side): Graug_A_Pult, Wep_Graug_A_Pult, Troll_Graugapult_Marker, Troll_Graugapult_Disabled_SetRenderID, the four box items and the element (FM_Siege_FireBeast on Troll_Graugapult, which also carries Attack_Structures; FM_Siege_CurseBeast on _Curse).

An AI type's side. Orc types carry it in GruntPlayerFollowerStatus: 0 enemy or wild, 1 a player follower, 2 the area's owner, 3 an invader, 4 and 5 the two sides of a fortress assault. Beasts carry it in GruntBrandStatus instead: the *_Branded types (Warg_Brown_Branded, Troll_Branded, FellBeast_Branded ...) read follower status 0 and brand status 1.

The world map

The world map is a model of the region drawn far below the world. Its object is [base+0x26FFAC8] (vtable 0x1F715F8; null while the map is closed):

Offset Meaning
+0xAC position (about (0, -24200, 0))
+0xB8 rotation (quaternion)
+0x2AC / +0x2B0 the model's size in x and z (512 in every region read)
+0x2B4 / +0x2B8 the height range
+0x2C0 the region record

0xD11D10 converts a point on the model to the world: the point is taken into the model's local space, u = local.x / sizeX + 0.5 (and the same for z), and world = rect.min + (rect.max - rect.min) * u. The rectangles come from a table at [[CGameClientShell+0x8C8]+0x10] (to +0x18): 0x110-byte entries {hash, path at +4, info at +0x108}, with the rectangle at info+0x18:

Region Rectangle (min x, min z, max x, max z)
desert -73950.6, -83550.3, 56049.4, 46449.7
island -88000.7, -50000.0, 55000.0, 93000.9
minasithil -55450.1, -53099.7, 43549.9, 45900.3
mtnpass -66001.9, -74401.9, 63200.0, 54800.0
snowmtn -47999.9, -62999.9, 48000.1, 33000.1
volcano -60000.5, -10000.8, 60000.3, 110000.0

The map camera is [[base+0x26FFB08]+0xA8] (vtable 0x1DB1F48): +0x158 position, +0x164 rotation, +0x174 and +0x178 the horizontal and vertical fields of view in radians, +0xD0 the gameplay camera; the renderer's per-draw projection agrees with it (P00 1.1309, P11 2.1445 at 3840 x 2025). The cursor is in pixels at [[CGameClientShell+0xE38]+0xEC] / +0xF0, the viewport at [CGameClientShell+0xC00]. The camera list at [[CGameClientShell+0xE38]+0x220] holds a free camera (vtable 0x22F4E18, unused by default) and the HUD minimap's camera (vtable 0x22F4F20).

The waypoint. The current target lives at [GM+0x6C80]: +0x20 its type (7 a point, 1 a tracked target), +0x10 position, +0x28 region, +0x90 its marker. The map's SPACE action (0x18E9AD4 -> 0x189286C) sets a point with 0x17A98AC(targets, &position, region record); System::ClearCurrentTarget is 0x17A8C5C. The action handler keeps the hovered target as a variant at [layer+0xA78] (types 0, 1, 3, 6, 7) and the region at [layer+0xA10] (0x18003A0 finds the map object by its +0x2C0). The waypoint's marker (vtable 0x1DC0708) holds NavMarkerTypes::UserWaypoint at +0x38 and MapDisplay/Targets::UserWaypoint at +0xE0. NavMarker::SetType (0x1162DE4) skips an unchanged type (0x3576A4); its body 0x3576B8 re-reads the default map target and the HUD configuration, sets up the marker's effect (0x357CD4), writes the type into its widget ([marker+0x60]+0x2C0) and sets the rebuild flag (+0x48 |= 1). The legend's outpost glyph is Interface/Menu/MenuTreeNode/Legend::Outposts (interface\textures\hud\glyph\outpost.tex).

Outposts on the map's own data. The world map lights outposts through material parameters: Interface/Menu/MenuLayer/WorldMap.OutpostStateParameters holds one entry, k_vOwned4567 (ownership) and k_vSelected4567 (selection), with four outpost slots of which two are bound (DE_Outpost_Central, DE_Outpost_West). The world map's update applies it (0xF252F0, together with the DLC4AreaMaterial region material) only when 0xD0B350 passes, which compares the current game mode against the name "DLC4": the lighting runs in Desolation of Mordor's own mode and never in the campaign. The zone map plays d4_menu_zonemap_outpost_over when the cursor is over an outpost (3DZoneMap.OutpostSFX) and steps an outpost's widget through stages of 2, 2 and 1 seconds (Interface/Shared.ZoneMapWidgetOutpostStageDurations). Of the 103 map canvases, every outpost zone and the Stronghold_ZoneMap, Stronghold_Cave and Stronghold_Alarm1 to 3 canvases carry the enemy colours (zone fill 0xE6A41606, outline 0xFFA41606); Friendly_Strongholds and Friendly_Stronghold_Cave the friendly ones (0xE609D5ED, 0xFF09D5ED).

The generic banner

The interface keeps a generic two-line banner that any text can fill. The script binding CPlayerObj::DEMO_ShowGenericBanner (a press-demo leftover, stub 0x1B80E20, two arguments: the player and a string key) is a jump to 0x1892F34(_, key, 0, 0). That function (37 bytes, two callers, first argument unused) takes the banner manager at [[UIManager+0x30]+0xE0] (nothing happens while UIManager+0x30 is null) and calls 0xE604C(manager, key, secondKey, flag). Each key goes through the string lookup 0x471F2C, the same table all game text uses, into a wide-character buffer, and 0xE7A98 (string "GenericAux") shows the banner: the first key's text as the title and, when a second key is given and its text is not empty, that text as the second line. The banner appears beside the minimap.

Open questions

  • Which placed spawners (and so which AI types) each outpost's layers hold, region by region.
  • What a category-override entry with every field left as is does (HighAlarm lists StrongholdDynamic and StrongholdDynamicArcher that way): a placeholder, or the list's own priority applied to the category.
  • Which override list each outpost's sovOutpost volume holds (its +0x120), and which remote scripts the controller's relays listen to.
  • Whether repeated OutpostStatusInit calls stack change handlers on the same variable.
  • What, if anything, changes a base region's outpost garrison when the region's fortress changes hands: no outpost script does; a candidate is an area-ownership predicate in the spawn data.
  • Whether Gorgoroth's own EnableAllOutposts listener, which ignores the outpost switch, is in a layer the retail game loads.
