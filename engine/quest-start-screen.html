The mission start screen

The game's own "start this mission?" screen: how a mission start reaches the quest-start menu layer, the layer object, its modes and actions, which captains it names, the 3D stage where they face each other, a sim event as it sits in memory, and the Army screen's Kill, Ambush and Reinforce orders that run through the same layer.

Before a nemesis mission starts, the game shows a confirmation screen: a 2D card for one captain, two captains or an Army-screen order, over a 3D stage where the mission's captains walk out and face each other. The screen is one menu layer, CUIQuestStartLayer, driven by the quest's WorldUIConfirmSequence and by the mission's sim event; the same layer confirms the Army screen's orders. Menu layers in general are described in User interface: Scaleform, menus and the debug menu.

How a mission start reaches the screen

  • From the world. The quest-confirm object [base+0x25D8E60] holds the placed quest at +0x168. Its input handler 0x7D4BA4 (input code 0xEF) runs 0x1A06BFC: a quest whose WorldUIConfirmSequence is null starts at once (0x189161C); otherwise 0x19F0E98(placed quest) fills the quest's jobs and its PresentationOnConfirm plays. That presentation's callback 0x434CF0 (event 4) runs 0x1A07DEC, which enters the flow only when the sequence is set: 0x17BDF6C([player+0x2F98], quest).
  • 0x17BDF6C picks the screen. It takes the quest's StartLayers when set; otherwise ActivationType 5 gives the matchmaking layer and 6 the online arena layer, a fort quest the QuestStartFort_Full layer list, and anything else QuestStart. It queues the push at [menu+0x5B0] and runs 0x188F2C0 -> 0x188F2CC(UIManager, quest), which also hands the quest to the matchmaking layer (+0xEA0) and the online arena layer (+0x1C338) and runs the setup 0x18E493C(layer, quest). Finally it sets +0x60 of the player component it was given to 6.
  • The push. 0x18BB000(menu, layer record) pushes at once (0x31A034) when [menu+0x728] is set, else queues the record at [menu+0x568].
  • Two more doors. The console command UI.EnterQuestStartFlow (0x17C09BC) takes the region's FortAssaultQuest, runs 0x19F0E98(placed) and then 0x17BDF6C with [placed+0x258]. The Army screen's ActionDemoBeginAssaultSetup (0x189907C -> 0x188BCC8) runs 0x19F0E98, 0x188F2C0 and 0x18BB15C -> 0x18BB000.
  • The setup runs before the push. The layer builds its request (below) in the setup and applies it when it enters (its enter method reads +0xA10).

The layer object

The layer factory 0x7219D0 matches the category global 0x27011B8, allocates 0xE720 bytes and runs the constructor 0x18E2C70 (string CUIQuestStartLayer::CUIQuestStartLayer). The menu's layer list and stack hold the object plus 0x48 (every caller of the layer lookup 0x466758 subtracts 0x48), so the menu-layer fields +0x6B8 (the menu) and +0x6C0 (the layer record) sit at +0x700 and +0x708 of the object. The tick commits. While +0xE710 is set, vf1 waits for the presentation ([[base+0x26FFB60]+0x3F0], its +0x222 set while it plays) and then commits: an order through 0x18911FC (create) or 0x18911B0 (augment) and back to the Army screen (0x18BB21C, 0x31A3FC); a quest through 0x188C060, which leaves the menu through [player+0x2F98].

Modes

Every one of the 15 instructions that touch +0x6C10 was read; the decision block is 0x18E4B4B .. 0x18E4BF2.

Mode When Content widget
any the quest's StartScreen is non-zero (read from [placed+0x260], else the record): that value
5 / 6 a fort quest: ActivationType 5 or 6 gives 6, else 5 the fort-assault prompt (0x77799C)
4 an Army-screen order is pending: create (0x7C6860) or augment (0x7B478C); the order setups 0x18E4CB8 / 0x18E4DA4 also set it Augment (0x7DBFF4)
3 members A and B both exist and neither carries the dead mark, flag bit 21 (0x1162D1C; see The Nemesis system) Duel (0x7DBF1C)

The widgets' quest text (name, description, icon) is written by 0x18E356C, which takes the description from the quest text resolver (see User interface: Scaleform, menus and the debug menu, "Quest text").

Actions

Confirm is a menu action, dispatched through vf19 from the layer record's Action* fields.

  • ActionStartQuest. A fort quest first checks its slots, and an empty slot opens the message box UI_FortAssault / UI_FortDefense_EmptySlots (callback 0x18E3BC8). The start runs 0x777878 -> 0x116E7A4 (through [placed+0x180] -> 0x7DB0E4, else 0x5BBF64). Then the record's EventSetup.ConfirmOrderEvt runs 0x777954 -> 0x7780B8 -> 0x7C0624, which walks the current sequence's SquenceBranches: the branch whose RequiredEvent is that event gives NextSequence (PresistSequenceData -> +0x223), and 0x798254 plays it. If no presentation takes the event, 0x188C060 leaves the screen at once.
  • ActionConfirmOrders. Takes the pending event, reveals a spy (RevealSpy) when the order's captain is one, then plays the event's ConfirmWUIPresentation with +0x6C00 (0xD604F0).
  • Cancel (raw input 0x21). A quest runs 0x1891E58 (not while matchmaking is pushed); an order runs 0x1B59EF4(FS+0x20) and 0x1B59F50(FS+0x28). Then CancelOrderEvt goes through the same branches.
  • The others. ChangeSelectionDirection moves the highlight between A and B, and only onto a captain whose name is known ([FM+0x510] & 1). SetDetailState runs 0x188EEF4(.., 2). SetTarget is 0x18928A8 and ClearTarget 0x188B0C8.
  • The prompt bar. The push 0x31A034 -> 0x31D85C(menu+0x6FD0, record) feeds the record's MenuSelectionPredicates to the menu selection; vf27 refreshes it (0x320B08), and so does 0x31A3FC after a set or clear of the target.

No captain cycling here. A fort assault's slot edits belong to the war-upgrades layer (vtable 0x1F895C0): its enter method 0x1937C4C copies the quest-start layer's +0x6C08 into its own +0x11890, and on return the quest-start layer recomputes mode 5 or 6.

Who the screen names

The setup's two keys (0x18E493C; it tests no job and no alias). With a sim event, the event's participants by position give the keys: entry 0 is A and entry 1 is B (0x61D0F8(UIManager, quest, first) -> key 0x400818). A participant counts only when it is filled ([p+0x3A] bits 3 and 0) and its slot's follower rule holds: 0x61EABC reads the slot's ExclusiveMustBePlayerFollower (0 any, 1 must be the player's follower, flag bit 27 through 0x114E020, 2 must not). Without an event the keys come from [placed+0x1A8] / [placed+0x1B8], then the holder [placed+0x430], then the quest's job entries 0 and 1.

The request (+0xA10, 0x70 bytes):

Offset Meaning
+0x00 the faction
+0x08 0xB
+0x0C flags: 0x40 a quest, 0x80 an order
+0x18 ONE named participant (A when valid, else B; 0x18E4C12 ..) as {army, row, seat}, when he has a row ([FM+0x268], seat byte FM+0x51B)
+0x28 / +0x30 otherwise the same participant as {army [FM+0x178], pool index [FM+0x174]}
+0x40 key A (orders)
+0x58 the sequence: the WorldUIConfirmSequence of the placed quest's record, else of the record (accessor 0x18E3520, read at 0x18E4B18)

It is applied by 0x18BB21C -> 0x1154EA8(menu+0x6FD0) and by 0x188E818 -> 0x18321E0([[base+0x26FFB60]+0x340], request, 6), the world-UI stage controller of the Army screen.

The stage's captains are CWorldUICharacter objects. The class test 0x2CF520 walks the type chain at [obj+0x78] to the node 0x2670C40 (name CWorldUICharacter; parents WorldUIInteractable -> WorldMapNavMarker -> GameBase -> BaseClass). The 219 member-state records (fields IncludedQuestJob, DominationSubject, OrdersMode, FortAssaultMode, Highlighted, Detail, IncludedMode ...) are tested by 0x366D80, the only caller of the IncludedQuestJob (0x367A88, 0x683098) and DominationSubject (0x3681E4) accessors.

IncludedQuestJob accepts a job or its alias, on three contexts the character carries (0x170424(character, job); the member is the character's vf56):

Character field Context Match
+0x6B8 the placed quest 0x19F6818: the member key at entry +0x20 must be equal and the job must be entry +0x08 or +0x10; a second list there passes an entry whose Quest/Jobs/List names the job, with no member check
+0x6E0 the sim event 0x1BEFBDC -> 0x34FB7C finds the entry whose +0x28 key is the member, then 0x620EC8 checks job == +0x08 or +0x10

So PS_Subject matches an outpost commander through the alias of his job, SC_Subject_OutpostCommander. IncludeHenchman False (0x1822B8C) refuses a member whose master (0x7E0614, [FM+0x2C8]) holds the job too.

The player's follower on the dual stage is the game's own case. Ten sim events put a PS_Other-aliased job with PlayerFollower True in slot 1: Feast, Feast_Origin, ArenaFollower, DuelFromGarrisonExistingFollower and six DuelFromFD / DuelIntoHierarchy *NonLegFoll events. The feast's 19 quests and the arena's 7 (SM_Arena, MI_Feast_00 ...) all start on QS_DualParticipant_Base_WUIP. The member state QuestJob_PS_SubjOther {PS_Subject, PS_Other, PS_Ambusher} is linked by nothing in the database, so no stage shows an ambusher by job.

A sim event in memory

An army's sim events hang off its army context (see The Nemesis system, "Turns and sim events"); the member on an event points at it from [FM+0x4F0]. Read live on five events:

Event offset Meaning
+0x00 vtable 0x1DBC8A8
+0x18 / +0x20 participant entries, begin / end, 0x40 bytes each
+0x40 the Faction/Definition
+0x48 the Faction/Events/SimEvent record
+0x50 / +0x58 the Quest/Quests record (twice)
+0x60 the SimEventGenerationType (IS_Outpost_OP1, PowerStruggle_Act2, NeverEndingShadowWar)
Entry offset Meaning
+0x00 its slot: a Faction/Events/SimEventParticipant record (KillOlogs_Outpost_01_01, Raid_Caragors_01)
+0x08 / +0x10 the job and its alias (SC_Subject_OutpostCommander / PS_Subject)
+0x20 a Faction/FortUpgrade/Definitions record on fort-defense entries, else 0
+0x28 / +0x30 the member key: army record, u32 pool index
+0x38 u16 0xFFFF
+0x3A flags: bits 0 and 3 = filled (0x29 on 22 of 23 entries read, 0x69 on one)

In one save, eight outpost events were active, each with one entry, the commander; in the same pass Raid_Caragors and Execution2 had two (PS_Subject-aliased, then PS_Other-aliased) and FortDefense 13. Over every army: 44 events with one entry, 4 with two, 3 with 13. An entry names its slot record, so a member on an event always sits in a slot that is a record of Faction/Events/SimEventParticipant.

Assignment, and the Army screen's orders

The engine's assignment

0x1BF02E8(event, jobGroup, member), read whole:

  1. It refuses a member already on the event (0x596BC4).
  2. It walks the event record's ([event+0x48]) Participants for the slot whose JobGroup is the argument (0x61F5A4).
  3. It takes the group's first job that no entry holds yet (0x620E84).
  4. It builds the entry {slot, job, alias, member} with 0x1BF0C98.
  5. When the slot's follower rule passes (0x61EABC), it runs 0x61CED0 (below).
  6. It pushes the entry onto the event's participants (+0x18).
  7. 0x1BEDF34 switches a full event to MaxParticipantsNewSimEvent (log string "Upgrading SimEvent %s to use record %s") when MaxParticipants is above 0 and the count reaches it. It returns 1.

0x61CED0(member, event, slot) is the member's side: - If [FM+0x4F0] holds another event, it ends that event (0x61DB24(other, 1)): a member is on one event at a time. - It moves the member's list node at FM+0x4D0 onto this event (0x40E6E4 unlinks and relinks it, +0x20 = the event), so FM+0x4F0 then names this event. - It clears FM+0x51D, sets the interrogation state 0xB (0x23 when [FM+0x510] & 1) and hands the slot's Purposes to 0x1B5E36C(FS, member) unless flag bit 2 is set; 0x4AA210(GM+0x6C80, member) can then raise a UI refresh flag.

Ending an event is 0x61DB24(event, force), 40 callers (the member's death 0x626E38, the seat move 0x61E13C, unseating 0x61B274, the per-turn expiry 0x1BF00C0, the follower setter 0x7D52B0 ...), all with force 1. It returns at once when [event+0x9D] is set; otherwise 0x61EE0C(FS, event) unbinds the event's quest (0x4FA558 the placed quest, 0x7DD708 unless it is active and not forced, then 0x7E04B4 on the quest system), fires the event's EventOnClear for each participant, starts each participant's ActivateCooldownOnFinish cooldowns and frees the event (0x61EBA0, its destructor, 0x596E84). The per-turn expiry 0x1BF00C0 (the participants' EventOnSimEventTimeOut events, 0x622A84, then the end) acts only once the end turn [event+0x98] has passed; it read 0 on 7 of 7 outpost events, so those never expire on their own.

The orders

The Army screen offers three orders that touch missions, each a menu-selection predicate with a mode type:

Order Prompt What it does
Kill Interface/Menu/MenuSelection/Prompt::OrdersAssassinate, "Command {1} to Kill {2}.", mode Orders_Success_Assassinate a follower or spy against a living enemy captain who is not on a mission quest; creates one of six attacks at equal weight (Duel, CampRaid2, Raid_Caragors, Raid_Checkpoint, Raid_Supplies, Chase): Army-screen vf19 0x1898A38 -> 0x1899114 -> 0x18911FC -> 0x61DE2C(context, candidate, player-created 1)
Ambush Interface/Menu/MenuSelection/Predicate/FactionMember::OrdersJobAmbusher, prompt "Ambush", ResultAction OrdersAugmentMission, mode Orders_Success_JobAmbusher adds the captain to an existing mission's ambusher slot
Reinforce mode Orders_Success_JobBackup adds the captain to an existing follower mission's backup slot

Only the Duel of the six attacks moves a seat (Actions 10, the follower as the other side, result SubjectKilledByOther); in the others a follower's win kills the enemy (Actions 7).

The augment chain (dispatcher 0x1899114, augment branch):

  1. PassSimEventAssignToJob (0x18BDD1C) and the event's PlayerAssignmentJobGroupPicker (0x189D5E0) feed 0x188ABC4, which builds the pending order at FS+0x28: +0x38 the event, +0x60 the member, +0x68 the job group.
  2. CreateWUIPresentation (0x1BEDED4) plays the order's 3D scene.
  3. The quest-start layer opens in mode 4 (0x4666E8 -> 0x466758 -> 0x18E4CB8 -> 0x18BB000).
  4. On confirm, 0x18911B0 runs 0x1BF02E8([p+0x38], [p+0x68], [p+0x60]) and then 0x1B59F50(FS+0x28).
  5. The create branch runs 0x18974EC -> 0x1898194 (PassSimEventCreationData) -> ... -> 0x18911FC -> 0x61DE2C.

The data. - The mode type Interface/HierarchyMode/Type::Orders_Success_JobAmbusher has the predicates CaptIsCaptainOrWCFollower_HLIsEnemyOnInactiveSE, the fail predicates IsCaptiveOutpostPos and IsCaptiveEasterling, PassSimEventAssignToJob true and the objective text UI_Orders_JobAmbusher. The other modes are Orders_Success_JobBackup, Orders_Failure_AmbusherFull / _Active and Orders_Failure_BackupFull / _Active. - The pickers: _StructuresFaction.SimEventAssignJobGroupPicker holds Entry items, each a SimEventAssignJobGroupEntry {Job: the target's job, IsFollower, AssignJobGroup}. There are 47 entries, and 412 of the 431 sim events have an empty picker. Raid_Caragors' picker [103]: entry 24, a PS_Subject or PS_Other enemy -> AmbushGroup; entry 25, a PS_Subject follower -> BackupGroup; entry 26, a PS_Other follower -> Backup2Group. - The database has ten job groups. AmbushGroup {PS_Ambusher_01, _02} is gated to Act 2 (GlobalVarPredicate Act2) with the objective override Quest_JobGroup_AmbushObjective; BackupGroup {PS_Backup_01, _02} and Backup2Group {PS_Backup2_01, _02} share Quest_JobGroup_BackupObjective. All three weigh QuantityWeights [90, 8, 2]. By the slots' JobGroup: AmbushGroup 19 events, BackupGroup 24, Backup2Group 15, the three *Invasion groups 1 each. The ambusher jobs carry OtherJob PS_Subject and OtherMustExist, with no AliasJob; 73 jobs alias PS_Other, and none of the ten groups holds one. - The strings: UI_Prompt_JobAmbusher "Ambush", UI_Orders_JobAmbusher "Command {1!s} to ambush the existing {PowerStruggle} Nemesis Mission.", Quest_JobGroup_AmbushObjective "{1!s} is ambushing a {PowerStruggle} Nemesis Mission."; UI_Prompt_JobBackup "Reinforce", UI_Orders_JobBackup "Command {1!s} to reinforce the existing {PSBranded}Follower Mission.", Quest_JobGroup_BackupObjective "{1!s} is reinforcing a {PSBranded} Follower Mission."; UI_Orders_MissionFull "This Nemesis Mission cannot accept any more Ambushers or Reinforcements.".

An ambusher reaches a mission only through its layer's script and spawners. duel_00.scripts checks QR:GetIsJobGroupAssigned(DBQuestJobGroup.AmbushGroup) and then calls ExMgr_SO:Ambush() (Backup and Backup2 likewise), with items such as PS_DuelAmbushC2 and NemesisStory_Ambush; every duel layer carries spawners for PS_Other and the six ambusher and backup jobs (6 of 6). Ambushers enter through per-mission intro branches (PS_Intro_Execution_WithAmbusher_SPR, PS_Chase_C2Ambusher_*, PS_FrameAmbusher_ELM).

Outpost missions

  • The 50 outpost sim events (*_Outpost_0<n>, *_UB_OP<n>) have one participant slot each, the commander's. MaxParticipants is 0 on all 50, so the full-event switch above never fires. Each event's assignment picker is its own primary and every one is empty (KillOlogs_Outpost_01: [106]); its Create and Confirm order-scene pickers are empty too (Raid_Caragors has 4 and 4). Their quests start on QS_SingleParticipant_Base_WUIP with StartScreen 0 and RequirePlayerConfirmation.
  • The 30 outpost layers (every spawncondition* layer of the six regions) carry 13 spawner jobs each (PS_Subject, the ten SC_<tribe>, Outpost_Commander, SC_DeathThreat) and none for PS_Other, an ambusher or a backup (the six duel layers carry all seven). A spawner asks by alias: the commander's spawner names PS_Subject, his job is SC_Subject_OutpostCommander. So no outpost mission spawns the holder of a second job, at its start or later.
  • The outpost layer script has no ambush code (Nurnen spawnconditionsop1, 3,066 lines: none names Ambush or Backup; it applies events to PS_Subject and SC_Subject_OutpostCommander only).
  • The outcome's results name only PS_Subject (ResultPickerJobOther is null on the outpost events).

Open questions

  • Whether the screen opens when the setup sequence above (record 0x4666E8 of [menu+0x518], layer 0x466758 - 0x48, 0x19F0E98 on the placed quest, 0x18E493C, 0x18BB000) is run from outside the game's own callers, on the main thread.
  • Whether 0x1B59EF4 and 0x1B59F50 are the order's confirm and cancel; and what plays QS_FortAssault_Edit_Player_WUIP (the war-upgrades layer is the candidate).
  • Who fills a stage character's three context cells (+0x6B8, +0x6E0, +0x708); the presentation's setup is the candidate.
  • What the second list in the placed quest's job match is for: it passes an entry by Quest/Jobs/List with no member check.
  • The event fields not decoded: +0x28 (u32 4 on four of five events read, 0x10 on the fort defense), +0x30 (16 bytes) and the entry's +0x34 (0, 1 or larger values).
  • Whether an engine function removes one participant entry from an event: the order's cancels act on the pending order only.
  • Whether a save keeps a participant entry whose slot, job or group record a later start lacks.
  • Which layer owns 0x18DAF8C, a reader of the quest description: it reads [this+0x10110] and [this+0x23558], past the quest-start layer's 0xE720 bytes.
