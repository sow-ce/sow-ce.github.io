Quests from anywhere — the quest state machine (PROVEN IN-GAME 2026-09-26, all regions)

A mission marker is a placed quest object (vt 0x1F9DFE0: +0x40 name, +0x58 context, +0x120 state machine vt 0x1F9DFB8, +0x180 trigger, +0x188 Quest record). Trigger +0x198 = NavMarker. - State = pending (+0x12C) unless -1, else current (+0x128) - SetState 0x159DE4 parks current at -1 mid-transition. Dispatcher 0x1162D8, events 0 CanEnter / 1 CanExit / 2 Enter / 3 Update / 4 Exit. States: 0 Inactive, 1 SimEventEval, 2 PreActivate, 3 DirectActivate, 4 FadeOut, 10 TimeOfDay, 11-15 Load, 16 InstantiateBundles, 17 Active (CanEnter = bundles loaded; Update = the fail-distance check), 19 PostActive, 20 Completed, 21 Failed, 22 Cancelled, 25 Cleanup. - ActivateBypassTrigger body 0x19F060C(obj): state <= 2 -> SetState(3); handlers run synchronously -> main thread only. - Tribe missions fail you beyond 120 m of the relay (QR:SetFailObject(QR, 15000) + RequestDistanceToObjectEvents(QR, 12000) in the prefab script), so move the player first: CCharacter.TeleportToObject 0x658C30 only QUEUES (push 0x659884 onto [0x2A86880], sets CChar+0x2C21 until the engine performs it) - call it on the main thread, target the quest trigger* (a relay can hang over a house; the trigger is where a player stands), wait for arrival + the pending flag to clear, then activate. The IMMEDIATE slot 111 from the render thread faulted inside the engine on a jump into an unstreamed section and took the game down. CCharacter.TeleportToLastKnowNavMeshPos 0x19B7AA0 is the engine's own unstuck (queued).

Story characters exist on demand — rebuild + ambush (PROVEN IN-GAME 2026-10-01)

On an end-game save that never had them, Daz, Gaz, Zog and Baz were rebuilt with the engine's own routine and their story ambushes played with their intros (user screenshots); a built copy is SAVED - Baz fired after a game restart. A story character is a Faction/PresetMembers record; a built orc carries it at FM+0x190. - Who builds them: army init (Faction/Definition.PresetMembers, 0xFDAC54) and quests — a quest's PrefetchPresetFactionMembers are built FRESH at its LoadFactionBundles state (0x625D98 -> 0x62662C -> army of the CURRENT region -> 0x62666C). - The sequence (no hook): ctx = 0x18DE04(FS+0x98, army) (asserts on a non-army record: check [army+0x18] == [FS+0x98+0x10] and the 0x290-stride entries first), fm = 0x1C1D378(ctx, preset), then if 0x1C1C638([ctx+0xD8], preset) (army's own preset) 0x1BD2300([ctx+0x20], fm). Main thread, one tick. Level at creation = NoRowXPLevel - 1 without a row (Daz: 0); the ambush levels him. - Death: the build copies GlobalVarToSetOnDeath to FM+0x398; SetDead 0x626E38 sets FM+0x508 bit 2 and that campaign variable True (Baz/Gaz -> BruzBrothers_*Dead, which gates Daz's ambush via BruzBrothers_BazGazDead). - A queued ambush request fires only in its own region: request +0x18 must equal [FS+0x1B8] (0x6DD92C, "The faction has changed") — Daz's, queued in the desert, sat at 566 retries in Minas Ithil until re-homed. - After the ambush the same orc is a captain of the current region (row, tribe, role, rarity) and FM+0x190 is cleared. The UI shows level FM+0x4B8 + 1. - Tools: AIRE story_member_create (the proven route), story_census, campaign_gates, quest_gates; framework Nemesis Events Force builds a missing one first (native op story_build, same sequence — compiled, NOT yet run in game).

Your Overlord betrays you — forced, it takes the fort (PROVEN IN-GAME 2026-10-02)

Vanilla never does it, by design, in three places: all 18 betrayal ambush defs list Overlord in ExcludedRowRanks (91 of 100 defs do); the betrayal Job General_Betrayal picks only Captain/Warchief rows; the hit-your-follower betrayal (ImmediateBetrayal_Predicate, 3 hits in 3 s then 5 in 6 s) requires IsOverlord_Not. No Overlord-specific betrayal VO exists. - Forced: AI_BecomeHighestLevelFollower_Betrayal (NeverPickAmbusherWithJob - a provided ambusher is its normal mode), Force gates + the Overlord ExcludedRowRanks cell cleared, then TriggerAmbush 0x6DDCB8 with the region Overlord's FM (must be out of the world). User-confirmed twice on Seregost's Overlord: spawned in 0.5 s, betrayal with his own personality's line, follower bit cleared, Overlord row kept; 15/15 cells restored each run. - Region ownership IS the Overlord's follower bit: Faction:GetFactionPlayerOwned (stub 0x7A2800) = 0x1E484C(FS, faction) -> the region's Overlord FM -> FM+0x508 bit 27, nothing else. So the betrayal loses the fort: the engine shows him as the enemy Overlord and the player's warchiefs were removed. Dominating him back restores follower = 1 with the row kept. - The fort-defence Lua (OwnerNamedOnSpawn) converts ANY named defender, FD_Overlord included, to the invaders on a FA_FollowerBetraysPlayer event (ActiveBetrayalFromAbuse/IsPlayerFollowerRemove). - Not yet a C++ Force button.
