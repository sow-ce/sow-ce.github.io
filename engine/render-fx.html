ClientFX System — the custom-VFX import surface (CRACKED OFFLINE 2026-08-19)

Everything below is MEASURED from the binary and cross-checked against the shipped .fxp corpus. No delivery claim here is in-game proven — see the delivery section.

The .fxp load gate is ONE function, and it never sees a filename

LTFX occurs exactly once in the whole 120 MB binary, as an immediate in code:

0x048FBB90  FxResourceLoad(rcx, rdx = stream)
    mov  rax,[rdx] ; mov r8d,8 ; lea rdx,[rsp+0x48] ; call [rax+8]   <- stream->Read
    cmp  dword [rsp+0x48], 'LTFX'  /  cmp dword [rsp+0x4C], 8         <- magic + version
    mov  ecx,0x60 ; call 0x3DE238 ; call 0x74D000                     <- new FxResource(0x60)
    call 0x74CF10                                                     <- GADB-from-stream
    mov  [rdi+0x48], rax                                              <- db at FxResource+0x48
    (fail) lea rcx,[0x20098E8] "Failed to load the database out of a stream."

It is reached ONLY through vtable 0x2312340 slot 29 (39 slots, no RTTI; ctor 0x1D22C0C, dtor 0x1D22CC4) — a resource-type handler class, one virtual per asset kind. Path resolution happens UPSTREAM, so the loader takes a stream object whose vtable slot 1 is Read(dst,size). That makes it a candidate in-process entry point for registering an effect with no file at all.

The node factory: 36 node types, 2,228 properties, all recovered from CODE

Two parallel tables, both static:

table base / stride per entry
A — descriptors 0x263F800 / 0x40 +0x00 property array, +0x08 COUNT, +0x10 short name, +0x18 desc vtable 0x1DB10E0, +0x20 "ClientFX.<Type>", +0x28 parent, +0x38 flags
B — runtime 0x2681DD0 / 0x50 +0x00 name, +0x10 create, +0x18 destroy, +0x20/0x28 update/render, +0x30 deleting-dtor thunk (reveals the node CLASS VTABLE + object size). CORRECTED 2026-10-28: not one table and no update / render slots - 36 separate 0x50-byte type entries reached through the registry 0x21DB460; +0x20 / +0x28 / +0x30 create / delete / destroy the node's load-time KEY, +0x38 / +0x40 size and build its per-instance object (kb/vfx-runtime.md "Node types")

READ THE ARRAY AT +0x00, NOT +0x30 OF THE NAME-ANCHORED ADDRESS. Anchoring on the ClientFX. string and reading proplist/count at +0x30/+0x38 assigns every array to the PREVIOUS type — silently and plausibly: the array full of NodeAttractors/BoltColor/ Component0..3 then reads as ClientFX.Model, and SceneRender's fog/HDR/DOF block reads as ClientFX.Sound. Caught only because the shipped files disagree.

The arrays live in uninitialised .idata (vsize 0x4F9000 vs raw_size 0x14CE00, so anything above 0x26F8E00 is zero at rest) and are built at start-up:

thunk:  sub rsp,N ; xor edx,edx ; lea rcx,[list] ; mov r8d, count*0x48 ; call memset
        ; add rsp,N ; jmp init            <- STOP DECODING AT THIS JMP: the next type's
                                             thunk follows the int3 padding and overwrites
                                             the size, which makes 35 of 36 types miss
init:   lea rcx,[list + i*0x48] ; call <stub_i>          (once per property)
stub_i: PropRegister(slot, "Name", TYPE_CODE, &default, annotation, 1, sub, accessor)
          rcx          rdx      r8d        r9        [rsp+0x20] [+0x28] [+0x30] [+0x38]

r8d is the FXDB descriptor type code — the same vocabulary as the file's own descriptors (Force -> 2 Float; Filter -> 5 StringEnum with annotation type=EImpulseFilter). The memset size is the proof of the array bound: Beam's is 0x708 = 25 x 0x48 exactly.

Three addressings must all be followed or the walk under-reports: lea rcx,[rip+d] (absolute slot), lea rcx,[rbx+N] (slot base+N/0x48, inside a shared GROUP function entered by call), and mov rcx,rbx (slot 0 of a group, no lea at all — omitting it leaves every type exactly one property short). A few properties (KeyName, FxName, every GROUP_BEGIN marker) are registered INLINE with no stub; decode those from the enclosing function START, never from a backward window — a misaligned backward decode resynchronises just before the call and silently drops the arguments.

50 descriptors / 2,228 properties / 2,227 named. The 14 without a ClientFX. name are not anonymous — they are the class hierarchy: BaseFX (15, the common header every visual node inherits), BaseSpriteFX (41), BaseCreateFX (38), LightningComponent (6), FlareComponent (4), DebrisType (8), OcclusionQueryFX (19), ReferenceFX (2), FxGlobalProps (5) and the five curve classes CurveFloat/Int/Vector/Color/File (2 each). Per-type counts are already FLATTENED (Lightning's 92 includes BaseFX's 15), so authoring needs no inheritance resolution.

Validated against data the code never saw: 7,653 descriptors across 40 shipped effects, 100.000% named, and every recovered type code that was recovered matches the file. A record carries a SUBSET of its type's properties (Lightning: 68 of 92 — the file omits the editor GROUP markers), so the engine binds by HASH, not by position or completeness.

Cloning a donor drags in an unreachable material 3 times out of 4

Census over 1,814 shipped effects (container sweep, 5 s): of 4,398 node materials, 3,241 are BUNDLE-ONLY (73.7%) and only 1,157 (26.3%) ship as loose entries. Those materials are not broken — they resolve while their own container is loaded, which is correct for an effect playing on the character whose bundle ships them. It breaks when a node is transplanted across characters, which is exactly what the forge does. Measured case: the SSJ2 aura's Lightning nodes inherited hand_of_god\materials\hog_beam_core.mat from the torment donor; that material is section-resident in player_eltariel.bndl (Patch_DLC3 embb[143]) and ships in no loose entry, so for Talion it is unreachable and the arcs draw nothing. In the same build the ParticleSystem's material (fx\common\smoke\smokeblack01a.mat) IS loose — and the sparks rendered while the arcs did not. Run call("fx_dependencies", path=...) on every authored effect and re-point anything bundle_only at a loose material or ship it in the mod.

Two socket vocabularies coexist. Across 95 distinct attach points, L_Hand (538) outnumbers LeftHand (369) and R_Hand (93) sits beside RightHand (114): the underscore forms belong to creature/orc rigs, the plain forms to the player rig. A donor cloned from a creature effect therefore carries socket names Talion's skeleton does not have. player_base.skel contains Torso, Head, LeftHand, RightHand, LeftFoot, RightFoot, Pelvis, SocketHead, SocketAttach, Socket_Ring. The literal string null (223 uses) means unattached.

Delivery — what is settled and what is not

  • Only 60 .fxp paths exist as loose archive entries (Patch_01/_LC 60, Patch_DLC4/_LC 3, Patch_07_LC 1) out of 5,915 known effects. The rest ship as LTFX sections inside .embb bundles. torment_troll_success.fxp — the file the 2026-08-19 dead-end round tried to override — is in_bundle, shipping inside player_eltariel.bndl across Patch_07/08/09/11. So that round tested the loose lane on an asset that also has bundle copies, which is exactly the [[loose-entry-vs-bundle-embb]] trap.
  • archivepatchloosefiles.txt and the "path index blob" are the SAME table — u32 ver=1 | u32 strtab_size | strtab | u32 count | count x (P919 hash, str_offset) sorted by hash. It is both "what this archive overrides" and "how a loose file is found by name". Verified on the staged mod: file #0 is 44 bytes declaring exactly fx\custom\ssj2_aura.fxp at 0x5EB546B4, hash-checked against the engine's own LOOKUP table at 0x1DB50D0 (1/1), the same shape as the working splash-menu mod (2/2). The payload in the mounted archive is byte-identical to source.
  • UNPROVEN: whether the engine will serve a path that exists in NO shipped archive. That is the one open question and it costs a single restart — python scripts/fx_delivery_verdict.py --arm, fast travel, then re-run without --arm. The verdict hunts a CANARY (SSJ2_Head/SSJ2_LeftHand/SSJ2_RightHand, written into each node's KeyName) rather than the path string, because we allocate the path string ourselves so finding it proves nothing.

THE .fxp EDITOR HID MOST FIELDS (CORRECTED 2026-10-20). FxpEditor.run() summed descriptor counts until the record's cell count was covered; packed bools share cells, so it stopped early on 23,294 of 27,889 records (83.5%) of 4,540 shipped effects, and an edit to a hidden field raised KeyError, which the build scripts' try_set turned into a silent skip. The run is fields[doff : doff + N], N = the u8 after the record's u16 cell count (the main-GADB law); those runs tile the descriptor table in 4,540/4,540 files. Fixed in scripts/fxp_editor.py; the AIRE editor is aire/vfx/fxp.py (FxDoc, byte-identical no-op 4,540/4,540, 226,028 verified edits), and fx_validate now checks complete runs. Among the hidden fields: Model.ModelScale / ModelColor - the "draw scale 0.12 whose source was never found" is the rock donor's own ModelScale curve (0.12 -> 0.0 over the node's life). The engine check - aire/formats/clientfx_engine_check.engine_check(bytes, path): the game's own load (vf3 0x48FBB90) + process (vf4 0x3E4540) under Unicorn, guard-paged heap, asserts recorded; 968 shipped effects all read to their last byte, 949 accepted clean (19 = empty-KeyList placeholders refused by design). Median 89 ms per effect.

_extract REFUSES a path that is not a loose entry, and that is correct — resolving a non-entry path by name returns somebody else's bytes. But it left 81.6% of the effect pool unreadable. The bundle lane closes most of it: loose 23.3% + bundle 56.7% = 80.0% readable, 0 wrong magic (n=60). It needs all THREE candidate sources — the BundleIndex, the fxp_bundle_members.json map (which has effects the index returns nothing for, e.g. rd_wind and the whole sauron_boss_fight set), and the content-verified resolve_blob (which finds bundles the name-keyed TOC lookup misses) — and must confirm by the container's OWN path table, because a manifest can declare an asset its paired EMBB does not carry.

SWEEP CONTAINERS, NOT PATHS — measured 100x. Resolving ONE effect through the bundle lane costs 4.0 s (40 paths / 159 s, 33 extracted), because the container is re-derived from the membership map every time; the 5,915-effect pool that way is ~6.6 hours. A single .embb holds hundreds of sections, so opening each container ONCE and taking every LTFX section out of it collected 1,814 effects from 227 containers in 6 seconds, and the exhaustive sweep — 190,407 containers, 30,531 effect instances — took 783 s. DonorAtlas.build_from_containers (what call("fx_donors", refresh=True) now uses) does this and MERGES with the loose sweep, since the two see different halves of the pool.

Result: 33 of 36 node types have a shipped donor (91.7%). The three that do not — AnimatedPhysicsModel, Tracer, VolumetricCloud — are declared by the engine with full property schemas (76 / 37 / 39) and used by no shipped effect anywhere. They are the only types where authoring cannot start from a donor.

GPU Shader Constant Pipeline (CRACKED 2026-04-17)

392 shader constant objects fully decoded — the entire Monolith render pipeline exposed. Objects are 0x50-byte (80 bytes) each, packed contiguously in static arrays. AIRE module: aire.visuals.shaders.

Object Layout (stride = 0x50):

+0x000  vtable ptr         → data type (Float, Vec4, Matrix, Buffer, etc.)
+0x008  size/type flags    → high word = value size (0x10=16B vec4, 0x04=4B float, 0x30=48B)
+0x010  bind address ptr   → points to self+0x040 (GPU reads from here)
+0x018  name string ptr    → "k_vShadowScaleXY"
+0x020  hash + sort index  → u32 name hash + u32 field_index
+0x028  prev-sibling ptr   → linked list
+0x030  next-sibling ptr
+0x038  padding (always 0)
+0x040  ** VALUE DATA **   → actual float/vec4/matrix data the shader receives

Key vtable classes: 0x2001A68 (Float, 22x), 0x2001A98 (Vec4, 110x), 0x2001AE8 (Vec3/4, 54x), 0x2001AC8/AF8 (Matrix, 38x), 0x2001AA8 (Buffer/UAV, 68x), 0x2001AB8 (Uint, 36x).

A writer thread can only win some draws (the framework's old "GPU Color Engine" flickered for exactly this reason; archived Archive/gpu_color_constants_20261014/). Constant in the sample (but unproven as levers): k_vAmbientColor, k_vVolumetricCloud*, k_vOverdrawColor, k_vLightFactorTransform, k_vParticleInitialColorMin/Max, k_HairLightFactor. Render thread and the command ring - the main thread's frame as the renderer receives it (MEASURED 2026-10-28)

Reader: call("render_commands") / call("render_commands", frames=3) (aire/pipeline/render_commands.py, read-only, no hook). Thread census: kb/live-runtime.md "Threads and the frame".

The render thread is a command processor. RenderThread is a static object [base+0x267E338] (thread class vt 0x1FFD4D0: vf8 name 0x7F9AE0, vf9 stub 0x7F9AF0, start stub 0x1C8F150 -> trampoline 0x797DD4), routine 0x1C8F158: one-time init 0x1C8ECB8 (registers wldmsh, wldclnt, txanm, texcpu, fog_overlay.mat ...), SetEvent (ready), then while (0x1C8EDE0(queue)) {}. It uses ~one full core (970-1000 ms of CPU per second, in combat).

The queue = 0x272E8D8, state at +0x38: +0x08 ring begin, +0x18 ring end (2 MB), +0xD0 read cursor, +0xD8 write cursor, +0x128 / +0x130 counters. The executor 0x188E08 calls the qword at the read cursor with rdx = &cursor (QueryPerformanceCounter-timed), then 8-aligns the cursor; state+0x120 != 0 stops the loop.

A command is a bound call {+0x00 thunk, +0x08 object, +0x10 method, +0x18 args}. The thunk advances the cursor by its own fixed size (mov r8,[rdx]; lea rax,[r8+N]; mov [rdx],rax: 0x18, 0x20, 0x28, ... - 35 thunk shapes seen) and tail-calls method(object, args). So the ring can be walked exactly from its start to the write cursor (~5-10% of steps need a resync on a variable-size thunk). Two snapshots: 24,944 commands / 68 frames and 18,169 / 49 frames; every frame had the same order of its ~22-23 once-per-frame commands (68 / 68, 49 / 49), 360-371 commands per frame, 44 distinct methods.
