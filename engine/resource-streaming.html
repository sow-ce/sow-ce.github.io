Resource streaming, bundles and the file system

How a path becomes loaded data: the file system's mount vector, the resource table, the open / load / parse stages and their request object, bundles and their reference contract, and the creature-bundle manager that decides which creature models exist in a region.

The file system

Every asset path is resolved through one priority vector on the file system object, a static at 0x2A54600 (a function-local static returned by 0x3DDD34). Entry 0 is consulted first.

Offset Meaning
+0x00 SRWLOCK (resolvers take it shared, mounting takes it exclusive)
+0x68 / +0x70 the mount vector: 16-byte entries {u32 kind, Source*}
+0x78 u32 capacity
+0x80 a hash -> path table {u32 hash, char* path}; +0xC0 its generation
+0xE0 the archive-scan bound: the index of the last archive entry + 1

Kind 0 is an archive tree (CArchiveTree, vt_0x22C21B8); kind 1 a directory source (DirectorySource, vt_0x22C21C8, with its directory string at +0x10). A directory source answers with GetFileAttributesW(directory + path); a hit stops the archive search, and the loader opens the loose file itself (0x529BF8 -> GetLooseFilePath 0x52A2F8). The retail game already mounts its Game\ folder as the last entry; that is how the cinematic .vib movies ship as loose files.

Mount(fs, Source** out, path, unused, index) is 0xC28560, the function behind the -arch command line option and the run-time DLC mounter. There is no unmount method. A mount affects the next load of a path only; an asset already resident keeps its data until it is streamed again.

Hashing names

Paths and names are hashed with StringHash 0x423E70: h = h * 919 + LUT[c] over the bytes, with the 256-byte table at 0x1DB50D0 (it folds case, so the hash is case-insensitive). The same hash names GameDB records, fields, animation clips, bones and world objects throughout the engine.

The resource table

Every resource the engine knows is a node in a hash table owned by the resource system [base+0x2A86758]: 0x800 buckets of 0x18 bytes, bucket = hash & 0x7FF, list head at +0x08. A node is resource + 0x10 (+0x08 next, +0x10 hash).

Resource offset Meaning
+0x08 the loaded data (null = not resident)
+0x28 char* path
+0x30 reference count
+0x38 u32 byte size (the engine's own accounting)
+0x52 type (27 bundle, 48 effect .fxp, 20 material .mat, ...)

A resource whose count reaches zero is not freed: 0x1BEAAC unlinks it from an unused list (+0x10) and keeps it for reuse. "Released" therefore does not mean "gone"; residency is decided by the data pointer.

The I/O pipeline

[base+0x2A86750] holds the I/O core (core, the bundle owner + 0x30; the owner, vt_0x22C0FF8, is built by 0x119E5D4 and its stages by 0x1183E8C). Three stages run on three threads, each thread receiving its own stage as its argument:

Stage Address Thread (routine)
open core+0x20 ResourceOpenThread (0x11AECC8, loop 0x1153AA4)
load core+0xF8 ResourceLoaderThread (0x11AEE50, loop 0x1153A00)
parse core+0x1F0 ResourceParserThread (0x11AEF58, loop 0x1153560)

The open and load stages each hold two queues of 0x38 bytes at +0x00 and +0x38, the thread object at +0x70, a CRITICAL_SECTION at +0xA0, a work event at +0xC8 and a stop event at +0xD0. A queue is a double-buffered vector of 16-byte {object, control block} handles:

Queue offset Meaning
+0x00 / +0x08 / +0x10 input vector: begin, end, u32 capacity (10,240)
+0x18 / +0x20 / +0x28 output vector: begin, end, capacity
+0x30 u32 high-water mark (the largest count ever reached)
+0x34 u32 current count

The consumer swaps the two vectors when the output is empty and reverses the run, so service is first-in first-out, and the stage runner always takes the first non-empty queue: queue 0 drains before queue 1 is touched. The parse stage has a request vector at +0x00, a second work vector at +0x18 (capacity 128, consumed by 0x3DC654), its thread object at +0x30, locks at +0x60 and +0x88, and events at +0xB0 / +0xB8. Bytes [base+0x262B520 / 521 / 522] switch the open, load and parse threads on; when one is 0 that stage's work runs inline in the caller. All three are on in the shipped game.

The request object

A request (SResourceLoadRequest, the name in its destructor 0x3DD77C) is allocated together with its reference count (a make_shared layout) and has no vtable:

Offset Meaning
+0x00 the opened file (vf0 closes it); null until the open stage has run
+0x08 u8 cancelled: every stage skips a cancelled request
+0x10 the resource being loaded (its path at +0x28)
+0x18 streaming detail (set by 0x3DD548 from the texture streamer)
+0x20 u32 queue index
+0x28 the resource data being built (+0x18 u32 state; 3 = finalized)
+0x30 a bundle, for a bundle content load (the .embb path at bundle +0x70)
+0x38 / +0x40 the bundle load's output slot and argument

The flow

  1. Submit 0x3DDDEC queues the request on the open stage (or straight on the load stage when the open thread is off). Producers include the texture streamer 0x3DD45C and the bundle content job 0x3DB5E4.
  2. Open 0x3DD588: picks the path (resource +0x28, or the bundle's .embb), waits on a semaphore at core+0x7B8 that bounds how many files are open at once, opens the file through the file system and passes the request to the load stage.
  3. Load 0x2D3444: a resource is read into new resource data (0x3DCFDC, 0x3DCF80) and passed to the parse stage (0x3DD248); a bundle content request goes to the bundle loader 0x3DBE50 with the path table below.
  4. Parse 0x3DD2A8: releases the semaphore slot (0x3DD424), parses the data (0x3DD3C4) and hands it to its resource type (0x3DD310).

Texture tiers wait. The texture streamer puts any request whose path contains tex0 or texuhd (the higher-resolution texture tiers) in queue 1 and everything else in queue 0. Because the runners drain queue 0 first, base textures, meshes and bundle content always open before the high-resolution tiers.

In a long play period the open queues' high-water marks reached 1,812 (queue 0) and 1,567 (queue 1) against 33 and 32 for the load queues: the backlog builds in front of the file open.

The path table

The load stage carries the engine's global name table at +0xD8 (core+0x1D0): a vector of {u32 hash, u32 0, char* path} sorted by hash, 30,639 rows in a loaded region. 503 of 503 sampled keys equal the hash of their path, and every row is in order. It names every kind of streamed file (.fxp, .tex, .bnk, .bndl, .anix, .vol.inst, presentation bundles in every language). The load stage passes it to the bundle content loader. It is a row-for-row copy of the file system's hash -> path table (fs+0x80), which Mount builds from the path index file each archive may carry (0x1182428 merges every index into it, sorted); see Archives and file formats.

Bundles

A bundle is a manifest (.bndl) plus a container of its contents (.embb); see Archives and file formats. The bundle registry belongs to the owner (vt_0x22C0FF8): vtable slot 24 0x3DC538 gets a bundle forcing the .bndl extension, slot 25 0x119F1E8 takes a raw path, and the registry at owner+0x718 keeps 0x18-byte rows {u64 hash, CResourceBundle*, u64} (get-or-create 0x1B5DC0).

CResourceBundle (vt_0x1E6E678, 0x178 bytes):

Offset / slot Meaning
vf0 / vf1 AddRef 0x3DEDA0 / Release 0x3DEA38
vf2 / vf3 Prefetch 0x3DECC8 / Discard 0x3DEAEC
vf6 memory accounting 0x6E001C: {loaded, total, bytes}, cached at +0x60..+0x6C once complete
+0x08 char* path
+0x14 reference count
+0x18 the loaded content (a vector of resource handles; null = not resident)
+0x20 the manifest resource (its data is null when the .bndl does not exist)
+0x28 u16 prefetch count
+0x2A u8 generation, incremented by every load and every discard
+0x70 char[0x104] the paired .embb path

The reference contract. A registry row holds no reference. Prefetch (0 -> 1) references the manifest, requests it and, once its data is present, queues the .embb content load as a job on the bundle system (0x3DB574 -> 0x3DB5E4). Discard is the exact reverse and asserts it is never the final reference. Release at zero unregisters and destroys the bundle (0x1B5C9C), detouring to 0x10DD00A if the prefetch count is still non-zero. A holder therefore keeps a handle and a prefetch, and lets go by discarding first and releasing second. A missing path is benign: the registry keeps an entry whose manifest has no data (ten such rows exist in a normal game).

Loading a region's layer bundle does not place it in the world: its resources become resident, but world contexts and placed objects are unchanged. In a loaded region the registry holds about 544 bundles, and every character bundle the region uses is already resident.

Gear needs two bundles. An armour piece's geometry lives in <piece>_g.bndl (.mesh, .skel, .anix) and its material and textures in a set-wide <set>_<slot>_m.bndl named by the design record (Inventory/ArmorData field DynamicBundle). The engine loads both through a gear load request (vt_0x1DB4F78, constructor 0x400AB8) that is created only for an equipped item (give path 0x355474 -> 0x61B868 -> 0x4B4C7C, item equip 0x40136C -> 0x401680, re-skin 0x645890). A piece placed into an appearance without an item gets no request: its mesh is in memory but its .mat is a registered resource with no data. The save loader 0x1C112F8 restores non-item pieces (smc_nonequipment_record_list -> 0x1162D40) without a request as well. A bundle that is resident only because another character's item requested it is released when that item goes away.

Effects only load through bundles. An effect reference (for example an attack's AOEFX path) never loads anything; the effect system finds resident effects by name, and only a bundle (or start-up) makes one resident.

A malformed effect stalls the loader. Every .fxp ends with a u32: the count of the database's (u32, u32) pair table (db+0x68; 0 in 968 of 968 shipped effects). A file without it makes the database body reader 0x4B9B50 read 4 bytes past the end of the file (0x4B9C60); on the raw asynchronous stream (vt_0x1E71010) that read does not return, and every later load waits behind it until the game restarts. A missing file, by contrast, is harmless. The effect database's categories are sorted by the hash of their path (371 of 371), and the loader binary-searches them (0x115B4D4).

Creature bundles

CharacterBundleMgr (CharacterBundleMgr.cpp) is MainScene+0x868 ([base+0x26FFAB0]+0x868). It decides which creature models are in memory.

Offset Meaning
+0x00 / +0x08 entries and their count (146 = the Server/NPCBundle records); an entry is 0x30 bytes: +0x00 the NPCBundle record, +0x08/+0x10 a vector of CResourceBundle* (the same objects as the registry's), +0x28 loaded
+0x18 / +0x20 / +0x28 the load / unload queue {record, u8 unload}
+0x30 the current WorldInfo record
+0x38 the always-loaded set (Nemesis, Playerskin_Talion)
+0x50 / +0x68 / +0x80 the world set, the override set, an extra set (Playerskin_DarkTalion)
+0x98 / +0xA0 two override list slots
+0xA8 the provider (_StructuresWorldInfoBundleData primary record)
+0xB0 dirty byte

The update 0x4B4FFC runs when the dirty byte is set: wanted = the first override list (or the default list) plus the always and extra sets; world set = the provider's list. The reconcile 0xE9F360 requests what is new (RequestBundleLoad 0x4B6204), queues what dropped out for unloading, then drains the queue, firing loaded / unloaded events through the global script agent (GM+0x6CF0).

A list's length is its field descriptor's element count (read by 0xE9EA30): every Server/NPCBundle/Lists record has two fields (the bundle array, hash 0x7AB8B862, and an empty second array). World_Island_Day holds six bundles (Goblin, Spider, Warg_Base, Fellbeast, Troll_Base, Troll_Poison) and World_MinasIthil_Day nine. A region keeps its whole creature set loaded for the visit; there is no per-encounter picker.

A region change resets everything: every set and every loaded creature bundle is cleared, including loads requested on demand, and the region's sets are rebuilt (skins first, then the world set, about 3 seconds to resident). Loads requested directly with RequestBundleLoad persist within a region, because no set owns them.

The spawn gate 0x16652C (template -> model -> NPCBundle -> IsBundleLoaded 0x1665B4) requests a missing bundle only when the region's WorldInfo.IsTestWorld is set (0x5B85B4); retail regions have it clear, so a spawn whose bundle is not loaded is rejected ([AI|SPAWNAMBIENT|REJECT] ... doesn't have character bundle loaded). The descriptor 0x166878 reads only the template and the spawn manager (SM+0x78 the per-template override table, +0x80 its count, +0x88 the AI/Templates category); the model and bundle are plain field reads (0x16680C, 0x166680). A null bundle allows the spawn: 94 of 177 templates have none (every orc and olog class, tamed wargs, the fellbeast), because their data is always resident. The chain from a spawn channel to its bundle is plain data: AITypes.Entries[] -> _StructuresAISpawnAmbientTypeEntry.AITemplate -> AI/Templates.CharacterModel -> Character/Models.Bundle.

Scripts and the console reach the manager through System:LoadOverrideNPCBundleList(list, slot) / LoadDefaultNPCBundleList and the console commands CharacterBundleMgr.Dump, LoadOverrideBundle and LoadDefaultBundleList (command table at 0x2674408); quests unload their overrides when they end.

Memory

The engine's own byte count understates the real cost of a single bundle and overstates a burst: Nazgul_base (36.0 MB by the engine's count) added 120 MB of committed memory and 120 MB of video memory, while 129 bundles requested at once (622 -> 4,337 MB by the engine's count) added only 571 MB of video memory and 665 MB of commit, because they share resources. Bundle loads do not consume the scarce low (below 4 GB) address space. A fast travel releases everything a region loaded; nothing accumulates across regions. WorldInfo.MaxBundleSizePC (1096 on PC, 548 on consoles) is checked only when content is packed; no run-time code reads it.

Open questions

  • The maximum count of the open-file semaphore at core+0x7B8 (its creator is not traced).
  • The meaning of the resource-data states other than 3 (finalized), and what the parse stage's second work vector carries.
  • Why the global path table's second field is 0 while the per-bundle name arrays carry 1.
  • Which other code submits I/O requests: only two callers of the submit function exist, so the resource system may queue some loads elsewhere.
