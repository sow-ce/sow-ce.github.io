Resource streaming, bundles and the file system

How a path becomes loaded data: the file system's mount vector and who mounts what, the resource table, the open / load / parse stages and their request object, bundles, their reference contract and the set algebra that decides where each resource's bytes come from, the engine's own hot reload, and the creature-bundle manager that decides which creature models exist in a region.

The file system

Every asset path is resolved through one priority vector on the file system object, a static at 0x2A54600 (a function-local static returned by 0x3DDD34). Entry 0 is consulted first.

Offset Meaning
+0x00 SRWLOCK (resolvers take it shared, mounting takes it exclusive)
+0x68 / +0x70 the mount vector: 16-byte entries {u32 kind, Source*}
+0x78 u32 capacity
+0x80 a hash -> path table {u32 hash, char* path}; +0xC0 its generation
+0xE0 the archive-scan bound: the index of the last archive entry + 1

Kind 0 is an archive tree (CArchiveTree, vt_0x22C21B8); kind 1 a directory source (DirectorySource, vt_0x22C21C8, with its directory string at +0x10). A directory source answers with GetFileAttributesW(directory + path); a hit stops the archive search, and the loader opens the loose file itself (0x529BF8 -> GetLooseFilePath 0x52A2F8). The retail game already mounts its Game\ folder as the last entry; that is how the cinematic .vib movies ship as loose files.

Mount(fs, Source** out, path, unused, index) is 0xC28560. A folder becomes a directory source. A file that exists (0x52A42C) becomes an archive tree, opened by 0x11AE014, which keeps the path as given at archive+0x50. A path that names nothing is skipped without a message. An archive's first file, archivepatchloosefiles.txt, is its path index: Mount merges it into the hash -> path table at fs+0x80 (lookup 0x3DDAD8, merge 0x1182428) and recomputes the scan bound. An index past the end of the vector mounts at the top (0xC28818). There is no unmount method.

Mount has three callers:

  • The command line. The file-system setup 0x119717C (called from the shell initialization 0x117CF30) first mounts every -arch <path> argument at index 0, before it reads the config list.
  • The config list. The same setup then mounts the list's lines through 0x1197418 -> 0x11972C8, each in front of the nearest earlier line's archive (the index comes from 0xC34960). The first line, ..\Game, therefore ends last, and every later line stacks above the one before it: this is the list's "file search order is from the bottom up".
  • Downloaded content. At run time the file system's "mount at the top" method (vt_0x22BF9C8 vf2, the object at [base+0x26FF048]) is called by 0x1848A50 for the archives the online service downloads into the player's profile folder.

In one running game the vector held 89 entries (capacity 96): 74 archives from the config list, with the 14 lines that name missing files skipped; the six downloaded packs at the top; and ..\Game\ last.

A mount affects only the next load of a path. A resource the game already holds, or keeps cached without references, is handed back as it is (see Reloading below), and a fast travel does not re-read it. Every open walks the vector from the top (the resource open stage 0x3DD648 -> 0x3DD8FC -> 0x3DD9F8). An archive answers from memory, through a binary search of its folder table (0x3DDAB8). A directory source first checks its extension filter (0x3DDC18, a list of hashes of the text after the last dot, which is empty unless set, and Mount leaves it empty) and then tries a real file open (0x3DDCBC builds the path, 0xC3C1B0 opens it).

Hashing names

Paths and names are hashed with StringHash 0x423E70: h = h * 919 + LUT[c] over the bytes, with the 256-byte table at 0x1DB50D0 (it folds case, so the hash is case-insensitive). The same hash names GameDB records, fields, animation clips, bones and world objects throughout the engine.

The resource table

Every resource the engine knows is a node in a hash table owned by the resource system [base+0x2A86758]: 0x800 buckets of 0x18 bytes, bucket = hash & 0x7FF, list head at +0x08. A node is resource + 0x10 (+0x08 next, +0x10 hash).

Resource offset Meaning
+0x08 the loaded data (null = not resident)
+0x28 char* path
+0x30 reference count
+0x34 u16 claim count: how many loaded bundle contents name the resource
+0x36 u16 flags: bit 0 a load finished; 0x10 a standalone request is pending; 0x08 a reload; 0x20 a re-request with stream detail
+0x38 u32 byte size (the engine's own accounting)
+0x52 type (27 bundle, 48 effect .fxp, 20 material .mat, ...)
+0x60 busy while a load is in progress

0x17DE40 is the engine's "loaded" test.

A resource whose count reaches zero is not freed: 0x1BEAAC unlinks it from an unused list (+0x10) and keeps it for reuse. "Released" therefore does not mean "gone"; residency is decided by the data pointer.

The I/O pipeline

[base+0x2A86750] holds the I/O core (core, the bundle owner + 0x30; the owner, vt_0x22C0FF8, is built by 0x119E5D4 and its stages by 0x1183E8C). Three stages run on three threads, each thread receiving its own stage as its argument:

Stage Address Thread (routine)
open core+0x20 ResourceOpenThread (0x11AECC8, loop 0x1153AA4)
load core+0xF8 ResourceLoaderThread (0x11AEE50, loop 0x1153A00)
parse core+0x1F0 ResourceParserThread (0x11AEF58, loop 0x1153560)

The open and load stages each hold two queues of 0x38 bytes at +0x00 and +0x38, the thread object at +0x70, a CRITICAL_SECTION at +0xA0, a work event at +0xC8 and a stop event at +0xD0. A queue is a double-buffered vector of 16-byte {object, control block} handles:

Queue offset Meaning
+0x00 / +0x08 / +0x10 input vector: begin, end, u32 capacity (10,240)
+0x18 / +0x20 / +0x28 output vector: begin, end, capacity
+0x30 u32 high-water mark (the largest count ever reached)
+0x34 u32 current count

The consumer swaps the two vectors when the output is empty and reverses the run, so service is first-in first-out, and the stage runner always takes the first non-empty queue: queue 0 drains before queue 1 is touched. The parse stage has a request vector at +0x00, a second work vector at +0x18 (capacity 128, consumed by 0x3DC654), its thread object at +0x30, locks at +0x60 and +0x88, and events at +0xB0 / +0xB8. Bytes [base+0x262B520 / 521 / 522] switch the open, load and parse threads on; when one is 0 that stage's work runs inline in the caller. All three are on in the shipped game.

The request object

A request (SResourceLoadRequest, the name in its destructor 0x3DD77C) is allocated together with its reference count (a make_shared layout) and has no vtable:

Offset Meaning
+0x00 the opened file (vf0 closes it); null until the open stage has run
+0x08 u8 canceled: every stage skips a canceled request
+0x10 the resource being loaded (its path at +0x28)
+0x18 streaming detail (set by 0x3DD548 from the texture streamer)
+0x20 u32 queue index
+0x28 the resource data being built (+0x18 u32 state; 3 = finalized)
+0x30 a bundle, for a bundle content load (the .embb path at bundle +0x70)
+0x38 / +0x40 the bundle load's output slot and argument

The flow

  1. Submit 0x3DDDEC queues the request on the open stage (or straight on the load stage when the open thread is off). Producers include the texture streamer 0x3DD45C and the bundle content job 0x3DB5E4.
  2. Open 0x3DD588: picks the path (resource +0x28, or the bundle's .embb) and waits on a semaphore at core+0x7B8 that bounds how many files are open at once (0x1184864 creates it with an initial and maximum count of 32, the u32 at 0x262AAA0). It then opens the file through the file system and passes the request to the load stage.
  3. Load 0x2D3444: a resource is read into new resource data (0x3DCFDC, 0x3DCF80) and passed to the parse stage (0x3DD248); a bundle content request goes to the bundle loader 0x3DBE50 with the path table below.
  4. Parse 0x3DD2A8: releases the semaphore slot (0x3DD424), parses the data (0x3DD3C4) and hands it to its resource type (0x3DD310).

Texture tiers wait. The texture streamer puts any request whose path contains tex0 or texuhd (the higher-resolution texture tiers) in queue 1 and everything else in queue 0. Because the runners drain queue 0 first, base textures, meshes and bundle content always open before the high-resolution tiers.

In a long play period the open queues' high-water marks reached 1,812 (queue 0) and 1,567 (queue 1) against 33 and 32 for the load queues: the backlog builds in front of the file open.

The path table

The load stage carries the engine's global name table at +0xD8 (core+0x1D0): a vector of {u32 hash, u32 0, char* path} sorted by hash, 30,639 rows in a loaded region. Every sampled key (503 of 503) equals the hash of its path, and every row is in order. It names every kind of streamed file (.fxp, .tex, .bnk, .bndl, .anix, .vol.inst, presentation bundles in every language). The load stage passes it to the bundle content loader. It is a row-for-row copy of the file system's hash -> path table (fs+0x80), which Mount builds from the path index file each archive may carry (0x1182428 merges every index into it, sorted); see Archives and file formats.

Bundles

A bundle is a manifest (.bndl) plus a container of its contents (.embb); see Archives and file formats. The bundle registry belongs to the owner (vt_0x22C0FF8): vtable slot 24 0x3DC538 gets a bundle forcing the .bndl extension, slot 25 0x119F1E8 takes a raw path, and the registry at owner+0x718 keeps 0x18-byte rows {u64 hash, CResourceBundle*, u64} (get-or-create 0x1B5DC0).

CResourceBundle (vt_0x1E6E678, 0x178 bytes):

Offset / slot Meaning
vf0 / vf1 AddRef 0x3DEDA0 / Release 0x3DEA38
vf2 / vf3 Prefetch 0x3DECC8 / Discard 0x3DEAEC
vf6 memory accounting 0x6E001C: {loaded, total, bytes}, cached at +0x60..+0x6C once complete
+0x08 char* path
+0x14 reference count
+0x18 the loaded content (a vector of resource handles; null = not resident)
+0x20 the manifest resource (its data is null when the .bndl does not exist)
+0x28 u16 prefetch count
+0x2A u8 generation, incremented by every load and every discard
+0x70 char[0x104] the paired .embb path

The reference contract. A registry row holds no reference. Prefetch (0 -> 1) references the manifest, requests it and, once its data is present, queues the .embb content load as a job on the bundle system (0x3DB574 -> 0x3DB5E4). Discard is the exact reverse and asserts it is never the final reference. Release at zero unregisters and destroys the bundle (0x1B5C9C), detouring to 0x10DD00A if the prefetch count is still non-zero. A holder therefore keeps a handle and a prefetch, and lets go by discarding first and releasing second. A missing path is benign: the registry keeps an entry whose manifest has no data (ten such rows exist in a normal game).

Loading a region's layer bundle does not place it in the world: its resources become resident, but world contexts and placed objects are unchanged. In a loaded region the registry holds about 544 bundles, and every character bundle the region uses is already resident.

How a bundle's content becomes resources

Manifests are sorted lists. Every shipped manifest lists its entries sorted by the P919 hash of the path as an unsigned number, then by the path compared case-insensitively. This holds for 806 of 806 loaded manifests (62,270 entries), and every stored hash equals the P919 of its path. The parsed manifest is reached as bundle +0x20 (the manifest resource) -> +0x08 -> [+0] -> +0x10, a block whose +0x0C is the bundle path's hash, +0x18 / +0x20 the entry list {u32 hash, pad, char* path} and +0x28 / +0x30 the size list.

The content loader is set algebra over sorted lists. 0x3DBE50 -> 0x3DC04C runs std::set_intersection (0x3E0218) and std::set_difference (0x3DC388, 0x3DC3E0) over the container's sections, the manifest and the load stage's path table, with the comparator 0x11B5AD4 (hash, then _stricmp). The content's first vector (content+0x00 / +0x08, resources made by 0x3E0628) is B = (sections and manifest) minus the path table: what the container itself supplies. The second (content+0x20 / +0x28, 0x3E03B8) is A = the manifest minus B: entries that come from elsewhere. Of 877 loaded bundles, 398 hold such entries, shipped ones among them, so the second vector is not a "still loading" list. A path in the path table is therefore never taken from the container: a file at that path in any mounted archive replaces the bundle's copy.

The first claim decides. Each A entry goes through 0x3E00FC, which adds a reference and a claim (+0x34); on the first claim only, it also sets flag 0x10 and requests the resource as a file of its own (0x2D40A4). Container bytes reach resources through 0x11B5D14, a single forward pass over the .embb sections in file order against the first vector (_stricmp on the resource path, with the progress kept in content+0x18). 0x1CD4A3C loads a section only when the claim count goes from 0 to 1, or when its type is in a force mask: it clears flag bit 0, raises +0x60 and calls the type's loader. Every later claimant is skipped, so whichever bundle claims a resource first decides its data for as long as anyone holds it. A manifest out of order breaks the set operations: its entries fall into A, each is requested as a file, and those that are not files of their own load empty and stay empty until every claim on them is dropped.

Shader trees are loose files that bundles list. A shader tree (.fxo, tag SRHR) ships as a loose archive entry. Of the 183,631 shipped manifests, 1,433 list at least one (9,381 rows in all), and the bundle's container usually carries a copy as a section as well. Because the tree is a file of its own, it falls into A and is requested standalone, and the container's copy is skipped. A material only registers the trees it names: unless a loaded bundle lists a tree, or the tree is loaded at start-up, it stays registered with no data and the material draws nothing.

Gear needs two bundles. An armor piece's geometry lives in <piece>_g.bndl (.mesh, .skel, .anix) and its material and textures in a set-wide <set>_<slot>_m.bndl named by the design record (Inventory/ArmorData field DynamicBundle). The engine loads both through a gear load request (vt_0x1DB4F78, constructor 0x400AB8) that is created only for an equipped item (give path 0x355474 -> 0x61B868 -> 0x4B4C7C, item equip 0x40136C -> 0x401680, re-skin 0x645890). A piece placed into an appearance without an item gets no request: its mesh is in memory but its .mat is a registered resource with no data. The save loader 0x1C112F8 restores non-item pieces (smc_nonequipment_record_list -> 0x1162D40) without a request as well. A bundle that is resident only because another character's item requested it is released when that item goes away.

The gear budget. These requests go through NemesisBundleMgr ([GameManager+0x6C88], named by its console commands NemesisBundleMgr.PrintMemory and PrintDynamicBundleData). Its initializer 0x1B42728, run once from the database setup, sets the budget +0x00 to Faction/Global.NemsisBundleMemoryLimit x 10 (320 x 10 = 3,200) and builds one object (vt_0x1FF6B90, constructor 0x1C52B10) for each of the 1,484 DynamicResource/BundleDefinition records, kept in a table at +0x08 of 16-byte {record, object} entries. An object's cost +0x3C starts as an estimate, its bundle type's Bundles/Types.MaxMemoryPC (10 for Flair_1MB, 20 for Flair_2MB, 30 for Flair_3MB, the names being the console figures). When the load finishes, 0x3FFA24 replaces it once (latch +0x58) with the real size, bytes / 2^20, sets state +0x48 to 2 and tells the requesters. The estimates are generous: resident Flair_1MB bundles held a median of 0.40 MB (124 bundles, largest 1.12) and Flair_2MB a median of 0.018 MB (20). In one loaded Lithlad 157 bundles were resident at a total cost of 66.3 of the 3,200, so the budget was far from limiting.

Each object's priority +0x38 is rebuilt from its requesters by 0x3FFB10. Each request carries five bytes at +0x50: bytes 0, 1, 2 and 4 are flags, merged by OR, and byte 3 is a number, merged by maximum (0x3FFD44). The score is the highest DynamicBundleLoadPriority among the requesters plus that number, +1,000 for byte 0 (when the bundle has a handle), +10,000 for byte 1, +500 for byte 2 and +1,000 for byte 4. It is then scaled by the requester count: x1.25 at exactly 4, x1.5 at 6 or 7, x1.75 above 8, and unchanged at 5 and 8. Recomputed from the live requesters, this formula gives the value in +0x38 for 157 of 157 resident bundles (requester counts 1 to 49).

The constructor 0x400AB8 copies the five bytes from a struct its caller passes. On the equip and re-skin paths, 0x400084 fills that struct:

Byte Value
0 always 1
1 set when the owner reference has a +0x40
2 set when the owning character has +0x2700, the follower byte +0x23B8 or +0x2C04 set (0x366B88)
3 the member's Player Interaction Score at that moment (0x595364, row 2 column 2 of the score object FM+0x150, the dword at +0x38)
4 from 0x77F804

The score byte is a snapshot: on 34 requests of this kind held by spawned captains it was at or below the current score every time, and equal on 16. Requests made on the give path (0x4B4C7C) instead take their bytes from a struct at +0xF8 of the 25-slot item table, and those carry byte 0 clear.

Each frame 0x614438 re-evaluates the requests when they have changed (+0x50): it sorts them by +0x38, highest first, and adds up their costs. Requests within the budget are loaded (0x614CB0), and the rest go on a local list. For each of those, 0x1B427E4 walks the armor's and then the weapon's OutOfMemoryBackups and takes the first backup whose bundles are all resident already. (In 0x1B424BC, for each bundle with an object, 0x614D3C requires a handle, its counters +0x4C and +0x50 equal, and the state +0x48 equal to 2.) The backup goes to the request's owner (0x1C11CD8, 0x1C11CFC). So a piece over the budget is replaced by something already in memory, and nothing new is loaded for it. The budget applies to this gear path only. Bundles/Policies carries budgets of its own (Character_Nemesis 1,600 on PC), which this manager does not read.

Effects only load through bundles. An effect reference (for example an attack's AOEFX path) never loads anything; the effect system finds resident effects by name, and only a bundle (or start-up) makes one resident.

A malformed effect stalls the loader. Every .fxp ends with a u32: the count of the database's (u32, u32) pair table (db+0x68; 0 in 968 of 968 shipped effects). A file without it makes the database body reader 0x4B9B50 read 4 bytes past the end of the file (0x4B9C60); on the raw asynchronous stream (vt_0x1E71010) that read does not return, and every later load waits behind it until the game restarts. A missing file, by contrast, is harmless. The effect database's categories are sorted by the hash of their path (371 of 371), and the loader binary-searches them (0x115B4D4).

Reloading

The engine's hot reload. ResourceMgr::Reload 0x119F4BC(owner, path), slot 7 of the I/O owner vt_0x22C0FF8 (owner = [base+0x2A86750] - 0x30), reloads one resource while the game runs. It works in four steps:

  1. the filter 0x119EB60 refuses .gamedb, and refuses .anix and .objres according to two engine switch bytes (0x262B50A, 0x262B509);
  2. the lookup 0x17AE1C refuses a resource that has no references;
  3. 0x1188A00 clears every registered bundle's loaded counters;
  4. CResource::Reload 0x3E0AE0 takes the lock, sets flag 8 and queues the resource through 0x2D40A4.

Nothing in the executable calls it. It has two siblings: slot 6 (0x5D5A000 -> 0xC2A880) reloads by path prefix, and slot 8 (0x119F528 -> 0x119DA54 -> 0x11B5F74) reloads by resource-type mask, bundle by bundle, asking for each bundle's content again.

The per-frame processor 0x2D3E10 (its queue served by 0x2D35E8) acts on a queued resource by its state:

State Action
claim count +0x34 is 0 releases the data and does not ask again: a reload of an unclaimed resource is an unload
flag 0x20 releases, asks again with the stream detail at +0x40
flag 0x08 releases, asks again by path with no stream detail: the reload
flag 0x10 and no data asks by path (a bundle's A entry)
always, at the end clears 0x08, 0x10 and 0x20 (and 0xFFC7 at 0x2D4001)

The parser thread runs the type's parse (0x3DD3C4); for a texture, the texture type's vf4 0x5018A4 creates the Direct3D texture. The finish, 0x3E0BD4, must run on the render thread ("Finalize can only be called on the Render Thread!", 0x4C2610). Reloading a 5.6 MB texture this way took about 14 ms from empty to whole: the resource received a new data object and a new ID3D11Texture2D, while its references and flags stayed unchanged. A changed file mounted under the texture's path reached the screen with that reload, without any travel.

Creature bundles

CharacterBundleMgr (CharacterBundleMgr.cpp) is MainScene+0x868 ([base+0x26FFAB0]+0x868). It decides which creature models are in memory.

Offset Meaning
+0x00 / +0x08 entries and their count (146 = the Server/NPCBundle records); an entry is 0x30 bytes: +0x00 the NPCBundle record, +0x08/+0x10 a vector of CResourceBundle* (the same objects as the registry's: an entry holds references to its bundles), +0x28 requested
+0x18 / +0x20 / +0x28 the load / unload queue {record, u8 unload}
+0x30 the current WorldInfo record
+0x38 the always-loaded set (Nemesis, Playerskin_Talion)
+0x50 / +0x68 / +0x80 the world set, the override set, the player's build set (Playerskin_DarkTalion at rest)
+0x98 / +0xA0 two override list slots
+0xA8 the provider (_StructuresWorldInfoBundleData primary record)
+0xB0 dirty byte

IsBundleLoaded 0x1665B4 asks 0x166630(entry + 8). That answers 0 while the requested byte is clear; otherwise it answers the state (vf5) of the first bundle whose state is neither 3 nor 4, or 3 when there is no such bundle. The entry counts as loaded when the answer is 3 or 4, so a bundle that failed (4) counts as loaded and one still streaming (1 or 2) does not.

The update 0x4B4FFC runs when the dirty byte is set. The world set is the provider's list; the override set is the first override list (or the default list) with the records of the always, world and build sets removed (0xE9F280 swap-removes them), so no record is owned twice. The reconcile 0xE9F360 requests what is new and queues what dropped out for unloading, then the update drains the queue, firing loaded / unloaded events through the global script agent (GM+0x6CF0). A request is a flag per entry, not a count: RequestBundleLoad 0x4B6204 turns a queued unload of the record back into a load, else starts the entry loading (0x4B6300) and queues {record, 0}, or fires the loaded event at once; RequestBundleUnload 0x19EB87C turns a queued load into an unload, else queues {record, 1}. The drain unloads an entry by dropping every bundle handle it holds (0x2EE10C, clearing the requested byte) and polls a load (0x4B52A8) until it is loaded. One unload therefore takes the entry's bundles whoever asked for them; only a separate handle on the .bndl outlives it.

The build set is kept by the player's model change (vf136 0x19BF404): the old model's Character/Models.Bundle is taken out of the set and unloaded and the new one requested and put in, one in and one out at every change; the player's build gate reads the set (0x19EAD34). RequestBundleLoad has four callers: the spawn gate 0x16652C, the reconcile, the player's model change and the wrapper 0x19EB83C. 0x19EAC44 (called once, from 0x178701C) is the teardown: every entry unloaded, the four sets and the queue cleared.

A list's length is its field descriptor's element count (read by 0xE9EA30): every Server/NPCBundle/Lists record has two fields (the bundle array, hash 0x7AB8B862, and an empty second array). World_Island_Day holds six bundles (Goblin, Spider, Warg_Base, Fellbeast, Troll_Base, Troll_Poison) and World_MinasIthil_Day nine. A region keeps its whole creature set loaded for the visit; there is no per-encounter picker.

A region change resets everything: every set and every loaded creature bundle is cleared, including loads requested on demand, and the region's sets are rebuilt (skins first, then the world set, about 3 seconds to resident). Loads requested directly with RequestBundleLoad persist within a region, because no set owns them.

The spawn gate 0x16652C (template -> model -> NPCBundle -> IsBundleLoaded 0x1665B4) requests a missing bundle only when the region's WorldInfo.IsTestWorld is set (0x5B85B4); retail regions have it clear, so a spawn whose bundle is not loaded is rejected ([AI|SPAWNAMBIENT|REJECT] ... doesn't have character bundle loaded). The descriptor 0x166878 reads only the template and the spawn manager (SM+0x78 the per-template override table, +0x80 its count, +0x88 the AI/Templates category); the model and bundle are plain field reads (0x16680C, 0x166680). A null bundle allows the spawn: 94 of 177 templates have none (every orc and olog class, tamed wargs, the fellbeast), because their data is always resident. The chain from a spawn channel to its bundle is plain data: AITypes.Entries[] -> _StructuresAISpawnAmbientTypeEntry.AITemplate -> AI/Templates.CharacterModel -> Character/Models.Bundle.

Scripts and the console reach the manager through System:LoadOverrideNPCBundleList(list, slot) / LoadDefaultNPCBundleList and the console commands CharacterBundleMgr.Dump, LoadOverrideBundle and LoadDefaultBundleList (command table at 0x2674408); quests unload their overrides when they end.

Memory

The engine's own byte count understates the real cost of a single bundle and overstates a burst. Nazgul_base (36.0 MB by the engine's count) added 120 MB of committed memory and 120 MB of video memory, while 129 bundles requested at once (622 -> 4,337 MB by the engine's count) added only 571 MB of video memory and 665 MB of commit, because they share resources. Bundle loads do not consume the scarce low (below 4 GB) address space. A fast travel releases everything a region loaded; nothing accumulates across regions. WorldInfo.MaxBundleSizePC (1096 on PC, 548 on consoles) is checked only when content is packed; no run-time code reads it.
