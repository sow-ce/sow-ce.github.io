User interface: Scaleform, menus and the debug menu

How the game builds and draws its interface: the UI manager, the generic view host and the UI render list; the Scaleform movies and the node API that drives them; the string database with its markup, glyph and color tokens; menus, selections and the prompt bar as GameDB data; nav markers and the nameplate; the HUD; the Army screen's 3D stage, highlight, target, Details panel, camera and mercenary screen; the title, save-select and loading screens; and Monolith's developer debug menu with the cheat backend and console behind it.

The interface is a set of Scaleform GFx movies that the engine drives entirely from code and data: the movies hold artwork and timelines, while the GameDB holds menu layers, element placement, prompts, HUD states, text tokens and cameras. This chapter follows the stack from the UI manager down to a single movie clip and a single line of text, then covers nav markers, the Army screen's 3D stage and its camera, the title and loading screens and the developer debug menu that shipped without its controller. The mission start screen has its own chapter, The mission start screen.

The UI stack

The top menu layer is what menu predicates test: the evaluator 0x276E74 compares each record of a predicate's IncludedTopMenuLayers / ExcludedTopMenuLayers with [UIManager+0xF0] and each record of IncludedTopMenuLayerStates / ExcludedTopMenuLayerStates with [UIManager+0xF8]. The cell holds the layer's record, not the layer object.

There is no UI thread in a running game. The UI manager's constructor also creates a thread object named UIThread (0x1889460 -> 0x193856C; vt_0x22F94B8 with the shared thread methods, vf8 the name, vf9 the stub 0x19385BC, vf10 a 0x4000-byte stack), but it is never started. The shared thread start 0x529500 has 30 call sites, and each starts another object: the named threads of Threads and the frame, a Bink worker, a queue worker and two event workers on static objects. The object sits at UIManager+0x08, and the UI's own console commands live in the source file CUIThread.cpp. The UI's per-frame work is done on the main thread instead. The HUD's CUIMgr::Render (0x1AB28C) runs inside the main scene's render submission. The nav-marker loop 0x1C4AEC runs on the main thread: its frame 0x2A9228 appears in 1.6% of 3,000 main-thread samples and in 0 of 1,938 render-thread samples. The menu selection's prompt rebuild runs from the client update (below), and captured movie frames reach the render thread through the main thread's command ring (below).

The UI state machine is vt_0x1F74D30: vf2 is the handler (state, event), and the current state is at UIManager+0x240. State 12 (HierarchyTransition, the move into and out of the Army screen) enters at 0x437514, updates at 0x437594 and exits at 0x4375F0. Its update waits on the world-UI owner's busy test 0x19C36A8, but the wait is capped: the duration [0x2671338] is 20.0 seconds, armed by 0x49F9C8 and expired by 0x16CFA4 on the real-time clock (a measured 1,508 ms per 1.5 s).

Layer setup 0x18CACF4(layer, record, index) reads ActiveFlashLayer and refuses a layer whose _Structuresuiflash.File is empty; it stores the index at layer+0x30 and the flash record at layer+0x48. The view's methods then do the rest:

  • vf1 0x18CB7DC, initialize. 0x18CBBA4 waits until the required and additional bundles are resident and the movie file (_Structuresuiflash.File, opened through the engine interface's vf13 service) is loaded into a movie definition at layer+0x40. 0x18CAD78 then creates the movie. The view index becomes a movie mode (0 -> 1, 1 -> 2, 2 -> 4, anything else -> 2). The definition's vf4 0x11BBE3C(mode) (vt_0x22C2B00) builds a 0x3938-byte movie wrapper (vt_0x1E6EE80, constructor 0x11BC268), which is stored at layer+0x38, and the record's EdgeAA, MaxCurvePixelError, StrokeQuality and BackgroundAlpha are applied to it. The method is called until the wrapper exists. It also fills the wrapper's glyph table (see Text below).
  • vf2 0x2A92A4, advance. The method takes the frame step from the layer's timer ([layer+0x58]+0x14) and calls the wrapper's vf4.

The engine advances only the views it owns in UIManager+0x360; a view built outside that list draws nothing until its vf2 is called.

The movie wrapper and the UI render list

The wrapper's +0x18 is the GFx movie and +0x38 its render ID. Its vf4 0x47D78F0 is one UI frame:

  1. It calls movie->vf24 Advance(step, 2, 0), then movie->vf25 Capture(1), which returns the captured frame.
  2. 0x115226C posts a 0x28-byte command on the main thread's render command ring 0x272E8D8 (see Threads and the frame): {+0x00 thunk 0x65086C, +0x08 the UI render list, +0x10 method 0x650888, +0x18 u32 render ID, +0x20 frame}. On the render thread 0x650888 locks the list and stores the frame into the entry with that ID.
  3. It calls 0x251E00(ring, 0); then 0x2AA3A8 runs the wrapper's callback queue at +0x3920.

The UI render list is a static object at 0x272EB20:

+0x10 / +0x18 vector of 0x18-byte entries, kept sorted by mode
+0x28 lock
Entry offset Meaning
+0x00 the render target (vt_0x22C6720)

0x1C8DAF4(list, handle, mode) registers a movie: it takes the next ID from the counter at 0x27966A0, inserts an entry before the first one with a higher mode and returns the ID. Every movie has its own entry, so two movies of the same mode do not collide. In a loaded game the list holds NavMarkers (mode 1), the Player HUD (mode 2), MessageBox (mode 4) and two more movies with modes 8 and 0x10. The last captured frame stays on screen until the next capture. Scaleform draws the list through its own D3D11 renderer (see Rendering).

Message boxes and the banner

Interface/MessageBox holds 173 box definitions; each picks one of three elements, Interface/Elements::GenericMessageBox (LIB-Dialog), Larger_GenericMessageBox (LIB-Dialog_Delete) or BannerMessageBox (LIB-Banner). A request is queued on the message-box manager at [CGameClientShell+0x890] (the request layout is in Saves, the store and the network layer); the caller's completion function goes into UIManager+0x248 / +0x250 and receives the button result. messageboxes.gfx is a shared-library client: it imports one symbol, CompLibrary, from the component library, which exports it as an empty sprite, and places it on its root, which is how Scaleform makes a library's exports attachable there. The dialog widgets animate out 0 .. 9 to off 10 (alpha 0) and in 11 .. 19 to on 20.

The generic banner is a two-line text banner beside the minimap, owned by the banner manager [[UIManager+0x30]+0xE0]: 0x1892F34(_, key, secondKey, flag) -> 0xE604C looks each key up in the string database and shows the title and, when its text is not empty, the second line (details in Outposts, strongholds and fortress upgrades).

Widget effects

The save-select screen's row frames and prompt bar, and the HUD's bars, are not Scaleform art but 3D ClientFX effects drawn beneath the Scaleform views. A menu widget that names an FXList hands its node to the UI effects manager [UIManager+0x58]. The call 0x15747C(node, fxList, 0) -> 0x157DF8 fills a 0x190-byte entry {+0x00 node handle, +0x138 FX list, +0x140 state (1 create, 2 running, 3 stop, 4 kill), +0x144 index} and stores the index in the node (+0xD0, node vf2 / vf3 0x157FB0); 0x157890(node) retires the entry (state 3). 0x2249E8 (from 0x224430) builds the effect. The save-select screen's prompt bar, for example, is the widget Interface/Menu/MenuWidget/Prompt::DifficultyPrompt (symbol LIB-PromptBanner, attached from the library, FX list Interface/ElementFXList::Difficulty_PromptBar), whose box is _StructuresUIFXData {UIFX Client/ClientFXSequence::Store_PromptBar = fx\ui\menuitems\store_promptbar.fxp, depth 26.5, TrackRotation}. At the title screen the manager held 23 entries, among them the save rows' frames DifficultySelect / DifficultySelect_Highlight. A menu widget's state is at +0xDC (0 out, 1 off, 2 in, 3 on), its record at +0xE8 and its clip's output handle at +0x58. UI_Widget_d 0x3293D0 attaches the clip (node slot 76, or slot 83 GetMember when the symbol is not taken from the library), and 0x46DC80 hands the node and the FX list to the manager.

What the movies contain

The movies are ActionScript 2 skins with almost no code. A widget's timeline has the frame labels out, off, in and on; the off and on frames run stop(); if (this._FrameEventHandler) this._FrameEventHandler(_root.EFrameEvents_Off) (or _On), and the root defines EFrameEvents_None, _On, _Off, _FX and _Sound (0 to 4). Code selects a widget with gotoAndPlay("in") and deselects it with gotoAndPlay("out"); the widget animates itself and reports the end of the animation through the handler. Layout, lists, counts and text all come from code and the GameDB.

Driving a movie from code: the node API

The engine wraps every Scaleform value it touches in a 0xF8-byte node (vt_0x1DAB888, constructor 0x1C309C): +0x28 the value's object interface, +0x30 the value type ((type & 0x8F) == 0xA is a display object), +0x38 the object. Callers receive nodes through output handles that the callee constructs in place (0x1C2F80, the node at handle+0x10); a handle holds pointers to itself, so it cannot be moved once constructed, and its destructor 0x1C68FC releases the node.

The attach-node lifetime rule

An attached clip lives exactly as long as the node attachMovie returned. attachMovie allocates the node, attaches the symbol (0x115BB34), then 0x4744EC sets the owner byte node+0x58 to 1 and registers an onUnload listener at node+0xA0 whose callback is 0x7941C4. The node destructor (vf0 0x1C3158 -> 0x1C318C) releases the listener and, while +0x58 is set, invokes removeMovieClip on the clip. If the clip is unloaded some other way (removed, or its parent removed), 0x7941C4 clears +0x58 first, so a clip is never removed twice. Lookup nodes (GetMember vf83 / vf84, _root) never set the owner byte.

Releasing an attach handle therefore removes the clip, while a lookup handle for the same clip is a different node whose release leaves the clip alone. Code that keeps attached clips on screen must hold their attach handles (and release children before parents).

Text

The string database

All game text is looked up by key in the string database [base+0x2702000] (vt_0x2008F70). The database is a list of loaded string tables (the list at +0x10). A table is its list node minus 0x40, with +0x0C the row count, +0x10 the rows, +0x18 the narrow rows and +0x30 the UTF-16 text. A row is {u32 key hash, u32 text offset in UTF-16 units}; the rows are sorted by hash, and the hash is the key's case-insensitive P919 (see GameDB). A table's lookup 0x472104 binary-searches its rows (0x472134). 0x471F2C takes a key string, hashes it and returns the text. The store's vf8 answers whether a hash exists, and vf8 and vf9 take the first table in the list that holds it. Because the key is hashed from its content, a key string can live anywhere in memory. The tables are the shipped per-language files (database\string\<language>\string.strdb, see Archives and file formats). Table-shaped data also lies elsewhere on the heap (one such copy lacked keys that the listed table holds); the game reads the tables reached through the database's own list.

Format arguments, color runs and tokens

Text carries three kinds of markup, resolved in this order:

  1. Format arguments ({1!s}, {1!d}, {1!.0f}, {1!ls}) are filled by the game's formatter (Str_WBFormatMessageT).
  2. Action and alias tokens are replaced by ReplaceActionsWithDevices 0x2995F8, named by its own assert string. It is reached through the UI callback 0x299520 that CInterfaceMgr::Init registers, which looks up $KEY strings and runs any text through it. For each {name}: - an input-action name (one of the 377 actions) becomes the button bound to it: {<Device>} when that button has a text glyph, otherwise its PCKey string; - a Profile/ActionAlias record becomes its FontColor as a <font color> run (0xD06CF0), otherwise its gamepad or keyboard-and-mouse string, which is run through the pass again; - anything else is copied back unchanged.
  3. Picture tokens left in the text are drawn by Scaleform's image substitution (below).

A letter key has no text glyph (KeyG has TextFieldGlyphReplacement off and device code 71), so the game prints its string, IDS_Key_G = {Color_Player}[G]</font>. The cyan bracketed key is the game's own style for a key in text.

Pictures in text

A picture inside a line of text is a Scaleform image substitution, set up per view.

  • The glyph table. Each owned view's initialize method (vf1 0x18CB7DC) fills its movie wrapper's glyph table: first every Profile/Inputs/PC/Buttons record with TextFieldGlyphReplacement on (27 of 155: the gamepad buttons and the mouse) under the token {<Device>} (wrapper vf37 formats {%d}), then every Interface/GlyphReplacement record (133) under its TokenText.
  • AddGlyph is wrapper vf38 0x11BCF78(wrapper, token wchar_t*, texture path char*). It returns at once when the table holds 256 entries (cmp [rcx+0xA0], 0x100). It gets the texture's handle (0x1BEAAC, get-or-create), its data object [[handle+8]] (0x3DF304 -> 0x3DF388) and, from [obj+0x10] (0x3DF2B8), the width and height words +0x52 / +0x54. There is no null check, so a texture that nothing has loaded faults there. It stores width and height in a 0x38-byte entry (entries from +0xA8, 0x469A5C), makes img://<texture> a BitmapData (0x11BED8C, main thread only) and pushes {image, subString, width, height, baseLineY = texture height x 0.8} onto _root._GlyphData (+0x38A8). The wrapper's constructor 0x11BC268 publishes _root.RegisterGlyphs and _GlyphData. The engine has no call that removes an entry.
  • Sized to each field's font. Setting a text that contains a { (above) calls vf108 -> 0x4697D0. Every picture's height is the font's getTextExtent("W").ascent x 1.2, and its width is that height times the entry's aspect; the function then calls setImageSubstitutions(null) and setImageSubstitutions(_GlyphData). A wide picture therefore becomes a strip one text line high.
  • The tokens. TokenText is a wide string capped at 15 characters, braces included: {BrokenCaptain} fills it, which accounts for the shipped {LegendarySkul}. The record name need not match the token: SocialCurrencyIcon is {Spoils}, CurrencyCoin is {Coin}, CurrencyIcon is {M}, and PremiumCurrencyIcon's {G} is the Gold icon, not the G key. Counted by TokenText, which is what Scaleform matches, the shipped strings use 95 of the 133 tokens 851 times in 593 strings; 185 of those uses are in strings that also carry format arguments. A record instance holds +0x00 ReplacementTexture, +0x08 PCMousePrimarySwapTexture and +0x10 TokenText.
  • The glyph textures ship inside UI bundles. A bundle-membership index placed 12 of them in no bundle, but parsing 19,525 bundle manifests of five archives puts 9 of the 9 checked inside patch bundles (Patch_DLC4's interface\bundles\gfx\ingame.bndl and ingame_navmarkers.bndl, Patch_05's store_icon.bndl). The views' initialization waits for those bundles, so AddGlyph's unchecked read meets a loaded texture.

Quest text

A quest's card text comes from one resolver, 0xCF9D90(_, quest record, out, kind), reached through the thunk 0xD64810 and the wrapper 0xD731E0(quest, out, kind). Kind 0 is Description, kind 3 ShortDescription, and two more kinds go through other accessors. For each kind it reads that kind's picker. When one is set, it asks the picker (0x18A0C4C with the live quest, otherwise 0x4AA370 with the record); the picker walks its entries in order and takes the first whose Predicate holds for the member filling its Jobs, or that has PassIfNoMember with nobody there. The entry's String and StringArgs are used only when an entry passes and its String is not empty (0xCFAAE8 .. 0xCFAB43); otherwise the quest's own field and its Args are used (0xCFABA7). The name's twin, 0x17DEE5C, shows what the argument bits mean: bit 1 the subject's name and title (0x4A9810), bit 2 the second participant, bit 4 SupporterStringPicker, bits 8, 0x10 and 0x20 numbers.

  • Readers. The two wrappers have 9 callers. Kind 0 is read by the world map's quest card 0x18EB6B4, the captain card with his 3D model 0x190338C (the CharacterPresentation widget) and 0x18DAF8C (an unidentified layer). The mission start screen's text writer 0x18E356C fills its QuestDescription field through the same wrapper. Kind 3 is read by the Army screen's captain line 0x18A36B8 and two others, kind 2 by one.
  • Pickers are shared. Quest/JobStringPickerGroup has 127 groups. All 11 Outpost_* groups are the same two entries on the outpost commander's job with PassIfNoMember True: IsNameKnown gives SC_<challenge>_Outpost_Desc ("Draw out {1!s} by ..."), IsUnknown gives ..._Desc_Unk ("Draw out the Outpost leader by ..."). Both predicates are MemberHasNameUnlocked, 0x1149E60(member) = [FM+0x510] & 1. Emulating 0x4AA370 on live memory picked the entry this rule predicts for 3 of 3 live quests. Text cells are shared too: on SM_SC_W_RapidStealth the Description, ShortDescription and StartPointDescription cells all point at one string, and the objective SpawnCon_KillChief_Obj ("Defeat {1!s}") is shared by 855 quests (outposts 233, vendettas 294, warchiefs and forts 100, others 228). An empty picker link reads 0.
  • The world map's quest card honors \n line breaks in the description.

Menus as GameDB data

A menu is data: layers, trees of nodes, widgets, elements and their placements, all under Interface/.

  • The menu manager record Interface/Menu/MenuManager::Menu (at [[UIManager+0x50]+0x518]) links the default pause layer (PauseRoot/PauseLayer), the title screen root (FrontEndRoot/FrontEnd) and one layer per screen, among them the world map, zone map, quest log, appendices, war upgrades, the Army screen (Hierarchy/HierarchyLayer), the captain detail (FactionMember/FactionMember), upgrades, equipment, gems, store, gold, mercenaries, skins and options.
  • Layers. Interface/Menu/MenuLayer has 48 layer classes and 74 layer records (one more class, Graveyard, survives only in an old patch). Every layer has the common fields ContentSymbol, LayerFX, the title fields, DirectExitAction, sounds for init / activate / sub-layer push and pop / deactivate / term, a Transition (Interface/Menu/MenuTransition, 43 records), Components, NavPane, a status header type, AutoWidgets, a HUDState, a default layer state, MenuSelectionPredicates and a telemetry alias; each class adds its own (the Army screen's has 97 fields, most of them actions). The Interface/Menu/MenuLayerList records (32) are stacks of layers pushed together, for example Hierarchy_Full and NewGameSetup_Full.
  • Trees, nodes and widgets. Interface/Menu/MenuTreeGroup records group Interface/Menu/MenuTreeBase trees (155). Interface/Menu/MenuTreeNode has 58 node classes, among them skills, gems, traits, quests, skins and game modes. Interface/Menu/MenuWidget holds 271 widgets, and Interface/Menu/MenuComponent holds buttons (78, each with a ContentElement naming a LIB- symbol), checkboxes, cycles, sliders and text entries. The trait card's rows are tree nodes too (see Captain traits); the Skills screen's node state is computed in code (see Items).
  • Elements and placement. The categories are Interface/Elements (242) and Interface/ElementAttribute (962). An attribute is a screen placement and its animation: AppliedProperties, InterpolationTime, DelayTime, InterpolationType, VisibleOnInterpolateTerm, UseSafeZone, Position (a screen fraction), Offset, Scale, Alpha, Z, ZScale, Rotation, a 3D rotation and Filters (Interface/ElementFilter: bevel, blur, color matrix, drop shadow, glow). Attributes come in named pairs such as AgeGate_Active / AgeGate_Inactive, an element's placement with its layer active and inactive.
  • Predicates. Interface/Predicates/* gate nodes and actions: Menu (66), HierarchyState (115), Hierarchy (28) and 39 more classes.
  • Selections. Interface/Menu/MenuSelection/Predicate/* and /Action/* tie an input to a prompt and a result action (below).
  • Text and input. The text and input records are Interface/GFX/Fonts::Main, Interface/GFX/FontMapping (Console, IntHUD, LatinHUD), Interface/GFX/KeyMaps (InGame, Menu) and 109 Interface/GFX/Text styles for the engine's own debug text. Menus take input through command sets (Profile/CommandSets).

The pause menu

The pause menu is data. Interface/Menu/MenuLayer/PauseRoot::PauseLayer names its SelectionTree Interface/Menu/MenuTreeGroup::PauseRoot, its audio hooks and its DirectExitAction; the group holds the trees MenuTreeBase::RootTree (Army, Quests, Character, Inventory), MinorSelection (Market, Online, Guide, Appendices, Options, Quit) and MOTD, the community challenge panel. The panel's text is not in the shipped string tables: it comes from the online service's broadcast feed.

Selections, prompts and the prompt bar

The menu selection is menu+0x6FD0; its first qword points back at the menu. It holds the predicates that are offered, the prompts drawn for them and the Army screen's mode lists.

Selection offset Meaning
+0x10 active
+0x11 byte: when 0, a predicate's keyboard-and-mouse input is preferred (below)
+0x18 13 type buckets of 0x20 bytes (0xD8EA20 asserts the type is below 13); each bucket's +0x08 / +0x10 is a vector of predicate sources, and each source's +0x08 / +0x10 a vector of predicate records
+0x1E0 the Army screen's mode lists, 0x20 each: +0x00 the list record, +0x08 / +0x10 the Interface/HierarchyMode/Type rules that passed

A source names its subject at +0x28. With the world map open, bucket 6 held one source (vtable 0x1DB12B0) whose +0x28 is the 3DZoneMap layer record and which held 7 of that layer's 8 predicates. On the Army screen, bucket 0's sources carry a member key at +0x28 and his position at +0x38, and the highlight's selection set 0x18BE498 appends one on every call (0x18BB704).

Who rebuilds it, and when. The client update 0x1A864C -> 0x52440C -> 0x1890700 calls 0x163CFC([UIManager+0x50]) -> 0x163D28(menu+0x6FD0) every frame. 0x163D28 rebuilds the prompts only when the selection's byte +0x418 is set, and then clears the byte. 0xD8F220(selection, 0) sets it and is called from 14 sites in the engine. The bar belongs to the main thread.

The refill. 0x320B08 (51 call sites) runs each type's sources in TypePriority order. A source's vf2 0x321338 clears its vector and calls vf21 0x322324, which reads the layer record's MenuSelectionPredicates (0x767E2C: the record's own run, then its instance) and keeps each predicate that 0x3223CC passes. The test covers the predicate's CommonPredicates and the running tutorial's DisableMenuSelectionPredicates. The common-predicate check 0x322D9C passes a null link; otherwise it tests the build, store and online-service predicates, then the required, allowed and excluded menu, hierarchy, faction, quest, game-state, player and bodyguard lists. None of the 74 shipped predicates has a null CommonPredicates; 15 point at a common-predicate record that sets no condition.

The build. 0x31EC5C skips each kept predicate that has no Prompt. Otherwise the predicate's input actions (InputPromptOverride, else InputKBM when +0x11 is 0 and the predicate has one, else Input) go through 0x31EDF0, which claims each action index for the first predicate that uses it, in a table of 377 entries; an index past the table is an engine assert. A predicate whose actions were all claimed is dropped. The kept ones are sorted (0x76CE58) and handed to each bar widget whose context matches the prompt's Context: 0xDDC940 -> 0xE4F570 fills one of the widget's 16 slots of 0x4D8 bytes with the PromptID key, two action IDs, Enabled and the device flags (KeyboardPrompt 1, GamepadPrompt 2, ClickablePrompt 4). A second loop reads each predicate's Prompt again (0x163F80) and uses it without a null check: a Prompt link that changes between the two reads would reach 0xE4F570 with a null PromptID. The accessors themselves return 0 for a null record (0x73E4CC).

Prompt-only predicates. A predicate may name a prompt and no ResultAction: it only draws the prompt, and the layer handles the key itself. The world map's SetWaypoint_KBM, Zoom_MordorMap, Zoom_Army and Player_Center are such predicates. Interface/Menu/MenuLayer/ZoneMap::3DZoneMap.MenuSelectionPredicates lists eight predicates (PushQuestLog, PopToQuestLog, 3DZoneMap_PushLegendLayer, Zoom_MordorMap, Zoom_Army, Player_Center, SetWaypoint_KBM, Back); its prompts use the context FortStatusHeader. Only SetWaypoint_KBM names ZoneMapHasHighlight (as an exclusion).

The input actions are an enum of 377 names (None 0 .. Search_Enter 376; see GameDB for the enum name registry): for example ZoneMapZoomOut 68, MenuAux0 78, CombatKBM11 135, MenuKBM00 145, PhotoMode_CameraMode 368. On the PC keyboard the menu actions are bound to Space, 1-7, A, D, Q, E, Z, X, B, Shift, Home and Esc (Profile/Commands).

Nav markers

A nav marker is a world-attached icon drawn by the NavMarkers view. Each type is an Interface/NavMarkerTypes record: an icon and a secondary texture, the SPH- symbol it shows (IconMovieClip), an optional PrimaryIconOverride -> Interface/NavMarkerCustomDraw, sizes, a HUD state and on- and off-screen configurations (Interface.NavMarkerScreenConfigCommon: AbsoluteOffset, AbsolutePosition, AbsoluteUseScreenSafe, AlphaRange, AlphaTransition, DistanceAlpha, ScaleFallOff, ScaleRange, UseAbsolutePosition). A marker object is 0x420 bytes (0x60CE2C). A world character's marker is [char+0x2380], and a stage character's is at +0x758. The waypoint marker and NavMarker::SetType are described in Outposts, strongholds and fortress upgrades.

The widgets. Each marker drives a widget (vt_0x1DA9640). The per-frame loop 0x1C4AEC walks every widget through an intrusive list: the sentinel is base+0x26725F8, the first node [sentinel+8], the widget the node minus 0x18 and the next node [node+8] (170 widgets in a loaded world, the walk ending at the sentinel). The nameplate

The card over a hovered captain on the Army screen (name, class line, level shield, prompts, arrow) is not drawn by the Army screen layer. It is a nav marker widget, updated by the same loop as every marker in the world, and it never polls: 0x189B438(clip, &position) refills its text only when flag 0x20000 is raised or right after the clip loads. Hovering away and back reloads the clip, and highlighting the captain already highlighted does nothing.

  • The text is read from the live member. 0x188CE30(position) finds the member from widget+0x290 = {+0x00 army, +0x08 u8 row, +0x09 u8 seat}, and 0x4A9810(member, ..) builds the line. A change to his name or title therefore shows at the next refill, without a summary refill.
  • The engine's raise is 0x17FE784(marker, &position): it copies 16 bytes to marker+0x3B8 and widget+0x290 and sets flag 0x20000 (bts [widget+0x48], 0x11), with no same-value test. It takes the 0x420-byte marker, not the widget. Its callers build the position from the member (0x60C424) or from a summary's +0x48 (vf74 0x1823448, vt_0x1F77FA8::vf1).

The Army screen

The hierarchy movie and the 3D stage

The Army screen is a 3D stage in a dedicated menu world with the hierarchy.gfx overlay on top. The movie draws only the 2D panels: its 22 HIE- symbols are the enemy overview, the trait card parts (HIE-TraitHeader, -TraitGroup, -TraitContent, -TraitDivider), dialogs (upgrade, target, cancel), quest start and complete panels, assault and defense groups, contract overview and the player icon. No symbol describes rows or seats: the captains, the seats and the fort are world objects. (The instance names Row0 - Row9 belong to the component library's control-bindings screen, and OverlordTree / WarchiefTree to the zone map's fort highlight.)

Faction/HierarchyMenu/Setup::Default (114 fields) configures the screen: the stage bundle bundles\hierarchymenu.bndl, the menu world collision prefabs\ui\worlduimenuws_collision.bndl, the henchmen, power-struggle and blood-brother link effects, the fidget bundle bundles\animationcharacters\menu\fidget.bndl (at most 20 fidgets at once), one camera state per mode (among them army, mercenary, orders, garrison and contract assignment, store, map and pause), the character model manager and 38 tutorials.

Each army's stage is chosen by its Faction/Definition.WorldUIFaction -> Faction/World/Faction (10 records): Instance names the stage rig (prefabs\ui\wuim_regionfaction_ws.bndl for five regions, wuim_minasfaction_ws for Minas Ithil, wuim_desert_dlc4_ws and wuim_dlc4merc_faction_ws for the Desolation of Mordor), FortPicker the fort pieces, and Member / GarrisonMember / VendettaMember the seat grids. The section is requested by the region's stage object in the menu world (vt_0x1FA4008, named Hier.Map.Region_*) when that object activates. Its vf16 0x1A34E78 maps the record Region to the region's army through Region_GetFaction 0x1E4418, which ends in Regions/Region.GameModeFactionOverrides keyed by the current game mode, then in Region.Faction. It then resolves the world section, requests it into the object's own group (0x4B420C) and links the object into the active-stage list 0x2675860. The activation runs when the menu world is rebuilt during a load, not on a visit to the Army screen. The stage objects sit at their regions' real positions on the map at scale 1.0 (eight active in a loaded game), and vf16 requests each section at its object's own transform.

Stage holders and the world-UI owner

The world-UI owner [base+0x26FFB60] (vt_0x1F97950; see Engine core) keeps one slot per army at +0x2B8: 38 slots of 0x50 bytes in army-table order (the key at +0x00 is the Faction/Definition, and 38 of 38 agree), with the count at +0x2C0. StageFor 0x455EDC(owner, army) returns a slot's +0x48, the stage holder; +0x28 .. +0x48 is an object handle (vt_0x1DC0488) chained on the region stage object's +0x2A8, which points at the spawned holder. The armies of one region share one holder (21 of the 38 slots are filled in a loaded game). After a load every slot is empty until the owner's +0x400 goes to 1, around the first visit to the Army screen; +0x400 drops again later, and the slots stay filled. A holder (vt_0x1FA2FB8) has this layout:

+0x160 the holder's frame {position, rotation}, from which grid seats are placed

The holder tick 0x16EE24 (called from the owner's per-frame Update, vf18 0x16F4A0) runs the fort reconciler 0x2EC464, which diffs the wanted fort pieces against the built ones. Then, when +0x275 is set, the tick prunes relationships (0x1B5E13C) and rebuilds every stage character from the summaries (0x1D7A918), writing the word +0x275 = 0x100 so that the row rebuild 0x1A284D8 follows on the next pass. The engine sets +0x275 itself when it sets a holder up for an army (0x1A29168, from 0x19C3760 and 0x19C3F60). With the menu closed an army has no stage objects; they are built fresh from the summaries when the screen opens.

An army with no stage cannot be shown. When a region's stage object activates before its region maps to an army, it spawns nothing (its +0x2A8 handle points at itself) and the army's slot stays empty. A screen that shows such an army (the Mercenary screen pointed at it) then holds a black loading screen indefinitely, although the UI state machine's own wait expires after 20 seconds (above). A later load in which the region is mapped rebuilds the stage, and the screen then opens normally.

The per-captain redraw is 0x19C395C(owner, &key), which the engine calls after a Training Order is applied (0x1C51630): holder 0x455EDC -> summary 0x1B5C0F8 -> stage character 0x1A28FAC(holder, key) -> UI_CWorldUICharacter 0x627F40(character, summary, 0, 0). Every step returns quietly when the army is not on a stage. 0x627F40 chooses the look (0x2EB2DC, below). 0x62EEE4 then swaps the new look in and rebinds the model; only when the look test 0x170564 reports a change does it tear down the selection and model objects, rebuild them and set +0xB3C. The look test does not compare the death bits (flag bits 2 and 21), so a change of state alone does not rebuild a captain's preview pose.

Under modification, a value written into an army summary reaches the open stage only when the screen is entered again, because the stage draws from its own copies. A stage character's private copy is deep (it owns its item instances), so refilling it in place frees items that the model has bound.

Every frame while the screen is open, the owner's tick runs the character model manager (HierarchyCharacterModelMgr, ConfigSwapsPerFrame) -> 0x628BF8 -> the stage character's vf63 0x3680B0 (its summary) -> 0x30DE28, which walks the summary's trait list for a MountAITemplate.

Seats, placement and animation

A fort's composition is data: Faction/World/Faction.FortPicker -> Faction/World/Fort/Picker -> fort setups -> piece entries -> pieces {world sections, position, rotation, fixed seats}. A piece entry (FortPieceEntry) is {FactionPredicate, HierarchyMenuPredicate, RequiredPredicateValue, Piece}. 0x62B600 builds the piece list from all seven entry lists of a setup and passes every entry through 0x62BB18, which allows the entry when the menu predicate's result (0x276E74) equals RequiredPredicateValue. The shipped data uses that switch only on lighting pieces: 132 of 132 lighting entries carry it, against 0 of 135 keep, 0 of 726 gate and 0 of 33 streamed entries. 0x2EC464 then diffs the list: pieces no longer listed are removed, and new WorldUIFortPiece objects are created. It rebuilds only when the fort's +0x271 is set, which 0x326168 does when called from 0x16E570, 0x455D78 (each tick from the owner's vf18, with regions sorted by distance) and 0x7A126C. 0xE83590 also calls 0x62B600. A normal fort's Foundation piece has no world section and sits on the map's own terrain. The Desolation of Mordor's mercenary camp brings its own ground (Fort/Piece::Foundation_Desert_Mercs -> prefabs\ui\mordormap\foundation_desert_mercs.bndl, 91 assets, 49.6 MB), which is why that camp shows on the map as a square of terrain wherever its stage is built.

The upper rows (Overlord, inner and outer warchiefs, the first captain row) sit on fixed seats (WorldUIFixedFactionMemberPos: a row and column, a position and a rotation), which any piece can register (0x629EEC -> 0x62A17C). The other rows are a grid (_StructuresWorldUI.FactionMember: RowGap, ColumnGap) placed from the holder's frame (0x1D79DF0). A seat is dropped onto the stage's collision by a ray, 0x62AA6C(seat, offset, out): on a hit the height becomes the hit point plus the offset, and on a miss the seat keeps its data position. The stage character (its vf11) calls it through 0x62AA48 with a zero offset, so the character's animated root, the hip, is placed on the seat itself.

Stage idles are chosen by data and played by clip name. A preview state's HierarchyPreviewTypeAnimData.RootAnimChoice / RootInAnimChoice is a choice group. 0x42E72C takes the first child whose predicates pass (0x42E984 -> 0x42EAFC); their inputs are the combat tree's CharacterType, the role, the personality and whether the name is known. 0x42E82C collects the child's Animation records, 0x42F794 picks one at random, and 0x42F1D0 plays it by name (0x4C8A0C -> 0x302540, which looks the name's hash up in the skeleton's animation set). The Army camera

The Army screen has two camera branches.

  • The overview. The army camera state Faction/HierarchyMenu/Cameras/States::CS_Army_Cursor names a fixed overview, but its UseWorldMapCameraPredicate is Faction/World/Predicates/HierarchyMenu::HierarchyFreeCursor, which passes while the top menu layer is the Army screen, contract assignment or the mercenary layer (and not in replay mode). While it passes, the camera belongs to the world-map layer: Interface/Menu/MenuLayer/WorldMap.HierarchyCameraState -> Interface/Camera/CameraStates::HierarchyFreeCam, whose two orbit keys (_StructuresUIOrbitPointParams primaries 340 and 341) are the near and far ends of the zoom, with radii 1025 and 5250 and a vertical field of view of 25 degrees. Two keys are what make a zoom axis.
  • The captain detail. CS_Char_Detail has no world-map predicate. Its UICameraSettings is an array of 153 Faction/HierarchyMenu/Cameras/UICameraState entries, each chosen by a predicate on the captain's row, seat and state (for example Orc_Row2_L, Orc_SlotOverlord_Row4_3, Orc_Dead and Talion) and naming one of 111 distinct camera states. Each of the 111 has exactly one orbit key (radius 250 to 550), so its radius is a fixed distance and the detail view has no zoom.

Orbit keys. An orbit key (_StructuresUIOrbitPointParams) holds fov, OrbitRadius and Roll as plain floats of the key's own instance, so a key's radius belongs to the states that reference that key alone. CameraOffset, CameraOffsetRange and CameraAdjust are shared float-pool pairs (type 7; see GameDB), each shared by every key that holds the same values. CameraOffsetRange is the (yaw, pitch) swing in degrees on either side of CameraOffset (the formula is below). The key unpack clamps both values to [0, 180] (0x526DAB .. 0x526DD5; it wraps CameraOffset into -180 .. 180 with the same 180), and at 180 the two ends of a drag meet behind the subject. The overview's keys 340 and 341 carry (24, 12) at radius 1,025 and (16, 10) at radius 5,250, both with fov 25. The 111 detail keys use eight distinct pairs: (0, 0) on 75 (one more key's pair was not decoded), (90, 20) on 16 (among them the standard captain views _base_Orc_* / _base_Olog_*), (45, 15) and (40, 15) on 5 each, (60, 20) on 3, and (90, 25), (80, 15) and (60, 15) on 2 each. The (0, 0) pair is the database's shared unset value (see GameDB): a view on it has no rotation axis at all, and a write to that pair would move every cell in the database that shares it. A key also has a node offset (orbit and focal offsets with position and rotation tracking masks) and a DepthOfField link to Client/DepthOfFieldSettings (near and far in-focus and blurred distances, blur intensities), authored for the shipped radius. Orc_Details is sharp from 120 to 325 and fully blurred past 375, so a camera pulled back beyond that band renders the captain as blurred background. WorldMapCameraMode is 4 on every Army camera state except two: CS_Store_ProductDisplay_Cursor (5) and CS_Mercenary_Cursor (6).

The camera object is ctrl = [[CGameClientShell+0xE38]+0x60]: the shell's frame update 0x1A864C passes [shell+0xE38] to 0x52440C, which runs [this+0x60] through 0x524BA0 every frame. The pointer is null when there is no menu camera.

All four act on [UIManager+0x88] and do nothing while the byte is clear. SetDebugMenuShown pushes Profile/CommandSets/DebugMenu on the input stack (0x1170D44; DisableAllOtherCommands with 26 menu commands enabled, so gameplay input is blocked), plays EnterMenuSFX and sets the open byte [[UIManager]+0x88]+0x7AE. Hiding pops the set (0x1170D34) and plays ExitMenuSFX. The Army screen action pushes the set and sets the byte without a sound. While the byte is set, IsDebugMenuOpen 0x381EEC makes the renderer 0x382044 call 0x381E68, which draws a full-screen black quad at alpha 0xDD over the world and the HUD, and the gameplay-input test 0x17B91EC fails. The commands the set enables include MenuEnter, MenuEscape, the four menu directions and the MenuAux commands.

The input data is live too: Interface/Shared.DebugCommandSet (DebugMenuActivate_Hydra) is pushed at every game start (0x1780A04), and Profile/Commands binds DebugMenuActivate1-4 (held together: Home or 9, End or 0, Left and Right; on a pad L3, Start and D-pad left and right). The input registration 0x3123CC gives the debug commands their IDs (DebugMenuActivate1-4 0xC8-0xCB, spectator and God shortcuts 0xCC / 0xCD, AI info next / last 0xCE / 0xCF, debug spawn modes 0xD0-0xDB, captain list / save / load 0xDC-0xDF, the debug camera 0xBC-0xC7).

What was stripped

  1. The view is never built: Debug is not in Interface/Shared.UIViews, so debug.bndl and the movie are never loaded.
  2. No code names the menu's records: DebugMenu_, DBG-, Debug_Menu, ScriptHook, ProdNotes and Showcase occur nowhere in the executable as strings, while the controls in the same scan do (NavMarkers 12, MessageBox 25, HierarchyLayer 4, FrontEndRoot 5). The component, attribute and view records have no inbound RecordLinks.
  3. The page data has no reader: the fields ConvarShortcut.Key / Title / String / ShowInDebugMenu / CloseMenuOnCommand, Interface/Cheat.CheatConsoleString, WorldInfo.InDebugMenu, Debug/FactionMember.Actions and DebugScript.Parent have no accessor, while Debug/Shared.DebugMenuCommandSet on the same record does (0x7B5A0C).
  4. Nothing opens it from input: the open functions have no caller besides the script binding, the console registry and the Army screen action, and the DebugMenuActivate commands are referenced only by their registrar.
  5. Most page commands are not in the retail console: the 530 items expand to 1,711 console commands; 85 name a live command, 18 a handler compiled down to ret 0, and 1,608 a name registered nowhere.

The only shipped script that touches the menu is the Bright Lord finale, which prints "Finale Part 4 Triggered" and calls System:ShowDebugMenu(false), the call the menu's Script Hook page made after firing a script.

The cheat backend

The cheat manager is [GameManager+0x6CA8]: a vector of 0x28-byte entries (+0x10 id, +0x18 the Interface/Cheat record, +0x20 toggleable, +0x21 on), built by 0x180EF9C, with per-id allowed flags (0x65B0E4). The retail game registers one entry, God. The names table 0x22F55A8 reads GOD, HEALTH, CLIP, REMOVEAI, SLOWMO (ids 0 to 4).

  • Toggle 0x65ADDC(manager, id) finds the entry by id, checks the allowed flags (0x65B0E4) and the record's CheatActivatedString (0x65AEA8), then calls Apply with the entry's +0x21 state.
  • Apply 0x65AD7C(manager, id, on, character system) applies one cheat. God stores the byte manager+0x30 and calls CCharacter::SetCanDamage(!on), then refills health. Health refills through 0x65ADCC on the player's combat object. Clip calls 0x19BFDA0(player, on, 1). RemoveAI calls 0x180EC7C and clears three fields of the client shell's +0xA50 object. SlowMo starts the slow-motion record Debug (0x7CE80C). 0x180F184 re-applies Clip when the player spawns.

The Interface/Cheat console strings (for example Cheat_God) are not registered in the retail console. The captain actions are faction events fired by CreateAndProcessFactionEvent 0x1B5B610(FS, event, member, other) on the Army screen's highlighted captain, the member of the stage character at [[[base+0x26FFB60]+0x340]+0x428] (see The highlight above, and The Nemesis system for faction events).

The console it drives

ExecuteCommand is the engine interface's vf29 (0x1180D8C): it hands the line to 0x1182FA4, which looks the name up in the console registry (Find, see The executable) and runs the command synchronously on the calling thread, splitting ;-separated commands. A name value line whose name is not registered creates a new settings variable (0x1182F10) instead of failing. Of the registered commands, 98 of 449 have handlers compiled down to ret 0.

The console's output goes nowhere. Command output and the engine log both end in the sink 0x6AAC14, which under the lock 0x27C45A0 calls the function pointer [base+0x27C45C8] if set, then writes to a stream if the byte 0x27C45D1 is set. In the retail game the pointer is null (written only by its static initializer 0x585A0 and the exit path 0x1196AF4) and the byte has one reader and no writer.

The debug camera these pages drive is described in Characters, the player and the camera.

Tutorials

Tutorials are data. Four families of records drive them:

Family Records What a record holds
Interface/Tutorial/Pausing 116 a modal pane set that pauses play: HUDState (Interface/HUD/State.PausingTutorial), HeaderString, DismissString, Panes (348 _StructuresTutorialPausingPaneData structures in all: BodyString, image, or video, an Interface/Movies record), its own Bundle (interface\bundles\kraken\tutorials\*.bndl), the input CommandSet that holds play (Profile/CommandSets.TutorialModal_A), InputLockout (0.5 s), RequireAllPressed, HoldAndPress, InputHoldDuration and enter / exit sounds
Interface/Tutorial/Gameplay 120 an in-play hint: DisplayString, duration, sounds
Interface/Tutorial/Menu 82 a menu tutorial: a Setup (screen position) and OnEnter, OnExitBegin, OnExit steps (253 _StructuresTutorial_MenuStep)
Faction/HierarchyTutorial 62 an Army-screen tutorial: a predicate, ExitMenuOnFinished and FirstState, a chain of Faction/HierarchyTutorial/States (84)

A menu step applies or removes an input command set (for example HierarchyTutorial_A or HierarchyTutorial_LStickX), enables or blocks mouse movement and fast travel, and advances on the common input. It may also change the menu around it through three record kinds. WidgetData (18) shows or hides a widget (Show_ / Hide_) such as the fort status header or the hierarchy overview. TreeData (24) restricts a menu tree to some nodes (for example ChallengesRestrict and GemSocketsRestrict) or clears the restriction. MenuSelectionData (8) lists Interface/Menu/MenuSelection/Predicate records to disable, for example every order on a captain during the Bruz ambush tutorials. Layer data adds per-screen settings (ShowMemberNavMarker / HideMemberNavMarker on the Army screen, SelectMtnPass on the quest log).

An Army-screen state names the menu tutorial to show, an optional map presentation, a preset or job member or the mercenary entry point to select, the view, and a camera transition to wait for (with a command set to apply meanwhile). It also holds PopupDelay (1.0 s in PlayerDiedFirstTime_State01), DelayNextState and Next, and closing conditions (CloseOnPositionSelected, CloseOnNewEquipmentHighlighted). The tutorials' predicates live in Faction/HierarchyTutorial/Preadicates (83 records, 73 fields; the category's name carries the misspelling). TutorialViwed links a Combat/Predicates/Bool record (whether this tutorial has been seen), and AnyTutorialsViwed, AllTutorialsViwed and NotTutorialsViwed test other tutorials. The rest test the Army screen's mode and state (normal, replay, interrogation, commanding, orders or assault setup; overview or details), the selected captain's known state (among them known, location known, full info, presumed dead, branded, decapitated and henchman), the active game mode, inventory and new-item counts, skill points and store counts.

From script. TutorialPausingShow / TutorialPausingHide and TutorialGameplayShow / TutorialGameplayHide are methods of the CCharacter script class (0x1BB2108 resolves the Interface/Tutorial/Pausing record and calls the character's vtable slot 99). The player raises OnTutorialPausingDismissed / OnTutorialGameplayDismissed. System:GetHierarchyTutorialViewed (0x1B86BA4) checks a Faction/HierarchyTutorial record against the viewed list reached through the player ([CGameClientShell]+0x888, with its byte +0x3880; the test is 0x30C46C). The HUD classes are CUIHUDPausingTutorial and CUIHUDGameplayTutorial. The Army-screen tutorials are run by the hierarchy menu's tutorial manager (HierarchyMenuTutorialMgr.cpp), and the console names a HierarchyMenu.ResetTutorials command.

Open questions

  • What class is [UIManager+0x88], the owner of the debug-menu open byte? The UI manager's constructor 0x1889674 only zeroes the slot. In a running game the object starts with a heap pointer rather than a vtable and holds a run of text-style entries that name the font "Anonymous Pro" with sizes 45 and 100; the name is not a literal in the executable, so it comes from data. The open byte sits at +0x7AE, near the object's end.
  • What was the PreLoad view for, and does its preload.gfx still ship? No archive entry has that name and no interface bundle's manifest names it, but ingame.bndl's manifest does not name sp.gfx either, and that movie ships inside its container. Which movies hold the UI render list's mode 8 and 0x10 entries?
  • What consumes the DebugMenuActivate1-4 command IDs (0xC8-0xCB)? Data enables them: both Profile/CommandSets records DebugMenuActivate_Hydra (pushed at every game start) and DebugMenuActivate_Menu list all four in EnableCommands, next to the AI-info and FactionMember debug commands. No code names them: neither their record links (0x9FD00091 - 0x9FD00094) nor their name hashes occur in the executable. A consumer would test the numeric IDs.
  • Which code selects the Interface/LoadingScreen record for a given load? Data names few of them. No shipped script names a loading screen (0 of 2,562 script sources), and the fields that can link one are GameModes.InitialLoadingScreen (8 of 13 game modes name Intro1, one DLC3_FastTravel_FromUI), Presentation/Elements.LoadingScreen (set on 0 of 3,000 elements), Regions/Region.ExitOnlineModeLoadingScreenOverride (0 of 19 regions) and Faction/MoneywallSetup/UI.LoadingScreen. In the shipped database Intro1 is linked 8 times and DLC3_FastTravel_FromUI once, while FastTravel_DesertLoadScreen is linked by no record at all, so the per-region fast-travel screens are chosen in code.
  • Where is the viewed-tutorial list stored, and is it saved with the game or with the profile?
  • What holds the screen black when an army without a stage is shown? The UI state machine's wait expires after 20 s, and in a frozen run only one word of the world-UI owner (+0x68) and none of the stage controller changed between 3 s and 30 s. Nine of the 21 callers of StageFor skip a null result; the other twelve were not read that far.
  • Does the Army screen's action dispatcher re-test the target rules? Emulating vf19 with the SetTarget action on a dead captain marked him, which suggests that only the prompt (withheld by the mode list) keeps the player from it.
  • Does verdict 3 of the Army screen's cursor test mean "off camera"? On one stage it marked the Overlord and the warchiefs; it should then change as the camera turns.
  • Who writes a drag into the menu camera's +0x88? None of 13 functions that store there in the camera code is the writer, so it likely stores through a pointer.
  • What consumes CameraAdjust from the parameter block (+0x200 / +0x34C)? A displacement scan of the camera code found only copies, blends and initialization.
  • Does the HierarchyTransition handler 0x1834BB0 refill the stage copies from the members? That would make the state change into the Army screen show member edits.
  • Is node slot 104 an htmlText getter? Its listing reads the member through 0x7B94F4 and converts it into a 0x200-character buffer (0x775DF4), but on the save-select prompt's field it returned false on 10 of 10 reads.
