The managers: five time domains in CGameClientShell (MEASURED 2026-10-28, live + offline)

CGameClientShell::InitializeSubsystems 0x1772E1C creates five managers, one per time domain, with the strings "Could not init SimulationClientFXMgr!", "RealTime...", "PlayerTime...", "CompanionTime...", "WorldUIClientFXMgr". Factories 0x176DC70 (Simulation, arena 0x100000 = 1 MB) and 0x176DBF4 (the rest, arena 0x80000 = 512 KB): alloc 0x18358 -> wrapper ctor 0x1779A64 -> inner ctor 0x1779B20; init 0x177BB44(mgr, time source, flag).

Wrapper (vt 0x22F3178, 0x18358 B): +0x08 link {next, prev} in the global intrusive list headed at [base+0x26C6A98] (0x1BBC24 returns 0x26C6A90), +0x18 an embedded {vt 0x1DAA870, time source} pair, +0x28 the inner manager. vf1 0x482DE0 / vf2 0x482EB4 take a resource (its +0x20 id): the wrapper is a resource listener, so an effect resource that unloads kills its instances in every manager (0x482EC0 -> 0x177C824 under the manager's lock). Live: 8 / 8 managers in the list, both vtables checked; a heap census found exactly 8 inner + 8 wrapper vtables (3.51 GB, untruncated).

Inner ClientFXMgr (vt 0x1F67400, 32 small slots, 0x18330 B): +0x08 the ClientFXThreadMgr, +0x10 / +0x11 flags (+0x11 = threaded: queue work to the FX thread, else run it inline), +0x68..+0xD8 six empty-by-default lists, +0xB8 the INSTANCE vector, +0x108 work-pending byte, +0x110 / +0x128 work lists (+0x128 = background), +0x148 {vt 0x1DAA870, time source} (+0x150 = the time source, a LEAD: per-domain objects in one heap run 0x17497050..0x17497640), +0x158..+0x170 helper objects, +0x178 arena bytes, +0x180 current-thread slot, +0x19C / +0x1A0 cost per key (128 / 64), +0x1A4 budget left this frame, +0x1B0 the per-frame arena, +0x18238 / +0x18250 two lists, +0x18268..+0x18320 six deferred queues, +0x18328 the work-done event. vf2 0x3E9E30 = CreateClientFX(cs, link).

Effect instances and how to enumerate them (MEASURED 2026-10-28, live)

Walk the manager's container, never the heap. inner+0xB8 is a std::vector of 0x28-byte entries; entry +0x18 is the instance. Two snapshots: 587 / 587 and 663 / 663 entries carried the instance vtable 0x1DAB360. A heap census in the same session counted 927 objects with that vtable: the 340 extra are freed slots of the instance pool 0x2A3E9A8 that keep a stale vtable (BEHAVIOR.md law 7 again).

The entry (0x28): +0x00 byte, +0x01 visible-this-frame, +0x02 budget-admitted, +0x04 cull position (3 floats, cm, world), +0x10 / +0x14 squared radii (a 40 m radius = 1.6e7 seen), +0x18 instance, +0x20 parent instance (child effects live in the PARENT's +0x18 vector, not in the manager's: 0x1BAD70 picks the container, stores it at instance +0x260 and the index at +0x25C).

The FX instance (vt 0x1DAB360 + second vt 0x1DAB350 at +0x08; ctor 0x1BB368, dtor 0x1BB79C "Failed to remove an effect correctly before destruction"):

offset field
+0x18 vector of child-effect entries (0x28 each)
+0x40 intrusive list head (self-linked when empty)
+0x58 flag word (bits 1, 2, 3, 4, 6, 7, 8, 11, 13 set / cleared by ctor and init)
+0x5C transform copied from the create struct (+0x38)
+0xB8 the KeyData container (+0xBC time, flags tested by 0x24EBB8: 4 active, 1 looping)
+0xD0 the owning inner manager (also KeyData container +0x18)
+0x150 / +0x1A8 handle objects (vt 0x1DABE28) to the parent object (LEAD: which object kinds)
+0x180 / +0x188 create struct +0x20 / socket index (+0x28)
+0x220 KeyData block (one malloc, 64-aligned: +0x00 raw, +0x08 size, then the node objects)
+0x228 resource hash (handle +0x20)
+0x230 the FxResource
+0x25C / +0x260 index in / pointer to the container it is listed in

fx_live reads all of this in ~0.05 s for 663 instances; a torn read (the main thread edits the vector) shows as non_instance_entries (0 in both snapshots).

Top effects in the desert (snapshot 1, 61 distinct; snapshot 2, 80): clothtorch_caponly 89, arrow_collectible_multi_dt 76, fliesattach 69, com_fireforge 51, morgaiflynest_idle01 43, torchorcnight01b 34, ds_atmodust_lrg01 26, thermalvents 20.

The FxResource and its keys (MEASURED 2026-10-28, live + offline)

Built once per loaded .fxp by the resource handler vf4 0x3E4540 (vt 0x2312410) from the effect's GADB (FxGlobalProps):

offset field
+0x00 length, s (ResourceLenMS / 1000)
+0x04 MaxUpdateDistance (1e34 = unlimited seen)
+0x08 / +0x10 key slot array / count (slot 0x18: +0x00 type entry, +0x08 KEY object, +0x10 KeyName)
+0x18 FxName (fx\...\x.fxp), +0x20 its StringHash, +0x28 the short name
+0x38 / +0x40 the aligned buffer holding the slots and the key objects / its size
+0x45 PauseWhenNotVisible
+0x48 the effect's GADB, FREED after processing (0x3E4765): the GameDB is load-time only
+0x50 data kept from the GADB (LEAD: the string / curve pool VFX Studio found as a heap copy)

Per key, 0x3E477C: type hash from the record -> FindFxType 0x3E451C (linear search of the 36 entries by entry +0x08) -> entry +0x20 builds the KEY object in the buffer -> key vf1 parses the record -> on failure entry +0x30 destroys it. A resource handle (create struct +0x00) is a type-48 resource: handle +0x52 == 0x30, [[handle+8]+8] = the FxResource (0x1BBBD4).

Heap census of KEY objects (one per node of every RESIDENT effect, not per play): ParticleSystem 9,100, MaterialController 3,746, StandardGPUParticleSystem 1,874, Sound 1,246, Model 1,235.

Node types: registry, families and runtime classes (MEASURED 2026-10-28)

The registry is the static array 0x21DB460, 36 pointers (ParticleSystem first, VolumetricCloud last) to 36 separate 0x50-byte type entries in .idata (0x2681DD0..0x26829F0), interleaved with ClientFX cvars (DebugPrintOverlays, EnableMTParticleFX, ParentedModel.AlwaysVisible). Entry layout:

slot meaning
+0x00 "ClientFX.<Type>"
+0x08 type hash (u32, filled at start-up)
+0x10 / +0x18 pooled RUNTIME object create / destroy (16 types; per-type pools 0x277CA08 + 0x10*i, Tracer 0x2A3EA10)
+0x20 / +0x28 KEY object create (bump alloc from the resource buffer; size = mov edx, imm) / delete
+0x30 KEY destroy in place
+0x38 / +0x40 KeyData measure / construct (20 types; 0x1BC8A0 calls both per new instance)

Two families. keydata (20): ParticleSystem, GPUParticleSystem, StandardGPUParticleSystem, AnimatedModel, AnimatedPhysicsModel, AnimatedSkeleton, Beam, GPUCloth, MaterialController, Model, ParentedModel, PhysicsModel, PhysicsImpulseRadial, PolyTrail, DynaLight, DecalLight, Sprite, FlareSprite, LensFlare, VolumetricCloud: one object per node inside the instance's KeyData block. pooled (16): Sound, CameraShake, Create, CreateRay, Lightning, Tracer, DebrisSystem, Overlay, Rumble, Volumetric, SceneRender, ImpactDecal, Wind, VegetationDisp, PolyString, PolyCurve: runtime objects from per-type pools (base class vt 0x1DAA9D0). Key objects derive from vt 0x1DB46A8 (sprites 0x1DCB558, GPU 0x1DB46C8); KeyData objects from vt 0x1DAB2F0 (12 slots: vf0 dtor 0x1D4AB88, vf1 / vf2 empty, vf6 / vf7 / vf8 / vf10 pure = the per-type overrides).

The tick: main thread, then the FXBackgroundThread (MEASURED 2026-10-28, offline + live)

  1. Main thread, CGameClientShell vf1 0x1A864C (after the perf manager [GM+0x6DB8] call 0x69909C) calls 0x1AA1F8(wrapper) for +0xA98, +0xAA0, +0xAA8, +0xAB0, then +0xAB8. 0x1AA1F8 gets dt from the wrapper's time source (0 when paused or below an epsilon) and calls ClientFXMgr::Update 0x1AAAFC(inner, dt).
  2. Update 0x1AAAFC: finishes last frame's work first when +0x108 is set (0x1A9F20, 0x1AC584, 0x1AA000), drains the deferred queues (+0x18268..), resets the frame arena (+0x1B0), reserves the work list at 2x the instance count, sets budget left = arena / 4, runs the instance loop 0x24E040(inner, &vector, dt, camera), queues itself to the FX thread (+0x11 set) or runs 0x1AC638 inline, sets +0x108; a synchronous join (0x70417C, then the three finishers) follows only when cvar byte 0x266D500 is set or +0x10 is clear.
  3. Instance loop 0x24E040, per entry: squared distance from the camera vs entry +0x10 / +0x14 -> visible flag; budget: FxResource.count x cost taken from +0x1A4, cost +0x19C (128) the first time (then entry +0x02 = 1) and +0x1A0 (64) for an already admitted instance; an instance over budget goes to 0x177BFE8 (budget handler, by resource hash); KeyData timing (0x24F2F0 "Attempting to loop a keydata illegally"); then the container is pushed to up to three lists: 0 -> 0x1779850, 1 -> inner+0x128 (background), 2 -> inner+0x110.
  4. Dispatch, CGameClientShell vf2 0x1F6928 / vf3 0x177473C -> 0x1F6258([GM+0x6DB0]): swap the front / back manager vectors, mark dispatched, SetEvent(work) (or run inline when there is no thread).
  5. FXBackgroundThread, routine 0x116B11C (arg = the ClientFXThreadMgr itself): wait on +0xA8, for each queued manager 0x1AC638(inner): under the manager's lock, every work item 0x188CA4(keydata container, 1, [inner+0x168]) (it reads container +0x168 = instance +0x220, the KeyData block), clear, SetEvent(inner+0x18328); then SetEvent(+0xB0).

ClientFXThreadMgr = the thread object (vt 0x22F3120, vf8 "FXBackgroundThread"): +0x08 handle, +0x18 routine 0x116B11C, +0x20 arg (itself), +0x28 name, +0x5C owner thread id (the main thread), +0x90 / +0x98 front / back vectors of managers, +0xA0 dispatched, +0xA1 quit, +0xA8 work event, +0xB0 done event. Live: routine 0x116B11C confirmed, owner = the main thread, Simulation's background list held 110 / 38 items in the two snapshots (3 / 3 sampled items had +0x18 = the Simulation inner manager, i.e. they are instance +0xB8 containers). CPU: 47-78 ms per second in combat (kb/live-runtime.md "Threads and the frame").

What runs where: creation, culling, budgets, timing and the instance list are main-thread; the KeyData update of queued instances (particle simulation, LEAD for exactly which vfuncs) is the FX thread. A mod that touches an instance must do it on the main thread between the join and the next dispatch, or not at all.

Particles: CPU vs GPU, compute and draw (MEASURED / LEAD 2026-10-28)

  • Three particle node types. ParticleSystem = CPU particles (KeyData 0x1DAB3B0). GPUParticleSystem = the "CustomGPUParticle" path (KeyData 0x1DC5D40). StandardGPUParticleSystem (KeyData 0x1DAB290) = the newer GPU path. In the desert the GPU nodes outnumber the CPU ones (976 + 103 vs 562, snapshot 2).
  • Per-manager GPU context (MEASURED, offline): the inner ctor 0x1779B20 calls 0x1D2E440, which loads StandardGPUParticle_SimEmit.mat, _SimEmit_Weather.mat, _Sort.mat, _ClearIndirectBuf.mat and TextureCopyTo2DArray.mat, and 0x1D2F1A0, which loads Client/GroupedGPUParticleFX (one record, Fire: RenderMaterial fx\fire\groundfire\groundfire_mega.mat, MaxParticlesInGroup 16384).
  • Render-side classes (MEASURED from strings, offline): vt_0x1DBC638::vf4 0x1B572C (CustomGPUParticle.Compute, _ParticleSource, _ParticleDest, _DrawIndirect), warm-up 0x1D2DB08 (CustomGPUParticle.Warmup), sort 0x587AE0 (CustomGPUParticle_Sort.mat / _Sort48.mat); vt_0x2009DA8::vf4 0x1F18D0 -> 0x103A960 (StandardGPUParticle_ParticleBuffer0 / 1); curves texture array 0x1B722C; grouped: vt_0x1DBC718::vf4 (GroupedGPUParticle_Counts 0x67F970, _SourceParticle 0x1EFE3C) and vt_0x23125F0::vf4 0x1EFF0C (Source / Dest DrawIndirect). So GPU particles are emitted and simulated by COMPUTE and drawn with DrawIndirect from GPU-written argument buffers.
  • They are not in the main-to-render command ring (MEASURED): 0 of 246 commands per frame over 9 frames (render_commands) used any of those methods, while the ring's usual methods were there (control). LEAD: they run inside the render passes as renderables' vf4.

Budgets and caps (MEASURED 2026-10-28)

  • Per manager: arena 1 MB (Simulation) / 512 KB; every frame the budget is reset to arena / 4 and each instance costs keys x 128 when first admitted, keys x 64 after; over budget -> 0x177BFE8. Live snapshot 2: Simulation 211,648 left of 262,144. Cvar ClientFXMgr.FXInstanceBudget (struct 0x266D4A0) feeds +0x19C / +0x1A0 from 0x266D4B8 / 0x266D4BC.
  • Per effect group (GameDB Client/ClientFXBudget, 7 records): MaxSimultaneousFX / MaxNewFX: OnFire 30 / 10, Blinded 25 / 10, BloodDecals 30 / 4, Poisoned 30 / 10, Footsteps 100 / 10, Easterling_SmokeScreen 2 / 2, OnFire_Balefire 30 / 10, plus FXList, BudgetExceededBehavior (EClientFXBudgetBehavior) and PoolingRules. LEAD: enforced at creation by the perf manager [GM+0x6DB8] (0x1BD23A check, 0x1BB5E0 register).
  • Distance: FxResource +0x04 MaxUpdateDistance; creation refused beyond the cull radius (0x1BB980); per-frame visibility from entry +0x10 / +0x14.
  • Particle caps are node properties (MaxParticleCapacity, MaxParticleLifeSpan, MaxParticleMethod, MaxParticleVelocity, SurfaceFireFXMaxParticlesFactor), not a global pool.
