World: regions, layers, placements and world objects

How a region's world is assembled from streamed parts, what a world part holds (the object registry and its fourteen blocks, static placements, prefabs, terrain and vegetation), how placed objects look in memory, how the engine creates, binds and moves them, and the world data behind traversal (context-action lines), weather-gated effects and collision.

A region's world is a set of world parts, each streamed in as a section and turned into a world context full of placed objects. This chapter describes the parts on disk, the streamer that loads them, the objects they create and the world data that the rest of the engine queries.

Regions and world parts

The game has eight regions. Each has one main part (worlds\retail\<folder>\<folder>, the only part with terrain) and a set of layers under worlds\retail\<folder>\sectionsandlayers\: story and side content, fortress pieces, lighting and its per-Overlord variants. 1,303 layers ship (each identified by the paths its own container lists, never by its archive entry name):

Folder Region Layers
volcano Gorgoroth 243
snowmtn Seregost 239
island Nurnen 228
mtnpass Cirith Ungol 228
desert Lithlad 221
minasithil Minas Ithil 138
blackgates the Black Gate 4
baraddur Barad-dur 2

Seven regions have a region archive and a lighting archive (<folder>.arch06, <folder>_lighting.arch06), and the patch archives add and replace parts. Lithlad has neither: its main part and all 221 of its layers are in the patch archives (the containers in Patch_DLC4, with standalone .objres and .scripts copies in later patches).

A world part is an EMBB container (see Archives and file formats). Every layer carries its own prefab (.inst), and 1,302 of 1,303 carry the same eight further parts, named after the layer: .objres (the object registry below), .terrain, .hkai (navigation mesh), .wldclnt (static placements), .veggrid, .scripts (its script; see Scripting), .uis and .uiwd; then the prefabs, meshes, materials, textures and effects it uses (176 layers also carry a world mesh, .wldmsh). A layer's .terrain is an empty 12-byte section; only main parts carry terrain.

Across all 1,311 parts (1,303 layers and 8 main parts) the object registries place 1,247,824 objects of 156 classes. The most common: AINodeMenacePlace 113,874, AINavMeshObstacle 67,714, SpecialFX 67,460, DynamicObjectGroupState 67,361, ScriptRelay 56,290, StaticLightOctreeBias 54,700, FireVolume 50,718, AISpawnerAmbientNormal 49,769, LightCube 47,771, Group 43,956, VolumeController 35,992.

Patched registries win. The engine does not load the registry embedded in a part when a patch archive ships a standalone .objres for that part (2,753 standalone registries ship). Lithlad's main registry in a running game is the copy in Patch_DLC5 (161,821 context-action lines), not the one embedded in the Patch_DLC4 container (161,828) or the copies in Patch_09 / Patch_10 (161,836). Layer scripts follow the same rule (see Scripting).

How a region's world is assembled

The section streamer

WorldBundleMgr (GameSystems\Core\WorldBundleMgr.cpp) is [GM+0x6D90]. It keeps a registry vector of world bundle groups at +0x00 / +0x08 (145 groups in Lithlad, each pointing back to the manager at +0x240). The scene tick walks the groups (see Threads and the frame) and services only those whose want-load byte +0x252 is set.

A group (0x258 bytes, constructor 0x1D297EC) is the head of a circular list of entries: +0x00 the first entry, +0x08 the last, closing back on the group in both directions. +0x251 set disables the duplicate check, +0x252 is the want-load gate. An entry (0x168 bytes, vt_0x1DB6558) is one requested section:

Offset Meaning
+0x34 u32 id = StringHash(path) (127 of 127)
+0x38 list links {next, prev}
+0x48 the CResourceBundle of the section (vt_0x1E6E678, path equal to the entry's: 127 of 127)
+0x50 the part's object-registry request (set on 126 of 127)
+0x58 the bundle load request
+0x63 the path, inline (...\<part>.bndl)

AddSection 0x4B41CC(group, path, &id) calls 0x4B420C, which rejects an empty path, appends .bndl, returns the existing entry when the path is already requested in that group (0x4B1FE4) and otherwise links a new entry at the front of the list. RemoveSection 0x4B1BCC(group, id) releases every entry with that id (0x4B5C34). The entry exists as soon as it is requested, long before its content has streamed. Requests are de-duplicated per group only, so the same section requested through two groups is loaded twice.

A plain bundle load (see Resource streaming) makes a part's resources resident without placing anything; a section requested through a group is what creates its world context and objects.

What a region loads

MainScene ([base+0x26FFAB0]) owns eight group slots. In Lithlad during play they held:

Slot Gates Sections
+0x720 none (the null group)
+0x728 flag +0x250 set worlds\retail\desert\desert.bndl, the main part
+0x730 flag set empty
+0x738 worlds\retail\shared\wraith\lightingwraith.bndl and prefabs\ui\worlduimenuws.bndl
+0x740 want-load 0 the quest group: sectionsandlayers\fortassault\fortassault.bndl

The lighting layer is requested by the weather manager in its own group ([[GM+0x6D98]+0x20]): the current weather pattern's Section field names it (see Rendering, "Weather"). In Lithlad the pattern was DS_OL_Outlaw_Clear, whose Section is worlds\retail\desert\sectionsandlayers\ol_outlaw.bndl, and that group held exactly that section. The ol_* layers are per-Overlord variants: Lithlad ships nine (ol_dark, ol_feral, ol_machine, ol_marauder, ol_mystic, ol_outlaw, ol_slaughter, ol_terror, ol_warmonger) beside its plain night01..03 layers; Nurnen, Cirith Ungol and Seregost nine each (Nurnen's and Cirith Ungol's include a shared ol_share01); Gorgoroth 27, each also in _bd and _bduc forms. Lithlad's ol_outlaw holds what a lighting layer holds (1,104 SpecialFX, 959 LightCube, 612 Sound, 175 WorldModel ... and an AtmosphereVolume), much like its night03 (1,492 SpecialFX, 959 LightCube, 612 Sound, 32 AtmosphereVolumes).

Of the 68 groups with entries, 63 hold only the menus' 3D scenes: 86 sections under prefabs\ui\mordormap\ (the world map's region pieces such as minasmorgul.bndl, and each fortress's keep and gate pieces by tribe, fortworldsections\keeps\blackguard\bgrdflairped05.bndl), 12 under prefabs\ui\store\, 6 battle-report scenes and 8 region-faction scenes (wuim_*_ws.bndl). 127 sections were loaded in all, 13 of them from worlds\.

Conditional sections. At load MainScene+0x760 .. +0x768 receives 16-byte pairs {section record, u32 id} copied from the region's WorldInfo.ConditionalWorldSections. The evaluator 0x1DFAC8 (called from 0x1DF500) reads each section's _StructuresWorldInfoConditionalSection.GameDataVariable: true with id 0 requests the section through [MainScene+0x758] (0x4B41CC); false with a nonzero id releases it (0x4B1BCC). Lithlad has none; Minas Ithil during the Shadow Wars has 12 (its pre-fall sections released, the post-fall ones loaded).

Region travel. The script call System:LoadWorld(DBWorldInfo.<world>) on the main thread starts a region load within 0.1-0.2 s (LoadWorldCustom, which no shipped script uses, shares its implementation 0x1780824). The current region record [[GM+0x6C68]+0x1B0] changes at the start of the load, before the destination's objects exist.

World contexts

The objects of a streamed part live in a world context (vt_0x1DB5D58). The object update manager's object sets (see Threads and the frame) are these contexts: 129 of 129 sets in Lithlad carry that vtable, and every placed object points back to its own at +0x58 (105,946 of 105,946).

A context's object-name table is [ctx+0x68]: 0x800 buckets of 0x18 bytes, bucket = hash & 0x7FF, list head at +0x08; the node is embedded in the object at +0x28 (+0x08 next, +0x10 hash, +0x18 name). 20 of the 129 contexts had a table, holding 105,946 objects; the largest is the main part's.

The object registry (.objres)

A part's .objres is an OBJR chunk registry:

'OBJR' | u32 13 | u32 hash | u32 block count
block count x { u32 name hash | u32 size | payload }

The chain ends exactly at the end of the section in 1,310 of 1,310 parts. Parts with context-action data carry 14 blocks (724 parts), the others 12 (no CAWR / CADB). Each block hash is StringHash of the name its handler registers with the resource manager; the names sit together in the image at 0x1E6B4E8-0x1E6B6B0, 14 of 14:

Atmosphere volumes and their VOLM brushes are described in Rendering; the context-action blocks and SWFX have their own sections below.

The object list (OBJL)

'OBJL' | u32 5 | u32 sets | u32 N | u32 class bytes | u32 name bytes | u32 group bytes
0x1C   class names, object names, group names (NUL-terminated string tables)
then   per set: u32 set hash | u32 count | count x 50-byte record (unaligned)
Offset Type Meaning
+0x00 u32 class name (offset into the class table)
+0x04 u32 object name (offset into the name table)
+0x08 u16 the prefab instance that placed the object (offset into the group table; 0xFFFF = none)
+0x0A u32 index of the object's record in the property database
+0x0E f32[3] position, world space (cm)
+0x1A f32[4] rotation quaternion (x, y, z, w)
+0x2A u32 0
+0x2E u32 an id (0 on the world-collision objects)

The table ends exactly at the block end and every offset lands on a string start in 1,310 of 1,310 registries (re-read on five layers and Lithlad's main part, 104,489 objects; the 9,284 layer objects all have unit quaternions). Most lists hold one set, the world set (hash 0x3BDE767D). Object names carry their prefab instance and their role: Barre_46.DOGS_Fire, MesaE_08.VC_NoHang, HideS_138.FP, pGCarags.spwCaptain. In all ten parts read, the list opens with a WorldInitializer object and then WorldCollision objects at the origin: PhysicsBSP (and LargeAIIgnore in some layers); Lithlad's main part has four (PhysicsBSP, PlayerBlocker, CameraBlocker, LargeAIIgnore).

The object property database (GADB)

ObjRes.ObjProps is a complete GameDB database (version 17) whose root type is ObjectPropertyDB, with the category ObjectDB and records named ObjectRec (see GameDB). An object's OBJL record index selects its record, and every property the object reads at creation comes from it. Records are de-duplicated: objects with identical properties share one (Minas Ithil night01: 3,160 objects, 1,886 records; Lithlad main: 95,205 objects, 21,430 records). In a running game an object keeps its record at +0x50.

Group members (ONLS) and script bindings (SCRB)

Both key objects by StringHash(object name).

  • ONLS lists the members of every grouping object: 'ONLS' | u32 1 | u32 area bytes | u32 index bytes; the area holds groups {u32 n, n x {u16 length, name}}, the index {u32 hash(owner), u32 offset of its group} sorted by hash. Over 400 layers 6,360 of 6,360 owners are objects of the part (Group 5,515, AINodeRoute 735, AINodeSearch 83, static-light probes) and 107,097 of 107,097 member names exist in OBJL. A prefab instance's children (Barre_00.DOGS_Alive, .VC, .NMO, .FX_P ...) form one group.
  • SCRB says which function of the part's script runs for which object and event: 'SCRB' | u32 1 | u32 string bytes | u32 bindings | u32 objects, then the strings, bindings {u32 hash(event), u32 event name, u32 hash(script resource path), u32 function name} and an object index {u32 hash(object), u32 first binding, u32 count} sorted by hash. Over 400 layers 18,129 of 18,129 scripted objects are named (ScriptRelay 8,906, ScriptObject 4,700, StartupCommand 2,795, QuestRelay 438, RemoteScript 365 ...), every script hash is the hash of the part's own worlds\retail\...\<layer>.scripts path (5,844 of 5,844), and every bound name exists in that part's shipped script. Events include Script, Script1, Start/Cleanup/Fail/CompleteQuestScript, PreActivateQuestScript, Departure/ArrivalScript, OnInitialize and OnEnterScript. A binding names either a function name = function(self, threadId, scriptId) ... end (4,938 of 6,312) or, for a ScriptObject's Script, a script object name = hmake <Type>_meta { ... } (1,374).

What a dynamic object draws (ObjRes.WorldPhysics)

The static placements (below) list only static prefabs. Everything the engine can burn, break, open or animate is an OBJL object, and its geometry and collision are found through this block:

u32 n_objects | u32 n_records
n_objects x u32 hash(object name)   (unsorted)
n_objects x u16 record index
records:  {u32 1, u16 0, f32[6]}                                   no path: world collision
          {u32 flag, u16 length, path, u32 key, f32 cull, f32 half[3], f32 centre[3]}   a prefab (.inst)
then the records' Havok shapes (tagfile TAG0, SDKV20160200, hknpCompoundShape)

Lithlad's main part lists 18,943 objects over 585 records. In Cirith Ungol's main part 12,638 of 12,639 hashes are OBJL object names, all of geometry or physics classes (FireProp 2,491 of 2,491, DynamicObjectGroupBrush 1,382 of 1,382, WorldModel 590 of 590, AINavMeshObstacle 6,397, the world-collision objects). A record's bounds are its prefab's decoded bounds (the orc furnace base: half-extents 18.1 x 8.9 x 22.1 m), and records are per (prefab, class), so a prop and its navigation obstacle use different records of the same prefab.

Motion paths, effects, ambient life and clutter

  • KEYF (CClientKeyframer): 'KEYF' | u32 1 | u32 n | u32 data bytes, n x {u32 id, u32 offset}; an entry is {u32 5, u32 keys, u32 frames, u32 frame bytes}, keys {u32 hash(name), u32 frame} (Open, Closed, Start, End), frames of 40 bytes {f32 time (s), f32 offset[3], f32 quat[4], u32 0xFFFFFFFF, u32 tag}. The id is the KeyDataIndex property of a KeyFramer object (449 of 449 resolve). 45 of 1,310 blocks carry paths (431 paths; quaternions unit 4,848 of 4,848, times monotonic in 431 of 431); a gate leaf slides 400 cm over its 10 s TotalPathTime.
  • SFXS, static effects that are not objects (falling leaves, furnace smoke): header 1 | off_a | off_b | n | n2 | 0 | 0, .fxp paths, at off_a n x {f32 position[3], f32 cull range}, at off_b n x {f32 quat[4], u32 .fxp path offset, u32 3, 0, 0}.
  • NLFE, ambient-life emitters: 'NLFE' | 1 | 0x1C | n | group-name bytes | name bytes | groups; the group names are NativeLife/Definition records (con_TourchLight, con_MeatFlies), then n group indices, n instance names (light_05L.Moths; prefixed by their prefab instance, not OBJL objects), n zeros and n positions.
  • Clutter (CClutterMgr, ClientShellDLL\ClutterMgr.cpp): instanced static meshes carried with their geometry. Header u32 1 | u32 string bytes | u16 meshes | u16 instances | u16 elements | u16 vertex buffers | u32 buffer bytes; .mat strings; per mesh {u32 material, u16 elements, u16 vertex buffers, u16 vertices, u16 indices, u16 users} with its vertex elements, 56-byte vertices {pos[3], normal[3], uv0[2], uv1[2], tangent[3], u32 colour} and u16 triangle indices; then 40-byte instances {f32 pos[3], f32 quat[4], f32 scale, u16 left, u16 right, u16 mesh, u16 1} forming a binary tree with one root per block. 51 blocks are non-empty (275 meshes, 9,630 instances); Lithlad's main part has 23 meshes and 1,657 instances.
  • PFDG, the prefab tree of the debug viewer (registered by CPrefabDebugViewer 0x1796274, which draws a cube CPrefabDebugViewer.Box scaled by each node's extent): 'PFDG' | 1 | n | string bytes, n x {f32 centre[3], f32 extent[3]} (the extent is signed: 21% have a negative component), n packed 21-byte nodes {u32 parent, u32 first child (0xFFFFFFFF none), u8 r, g, b, a, u32 path, u32 name, u8 flag}, strings. 381,195 nodes, every link valid.

Layers place few or none (0 to 17 in five read). These are the static buildings, walls and rocks; prefabs that can change (destructible, animated, interactive) are objects instead.

Prefabs (PRFB, .inst)

A prefab's baked geometry; static world geometry is never .mesh (prefab .mesh files are the destructible and animated pieces). 'PRFB' | u32 8 | u32 hash | ... with header words for draws [4], materials [5], child prefabs [6] and vertex formats [9], then:

  • LOD records from 0x38, 44 bytes each with -1.0 at +28, in groups that open with a per-group tag (0xD238B9DD on a keep wall, 0xD238B9DE on human buildings, 0x3249 on lanterns, an extra leading group 0x159A on fortress pieces): a root {tag, -1, 0, 0, next = first unit, f32 cull distance} and units {tag, name hash, first draw, draw count, next unit (-1 = finest), f32 switch distance, f32, -1.0, 0, 0, distinct draws}. Per instance the engine walks coarse to fine and draws the first unit whose next is -1 or whose switch distance the camera is beyond (a keep wall switches at 320, 150 and 80 m and is culled at 7 km). A unit may draw nothing at its range; draws in no unit are depth-prepass and shadow casters. Header word [7] is not the unit count (88 of 431 chained prefabs disagree).
  • {u32 draws, u32 vertex bytes, u32 index bytes}, then per draw one vertex block ending at its vend (stream 0 then stream 1, stride-aligned), then u16 indices (idx_min .. idx_max, rebased by idx_min).
  • The tail: vertex formats {u8 stream, u8 type, u8 usage, u8 index} (types 2 float3, 12 half4, 10 half2, 4 ubyte4; usages 0 position, 1 normal, 2 tangent, 3 binormal, 4 uv, 5 colour), 52-byte draw records {0, n, n, index start, base, triangles, material, 0, 0, format, vend, f32, f32}, then the material paths. Positions are prefab-local with the pivot at the base centre. A composite prefab ends with a block of placed child prefabs.

A layer carries the prefabs it places as PRFB sections of its own container (Minas Ithil's sabotagecages_00 carries guard_caragors.inst and three footprint-tracking prefabs).

World meshes, texture arrays, terrain and vegetation

  • MESH version 5 (.wldmsh) is a part's own world-space mesh, laid out like the PRFB tables with the vertex buffer at 0x2C (header [3] draws, [4] formats, [9] vertex bytes, [10] index bytes); its materials index the part's WDSC list. Draws wider than 20 km are sky domes and vista cards (504 km in Minas Ithil's night01, 960 km for Cirith Ungol's mt_v01).
  • In Cirith Ungol about 90% of the world's triangles use texture-array materials (.texa), which blend array slices by a mask and a height map.
  • TERR version 9 (<region>.terrain), main parts only (Barad-dur has none), read by 0x7AC0F4: per terrain a root grid (4x4 or 8x8), position (the centre), quaternion, extent, height range, an f32 (400; 500 in Lithlad, 1000 at the Black Gate), the node count, a material and a global texture (a 32x32 flag map, one cell per depth-3 node), then nodes {u32 flags; unless flags & 0x20: f32 min, f32 max, u32 tile} and tiles of three texture paths; the file ends exactly after them in every region. Each root is a quadtree stored in pre-order (flag bits 0-3 = children present, 0x40 root, 0x20 no data); every root's tile 0 is the region overview, deeper nodes own a 68x68 16-bit height tile and two 132x132 BGRA maps (four texture-array slice indices and their weights). World placement: U = (x - pos.x) / size + 0.5, V = (z - pos.z) / size + 0.5, y = pos.y + h * range. The terrain shader disp_terrain.fxo keeps the four heaviest of up to 24 slices per point; slice index 255 means no layer, which marks the holes (outside the play area, and pockets such as forts and caves).
  • VEGT (.vegtile), vegetation, read by 0x503A0C: 'VEGT' | u32 version (1-3) | f32 centre[3] | f32 half[3] | u32 species, then per species {u16 length, name, u32 n, n x 16-byte instance}. An instance is u16 qx, qy, qz (position = (centre - half) + q * step, step = max(half) * 2 / 65535), u8 scale (b / 127.5), a u8, four rotation bytes, a 3-byte bounding-sphere offset and u8 flags (bit 0 hidden). The rotation is decoded on the GPU (vegetation_sort_nomotion.fxo): cos yaw = 2 b0 / 255 - 1, sin yaw = 2 b1 / 255 - 1, a2 = b2 * 2pi / 255 - pi, a1 = b3 * 2pi / 255 - pi, world = s Rz(a2) Ry(yaw) Rx(a1) local + position. Species are Vegetation/Type records; 108 species and 1,291,234 instances ship, in tiles worlds\retail\<folder>_<n>v.vegtile (inside the region folder for Gorgoroth and Seregost) and in layer tiles. A tile's file ends exactly after its last species.

Creating, binding, moving and removing objects

All of this runs on the main thread.

The object server

The object server [base+0x26FF058] (vt_0x22C0B28) is the world-object factory:

Slot Function Role
vf4 0x7AAB6C -> 0x43DBC8 the time-sliced object-set streamer
vf5 0x1F6EA0 "busy" (the update walk is skipped while it reports busy)
vf8 0x43D630 CreateObject(params): requires a class at params+0x40, copies the parameters (0x43D680), calls the creator, then the new object's vf21 (+0xA8, post-create)
vf14 0x502034 find an object by name in a context

The creator 0x1CD454 (also called by the part loader 0x11B4EC0 for every object a part streams in) requires an object set at params+0x1A0, allocates the object through the class holder at params+0x40, runs its ReadProps (vtable +0x60, which pulls every property from the ObjectRec), builds the transform from the parameters into +0xAC, registers the name, links the object into its context, builds its components (vtable +0x68) and activates it (+0x80, +0x70, +0x48). A part's loader creates every object first and post-creates each afterwards.

Names

The name registrar 0x4DBF08 either copies the name (and sets +0xDE to 1) or keeps a pointer into the part's strings (+0xDE = 0), hashes it into the node at +0x28 and calls the context's vf10 0x4DBF78, which picks the bucket (hash & 0x7FF, 0x4DBF84) and appends the node at the tail (0x115ED3C, which asserts "Error: Adding a link that is already inside of a list" only when the node itself is already linked). Duplicate names are legal: nothing checks the name. The lookup 0x4DC078 compares the hash and then the name case-insensitively, walking from the tail, so the newest object of a name answers.

Render and collision are bound by name. The component build (vtable +0x68 -> 0x333430) asks the context's vf5 0x3334F0, which looks the registered name (+0x40) up in the context's resource table (ctx+0x98). An object created under a name its part does not list gets no render component and no physics; created under an existing object's name it receives that object's model and collision. Because the newest object answers a name, the members of a prefab created after the original members bind to each other during post-create.

Binding from script

A script's Create does not construct anything: the objects already exist in the part before any script runs, and scripts bind to them by name. The <Class>.Create(scriptId, name, b3, relative) stubs of 117 of 125 script classes share 0x5013A8 -> 0x501B64, which composes the name (a #. prefix or relative prepends the prefab instance's name) and calls the object server's vf14 with the scriptId's own context; the lookup is not given the class. A missing name or a class mismatch returns Class.None; ScriptObject.Create is a function of its own, 0x501CAC. A scriptId is {PrefabName, PropertyName, Instance}; Instance is a weak handle (prefab instance at payload +0x48) that becomes null when the prefab's part streams out.

Moving

GameBase:CopyXForm(A, B) 0x1823B70 is SetPosition(A, B+0xAC) 0x1454EC followed by SetRotation(A, B+0xB8) 0xEF690; render state and spatial structures follow the setters, and it works across contexts. Collision follows ownership: the setter path 0x274C3C forwards to the physics body at +0x98, so only pieces the object owns move. 3,382 of 3,491 FireProps own no pieces (their collision is baked into the part's static PhysicsBSP), so a moved bench or barrel stack keeps its old collision; DynamicObjectGroupBrushes (607 of 634) and cage brushes (vt_0x1FA3C00, 84 of 84) own theirs and stay solid where they go. A destructible prop is a prefab of sibling objects (brush, explosion, effects, nav obstacle, volume controller): moving one member leaves the others behind.

Removing

Objects live and die with their part's context. When the part streams again its objects are created again from the file, so a moved object is back at its authored transform and an object created into that context is gone. Nothing about placed objects is saved. A class's destructor is at +0x20 of its static descriptor.

Dynamic object groups

Cages, nests, barrels, gates and traps are dynamic object groups: a DynamicObjectGroup object (the root) with DynamicObjectGroupBrush members (the breakable or interactive geometry), DynamicObjectGroupState members named after their states (Barre_46.DOGS_Fire, WaspN_03.DOGS_Shoot) and the prefab's effects. The brushes bind the group's composite prefab (caragorcage, waspnest, ghulcloset: no draws of their own) and sit at fixed offsets from the root (35 of 35, 53 of 53 and 226 of 226 in those three); the drawn art is the prefab's children at the root's transform.

The data is in four GameDB categories:

Category Records Fields
DynamicObjectGroup/Setup 103 States, VisibilityMaxDistance, Tags, ValidateStateTransitions, ValidateBrushDamage
DynamicObjectGroup/StateTransition 101 StateToEnter, ActiveQuestList, IncludedParentStateTypeList, ExcludedParentStateTypeList, IncludedBrushDestroyedAttackCategory, ExcludedBrushDestroyedAttackCategory, ChildState, ChildrenInStateMin
DynamicObjectGroup/StateType 77 none: bare state tags (Alive, Destroyed, Hidden ...)
DynamicObjectGroup/PlacementID 16 none: fortress slots (GateBrow, WallTop, TowerFace, Keep ...)

A transition is a guarded rule: the attack categories and parent states it accepts, and the state tag it enters. The state tags carry no data; what a state shows is the part's DynamicObjectGroupState objects for it and the scripts bound to them.

At run time a group's current state is DOG+0x188 (the state object; its +0x180 is the StateType record), and DOG+0x190 holds its 32 state links. The group's post-create 0x4871190 collects the links but does not enter a state; a group streamed in with its part receives its initial state afterwards. DynamicObjectGroup:Script_SetState is 0x5ADF0C(dog, StateType record): when the ready flag +0x22C is set the request is queued at +0x160, otherwise it is applied at once (0x5AEABC). A brush's current state object is brush+0x148; while it is null, hits on the brush are routed nowhere. A brush's ReadProps does not fill the visibility flags (a FireProp's does), so a brush created without them is invisible.

Context actions: traversal markup

Where Talion can hang, pull up, vault, rail-run or leap from a mount is world data: context-action lines owned by VolumeController, WorldInitializer and StreamingStamp objects, built into a world grid on the ContextActionBuilderThread (see Threads and the frame) and queried by the movement behaviour graphs. ContextActionDB (ContextActionDB.cpp, initialised by 0x1B43A90, vt_0x23010A8) is [GM+0x6DA0]; it registers the cntx resource type.

On disk: CADB and CAWR

CADB (read by 0x7CB194 for the header and vt_0x1FF6B98::vf3 0x501478 for the body; exact in 724 of 724 parts, all version 3):

'CADB' | u32 version | u32 nA | u32 nL | u32 nP | u32 nV | u32 nO          (0x1C bytes)
nA x u32   action palette: hash of a Character/Models/ContextActions record
nL x 0x34  line   {f32 p0[3], f32 p1[3], f32 normal[3], u128 mask}   mask bit i = palette action i
nP x 0x10  plane  {f32 normal[3], f32 d}
nV x 0x20  volume {f32 min[3], f32 max[3], u32 first plane, u32 plane count}
nO x 0x34  owner  {u32 key, f32 min[3], f32 max[3], u32 first line, u32 line count,
                   u32 list-1 first volume, u32 count, u32 list-2 first volume, u32 count}

Across 724 parts: 7,883 of 7,886 palette entries name one of the 124 Character/Models/ContextActions records (fields Group, DebugColor, AdditionalReferencedActions; so a global mask fits 128 bits); 2,209,930 lines, every one owned exactly once and inside its owner's box; 314,834 planes (all unit); 50,668 volumes; 32,104 owners, whose key is the hash of an OBJL object name (32,104 of 32,104: VolumeController 31,803, WorldInitializer 288, StreamingStamp 13), sorted. Lines are not level in general (1,551,979 slope) and 68,951 normals have a vertical component. The busiest actions by line count: Edge_Hang 997,374, Edge_Pullup 388,445, Edge_NoHang 350,260, Block_Movement 326,177, Block_Movement_RailRun 219,953, Edge_Hang_Dangle 216,272, Hurdle 94,327, Edge_MountJumpTo 93,946, VaultOver_Mount 91,633, Edge_NoTrollJump 83,358, Rail_Running 56,365.

CAWR (ObjRes.ContextLineDB) is the owner index: 'CAWR' | u32 1 | u32 n | n x {u32 key, u32 asset, u32 key} (exact in 724 of 724). key is the hash of the object name; the middle word is 0 on disk and is filled at load with the hash of the cntx resource that holds the owner (2,777 of 2,777 live).

Loading

A loaded cntx object is 0x80 bytes (0x7CD444): lines at +0x20 (stride 0x38: the mask at +0x00, the vectors from +0x10), planes +0x30, volumes +0x40, owner keys +0x50, owners +0x60, the asset's hash at +0x1C, and a node at +0x08 in the database's list DB+0x68 (vf5 0x79A948 asserts "Duplicate asset being loaded."). vf4 0x41E564 rewrites every line mask from palette bits to global bits: the database's action table (DB+0x10 count, 124; DB+0x18 entries of 0x28 bytes {u32 record hash, u128 own bit, u128 closure}, sorted, "Improperly sorted database records!") closes each action over its AdditionalReferencedActions to a fixed point, and a line stores the OR of its actions' closures. A query for one action therefore also finds every line whose action lists it.

Live, for the four loaded parts with a shipped source, 163,048 of 163,048 lines equal the file in geometry and in the predicted global mask (the unconverted file mask equals the live one in only 806 of 161,821), as do 2,364 of 2,364 planes, 344 of 344 volumes and 2,091 of 2,091 owners.

Registration

Register 0x2B9E9C(DB, &handle, object, cut group) is called by three classes: VolumeController (vf21 0x2B9758), WorldInitializer (vf21 0x7A53B8) and StreamingStamp (vf16 0x1C2CF04). It resolves the object in two steps: CAWR (list DB+0x98) binary-searches the hash of the object's name (0x2BA01C), then the owner is found in the cntx object named by the middle word (list DB+0x68) by its key (0x2BB7B8). Live, 3,889 objects carried the VolumeController vtable, 3,748 of them named *.VC* (.VC, .VC_NoHang, .VC_Pullup, .VC_Side, .VC_Alive, .VC_Destroyed) and the rest other markup names; 126 were WorldInitializers and one a StreamingStamp (SS_00).

A registration row (DB+0x50, 0x38 bytes) is {u32 A, u32 B, ptr handle, u8 active +0x10, f32 pos[3] +0x14, f32 quat[4] +0x20, u32 cntx hash +0x30, u32 owner key +0x34}. A is a serial from DB+0x48. B is the cut group: the hash of the object's ContextCuttingGroup property, one of the 11 field-less Character/Models/ContextActionCutGroup records (PropKit, WallKit, WallFlair, GateKit, GateFlair, KeepWallFlair, KeepWallKit, TowerFlair, TowerKit, WildFlair, WildTower); only VolumeControllers pass one. VolumeController::SetEnabled 0x5B21A8 (a script function; the StartEnabled property seeds it) calls 0x2BA65C, which writes the row's active byte and sets DB+0x4C, the rebuild flag.

Building the grid: KILL and CUT volumes

QueueRebuild 0x2BB1C8 files each row by its transform (full rotation, translation only, identity). The build 0x2BA9F8 first instances every owner's two volume lists (planes transformed by 0x2BB01C, {A, B} copied, covered cells flagged), then inserts every line through 0x257C70:

  • List 1 = KILL. The engine calls these volumes MarkupKiller (4 to 64 cutting planes, asserted in 0x694AC4; the editor class is MarkupKillerBrush). A line that touches an applicable kill volume is dropped whole.
  • List 2 = CUT. 0x2582F8 removes the part of a line inside an applicable cut volume; the outside pieces survive if they are at least 25 cm long (the constant 0x267A4D8, compared squared: grid +0x28 = 625). Uncut lines keep any length (20,199 live lines are under 25 cm).
  • Which volumes apply (0x258280): a volume applies to a line unless the line belongs to the volume's own owner (same A) or both have the same nonzero cut group. A line with A = 0 is never touched. A disabled owner's cut volumes are still built (125 of 1,051), but its own lines are hidden from queries.

Measured in a running game (two reads with the world re-streamed between them; 186,023 and 184,993 lines): no line lies more than 1 cm inside a volume that applies to it, for 106 kill and 1,051 cut volumes. Control: the same volumes moved 300 cm along x would contain 31 kill and 1,890 cut lines.

The query

ContextActionDB::Query 0xFEAFB0(DB, AABB box, u128 any, u128 all, u128 none, u128 not_all, results ) locks DB+0x20 and runs 0xFEAE40 over every cell the box covers (0xFEB3B0) and every run in it (0xFEB070). It returns each active line once (de-duplicated by its home cell) for which mask & any != 0, mask & all == all, mask & none == 0 and mask & not_all != not_all (a zero mask skips its test) and whose segment meets the box (slab test 0x5AA774). Results are {u32 n, n x 0x38 {u128 mask, p0, p1, normal}}, at most 256. Running the engine's own 0xFEAE40 in an emulator against live memory, on boxes around the player and on random lines with five or six mask sets, gave the same answer as this model in 96 of 96 and 80 of 80 queries; returning inactive lines would have changed the answer in 18 of 19 and 9 of 9.

The callers build the masks from the action table's own bits (0x41F954): any from a node's GameDBContextAction and GameDBContextAction_OR, all from _AND, none from _NOT_OR, not_all from _NOT_AND. The seven callers of 0xFEAFB0 are behaviour-graph nodes (see Animation): Predicate.DetectedEdge (DetectEdgeData 0x1C6EF90: fields Direction, VerticalOffset, Radius, Height and the five action lists; box = position + (0, VerticalOffset, 0) +- (Radius, Height / 2, Radius); defaults -104, 100 and 10 cm), Predicate.FoundRailing / Modifier.FindRailing (RailingData 0x1C700D4), Modifier.MoveWithBrush (vt_0x2303CD8::vf11 0x1C46DE0), Predicate.FoundContextActionBasic (0x41F39C), Character/Models.LockPhysicsContextActionRecords (0x41E70C -> 0x41FBF0), 0x1C6FA58 (from 0x1BE703C, R_Foot) and 0x3ADC94.

Collision and navigation

  • World collision objects. Every part opens its object list with WorldCollision objects (vt_0x1DCD4A8; PhysicsBSP, and in a main part also PlayerBlocker, CameraBlocker, LargeAIIgnore). Their records in ObjRes.WorldPhysics carry no prefab path; the block ends with the records' Havok shapes (hknpCompoundShape in a TAG0 tagfile, SDK SDKV20160200; see Physics for the shape classes). A FireProp that owns no physics pieces is covered by its part's static PhysicsBSP collision instead.
  • Navigation. Every part carries one HKAI section, an HKAI header around a Havok tagfile holding hkaiNavMesh data (see Physics for the navigation-mesh layout). Placed objects carry more navigation data: AINavMeshObstacle (11,588 live in Lithlad), AINavMeshDynamicNavMeshPiece (the props' own navigation pieces, .dnmp; 1,998 live) and DynamicOffMeshLink (2,986 live).
  • A prop's navigation obstacle and context-line controller are prefab siblings at one position, named with the prefab instance's prefix (barre_02.VC, barre_02.NMO, barre_02.FV_00).

Open questions

  • What the 109 world contexts without a name table hold, and whether every loaded section maps to exactly one context: 127 loaded sections, 129 contexts and 126 live WorldInitializer objects (every part read opens with one) suggest it.
  • The meaning of the OBJL id field (+0x2E): zero on the world-collision objects, otherwise repeated across objects (134 distinct ids over 286 objects in one layer) and not the hash of the object's or its group's name.
  • The data after the WDSC instance table (52-268 bytes in layers, 137,850 bytes in Lithlad's main part), and the meaning of the instance kind (0, 1, 3) and hash words.
  • Whether NativeLife emitter positions are world space: of 48 axis and sign choices the identity is by far the closest to the prefab's own objects (median 41 m), but no live emitter has been read.
  • What the second SFXS count means: it differs from the first in some parts (Minas Ithil main 1,273 against 1,271), and the sections tile with the first.
  • What spawns a SWFX effect at run time: the block handler's vf5 0x6FEAF90 only queues the object on [GM+0x30]. Whether the rain-drip points are generated from the same ledge markup as the context-action lines, as their placement suggests.
  • Whether the lantern lights that sit 2-22 cm from their authored points follow an animated or simulated lamp socket (16 of 42 moved within a minute).
  • Which context-action nodes Talion's own behaviour graph uses, and whether the other node types that carry the same action lists (FoundContextAction, AlignToBrush, FoundContextActionEnd, FoundRailingCorner, CameraContextActionData, FindMoveAndPinIK) reach the grid through the seven known callers.
  • Why the AI placements move vertically at load (class medians 0.5 to 2.9 m down, single objects up to 38 m down and 7 m up): a projection onto the navigation mesh or the ground would explain a move without a horizontal component.
  • Whether the context's resource table at ctx+0x98, which the render and collision binding queries by name, is built from the part's ObjRes.WorldPhysics block.
  • What the unnamed TERR f32 is (400 in most regions, 500 in Lithlad, 1000 at the Black Gate); the terrain texture repeat is the obvious candidate.
  • Whether the PFDG prefab tree is used outside the debug viewer.
